that memory holds durable constraints rather than a running diary. Everything
below is recorded properly in the repo - `docs/CHANGELOG.md` (milestones),

As of 2026-08-16, Ouroboros has a real, physical USB keyboard working end-to-end on real Parallels-on-Apple-Silicon hardware (typing, backspace, Enter all confirmed into the userland shell). This closed the last major gap left by the earlier GOP framebuffer console milestone (write-only, no input path).

**Why this took a full session:** a from-scratch xHCI driver (`kernel/src/xhci.rs`) hit five independent, real-hardware-only bugs, none visible on QEMU: a PCI Command register bit-position error (Memory Space Enable is bit 1, not bit 0); a genuine UEFI firmware panic (`ArmPciCpuIo2Dxe.dll`) from a PCI config-space write real firmware doesn't tolerate the way QEMU does; the discovered PCI BAR landing outside the identity map's original single-top-level-table-entry assumption; a confirmed gap where Parallels' USB passthrough doesn't forward HID *class* requests (`SET_PROTOCOL`/`GET_REPORT`) to the real device at all, only *standard* requests (fixed by switching to a real interrupt endpoint, the mechanism production USB HID drivers actually use); and a working interrupt endpoint that turned out to be reading the virtual mouse, not the keyboard, until the driver started actually checking each device's HID interface protocol.

**Where the detail lives:** the full technical postmortem — deliberately written to be useful to other bare-metal-OS developers, not just this project's own history — is at `docs/xhci-keyboard-postmortem.md`. The project's own running narrative log (`CLAUDE.md`) has a shorter "USB HID keyboard driver" section cross-referencing it. `docs/CHANGELOG.md` has the milestone entry; `docs/roadmap.md`'s parking-lot item for this is now marked done.

**What's still open after this milestone:** preemptive multitasking is still unavailable on Parallels (separate gap — needs real interrupt-controller/GICv3 discovery via ACPI MADT, not blocking anything the keyboard driver needed). The keyboard driver itself is narrow-scope: one port/device/slot, no hot-plug, no hubs, no real HID report-descriptor parsing, no stall recovery on the interrupt endpoint specifically.

**How to apply:** before recommending further Parallels-specific work, check whether it depends on preemption (still gated off there) or assumes multiple simultaneous input/USB devices (only single-keyboard scope is implemented).

**Later the same day (2026-08-16):** the project's debugging history was written up as three cross-linked postmortems (`docs/boot-bringup-postmortem.md`, `docs/shell-and-filesystem-postmortem.md`, `docs/xhci-keyboard-postmortem.md`) and published both as Claude Artifacts and as a public GitHub Pages site (`hansolovkarlsson.github.io/Ouroboros`, served from `docs/` on `main`), including a glossary page for the acronyms used throughout. See [[reference-prlctl-parallels-testing]] for a separate, significant discovery from the same day: Parallels Desktop's CLI (`prlctl`) can script the previously-manual real-hardware test loop (start/type/screenshot/stop), now wired up as `make test-parallels`.

**Still later the same day: real ACPI MADT/GICv3 interrupt-controller discovery landed, and preemptive multitasking on Parallels is now fully working.** `kernel/src/madt.rs` (new) parses the real ACPI MADT instead of relying on `gic.rs`'s old QEMU-devicetree-derived GICv2 addresses; `kernel/src/gicv3.rs` (new) is a real GICv3 backend, `gic.rs` is now a version-dispatch facade over `gicv2.rs`/`gicv3.rs`. Confirmed on real Parallels hardware: MADT discovery is clean (`GIC V3, GICD @ 0x2410000, GICC/GICR @ 0x2500000`, genuinely different addresses from QEMU's), GIC/timer IRQ delivery is conclusively confirmed working, and — after a second, separate real bug surfaced (the task switch itself hung the system outright the first time it ran on real hardware, isolated via a single-variable diagnostic to rule out GIC/timer delivery) — that bug was root-caused well enough to fix in the same session: task 1's idle loop used `wfe`, and real hardware's `wfe` under Apple's virtualization layer is the leading (not fully proven) explanation for the hang. Swapping the idle loop for a plain busy-spin (`nop; b 1b`) fixed it completely, confirmed by a sustained interactive real-hardware test with a correctly, continuously incrementing tick count throughout (no hang). Task switching is now unconditionally enabled everywhere (the temporary `TASK_SWITCH_ENABLED` gate was added, tested, and then removed entirely once the real fix was confirmed) — real, preemptive, two-task round-robin multitasking works on real Parallels hardware for the first time ever. Two real GICv3 bugs (not hardware-specific — found and fixed on QEMU first) along the way: a PPI defaulting to Group 0/FIQ without an explicit `GICR_IGROUPR0` write, and `GICD_CTLR` needing more than GICv2's single enable bit. A minor, secondary, unchased finding: an occasional dropped keystroke under active task switching (never worse than one character, never reproduced in the final confirmation run) — plausibly `xhci.rs`'s single-outstanding-interrupt-buffer having less slack now that task 0 only runs in alternating time slices. Full writeup in `CLAUDE.md`'s "MADT/GICv3" section, `docs/CHANGELOG.md`, and `docs/roadmap.md`.

**How to apply, updated:** preemptive multitasking now works on Parallels — the earlier "gated off" guidance no longer applies. `uptime` is trustworthy there (previously always reported 0). The remaining open Parallels-specific gap from this arc is the unchased dropped-keystroke issue (minor, cosmetic) — not a blocker for anything.

**Still later the same day: real task blocking (no more busy-poll round-robin) landed, then dynamic task creation and a real `exec` shell command — the last item in the roadmap's parking lot for running more than one loaded program without a reboot.** A new `spawn` syscall (16) loads a second/third/fourth program from disk at runtime and starts it as a genuinely independent task alongside the caller (`tasks::spawn`, deliberately not POSIX exec-replace semantics, even though the shell command is named `exec` to match the roadmap's wording). Needed: a runtime physical-page bump allocator (nothing before this could hand out RAM after boot services exited), `mmu::install_identity_map` made callable a second time by stashing the boot memory map/extra-device list, and the scheduler grown from 2 fixed slots to 4 (`Unused` state for the new ones). A real bug found by testing, not review: `parse_program_headers`'s `Vec`-based parsing hung completely (zero aborts, zero output) when called from the new runtime path, since the global allocator is boot-services-backed and silently just hangs rather than erroring once invalid — fixed with a fixed-capacity array instead. Confirmed on QEMU (two concurrent tasks, ticks still advancing, full regression clean) and on real Parallels hardware for every piece *except* the actual disk-load success path — Parallels still has no working virtio-blk driver at all (a separate, pre-existing, already-tracked gap), so `exec` there correctly hits the same `NO_FS` path every other disk command does, confirmed clean with no crash. Full writeup in `CLAUDE.md`'s "Dynamic task creation and exec()" section, `docs/architecture.md`'s "Dynamic task creation" section, and `docs/roadmap.md`.

**How to apply, updated again:** a second program can now genuinely run concurrently with the shell via `exec <path>` — but only on QEMU (`make run-image`) until Parallels gets a working disk driver of any kind; on real Parallels hardware `exec` will always report "no filesystem mounted" today, same as every other disk command.

**Same day, fixed immediately after the user tried `exec` live and saw it firsthand: keyboard input racing between concurrent tasks is fixed, not just a documented limitation anymore.** `on_tick`'s wake-check in `tasks.rs` used to poll every `Blocked(WaitReason::Keyboard)` task once per tick in index order; since the underlying poll destructively consumes a byte the instant anything asks, a keystroke went to whichever task happened to be blocked at that exact tick — confirmed live by exec-ing a second shell and watching `uptime` arrive split as `ptime`/stray `u` across the two prompts. Fixed with `tasks::INPUT_OWNER_TASK` (hardcoded to task 0): the wake-check now skips polling keyboard input entirely for every other task, so a non-owner task blocked on keyboard just stays blocked (behaves like a real background task) rather than stealing input. Confirmed fixed on QEMU (clean multi-word commands after `exec`) and no regression on real Parallels hardware (this is the same wake-check that's the *only* keyboard path there). Committed as `a432926`.

**How to apply, updated once more:** the "keystrokes race between concurrent tasks" limitation is gone — a spawned second task simply never receives keyboard input at all (no job control exists to change that yet), so it behaves as background/non-interactive by construction. Don't cite the old racing behavior as still-true.

**Next day (2026-08-17): output redirection (`>`/`>>`) shipped** — the last open item from the original write-support arc. Pure shell-side (zero kernel changes, composes `fs_read_file`/`fs_write_file` like `cp` did): an `Output` sink threaded through command handlers (no static mutable state allowed in userland, so it's passed down like `cwd`), errors stay on the console (POSIX stdout/stderr split), `>>` is read-concatenate-rewrite. Two real findings: (1) the kernel's `MAX_USER_LEN` (512-byte per-syscall buffer cap in `syscall.rs`) rejects longer buffers as `FS_ERROR`, indistinguishable from "no such file" — a 1024-byte append buffer silently turned `>>` into `>`; any future userland buffer must respect that cap. (2) Panicking str-slicing (`&line[..n]`) pulls `core::str::slice_error_fail`'s formatting into the link and breaks the PIE build with non-PIC libcore objects *even in release* — use `.get()` slicing in userland code. Also: `scripts/test-parallels.sh` now supports `>` via a held-Shift scancode chord (`prlctl send-key-event --event press/release`), confirming the full chord path (HID modifier byte → `xhci.rs` shift mapping) works on real hardware. Committed as `eddcba4`; changelog entries for the three prior milestones (blocking primitives, exec, keyboard routing) were backfilled in the same commit.

All storage flows through a proprietary non-PCI path (vendor 0x1ab8 the only candidate). **REAL-HARDWARE EXEC/IPC SUCCESS PATH CONFIRMED (`8cb8381`)** — the user copied PONG.BIN/HELLO.BIN/SH.BIN onto the USB stick; on real Parallels: `mount` → `exec /pong.bin` (first-ever runtime program load on real hardware; real RAM span is `0x40000000-0xc0000000`) → full IPC round trip → quit/wait → `exec /hello.bin` + blocking `wait`. Every userland facility now demonstrated on the primary target. The stick stays assigned to the VM (`prlsrvctl usb del '2200000|21c4|0809|super|--|9713517587108382'` to revert). Parallels exec workflow: binaries must be ON the stick (boot ESP unreadable at runtime).

**USB MASS STORAGE IS DONE (`803a00b`+`b561a78`, evening 2026-08-17): real Parallels hardware has its first working disk.** `usb_msd.rs` (BOT+SCSI: INQUIRY/READ CAPACITY/READ(10)/WRITE(10)) over bulk endpoints in `xhci.rs`; `block.rs`'s `BlockDevice` enum (Virtio|UsbMsd) decouples fat32; boot auto-mount (QEMU) + `mount` syscall 22 with runtime port rescan (Parallels attaches passthrough ~6-8s post-boot). **USB mass storage on Parallels: GO (`6bd97ca`, evening 2026-08-17).** A real USB 3.x stick (SuperSpeed, `idVendor=0x21c4`) passed through to the VM landed on xHCI port 3 at speed=4, enumerated through the kernel's multi-device scan, and presented exactly `class=0x08 subclass=0x06 protocol=0x50` (SCSI-transparent Bulk-Only Transport) — driver plan in `docs/roadmap.md` applies as written. **Key design input: Parallels attaches passthrough USB a few seconds AFTER VM start** — the boot-time one-shot scan misses it; the storage driver needs a delayed/repeated scan or Port Status Change hot-plug. **Also 2026-08-18: PER-TASK PAGE TABLES — MMU-ENFORCED ISOLATION.** Each of the 5 scheduler slots runs under its own L0/L1/L2/L3 view (mmu.rs): identical kernel/device mappings, EL0 access to its own region ONLY. Touching another task's memory faults → fault-isolation kills the toucher alone (A/B-proven: a probe reading the shell's region succeeded under the old shared map, faulted under views). `mmu::activate_task` = TTBR0 switch + TLBI at every CURRENT change. Syscall boundary hardened: `in_caller_region` validates every (ptr,len) against the caller's own region (else access laundered through kernel copies). This forced **FSOP v2**: the FS protocol became fully self-contained (payloads INLINE in the message, kernel-copied task-to-task — no cross-task pointers, since the server can't read a client's isolated memory), MSG_MAX_LEN 64→768, 512B per-op cap = FS_DATA_MAX. Chosen over mapping-based grants (leak neighboring client memory) = first half of MINIX's real design; grant/safecopy can lift the cap later. **ASIDs (stage 3) attempted + REVERTED**: passed QEMU but faulted the idle task on real Parallels (instruction permission fault); fell back to flush-on-switch (correct both platforms). Commits 36b4aa6 (v2), 4eb9db4 (views), 2ac55b8+f23101b (asid try/revert). Confirmed real Parallels: selftest/echo/ps/uptime clean, isolation enforced.

**Also 2026-08-18: GRANT/SAFECOPY IPC DONE — the enforced bulk-transfer primitive (second half of MINIX's IPC design).** Two new syscalls, `GRANT`(31)/`SAFECOPY`(32): a client grants an exact buffer in its own region to one server task with a direction (`GRANT_READ`/`GRANT_WRITE`, single per-task slot cleared at task death); the server, *while the client is blocked in a MSG_CALL to it*, safecopies within that grant. Kernel-enforced (chosen by the user over a simpler "server names a client pointer" model, explicitly to avoid the trust/security issue): the copy is allowed only if the grant names this server + permits the direction + the client is currently blocked-calling-me + both ranges in bounds. The copy runs at EL1 where all RAM is identity-mapped RW in every per-task view (only the EL0 overlay is per-task), so it reaches both regions regardless of active TTBR0; never a third task. `SAFECOPY` takes 5 args (dir read from the saved frame's x4 — dispatch's 4 named args are full). New FSOP ops `FSOP_READ_BULK`(with a `want` param so a smaller client buffer isn't overrun)/`FSOP_WRITE_BULK`. **`cat` now streams a file of ANY size** (loops the bulk read, one SAFECOPY_MAX=2048 chunk at a time — old 512 truncation gone); `cp` up to 2048 (was refused >512); `>`/`>>` past 512. `cmd_write` stays on the cheap inline path (line-bounded at 128). Buffer sizes chosen against the guard-page-less 8KB stack: cp=2048, redirect capture/append=1024 (they nest with cat's 2048 chunk + fs_call's 768+768 on run_line's frame).
