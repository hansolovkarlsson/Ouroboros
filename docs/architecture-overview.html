Ouroboros aarch64 · rust · pre-alpha

Architecture A microkernel for Apple Silicon, drawn as its layers — and the one boundary everything crosses.

Most operating systems put the filesystem, the drivers, and the scheduler together in one privileged blob. Ouroboros draws a hard line instead. The kernel keeps only what must touch privileged hardware; everything it can push out — the shell, the programs, even the filesystem itself — runs as an unprivileged, isolated, restartable process on the far side of that line.

The one boundary

Privilege is the organizing idea

The ARM processor runs code at exception levels. Ouroboros uses two: EL1 for the kernel, EL0 for everything else. EL0 code cannot touch kernel memory, device registers, or privileged system registers. The only way from EL0 into EL1 is a trap — a system call, a fault, or the timer interrupt — caught by the exception vector table. That single crossing is where the whole design lives.

EL1 · what stays privileged

Inside the kernel

The kernel is deliberately small. It owns the things that require privilege — trap handling, memory mapping, the interrupt controller, raw devices — and the mechanisms tasks use to talk to each other. It does not contain policy it can push outward.

EL0 · what runs unprivileged

The tasks

Five scheduler slots. The first three have fixed roles; the last two are filled at runtime when the shell's exec starts another program. Each is an ordinary EL0 program — the shell is not special kernel code, it is just the program loaded into slot 0.

Enforced, not trusted

How the tasks are kept apart

Isolation here is enforced by the hardware MMU, not by good behavior. Three mechanisms compose: separate address-space views, message passing by copy, and a capability for the cases where copying through a message is too small.

01 — separation

Per-task page tables

Every task runs under its own translation-table view. From inside any task, another task's memory is simply not mapped for EL0 — touching it faults, and the fault kills only the toucher. Proven by injection: the same read succeeds under a shared map and faults under views.

02 — communication

Messages by copy

Tasks never share memory. A message is copied — task, into the kernel, out to the destination's mailbox. Small, bounded, and safe by construction: no pointer from one task is ever dereferenced by another.

03 — bulk data

Grant & safecopy

To move file contents, a client grants the server an exact buffer, in one direction. The server may copy only those bytes, only while the client's call is in flight, and never a third task's — a capability the kernel checks, not a trust it assumes.

The design, in motion

One file read, end to end

Because the filesystem is a separate process, a plain cat crosses the privilege boundary several times. This is the cost the microkernel split pays — and, right beside it, exactly what it buys.

The payoff An EL0 fault is contained, not fatal. A wild pointer in any userland program used to halt the whole system. Now the kernel reports the fault, tears down just that task, and resumes the rest. If the dead task is the filesystem server, it is reloaded from an image kept at boot and remounts from disk — because all of its state was always derivable from the disk. That is the whole reason the filesystem was worth moving out.
Cold start

From firmware to EL0

There is no separate bootloader — the kernel is a UEFI application, the only boot path that works on both the QEMU dev loop and the real Parallels target. It sets itself up while still inside firmware, then leaves that world for good.

Why UEFI, not a bootloader

Parallels boots ARM VMs exclusively through UEFI firmware — there is no direct-kernel shortcut like QEMU's. Building the kernel as a UEFI app is the one path that runs on both the fast emulator loop and the real hardware target.

Two targets, one code path

Development runs against QEMU, where a console and disk are easy. The proving ground is real Parallels on Apple Silicon — where the framebuffer console, USB keyboard, USB storage, GICv3, and preemption were each confirmed on hardware.

Ouroboros is an ARM64 microkernel written in Rust, in its earliest stages — microkernel architecture, POSIX-ish syscalls, preemptive multitasking, drawing ideas from Linux, MINIX, and Plan 9. This page is the overview; the reference documents go deeper.
