Architecture · EL1 / EL0

The shape of the system

Most operating systems put the filesystem, the drivers, and the scheduler together in one privileged blob. Ouroboros draws a hard line instead — and pushes everything it can across it. This is that line, and what lives on each side of it.

Privilege is the organizing idea

The ARM processor runs code at exception levels. Ouroboros uses two: EL1 for the kernel, EL0 for everything else. EL0 code cannot touch kernel memory, device registers, or privileged system registers. The only way from EL0 into EL1 is a trap — a system call (svc), a fault, or the timer interrupt — caught by the exception vector table. That single crossing is where the whole design lives.

Inside the kernel

The kernel is deliberately small. It owns the things that require privilege — trap handling, memory mapping, the interrupt controller, raw devices — and the mechanisms tasks use to talk to each other. It does not contain policy it can push outward.

The tasks

Five scheduler slots. The first three have fixed roles; the last two are filled at runtime when the shell's exec starts another program. Each is an ordinary EL0 program — the shell is not special kernel code, it is just the program loaded into slot 0.

How the tasks are kept apart

Isolation here is enforced by the hardware MMU, not by good behavior. Three mechanisms compose: separate address-space views, message passing by copy, and a capability for the cases where copying through a message is too small.

One file read, end to end

Because the filesystem is a separate process, a plain cat crosses the privilege boundary several times. This is the cost the microkernel split pays — and, right beside it, exactly what it buys.

The payoff

An EL0 fault is contained, not fatal. A wild pointer in any userland program used to halt the whole system. Now the kernel reports the fault, tears down just that task, and resumes the rest. If the dead task is the filesystem server, it is reloaded from an image kept at boot and remounts from disk — because all of its state was always derivable from the disk. That is the whole reason the filesystem was worth moving out.

From firmware to EL0

There is no separate bootloader — the kernel is a UEFI application, the only boot path that works on both the QEMU dev loop and the real Parallels target. It sets itself up while still inside firmware, then leaves that world for good.
