# 2026-09-26

## Step 6: the export keys a session, and a stack cost the disassembly found

The standup's one new item was step 6 of
[`roadmap-session-auth.md`](../roadmap/roadmap-session-auth.md): `netd`'s export
keys a session on an `NP_SESSION` offering an ephemeral key, then accepts only
`AUTHNP04` on it. The design came straight from the plan and the Python server
of step 5: the keyed state went on `TcpConn` (two keys, the last `seq`, and the
user the `NP_SESSION` was signed as), the handshake's crypto into its own
non-inlined `key_session`, and every authentication failure became a `true`
from `handle_9p` that the call site answers with an RST and nothing staged.
One decision was taken on the side of explicitness: whether a frame is a
connection's first is a `carried` field, not `!session`, even though the two
coincide today, because they coincide only because a one-shot connection never
dispatches a second frame.

The check was a new `keyed-gate` in `np9p_client.py`, eleven PASS/FAIL checks
with the plan's controls among them, and it was run against the Python server
first, so that the instrument was known to work before it was pointed at
`netd`. Against the guest's ext2 image all eleven passed on the first build, and
the three mutation builds (the `seq` check, the tag check, the user binding and
the small-order check, the boot counter, each switched off) failed exactly the
checks they should. The gate's one instrument defect showed up there, and is in
the blind-instruments postmortem.

The stack took the rest of the morning, and it is the part worth reading. A
probe painted the stack below the 9P dispatch and reported each frame's peak
and verb; a 4 KB pad in `key_session` moved the handshake's peak by 4,144 bytes,
so it saw that depth. The keyed handshake was not the problem. Every keyed
*verb* peaked 1,520 bytes deeper than the same verb signed. I guessed twice and
was wrong twice: the HMAC state inlined into the dispatch (un-inlining
`keyed_tag` bought 48 bytes, and its comment claimed 1.6 KB, so it was
reverted), then the call site (moving the keyed dispatch beside `handle_9p`
changed nothing). The disassembly answered in one look: `serve_keyed`'s frame
was 1,472 bytes, and the calls in it were a `svc` with `x8 = 29` to task 3 with
a 552-byte request and a 768-byte reply. That is `log` to the console, inlined
into the frame the whole dispatch runs under, for refusal messages that almost
never print. Moving them into a cold `close_keyed` took `serve_keyed` to 96
bytes.

Comparing against `main` with the same probe then found the second cost, worse
than the first because it was on the path step 6 was not supposed to touch:
every *signed* export verb was 1,760 bytes deeper than on `main`. The keyed
dispatch was a second caller of `build_9p_reply`, so the compiler stopped
inlining it into `handle_9p`'s host frame, and its locals stopped sharing that
frame's slots. The fix restored the single call site: `handle_9p` authenticates
by the connection's format, makes one dispatch call, and seals in the same
format. Measured per verb, `main` had 11,392 bytes of headroom on every verb,
the step had 10,864 for a signed verb and 10,960 for a keyed one, and 10,736 at
the keyed handshake, the new peak. The 528 a signed verb lost is the resident
keyed state in `serve`'s frame. Four `Option<KeyedSession>` in the connection
table, exactly what the plan's Risk 2 said to count rather than assume.

I also lost an edit to the branch switch the standup had warned about the
evening before: the `keyed_tag` change was uncommitted when I moved to the
measurement branch, and its `reset --hard` took it. It was one line, so it cost
a re-apply; the rule already said commit before the next thing, and the
trigger this time was a checkout rather than a mutation.

## Step 6's review

Eight findings at high effort, all acted on. The two that mattered were about
secrets. The machine seed had been added to `Auth` beside the signing key,
all zero on a node without one, with only a comment saying it is never read
then; it moved inside the identity's `Option`, so "a key but no seed" cannot
be written. And `key_session`'s comment claimed the shared secret and the whole
of `K` were wiped, which was true of the named buffers and false of the moved
`Option`, the returned tuple and the hash states; it now says exactly what is
wiped and what no Rust code can promise, and the keys go straight into the
connection. A keyed request is now bounded by its declared frame length, which
added two gate checks (trailing bytes ignored, a length the segment does not
hold closes), and a mutation that ignores the length fails exactly those two.
The boot-entropy bound moved into `syscall-abi` so the kernel and `netd` cannot
drift. #166 merged at thirteen checks.

## Step 7: the client, and a probe that measured its own console

Step 7 is the client: `sign_parked` offers the key on an opening `NP_SESSION`,
phase two derives the keys from the export's signed answer in its own frame
(the plan's note (c), paid), and later verbs are framed `AUTHNP04` with every
reply checked against `k_s2c` and the `seq` in flight. Risk 2 again decided
where the state lives. The session, path and dial tables are all one generic
`Wire`, so a new field would have sat in nine slots on `serve`'s frame; a fourth
const parameter gives the session table `keys: [SessionKeys; 1]` and the other
two a zero-length array that costs nothing.

The host rig passed first time, and one result looked wrong: all four
misbehaving peers were refused, but `cremote` printed "failed" rather than
"authentication failed". The status was right and libc had no name for it.
`FS_ERR_AUTH` is in `sys.h` now, so the wire check pins it. On the two-node rig
`cbig` and `cwrite` passed over keyed sessions, and the capture census, which
had learned `AUTHNP04` first as the plan said it must, read 3 signed and 21
keyed frames per node. Without that row it would have read three signed frames
and nothing else.

The stack question had a surprise too. A whole-run low-water mark put the
client's deepest point at 3,840 bytes on `main`, far below the per-site
figures. That is the park path during `cbig`, the depth step 1 found, and the
branch sat exactly 3 × 144 bytes lower: three slots of resident key state. A
4 KB pad in `phase_two` did not move the mark at all, since phase two runs from
the service pass. The new crypto is nowhere near the peak.

The measurement nearly misled. Step 0's counters around the four keyed
operations gave 169 µs against 2,926, with counts matching the capture exactly,
but the probe's own round-trip counter read an 18 ms median verb against step
0's 6.65, which would have meant keying made verbs slower. Step 0's probe,
re-run the same day on the same host, still read 5.9 ms, so the host had not
moved. The capture had: requests got replies in about 1.4 ms. The difference
was the probe itself. Its dump is a blocking console write at the top of
`serve`'s loop, and it fires between framing a request and sending it. So the
verb figures came from the capture instead, on non-probed builds of both trees:
the median request-to-reply went from 3.59 ms to 1.41, and the median verb
cycle from 7.50 to 4.53.

## Step 7's review, step 8, and the release

Nine findings. One was my own `git add -A` committing an empty `qemu-int.log`
from a `drive-qemu.py --help` that took `--help` for an image path. The one
that changed the design was identity: a keyed frame carries no name, so a verb
runs as whoever opened the session, while sessions are looked up by uid. A
session now records its opener's name and refuses a verb whose caller resolves
to another, which can only happen if `/etc/passwd` changes under a held
session, and which is checked by reading since no rig can do that. The handshake
secret and the keys became one enum, since they are never live together; the
low-water mark then read 3,504, exactly `main` less 3 × 112. The unkeyed fallback
went into `make test`, and `sys.h`'s floor rose so deleting `FS_ERR_AUTH` fails
the wire check; both controls were run.

Step 8 was the documents and the release. One claim had to be taken back as it
was written: the plan's header said "released as v0.21.0" before any release
existed, and the manual's "since v0.21.0" would have been served live by the
site before it was true. That is why the release preparation went into the same
PR as the docs, so merging it left the tree release-ready. `RELEASING.md`'s
version table turned out never to have had a `0.20.0` row, and got both. v0.21.0
was published on a typed go-ahead, and the state was checked rather than the
script's "published": the tag, `HEAD` and `origin/main` all at `03857a6`, and the
release's `SHA256SUMS` byte-equal to the local build.

## Per-user keys: the fork settled before the plan

*The day was closed out twice. The first closeout was `491ea42`; the
postmortem section above and everything below came after it.*

The standup's last decision was the next arc, and Hans picked frontier item 1,
per-user keys for the cluster, after asking for it to be explained. Before
anything was proposed, three read-only searches mapped the identity path, the
credential stores and every earlier note on the subject. The first of them
changed the premise. The roadmap had always described the gap as an
authorized machine claiming "any of its own users' names". The code is worse:
the export checks only that the machine is authorized and that the claimed
name exists in *its own* `/etc/passwd`, and `map_user` has no uid-0 case, so
any authorized machine is root on every export that lists it, through
`fsd`'s root bypass. That is why root squash became step 1, before any
cryptography.

Three facts narrowed the design before any taste did. Parallels and the Pi
have no entropy, so a random per-user key cannot be generated there. There
is no cipher and no KDF in the tree, only the HMAC the session-auth arc
added. And stored per-user keys, the obvious answer, do not close the gap
at all, because root on a compromised node reads them; the roadmap had
already said so. That left password-derived keys against an auth server.
Hans's question was the right one: does choosing the first lock out the
second? It does not, and the answer is what shaped the plan. Kerberos derives
the user's key from the password too, and the master's job is to vouch for
it. So the plan keeps the three things an auth server would need (a typed
credential slot on the wire, a key that is the user's and not the node's,
and the check turned on per user rather than by a flag day), and what a
master would later replace is exactly the cost this design accepts:
distributing every user's public key to every export by hand.

## Four reviews of a plan, and a rewrite

The plan went through four review rounds before merging as #169, with ten,
ten, six and seven findings. The pattern the session-auth plan showed on
09-22 came back, sharper.

The first round found real gaps in the original design. Among them, logging
out did not end the keyed session the key had opened, and `/etc/shadow`'s
single SHA-256 made the slow derivation worthless. It also found that root
squash and the `/host` rule contradicted each other. I repaired each finding
where it was, and most of the repairs landed in one mechanism: `accountd` as
the key holder, which grew login handles, a lock notice to `netd`, and
capabilities in both directions. The second round found eight of its ten
defects in those repairs, six of them in that one mechanism. The lock notice
could be lost, spoofed, or never sent on an `accountd` restart. The unlock
operation was a password oracle any task could call. And a sign call would
block `netd`'s event loop, the exact thing the async arc had removed.

I did not patch it a third time. I proposed moving the keys to where they are
used: `login` derives the key (it already reads the password, so keeping the
key from it had protected nothing) and `netd` holds it and signs. That removed
the notice, the capabilities, the deadlock risk and the blocking call instead
of guarding each. It reversed something I had told Hans an hour earlier, so I
asked rather than decided; he chose the rewrite. The third round found six,
two of them serious and both in the one new mechanism the rewrite had kept,
the version-2 shadow line. A derivation inside `accountd` runs past the
supervisor's `WEDGE_TICKS` (2.56 s) and gets it restarted mid-request. And an
upgrade that changed a line's length forced `accountd`'s truncate-then-write
path, which can empty `/etc/shadow`. Both are constraints of the system rather
than of the design, which is why no reading of the plan alone found them. The
fixes were to keep derivations out of every supervised server, and to make a
version-2 line exactly as wide as a version-1 one.

The fourth round's most important finding was in the original design, not in
any repair, and three rounds had read past it. Every credential is a signature
by a password-derived key over bytes that cross the wire in cleartext, so
anyone who captures one can guess the password offline, whatever the
registry's file mode. Today no user secret crosses the wire at all. Hans
decided to state it and cure it later, with the trigger-gated encryption tier
named as the cure, rather than mask credentials inside sessions: one-shot
requests have no session key, so masking would close half of it with new
mechanism. The plan now says it adds this exposure knowingly, the same one
Kerberos has, and that strong passwords are part of the model.
