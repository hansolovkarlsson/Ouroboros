# 2026-10-03

## The fix on the board

Hans staged a card from `main` with #191 and booted it four times under
`NOXHCI`. Four shells, no fault. The banner line said what the day before
could only be inferred: the kernel's stack is in its own image, and the
firmware's stack pointer at entry was `0x3b3ff730`, 0x8d0 below the top of
the firmware's 16 KB stack and 0x5730 above the root translation table the
whole boot had been running over. The card from before the fix, booted once
more before it was re-staged, faulted in the variable store's write with
the identical garbage in the root table, the same three words. So the
overflow is confirmed from both sides: present without the switch, absent
with it, where the day before one boot in two to one in four died in
firmware code. Two smaller firsts in the same capture: `shutdown` powered
the board off through the `smc` conduit the FADT names, the first PSCI
power-off on this hardware; and with no HDMI display attached the console
server took the serial backend, so the shell's own lines came over the
cable, including `no /etc/passwd` and `unknown command: ls`, which under
`NOXHCI` are the known limit (no block device after the exit) and not
defects.

What remains on this board is the takeover itself, with the kernel's own
stack under it: the 2026-10-01 faults there carried the same instruction
address as the exit's, so the expectation is a clean takeover and the
first USB keyboard and stick on the board. If it faults, the dump now has
the rows, the tables and the canary. The 2026-10-02 closeout is still owed.

## The takeover, clean

Hans removed `NOXHCI` from the same card and booted. No fault anywhere: the
controller was taken before the exit (PCI command `0x0140 -> 0x0146`, the
CPU address `0x600000000` through the BAR translation), the exit, the drop
and the identity map went as on the flagged boots, and the driver reset the
VL805 and read `max_slots=32 max_ports=5` under the kernel's own tables. So
the 2026-10-01 takeover faults were the stack overflow as well, as the
morning expected.

Then the driver declined the controller itself: `controller wants 31
scratchpad buffers, only 8 are supported`. `HCSPARAMS2` reads `0xfc000031`,
Max Scratchpad Buffers 31, and the DMA pool reserves eight pages, a number
QEMU's controller never came near. Not a fault and not a hardware problem,
a limit set when QEMU was the only controller this driver had seen. The
shell came up over serial without a disk, as under `NOXHCI`. The fix is
the pool's size, 32 pages; the board boot after it is the first run of
this driver past the controller's setup on real hardware.
