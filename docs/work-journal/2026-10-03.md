# 2026-10-03

## The fix on the board

Hans staged a card from `main` with #191 and booted it four times under
`NOXHCI`. Four shells, no fault. The banner line said what the day before
could only be inferred: the kernel's stack is in its own image, and the
firmware's stack pointer at entry was `0x3b3ff730`, 0x8d0 below the top of
the firmware's 16 KB stack and 0x5730 above the root translation table the
whole boot had been running over. The card from before the fix, booted once
more before it was re-staged, faulted in the variable store's write with
the identical garbage in the root table, the same three words. So the
overflow is confirmed from both sides: present without the switch, absent
with it, where the day before one boot in two to one in four died in
firmware code. Two smaller firsts in the same capture: `shutdown` powered
the board off through the `smc` conduit the FADT names, the first PSCI
power-off on this hardware; and with no HDMI display attached the console
server took the serial backend, so the shell's own lines came over the
cable, including `no /etc/passwd` and `unknown command: ls`, which under
`NOXHCI` are the known limit (no block device after the exit) and not
defects.

What remains on this board is the takeover itself, with the kernel's own
stack under it: the 2026-10-01 faults there carried the same instruction
address as the exit's, so the expectation is a clean takeover and the
first USB keyboard and stick on the board. If it faults, the dump now has
the rows, the tables and the canary. The 2026-10-02 closeout is still owed.

## The takeover, clean

Hans removed `NOXHCI` from the same card and booted. No fault anywhere: the
controller was taken before the exit (PCI command `0x0140 -> 0x0146`, the
CPU address `0x600000000` through the BAR translation), the exit, the drop
and the identity map went as on the flagged boots, and the driver reset the
VL805 and read `max_slots=32 max_ports=5` under the kernel's own tables. So
the 2026-10-01 takeover faults were the stack overflow as well, as the
morning expected.

Then the driver declined the controller itself: `controller wants 31
scratchpad buffers, only 8 are supported`. `HCSPARAMS2` reads `0xfc000031`,
Max Scratchpad Buffers 31, and the DMA pool reserves eight pages, a number
QEMU's controller never came near. Not a fault and not a hardware problem,
a limit set when QEMU was the only controller this driver had seen. The
shell came up over serial without a disk, as under `NOXHCI`. The fix is
the pool's size, 32 pages; the board boot after it is the first run of
this driver past the controller's setup on real hardware.

## Past the scratchpads, stopped at the first command

#192 merged, and Hans booted a card from `main` twice. `scratchpads=31`, the
controller accepted and started, a High Speed device connected on port 1
and reset, and then the first command, Enable Slot, timed out on both
boots. The non-cacheable pool's self-check passed, so it is not Risk 8's
missing cache maintenance, though the symptom is the one Risk 8 predicted.

Reading the driver against the ones that work on the VL805 gave two
differences, both invisible on QEMU: the 64-bit registers were each one
64-bit store across the PCIe bridge (edk2, Linux and U-Boot all write two
32-bit halves), and nothing ordered the ring setup in memory before the
register writes that point the controller at it. The first build of
`pi4/xhci-mmio-order` changed both and added a probe: one 64-bit store to
DCBAAP, read back and logged. The review pointed out that this was three
variables in one board round, and that the probe was the suspect access
itself, able to damage the CONFIG register beside DCBAAP while reading back
intact. So the branch now changes only the store (two 32-bit halves), the
barrier waits on the roadmap for the round after, and the diagnostics are
passive: HSE after Run, and a dump of the controller's state on the first
command timeout, checked on QEMU by removing the command doorbell.

## A target for the stick

Before staging the stick Hans asked whether it needed a particular format
and the OS on it. It does, in a sense: the SD card is invisible once the
kernel runs, so the stick is the only disk, and `ls` and the rest are
programs in `/bin` that only a stick can supply. `make stick` stages the
card's tree on it. It is `scripts/sdcard.sh` with a stick mode rather than a
second script, so the guards that protect a card protect a stick too; the
first version dropped the firmware, accepted FAT32 or exFAT and took
`EFI/ORBS/INIT.CFG` as the sign a volume was ours. The review found that
sign was copied last, so an interrupted first run left a stick the script
refused forever; that Disk Utility's default GUID scheme hides an EFI
partition where `fsd` looks first; that the stick's own `EFI/BOOT` could
be booted in the card's place; and that the stick is where Pi-made
accounts live, so re-staging its `etc` by default lost them. Now the stick
gets no `EFI` tree, a marker written before anything else, an MBR
partition-1 check, a refusal of a card, and its `etc` kept unless asked.
That the two halves of a Pi boot can come from different builds went on
the roadmap. Checked on `hdiutil` images only, which the first real card
showed is not the same thing.

## The SuperSpeed port, explained

The stick on a blue socket came up on root port 2 at SuperSpeed, and #194's
log said what `speed=0` had been all along: the port was already up before
the driver reset it, the Hot Reset sent the link back to Polling, and the
old code read the speed in the instant before it retrained. The wait for
the port to enable was the fix; the Warm Reset path was not needed. Hans
asked whether reformatting the stick could have changed the test. It could
not: USB enumeration happens before any sector is read, and which path a
USB 3 stick takes (SuperSpeed on a root port, or High Speed behind the hub)
is decided by the socket and whether its SuperSpeed link trains.

## What the day was made of

The day began with the kernel's own stack confirmed on the board and the
xHCI takeover still untried, and ended with a full session on the Pi 4: a
USB keyboard typing, a USB stick mounted, programs loaded from it. Between
them were four board boots, each stopping one step further on, and four
pull requests, each a single change for the next boot to answer. The
takeover was clean; the driver then turned down 31 scratchpads it had room
for 8 of (#192); then the first command timed out because a 64-bit register
store did not survive the PCIe bridge (#193); then a SuperSpeed stick read
`speed=0` because its speed was read while the link retrained after the
reset (#194). `make stick` (#195) gave the stick the tree it needs, after a
review found four ways the first version could leave a stick unusable or
boot a stale kernel. Hans then put six directions on the roadmap for later:
partitions, an SD driver, booting from a stick, multi-core, SSH, and more
boards.

The lesson is in how the round trips were kept to one variable. Twice the
first build of a fix carried more than one change, and twice the review
pulled it back to one: the barrier and the probe out of the 64-bit round,
and in the port round the warm/hot decision moved to before the reset so
the round could answer cleanly. Each board boot then read as a yes or a no,
and four boots took the driver from refusing the controller to a working
system. The board stayed the only check that could fail for every one of
these fixes; QEMU's controller has no scratchpads, no bridge and no link
timing to get wrong.


## After the closeout: the barrier the board did not need

The closeout above was committed and pushed (`a81c375`), and the afternoon
took the first item on its list, the barrier between the xHCI ring setup
and the registers that hand it over. It had been held out of the #193
round so the board answered one question, and the board's answer (the
split 64-bit write alone brought the controller up) left it a correctness
fix with nothing to show on any machine here. `init_inner` now has a
`dsb sy` before DCBAAP, CRCR, the ERST block and Run, the barrier every
doorbell in the driver already had. Both rigs passed, and both would have
passed without it: QEMU has no write buffer. The only direct check was the
image, `dsb sy` from 18 to 22 in debug and 82 to 86 in release.

The review at high effort came back with seven findings, and one was
older than the branch and worth more than it: `ring_push` wrote each TRB
in one four-word store, the cycle bit included, so on the Pi's
non-cacheable pool the controller could see a fresh cycle bit over a stale
pointer or length. That went on the roadmap as the next item, with two
more: the barrier belongs in the register-write path rather than placed
by hand at each site (which also settles `event_ring_pop`'s lone
`dmb sy` before ERDP), and ERDP is programmed after ERSTBA where the spec's
initialization order puts it before, a change for a board round of its
own because it changes what the controller sees. One finding was taken on
the branch: the comment had said Linux puts the same `dsb sy` before every
MMIO write, and arm64's `writel` is `dmb oshst`. Merged as #196.
`screenlog.0` went into `.gitignore` (`26b78c2`), so the serial capture
stops showing in every status.

## The cycle bit, and then the whole TD

The first build of the cycle-bit fix did what the roadmap item said:
dwords 0 to 2, `dmb oshst` (Linux's `dma_wmb()`), then dword 3. Both rigs
passed, and the image showed 17 `dmb oshst` where there had been none. The
first note on the roadmap said each sat between the `+0x8` and `+0xc`
stores, written after looking at three of the seventeen; checking all of
them found five with register arithmetic between the barrier and the
store, and the note was narrowed to what had been checked (the first store
after each barrier is the one at `+0xc`).

The review of that build found the fix was the right size for the item's
wording and the wrong size for the bug. A control request is three TRBs,
and the per-TRB barrier published each as it was written: under the very
premise of the fix, a controller that re-reads the dequeue TRB without a
doorbell could take the Setup stage before the Data and Status TRBs were
in the ring. Linux's `giveback_first_trb` exists for this. The second
build replaced `ring_push` with `ring_push_td`, which writes every word of
a TD with the first TRB's cycle bit still software's, then one
`dmb oshst`, then flips that bit; `ring_push` became a TD of one, so there
is no way left to write a TRB into a live ring outside the rule, and
`control_transfer` builds its TRBs and pushes them as one TD. One barrier
per TD instead of per TRB, and the Link TRB's wrap writes its cycle word
only. The review's other findings were taken (the doc comment now states
the contract; the roadmap item no longer asks for a Link TRB barrier the
build deliberately lacks, and no longer calls `ring_push` the only TRB
writer, since ring setup writes them before the handover) or put on the
roadmap (`INT_RING` is not zeroed when the keyboard is set up, latent while
that runs once per boot).

This time there was a check that could fail. With the final flip removed,
`test-usb-hub` went red on every device, and the kernel's own timeout dump
showed the Enable Slot command in the ring as `[0, 0, 0, 0x2400]`, type 9
with its cycle bit 0: the held TRB is not the controller's until the flip.
With the flip back, 19 ok and `test-el1-drop` green, and in the release
image all 19 `dmb oshst` have the flip as the first store after them. The
mutation cannot show the barrier is needed, nothing on QEMU can, but it
shows the hold is real.

The second review, of the code the first had not read, traced every case
(a single TRB, a batch wrapping through the Link TRB, a held first TRB at
the ring's last usable slot) and found no correctness bug. What it found
was the shape around the path: `ring_push_td` took its addresses out
through a caller's slice beside the TRBs' slice, two lengths nothing tied
together, so a short one could panic halfway through a held batch; a
control transfer was called one TD when it is three stage TDs published
together (Linux's `xhci_queue_ctrl_tx`); the history note said the old
four-word `write_volatile` was one store, when the point is that the
compiler may split it in any order; and the contract said ring setup zeroes
the ring, which `INT_RING`'s did not. All taken, in `a7f48a0`: the function
became `ring_publish`, returning a `[u64; MAX_PUBLISH]` by value with the
count asserted before anything is written, and `INT_RING` is zeroed at
keyboard setup. The one finding not taken in code went on the roadmap: no
committed check guards the barriers, so a refactor can drop one with every
rig green. The mutation was run again on the final code (17 FAIL, the same
held Enable Slot), both rigs passed, and all 19 barriers in the release
image still have the flip as the first store after them. Merged as #197.
Neither #196 nor #197 has been booted on the board yet.

## The ordering fixes on the board

Hans staged a card and a stick from `main` at `e738302`, with #196 and #197
both in, and booted the Pi 4. The same full session as the morning's: the
stick on SuperSpeed root port 3 through #194's wait, the keyboard behind the

board, and nothing more: the board ran without them, and what they close is
a timing window no single boot is likely to hit.
