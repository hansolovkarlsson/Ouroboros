# 2026-10-23

## A blank disk, and a rule told wrongly before it was built

The day opened on the 22nd's second closeout pass (#345) and took the
standup's first item: a virtio disk whose sector 0 has no MBR signature was
dropped by `init_storage`, so a blank disk never reached fsd, and `partition`
and `format` could not prepare it. The check came in with Phase 3c on
2026-08-15, when the kernel mounted FAT32 itself and a valid signature was
proof that bytes had come off the disk; it only logged then, and became a
drop later. Nothing depended on it any more. The case that makes it a defect
rather than a curiosity is the system's own: `erase disk` zeroes the first
MiB, signature included, so a disk erased and the machine rebooted before
`partition` was gone.

Hans asked for the explanation first. It recommended holding the disk as
"not the boot disk" and said the stick would still win. That was wrong, and
it was found only when the rig was being designed: `install_boot_disk`
refuses a stick that is not the boot disk whenever any virtio disk is held,
and fsd's boot mount does not rescan, so a blank disk beside an ordinary data
stick would have brought the boot up with nothing mounted, where main put the
stick at `/`. The work stopped and went back to Hans with the correction, and
he chose the other rank: a blank disk below any stick, installed only when
none goes in. The lesson is the one the 22nd's standup carried, one level
up: an explanation is a claim about the code, and this one had not been
checked against the function it described.

The first version held a disk for its missing signature alone and built
`make test-blank-disk` with three cases (a blank disk prepared, the same
across an `erase disk` and a reboot, a blank disk beside a stick), each with
a control that failed. A max review then found the definition too wide.
EDK2 boots a GPT disk whose protective MBR carries no signature, and both our
boot-disk check and fsd read GPT from LBA 1, so a GPT boot disk could be held
as blank and lose to any stick, the mistake GPT0 removed the day before for
an unreadable sector 0. An MBR whose signature alone is damaged was blank to
the kernel and mounted by fsd. A blank disk whose first read failed lost the
label on the retry, and one beside a stick whose init failed was dropped,
the original bug on another path. Blank is now `parttable::is_blank`, a
disk holding nothing a reader here or a firmware takes for a table or a
volume, host-tested, asked twice as D6 asks the table. fsd's boot line names
`partition` and `format` on a disk with no partition.

The review also refuted a sentence copied into two rigs: that no rig could
boot with the boot partition unknown, "since QEMU's firmware always names the
partition". esp.img's FAT32 alone on NVMe, a superfloppy, boots, and its
device path names no partition. UNKNOWN now runs there. The sentence had been
written into `test-probe-ioerr` the day before and copied without a test.

Finding 12 went back to Hans and stays a roadmap item: a disk that is signed
but holds nothing fsd mounts (one `partition` wrote, rebooted before
`format`) still keeps a non-boot stick out at boot, and `mount -a` then
swaps it in, two rules for one pair of disks. One rule would mean ranking a
held disk by what fsd finds on it, or letting fsd's boot mount rescan, which
changes the boot on Parallels and the Pi.

The last final run found a miss of mine: `test-probe-ioerr`'s SECTOR0 and
GPT0 graded the kernel's old `read of sector 0 failed` line, renamed when the
first read became `is_blank`'s. I had grepped the rigs for fsd's changed line
and not the kernel's. The behaviour the two checks guard passed throughout;
they read the new line now. #346 merged.
