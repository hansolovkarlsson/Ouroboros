## D5: kept, demoted, and the rollback it showed

D5 was the arc's one open decision: whether to retire `make sdcard`, now
that `make bootstick PI=1` writes a whole card. Hans asked what it was, and
then took it. Keep it, and demote it. A card is staged by `make bootstick
PI=1`, but `make sdcard` is the one way to re-stage the boot partition
alone. It copies `build/esp` onto the mounted FAT volume and never writes
partition 2, so the files on the root survive a new kernel. A card already
in use needs exactly that when a new release comes out. #416 recorded the
decision in `roadmap-sd-card.md`, `testing-pi4.md` section 4,
`make-targets.md` and `CLAUDE.md`.

Hans then asked whether to try it on the board, and I predicted the run
from `testing-pi4.md` section 4. That section said the counter's preferred
store was the UEFI variable, which lives in `RPI_EFI.fd` and which the
script keeps, so the count would survive. It did not. The root's files
came through: `cat keep` read back the line written before, and the login
and cluster identity were unchanged. But `bootid` went from boot 6 to boot
1, `variable no, file yes`. The Pi's variable has read absent on every boot
since 2026-10-01, so `EFI/ORBS/BOOTID.TXT` is the counter's only store, and
`sdcard.sh` replaced it with the build's record of 0. A count that starts
again can reissue a boot number, and the boot number is what makes a
session's ephemeral key differ across reboots. The claim in section 4 was
corrected in the same PR. The prediction is scored in the true-when-written
postmortem, because I read the summary of the stores and not the board's
own `bootid` lines, which had said `variable no` for five weeks.

## #417: the counter carried, and two reviews

`c1eb6e59` made `sdcard.sh` keep the larger of the card's value and the
build's, as `bootstick.py` already did. It did this in the new `EFI/ORBS`
copy, before the swap, so the old entry is still whole until the new one
is right. `make test-sdcard` is a new rig. It is a FAT32 image hdiutil
attaches under `/Volumes`, so the script's own guards pass, with a stand-in
`RPI_EFI.fd` to make it a Pi card. The card at 6 against a build at 0 fails
on the old script.

The first review found eight things, and the one that mattered was the
record rule written a second time, in shell. It took a newline followed by
twenty digits as a record, which the kernel refuses. `d0bd160f` made
`scripts/bootcounter.py` the one host-side copy of the kernel's rule. That
is 21 bytes, twenty ASCII digits and a newline, and a value that fits a
u64. `bootstick.py` imports it and `sdcard.sh` runs its `carry`. The same
commit read an interrupted run's `EFI/ORBS.sdnew` too. A run cut off
between the swap's `rm` and its `mv` leaves the counter only there.

The second review, which Hans ran, found that this repair had its own
version of the bug. To read the leftover, `place()` copied its counter to a
host temp file and then deleted `.sdnew`. A failure after that point left
the count only in `$TMPDIR`, and the next run staged 0. `116e6d90` turned
it around. When the entry is missing and `.sdnew` is there, the earlier
swap is finished first. That is always safe, because the `rm` comes after
the copy completed, so the leftover is whole. The temp file is gone. The
same review found a self-test case that could not fail: a non-ASCII digit
two bytes wide made the input 22 bytes, and the length rule refused it
before the digit rule was reached. It also found a build record that was
no record being staged with no word said, which now stops the script. The
rig gained `cut-twice`, a re-stage that fails in its copy after an
interrupted run, and `bad-alone`. With the fix removed, `cut-twice` reads
0. One of the three mutations, a loosened digit class, was caught as a
traceback from `int()` and not as a FAIL line. The exit is still nonzero,
so `make test` goes red, but it is a crash and not a graded check.

Hans merged #417 as `56946121`, re-staged the card from it, and the next
boot read boot 2, `file yes`. The root was kept and there was no fault.
#418 recorded that.

## A defect I flagged that was not there

Earlier in the day I told Hans that `bootid.rs:106`'s `v + 1` was an
unchecked add. When he asked for the fix, I read the function and found the
match arm above it. It turns a `v` of at least `BOOT_ID_NONE - 1` into no
counter, and `BOOT_ID_NONE` is `u64::MAX`. The add can therefore never
wrap, and the guard is the stronger rule, since it also keeps the counter
off the syscall's "none" value. Hans said to leave it as it is. I had
written a defect down after seeing one line, without reading the code that
would have had to produce it. That is the shape the true-when-written
postmortem recorded on 2026-10-12.

## Pi item 1, asked for what was already built

Weighing the next arc, I read Pi item 1, "more than one partition in use".
It said `fsd` "mounts only the first one that probes" and asked for the
card's boot partition and a data partition to be mountable side by side.
`shell-commands.md` says otherwise: `mount <n> <path>` has mounted a disk's
`n`-th partition beside `/` since 2026-08-25 (`b2159609`, the cluster's
Phase 0 multi-mount). The item was written on 2026-10-03, so it was false on
the day it was written. I proposed `mount 0 /mnt/boot` on the board as the
check.

Hans tried it, and it seemed not to work. The log showed why. `mount <n>
<path>` prints nothing when it succeeds, and nothing after it looked inside
`/mnt/boot`: `ls /mnt` did not list `boot`, `cd boot` from `/` looked for
`/boot`, and bare `mount` still named only the ext2 root. After reading
the shell's `cmd_mount_at`, which binds a path and prints nothing, I ran
the same steps on QEMU's `disk.img`. Both
partitions mounted at once there, and `ls /mnt/boot` listed the ESP. Hans
ran `ls /mnt/boot` on the card next, and it listed the boot partition whole,
`RPI_EFI.fd` and the firmware's files beside `EFI/`. So the feature works,
and what the board showed is that it cannot be seen. The bind is a namespace
entry, not a directory entry, so its parent does not list it, and with no
`/mnt` on the disk `ls /mnt` says `no such file or directory` while `ls
/mnt/boot` works. #420 rewrote the item to what is left: bare `mount`
listing every mount and its path, and a parent that shows the mounts below
it. Both are changes to the shell's and `fsd`'s mount reporting.
