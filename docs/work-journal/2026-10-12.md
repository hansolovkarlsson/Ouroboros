# 2026-10-12

## Parallels boots the multi-core arc

The day opened on the standup's first two items: #276, the evening
closeout's records, merged on Hans's word, and then the one boot the
multi-core arc still owed, Parallels. The VM had two vCPUs; it was set to
four and `build/esp.hdd` built from `main` at `f61138f`.

The first boot answered less than it seemed to. The kernel and every server
came up with no fault, the cursor stood after the prompt, and `ps` named the
shell `running on core 0`. But the boot lines the plan named as the check,
`MADT: 4 cores` and the `core N up` lines, were never on the screen long
enough to read: `cond` clears it about two seconds after power-on, a
`prlctl capture` takes about a second, and the frames went from the
Parallels logo straight to `cond`'s screen. The serial port's file stayed
empty. The usb-storage postmortem met the same wall in 2026-08 with the PCI
inventory and answered it by re-printing after the exit; that answer does
not reach this far, because `cond` clears the kernel's re-print too. And
`coreprobe` and `cat` were unknown commands: on Parallels `/bin` lives on a
passed-through stick, since the kernel can read no other storage there.

That turned into a question from Hans: is it time for one disk carrying
both the boot partition and a root partition, on a stick, a card or a
virtual disk, and should it come before Parallels? The answer was yes to
the direction and no to the order. QEMU already boots two-partition images;
the Pi needs roadmap items 1 and 3 (more than one partition in use, and
booting from a stick); but a two-partition `.hdd` would not help Parallels
at all, since the kernel cannot read that disk after the exit whatever is on
it. The only thing that could change Parallels is the firmware booting from
the passed-through stick, which is the arc's cheapest first experiment.
Hans set it as the direction after multi-core, written into `ROADMAP.md`
item 3; the plan document is not yet written.

So the stick. It was the Pi's, exFAT, staged again by `make stick` with its
`/etc` kept, and assigned to the VM with `prlsrvctl usb set`, which this
project had not used before: it connects the stick whenever the VM runs, no
click in Parallels' window needed. Login refused `root`/`root` twice before
it was clear that the password was right and the keys were not arriving:
an Enter went missing and login read `rootroot` as the user name.

From there every check went through, some of them on a second or third
typing. `coreprobe` ran on core 1 with `4 cores up`; the pair ran on cores 3
and 1 at once; `coreprobe calls` made 100 calls to `fsd` from core 1 at 20
µs each, the first cross-core call figure from hardware; `coreprobe hold` on
core 1 was ended by Ctrl+C; a held probe in the background was `running on
core 1` in `ps` and in `/proc/6/core`, `/proc/cpus` read 4, and `kill 6`
emptied the slot. `4 cores up` also stands in for the unread boot lines more
exactly than it first looked: it is `smp::up_cores()`, and a secondary marks
itself there only after its `up` line is printed. Four probes in one
pipeline never got through the typing and stays with `make test-smp`.

The lost keys were their own finding, and one boot settled what kind. With
the stick and one vCPU, keys were lost just the same (`corprobe`, `ove the
lazy dog`), and a slower key delay had already failed to help at four. The
two boots without the stick that morning lost none. So it is the keyboard
and the stick on one xHCI, not the cores: a third mode beside the two the
contention fix closed in v0.4, where the keyboard is addressed and the stick
works but reports go missing. `ROADMAP.md` item 4 has it as a sub-item, with
the boot lines as another; `testing-parallels.md` has the boot as a section.

## The stranded task that could not be stranded

Hans asked how much work the arc's one open fix was: a task left reading as
running on a secondary core that had halted alone. Sizing it meant reading
the halt itself, and `power::halt` already answered it. A core halts alone
only when it holds no lock, is not the boot core, and runs the idle slot; a
core running a program halts the whole kernel (`runs_a_program`, from the
review of #266 on 2026-10-10). A core is marked down only on that function's
halt-alone path; the two places a secondary parks without it (no GIC
interface, the entry stub's last loop) are before it ever runs a task, with
its `CURRENT` still the idle slot it started at, which `running_core` reads
as no task. So the dead core never holds one, `ps` cannot show it, and the
remote kill's "which ends it" is true in every case.

The roadmap item had been written a day after that rule, by the third review
of #271, which read every reader of `CURRENT` and not the one function that
decides what a halting core leaves there. The fix was to the records: the
item closed with the reasoning, the comment in `tasks.rs` that pointed at it
now says why the case cannot arise, and the true-when-written postmortem,
which had called the kill line false in the stranded case, gained the
correction and its rule (before writing down a defect, read the code that
would have to produce it). What the item's sketch would still buy, keeping
the system running when a secondary faults in the kernel under a program,
is resilience, not a defect, and went to the roadmap as that.

The high review of #278 found five things, and the first was this
document's own subject. The rewritten comment in `tasks.rs` said a halted
core's `CURRENT` is always the idle slot, a claim only a test in `power.rs`
made true, while the same pull request proposed changing `power::halt` to
let such a core halt alone. So the rule became code: `smp::mark_down_here`
became `smp::halt_alone_here`, which answers whether this core may halt
alone and marks it down only when it may, refusing the boot core and a core
running a program, and `power::halt` asks it last. The other four were the
records' own: my "every halt passes through `power::halt`" (two park loops
do not, both before any task), the postmortem's 10-12 paragraph sitting
inside the 10-11 section and its abstract not saying so, and the resilience
idea announced as a `new` item while living inside a closed one; each fixed.

A second high review of #278 found eight more, and it confirmed the
central claim by reading every writer of `CURRENT`. The first was the same
claim one step further on: the halt-alone outcome still lived in an `else`
arm of `power::halt`, reached only because `halt_alone_here` sat last in an
`||` chain. The decision, the mark and the `halted alone` line are now all
in that function, and `power::halt` halts the kernel unless it answers yes.
It also found a window the boot-core check could not see: in `smp::start`,
between `BOOT_INDEX` and `TPIDR_EL1` taking the MADT index, the boot core's
two indexes differ and `is_boot_core` says no. A fault there could not
happen in practice, but the check now also compares the core's MPIDR
affinity with the boot core's, recorded before either index moves
(`smp::BOOT_AFFINITY`). Three comments that still said a secondary holding
nothing halts alone (`exceptions.rs`, `lock.rs`, the plan) now add "running
no program". The records' share: "the one place a core is marked down" was
false (the no-GIC park marks a core failed too, before it ran anything);
the roadmap's pointers named sub-items by a position that had moved; and
the resilience idea, which my last fix had made a `new` sub-item, was still
inside item 4 while saying it was not arc work. It moved to the follow-ups,
with the two Parallels findings (lost keys, unreadable boot lines), which
are not arc work either; item 4 keeps only the `fsd` wedge, and the claim
in my previous paragraph that each finding was fixed was not true of that
one until now. The `fsd` wedge itself, the rig failure this review also
named, was traced today; its fix is #280, on #279, both open as this is written.

#278 was merged on Hans's word, and a high review of its last commit
(db0288a) followed, since that round of fixes had not been reviewed. It
found the affinity check in the wrong place: `halt_alone_here` was right in
`smp::start`'s window, but `is_boot_core` itself still answered by index,
so the fault report that comes before a halt (the stack canary check)
would read the wrong core's stack there. `is_boot_core` now compares MPIDR
affinity, recorded by `set_boot_core_index` as the kernel's first act, so
every caller is right in the window and `halt_alone_here` needs no check
of its own. It also found the `halted alone` line printed after the core
was marked failed, which `smp::start` reads as "its own line said why";
the line now comes first. A worry that `lock::held_by_me` is wrong in the
same window does not apply: `main.rs` never takes the kernel lock, and
`smp::start` runs before any entry can.
