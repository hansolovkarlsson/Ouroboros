# 2026-10-17

## What a listing and a spawn read, counted by the disk

The day began with #306 merged and DevTools's alloc-size note triaged (#307):
its `cc` reads `__alloc_size__`, which was patch 0003's condition. The triage
built `cc` twice in a scratch directory, from DevTools's HEAD and from the
commit before, and compiled each of the 136 headers alone with each; the old
`cc` refused `stdlib.h` and `malloc.h` with the macro defined, so the check
could fail, and the new one refused the same 26 headers either way. The
note's correction held too: the inline pair costs four headers, not two.
Patch 0003 went in #308. `libc.a` regenerated byte for byte, and every
program built on picolibc was the same bytes before and after, 75 objects and
binaries, Edit's and cpp's under all four toolchain combinations, so the C
rigs that read the staged headers were the ones left to run. Two of them did
not run the first time: a loop over `"test-cpp CCOMP=devtools CLINK=devtools"`
in zsh handed `make` one word, and the log had no check lines in it, which is
how it was caught. Testing whether `cc` answers `__has_attribute` for the
roadmap's held alternative found it answers 0 for everything, `alloc_size`
included, which went to DevTools as a finding (#309); by evening DevTools had
made `cc` answer 1 for the eleven attributes it takes.

The rest of the day was the roadmap's listing walk, and then whatever the
disk showed. fsd answered each `NP_READDIR` page by walking the whole
directory and keeping the page. #310 made the walk stop where the page ends:
`ReaddirFill::push` answers `ControlFlow`, and every filesystem's `list_dir`
stops on `Break`. No listing check can see that, since `ReaddirFill` drops
what a walker pushes after a full page, so the measure was QEMU's
`virtio_blk_handle_read` trace. The first measurement was wrong twice over.
It compared `ls /include` with `echo x`, and the difference was mostly the
size of `/bin/LS`: spawning reads a program 512 bytes a request, each one
resolving the path from the root, so the larger binary swamped the listing.
Then it compared with `ls /include/stdio.h`, which the review pointed out
walks `/include` to that file and so took part of the listing out of its own
figure. The baseline that differs by the listing alone is the shell's glob:
`echo /include/qqq*` lists the directory, matches nothing and keeps the word,
against `echo /include/qqqq`, the same binary and argument length. The stop
saved little on the two-page `/include` (72 to 69 sectors on FAT32), because
three walks of every listing still read it all, the last page, the question
past the end and the empty page, and the roadmap's claim that the stop would
end the past-the-end question at once was wrong: only a whole walk can say
nothing is left. The review's sharpest finding was that nothing could fail
on a walker ignoring `Break`. `test-listing-walk` grades it now: without the
stop a listing's requests all do the same work, so every sector's count is a
multiple of `p + 2`, and the counts must share no factor above 1. Its first
version graded "some sector read fewer times than the most-read", which held
on FAT32 and meant nothing on ext2, whose most-read sector was an inode table
block read once an entry.

That inode block was the next item. ext2's walk read every entry's inode,
the entries before a page's start included, for a kind and a size no caller
used: 288 of the 888 sectors a listing read. #311 takes the kind from the
entry's `file_type` byte and drops the size from `list_dir`. A listing of 300
files went from 3,698 sectors to 74, and the rig went blind on ext2 in the
same change: `/include` there is now two blocks with page one ending in the
second, so every walk reads both. The rig only ever saw ext2's stop through
the inode reads it had just removed. It now builds `/walk`, 300 files, on its
copy of the image. Its review found the fallback, a volume without
`filetype`, covered by one hand check that nothing repeats, so the rig
rebuilds the root from the image's own tree with `mke2fs -d` twice, with and
without the feature, and `ls /kinds` must mark the directories on both;
trusting the type byte with the feature off fails it.

The trace had also shown where the cost of a command really goes: starting
`ls` read about 1,040 sectors more than starting `echo`, `/bin`'s directory
read once for every 512 bytes staged. The roadmap said one opened fid would
resolve the path once. It would not: fsd's `Fid` keeps the path, and
`NP_PREAD` resolves it on every read, so every C program's `read()` pays this
too, which went on the roadmap as its own item. #312 makes fsd's `NP_READ`
resolve once and copy the file to the client's grant a `SAFECOPY_MAX` piece
at a time, each at its own offset, and the shell and netd read 8 KiB a
request. Three things broke on the way, each found by booting. The first
spawn failed outright because the kernel capped a grant at 2048 bytes, one
copy's worth, which also meant fsd's piece loop could never run a second
piece; `GRANT_MAX` is 64 KiB now, each copy still 2048 and still checked
against the grant and the client's live region. netd faulted at boot with an
8 KiB buffer on its stack, before any `cpu` ran, the function being inlined
into the serve loop's frame; its buffer is in its heap region. And the
review found the shell's copy of the same buffer on its stack too, where with
no stack probes a frame that size can step over the guard page into the
heap's pipeline capture without a fault; it is the heap's last 8 KiB now,
split once from the capture. Moving to larger reads also changed the order
of FAT reads enough that `test-listing-walk`'s two FAT32 boots differed by
one read of the cached FAT sector, so its boots start with one listing to
warm fsd's caches. One run of `ls` reads 199 sectors on FAT32, from 1,201.
`test-spawn-reads` began with a bound of one read a 512-byte chunk, which the
review showed would pass fsd resolving once a 2 KiB piece; it now counts
exactly, a program padded to 200 KiB resolving its path 23 more times than
the plain one because it makes 23 more requests, where the two undone halves
make 93 and 374.

After the closeout #312 and the closeout itself (#313) merged, and exFAT got
its read cursor. The roadmap had the item backed by `test-spawn-reads`'s
290 sectors against FAT32's 199, but the image's `/bin` files are all
contiguous and walk no chain: of the 272 sectors a run of `ls` reads now,
14 are FAT reads, one sector each time, for `/bin`'s four-cluster
directory, and 168 are that directory read seven times. The case the cursor
is for is a file fsd writes, always chained. The rig's first try copied
`/BIG` to `/CHAIN` with the guest's `cp` and compared the two, and read 0:
macOS had written the host's `/BIG` chained too, so both sides walked the
same chain. Comparing two fsd copies of different sizes read 2,441 FAT
sectors on the unchanged fsd against the 46 the two chains' steps predict,
and exactly 46 with the cursor. Nothing checks the cursor's invalidation,
on FAT32 or here, since every spawn replaces the cursor; that went on the
roadmap.

The high review of #314 found the fix one layer too high: `write_at` still
walked the chain from its first cluster a FAT read a step, so the rig's own
`cp` of 200 KiB read 3,838 FAT sectors. exFAT got FAT32's one-sector FAT
cache, and the `cp` reads 116. The cache hid the cursor from the rig, since
a chain inside one FAT sector costs one read with or without it, so the rig
copies 640 KiB now, 160 clusters, past one sector's 128 entries, and the
host reads the chain off the boot's disk and predicts the reads one walk
through the cache makes: 6 on the rig's image, and 7 on the controls'
image, which had different host files and so a different layout for `cp`;
the count followed the layout exactly. Ignoring the cursor
read 1,436, bypassing the cache 159, and a cache `write_fat_entry` left
stale stopped the program running. The review's guard that "no FAT sector
was read" could not fail, because `cp` reads the FAT; the guards now are
that the chain is FAT-chained and crosses a FAT sector, which the controls
need. The remaining findings, one cursor a volume, the write side's walk,
and the two copies of the read walk, went on the roadmap. A second review
found the rig's own weak points: the host's walk of the FAT had no bound,
so a looping chain would have hung the rig, an inspect of a failed boot
raised past its verdict, and the prediction assumed a one-cluster root
without checking it. Each is a graded problem now. #314 merged with both
reviews' fixes, nine PRs in the day (#306 to #314).
