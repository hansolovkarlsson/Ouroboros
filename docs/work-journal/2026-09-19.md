## 2026-09-19: a newtype, twenty reviews, and the two bugs they turned up

The standup left the smallest of its three fixes at the top: `activate_task`
clamped an out-of-range view index onto the last translation-table view, so a
task past the end would have run under another task's tables, silently. The
fourth review of #135 had noticed it in passing. It was to be a `const` assert
tying two literals together, one commit, one review. It became four pull
requests (#136, #137, #138, #139), thirty-one commits plus four merges,
twenty-six high-effort reviews, and two real bugs that none of the reviews
were looking for. Everything merged; `main` ends the day at `6e84210` with
the suite green and clippy at zero for the first time. The reasoning below is
about why one small fix took twenty reviews, what the reviews were actually
finding, and the two bugs.

### The assert that could not fail, and the refusal no caller could reach

The first commit added `const _: () = assert!(MAX_EL0_REGIONS ==
tasks::NUM_TASKS)` and I wrote in the PR that a mutation (`NUM_TASKS = 12`)
had shown it could fail. The review pointed out that the equality was already
enforced by the type system: `install_identity_map` and
`rebuild_with_el0_regions` take arrays sized by one constant and their callers
pass arrays sized by the other. My mutation had failed the build on four type
mismatches with the assert deleted too, so it proved nothing about the assert,
and the comment I wrote saying there had been "no check" was false on the day
it was written. The assert went; `MAX_EL0_REGIONS` is defined as
`tasks::NUM_TASKS` now, one definition, and the two "must stay equal" comments
are corrected.

The refusal came next, because with the clamp gone a bad slot would panic,
and a post-exit panic under the `uefi` crate's handler is silent. I ran that,
rather than read it: a temporary `panic!()` after the identity-map install
printed nothing further, QEMU's trace showed no abort, and the machine shut
down on a PSCI call a minute into the boot. So `activate_task` grew a guard
that reported the slot and halted, and I exercised it by calling
`activate_task(NUM_TASKS)` from `main.rs` and watching the line print. The
sixth review showed that mutation was not in situ: every runtime caller
indexes `TASKS[next]` before it switches, so a real bad slot panics there
first and the guard never prints. It had been proved to work in a position
nothing reaches. The guard became `l0_table`, one lookup, with a doc that says
what it does and does not guard, and the check at the right depth became the
next PR.

### The newtype, and what twenty rounds were finding

`TaskIndex` is a `usize` below `NUM_TASKS` by construction, with its field
private to a nested module so that even `tasks.rs` cannot spell
`TaskIndex(x)`. The code converged around the ninth round: no correctness
finding in the kernel after that. What the first nine rounds found was real
and shrinking. The first round's `current_index()` rebuilt the type with a
modulo, which is a clamp wearing a type. The second round found the modulo
constructor itself was the escape hatch, total and crate-visible; it is gone,
and the round-robin step is a method on the type. The third round found I had
swapped the atomic for an `UnsafeCell` and turned race-freedom into an
unenforced precondition; the storage is atomic again, inside the type's
module, with one typed store. The fourth round found `make test` red: I had
edited two documents whose published pages are stamped against their source,
and I had run build, clippy, compile mutations and driven boots for four
rounds and never the suite the project defines. The project's check caught
what mine could not, and that is now in memory as a rule for every push.

From the tenth round on, the code findings were placement and naming, and the
prose findings were sentences I had written in the previous round. The
ledger named a `CurrentCell` the same PR's third commit had deleted. A shell
message said "use exit" for a shell whose `exit` only logs out, which I had
watched happen during a witness run and not read. I wrote that Ctrl+C ends a
nested shell after its keyboard has reverted, and it does not; I wrote that a
wait is interrupted whenever the waiter holds the keyboard, and only the boot
shell's is; I fixed that in the architecture doc and wrote the wrong version
into the manual in the same commit. Every caller inventory in a doc comment
was wrong within a round. The fix for that class was not another correction
but fewer claims: no inventories, no advice in error messages, docs that
state the mechanism and stop, and a stopping rule written into the PR body:
a further round only for a finding that changes behaviour, a check that
cannot fail, or a claim the kernel contradicts. Under that rule the last four
rounds each qualified two or three items and filed the rest, and I recommended
merging with the filed items as the next PRs.

One more thing the rounds found, about the tooling rather than the code: after
the fourteenth commit a review run had checked out the remote ref in my
working tree, so two commits landed on a detached HEAD and each push of the
branch name pushed nothing while printing success. The reviewer's own "the
remote is two commits behind" was the only signal. Reattached, pushed, and
every commit command since checks the branch first.

### Two bugs found by review, both witnessed before they were fixed

The fifth review read `kill_task`'s doc, which said the syscall layer
guaranteed the victim was never the running task because "only tasks at slot
two and above can be killed, and the caller is always whichever task is
running". True when the boot shell was the only task making syscalls; false
since spawned programs run. A child shell spawned from the boot shell into
slot 6 ran `kill 6` on the pre-fix image: the kernel printed "task 6 killed",
the `eret` landed in the freed region as an EL0 instruction permission fault,
and the fault handler tore the slot down a second time. The arm refuses a
self-target now, with its own code, `TASK_ERR_SELF`, and `kill_task` checks
it again as the mechanism, which I exercised by disabling both refusals and
watching the mechanism's line print. The related fallback, resuming a
torn-down task when nothing else is runnable, is a reported halt, exercised by
blocking the idle task at boot; the supervisor's kill of a wedged server
reached it, not the exit path I had planned, and the commit says so.

The second review of #138 found the other one. `TRY_READ_CHAR` and
`READ_CHAR` polled the keyboard for whoever called; only the tick's wake-check
gated on the owner. `readkey` gained a `poll` mode as the observer, and on the
pre-fix kernel `exec /bin/readkey poll` then `echo hi` at the shell arrived as
`ehoi`, the poller having echoed the stolen `c`, space and `h`. The fix went
to the choke point: `poll_keyboard_byte` takes the reader it polls for and
answers nothing, reading nothing, unless that reader owns the keyboard. The
parameter is required, so a new caller cannot forget the rule, and the six
sites that each restated it keep no gate of their own.

### The Ctrl+C mark, and the rig that can type a Ctrl+C

`PENDING_KILL` held the keyboard owner's slot; a slot reaped and re-spawned
between the mark and the tick would have had its new occupant killed. It holds
the owner's packed identity now, generation and slot, the value the kernel
already captures for a message sender, and the tick kills only if the slot's
occupant is that identity. It turned out `drive-qemu.py` can type a raw `0x03`
to a foreground program, so this was witnessed both ways in situ: Ctrl+C at a
foreground `readkey` terminated it, and with the mark mutated to a stale
generation the same Ctrl+C did nothing and `readkey` ran to a normal exit. The
re-spawn window itself cannot be driven, and the ledger says the identity
check is what the mutation exercises.

### The numbering, off by one

`TASK_ERR_SELF` went in at `MAX-43` with the floor at `MAX-44`, leaving
`MAX-42` a hole. The band's pattern, followed by both previous reservations,
is that the new code takes the floor's old value and the floor steps down by
one. Corrected the next round, in the ABI crate, the C header's mirror, both
manuals and the ledger, and the pattern is now stated on the floor's own doc.
This is a release-note fact: the floor moved, and the next cut has to say so.

### Where it ends

Four pull requests merged, `main` at `6e84210`, suite green: 137 unit tests,
107 wire constants across four peers, 17 site pages matching their source, 65
binaries with no absolute relocation, clippy at zero. What the day settled:
a task slot is a type, ending a task is one function in one order, the
scheduler's "nothing runnable" has one handler, every syscall arm that takes a
slot argument constructs first, a task cannot kill itself, a keystroke is
consumed only on the owner's behalf, and the Ctrl+C mark names an occupant.
What it did not settle is in the roadmap ledger: the nested-shell keyboard
revert, the five-site switch tail, the two scan loops, the three names for
one liveness predicate, a generic sync cell, the task codes in the C header,
and the placeholder em-dash cells, which are a rule question.
