# 2026-11-08

## Mount points, built the evening before

The work merged today began on the evening of 2026-11-07, after that day's
second closeout (`1d7a6c80`), so it is recorded here, where it landed.
Pi item 1 had narrowed to one question: how a mount becomes visible to bare
`mount` and to `ls` of its parent, when a mount is a binding in the shell's
namespace and not a directory entry. There were two ways to do it. Unix
requires the mount point to exist as a directory first. Plan 9 has the
client add the names of the bindings below a directory to its listing. Hans
chose the union in the client. The Unix rule would have needed every image
and rig to grow the directories, and it could not mount anything on a
read-only root.

The walk is `ninep_abi::MountPoints`, host-tested, which names each
binding's first component below a directory. `ulib::fs_list_dir` and
`fs_stat`, the shell's own walk and `cd`, all use it. My first version
statted every name where a binding ended to decide whether it was a
directory, and `/dev/cons` listed as `cons/`. Asking the server was the
wrong source anyway: a remote mount's peer may be dead, and a listing
should not wait on it. So the kind now comes from the binding itself (the
console is a file; only a `bind` of a subtree is statted). Bare `mount`
walks the namespace with `for_each_binding` and names every mount at its
path. To name the root's own partition as ext2 rather than `bind of /`,
`FSOP_MOUNT_INFO` takes a tree in its first parameter. `make
test-mount-points` boots `disk.img`, which has no `/mnt`, and checks that
`ls /mnt` is refused before anything is bound. That rig also found an older
bug: a glob of the root from below it (`echo /b*` from `/etc`) searched
the cwd, because trimming the trailing slash turned `/` into an empty
string. The high review found seven more things, and all were fixed. Two
were left: names compare by bytes, so on FAT32 a disk's `MNT/` and a
binding's `mnt/` both list, recorded as a limit; and the repeated `GET_NS`
reads, skipped as not worth the change. Merged as #422, after the closeout
#421.

## The message, and a first version that asked the wrong party

He asked for the fix before the PR. It needed an error code a client can
give when the disk says "not found" but the namespace says the directory is
there. `FS_ERR_MOUNTS_ONLY` took `MAX-45`, the floor moved to `MAX-46`, and
`sys.h` moved with it, the way the last four client-side codes went in. The
first version asked only the namespace: is something bound below the path's
directory? I gave the rig six create commands in `/mnt` and one control,
`write /mnt/boot/nope/x`, a missing directory inside a mount, which must
still say "no such file".

Two things went wrong in checking it. When I ran the first two mutants, I
called the script directly and piped its output through `grep "^FAIL"`.
Nothing came out. I told Hans the script had booted the old `disk.img`,
since only `make` rebuilds the disk, and reran both through `make`, where
they failed as they should. That explanation was wrong. At the closeout I
ran the script on a changed tree, and the stale-image guard refused to boot
with exit 2. Its refusal line does not start with `FAIL`, so my filter
showed nothing. The guard worked; the filter hid it.

The second came from the high review. `/` has bindings below it on every
boot, so under the first version any "not found" in `/` became "holds only
mount points". `writeat /nofile 0 x`, a missing file in a real directory,
would have printed it. My one control was inside a mount, where nothing is
bound below, so it could not see that. The namespace can say a directory
has mounts below it. Only the server can say whether the directory exists.
So `ninep_abi::mounts_parent` now only names the directory, and the client
(`ulib`'s `mounts_only`, and the shell's copy behind its redirect) asks that
directory's own server for its stat. The message changes only when the
server has none. "Not a directory" counts as well, as it does in the
listing's union. `NO_FS` does not, because `/` answers that while `fsd`
restarts. The rig gained `writeat /nofile` as a second control, and four
mutants were each caught by the check meant for them. One gap is stated in
the PR: the shell's copy of the server check has no control, because a
redirect into a real directory creates its file and never gets a "not
found" to change. Merged as #423.

## After the closeout: per-user keys, the wire and both Python peers

The day's closeout merged at 09:46 (#425), and the rest of the day went to
the per-user keys arc, whose steps 0 to 4 had sat on `main` since
2026-09-27, below the wire. Step 5 (#426) wrote `AUTHNP05` into
`ninep-abi`'s normative block. The plan said the credential block was
"covered by the machine signature" without saying under which tag, and the
answer was a new one: under `AUTHNP03`'s tag, a captured credentialed frame
relabelled as the old format, its block read as the head of the NP
message, would carry a machine signature that still verified. The high
review then found a hole in Decision 8 itself. The user's signature bound
the calling machine but not the export, so an export that received a
credentialed one-shot request could replay the whole frame to a third
machine that authorizes the caller and act there as the user. The
export's key went into the signed input, and Decision 8 was amended in
place to say so and why. Three more of that review's findings were
contradictions inside the normative block, each of which a transcriber
would have carried into a peer.

Step 6 (#427) taught both Python peers the format. The server checks the
reason for every refusal, not only the status, because ten misbehaving
credentials that each fail for one reason are worth nothing if a frame
broken in some other way fails first; that check caught a bug in the test
on its first run. The high review found the server reading
`/etc/cluster/users` by Python's rules rather than clusterkeys'
(whitespace, a key with spaces in it, a file past the buffer), so the two
exports would have judged one file differently and step 8 would have
blamed the credential. The rules were transcribed and the wire check now
compares the buffer size.

## Step 8: the client, and a stack loss traced to a copy

Step 8 began that evening on `netd/user-cred-client`. The client signs a
credential for the uid captured when a request is parked, never for
whoever sent the last message, and a session opened with a credential is
closed when its user's last key goes. The send buffers grew by the 68-byte
block, and the probe read 2,016 bytes of headroom, 960 below step 7 and
under the 1,936 step 7 had rejected. Three experiments placed it: the new
close and reap removed, nothing; no credential sent at all, nothing; the
buffer back at step 7's size, 2,928. A frame-size diff named
`park_session`, 1,824 bytes then 2,800: it assembles a new `SessionConn`
on its own frame and copies it into the slot. Writing it by `ptr::write`,
and through a constructor never inlined, both left the copy in place, so
the session slots keep step 7's buffer (`SESSION_SBUF`) and a build-time
assert holds the largest fid verb, 560 bytes, under the room left.

The rig, `make test-cred-client`, needed three fixes before it graded
anything. It waited for a `login:` it had already matched. A background
program's line printed before the rig looked for it was invisible to a
wait that reads only new output. And the no-close control's fid checks
stayed green because the fid was held for 60 seconds, past the far
export's own 30-second idle reap, which killed it whatever the client did;
held for 25, the control fails as it should. The high review that night
moved the guard into the session lookup itself, so no future path that
drops a key has to remember to close sessions, wiped the stack below the
user's signature, where Ed25519 leaves its expansion of the key, and
signed with the newest of two keys for one user. Its records were
committed at 21:05, the branch not yet pushed.
