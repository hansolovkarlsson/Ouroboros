# 2026-09-28

## The third review of #179, and the Pi's desk work on `main`

The morning picked up the nine findings the last review of #179 had left
the evening before. Two mattered for the board. The event ring read an
event's four words in one volatile load and only then looked at the cycle
bit, with no barrier between them, so a CPU could pair a fresh cycle bit
with a stale completion code or pointer. QEMU cannot show that; on the Pi,
where the ring is non-cacheable memory a device writes, it is the ordering
that makes an event whole. `event_ring_pop` now reads the word with the
cycle bit, checks it, and only after a load barrier reads the rest. I wrote
`dmb ishld` first and changed it to `dmb oshld` before building on it: the
writer is a device, not another core, and `oshld` is what Linux's
`dma_rmb()` uses on arm64.

The other was my own check that could not fail. The compile-time assertion
that no xHCI ring crosses 64 KB tested offsets inside the DMA pool, and the
pool is aligned to 4 KB, so where its 64 KB boundaries fall is unknown at
compile time. The fix checks every ring against the page instead, which the
pool's alignment makes exact and which rules out a 64 KB crossing with it;
an event ring made larger than a page now fails the build, which the old
assertion would have let through.

The rest were smaller and each got a run that could show it: a range
outside RAM that the non-cacheable plan used to skip in silence now prints
a warning (a mutation passing one showed it); the `_CCA 0` log line names
the table and offset of its match (the control, looking for QEMU's
`_CCA One` instead, printed `in DSDT at offset 0xa2`); and the framebuffer
writers clean a glyph's eight rows with one barrier instead of eight, where
a 1080p clear had cost about 259,000. Screendumps covered both writers. The
console server's path was driven through a full-screen scroll with `help`
typed a dozen times on the USB keyboard. The kernel's own framebuffer
console only runs when no serial console exists and only until the console
server clears the screen, so it took a mutation that finds no serial
console and three timed screendumps; the first caught nothing but the
firmware's splash, the second the kernel's lines, drawn cleanly.

The evening's closeout went onto `main` (`4bc075f`) and #179 merged
(`e1a37e6`). With it, the desk work planned for the Pi 400's first boot is
all on `main`: the xHCI found through its own `PciIo` at firmware's CPU
address, USB 2.0 hubs, EP0 recovery, completions matched to their request,
the DMA pool non-cacheable where ACPI declares `_CCA 0`, and framebuffer
writes cleaned out to memory for the display engine. None of it has run on
the board. What only the board can settle, the translator fields behind
the Pi's high-speed hub, the cache behaviour itself and the `_CCA` scan's
positive case, is written into
[`testing-pi4.md`](../testing/testing-pi4.md) as the log lines to read on
it.
