## 2026-09-13: one constant, and the four reviews that kept finding its copy one hop further out

The standup left a small item at the top of the day: `STACK_PAGES` was
written in both `kernel/src/loader.rs` and `kernel/src/mmu.rs`, held equal by
a `must match loader.rs` comment, and the previous evening's client-session
work had grown one without the other and lost a chunk of the session to a
guard page sitting mid-stack. The fix was meant to be a first commit of ten
minutes. It became the whole day: two pull requests (#134, #135), five
high-effort reviews between them, and a chain of findings in which every fix
was correct and every review found the same shape one file further out. The
reasoning below is mostly about that chain, and about the two decisions I
defended for three rounds before a review showed the reasoning was borrowed
from a doc whose scope did not cover the case.

### The fix, and what the first review found beside it

The first commit did the obvious thing: `STACK_PAGES` and `GUARD_PAGES`
became `pub(crate)` in the loader and `mmu.rs` imported them. Value
unchanged, layout identical, the guest booted and ran a pipeline with no
aborts. A high review of that small diff came back with ten findings and the
top one was not in either file. `/bin/edtest`'s stack probe carried its own
`STACK_BYTES = 32 * 1024` under a "must match the loader's `STACK_PAGES`"
comment. The 40 KB growth had left it stale, its sanity check (is my own
frame inside the window I computed?) refused every run, and the peak-stack
measurement had been printing "unavailable" since, with nothing failing. I
confirmed it the way the project asks: the old source built against the new
kernel prints "unavailable" twice; the new one, which asks the kernel for the
stack extent through two new `HEAP_INFO` fields, calibrates and reports 3456
of 40960.

That review also pointed out that sharing the constants had not shared the
*layout*: `mmu.rs` still re-derived `base + size - (STACK + GUARD) * 4096`
from the imported numbers, so a layout change that was not a page-count bump
would still break the pair silently. `guard_page_addr` moved into the loader
beside `heap_area`, `STACK_PAGES` went private again, and `mmu.rs` asks. A
compile-time assert pins `GUARD_PAGES` to the single page `build_view` maps,
because the count had been imported as if it were honoured and it was not.
Two further findings were ledgered rather than fixed, and a third became the
next pull request.

### The slot-fit check, witnessed before it was written

Nothing checked that a loaded region fits the one 2 MB slot `mmu.rs` splits
into pages per task. A program's memory size is not its file size, so a large
`.bss` passes the 128 KB staging bound and arrives at the loader at a couple
of megabytes; the runtime allocator rounds up and hands out 4 MB; `build_view`
fills its one L3 table once per sub-slot and points both L2 entries at it.

Before adding the check I built the witness: a throwaway C program with a
1.9 MB `.bss`. The first attempt ran fine, which was the compiler folding the
array away at `-O2`; `volatile` made it real, and the program faulted at its
own region base with an unknown-instruction exception, its code fetched
through the aliased table as zeros. Exactly the prediction. With the bound in
place the same program is refused by name and an ordinary C program still
spawns. That witness, and two more crafted with a Python script that patches
program headers, drove the rest of the day.

### Two kernel halts from an unprivileged exec

The review of the check found that it compared a product computed *after* an
unchecked multiply. A `p_vaddr` near the top of the address space wraps
`region_pages * page_size` to a small number that passes the bound; in a
debug build the multiply panics inside the syscall handler. And a segment
with `p_filesz` larger than `p_memsz` passed the bound (sized from `memsz`)
and underflowed the `.bss` length in the copy. I crafted both files and ran
them against the branch as it stood: after each command the guest went
silent, no prompt, nothing. Any user with `exec` could take the machine down
with a 17 KB file. The bound moved to pages, before any multiply; the
inversion is refused by a `checked_sub` at the write.

The same round found the slot size in three untied copies (`SLOT_ALIGN`,
`RUNTIME_SLOT_ALIGN`, `MIB2`) and `build_view` still trusting the invariant.
The copies became one definition pinned by an assert, and `build_view` got a
fail-safe: a second overlapping sub-slot mapped EL1-only with a warning. That
fail-safe was itself the next review's top finding, twice over: the warning
went through the ordinary console print, which the kernel silences once the
console server is up on a framebuffer boot, so it was silent on exactly the
platforms where a later fault is hardest to read; and the flag that detected
the second sub-slot reset per 1 GB block while the per-view tables are shared
across blocks, so a region straddling a gigabyte boundary would alias the
whole first gigabyte unseen. It became a containment check at the top of the
function, first and last byte in one slot, refusing the region outright and
warning through the forced print. Mutation-tested by disabling the loader's
bound: the warning fires, the task dies on an instruction-permission fault at
its own base instead of executing zeros, the shell lives.

### The decision I defended three times with a borrowed reason

Every review asked for a distinct spawn error code for the image bound, so a
user could tell "shrink the file" from "shrink the static data". I refused
three times on the same ground: the reserved error band is full through
`MAX-40`, `MAX-41` is already libc's client-side sentinel, and moving
`FS_ERR_MIN` is a cross-node flag day. The fourth review took the objection
apart. `FS_ERR_MIN`'s own doc scopes the flag day to *a code that crosses the
wire*, and no spawn code ever does: `cpu` turns any spawn failure into a text
line before it reaches a peer. `FS_ERR_BUSY` had moved the floor on exactly
that reasoning six days earlier, one ABI line and one header line. I had
reused a true sentence past the case it was written for, and each time I
restated it the restatement looked more settled. `SPAWN_ERR_IMAGE_TOO_LARGE`
is `MAX-41` now; the floor is `MAX-42`; libc's sentinel stepped down under
its own static assert, which is what that assert was for.

The second reversal was the ceiling itself. Round three had put the most a
program's image may occupy into the ABI as a literal, pinned by a
compile-time assert in the loader against the tail it is derived from. It was
correct and it was wrong: a shell built against an older ABI prints a stale
number after a kernel tail change, and the MMU's slot size was now owned by
the userland ABI crate. The same branch had added `HEAP_INFO` stack fields
precisely so a program never restates the loader's page count. The ceiling
is a `HEAP_INFO` field now, served by the running kernel; the literal and its
assert are gone. The shell prints 1748 KB, and that number exists in no file.

### The smaller wrong turns, kept because they are the same shape

The site checker's `--update` re-stamps a page as fresh against its source.
Round three re-stamped `site/manual.html` without editing it, so the page
kept saying "128KB" after the manual said `SPAWN_STAGING_SIZE`. The script's
own docstring calls that the one way to make the check lie, and I did it by
following the command the check printed. The page is edited now, and the
next closeout should read what a stale page says before re-stamping it.

Three pre-existing em dashes rode along in table rows I edited, one per
round, each caught by my own diff grep only after the commit. The rule is
checked on added lines, and a rewritten row is an added line. Two more sit
in the site's rendered manual page, in HTML I did not write; they are a
style-check job, not this branch's.

And the boot-time containment warning, once forced past the quiet console,
still went nowhere on Parallels and the Pi: the five boot views are built
before any console exists there. It is recorded in a static now and printed
from `main.rs` once every console mechanism has had its turn. Mutation-tested
by forcing netd's boot view non-contained: the line printed once before any
task ran, netd faulted cleanly and was restarted, the shell came up.

### Where it ends

Both pull requests merged, `main` at `bb934cf`, suite green: 137 unit tests,
107 wire constants (five `HEAP_INFO` field selectors pinned today), 17 site
pages, 65 binaries with no absolute relocation. What the day settled: the
region layout has one owner, the loader; the slot fit is a check in two
places and a claim in none; a crafted file can no longer halt the kernel
from `exec`; and the two numbers a user hits when a spawn is refused come
from the kernel that refused it. What it did not settle is in the roadmap
ledger: the remaining prose copies of the stack size, the seven hand-derived
stack tops, and a silent clamp in `activate_task` the fourth review noticed
in passing, which runs an out-of-range slot under another view's tables.
