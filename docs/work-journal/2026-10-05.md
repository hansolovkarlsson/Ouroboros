## Last night's closeout committed, and PORTSC a type of its own (#209)

The day began with the closeout of 10-04's late night, committed as
`30422e8` after a read and pushed once `make test` was green (175 host
tests). No handoff was open.

The first item taken was the one #207's reviews had left: PORTSC was a
`reg::Whole32`, the same type as the doorbells, so a port function would
take a doorbell, and every write had to pass through `portsc_preserve` by
convention, or it wrote PED back (disabling the port) and cleared change
bits still pending. The same opt-in shape #207 removed for RsvdP. The first
cut gave PORTSC a handle of its own, `reg::PortStatus`, whose write read
the port itself and masked PED and the change bits, taking the bits to set
and the change bits to clear as two arguments. Three spellings were shown
not to compile by mutation (a one-value write, a doorbell for a port, a
hand-built handle), and a merge writing the change bits back failed the
new build-time asserts.

Its review (`/code-review high`, seven findings) showed the first cut had
kept the very shape it was meant to end, on other bits. The mask still
worked by exclusion: everything but PED and the change bits went back as
read, so PR, which is RW1S, would start a second reset if written while one
was running, and a RsvdZ bit reading 1 would go back as 1. Linux works by
inclusion (`xhci_port_state_to_neutral`): it writes back the read-only bits
and the bits that hold settings, and nothing else. The write now does the
same (`PORTSC_KEPT`), and `set` is held to the two resets
(`PORTSC_SETTABLE`), a list that grows with its callers. The review's third
point was one I had recorded as harmless: the write's own read made the
value written differ from the value the caller had decided on and logged.
The write now takes the caller's read, which also puts the read count back
where it was. The other four were records: the barrier check's docstring
claimed every routed write passed through both stores, the roadmap still
pointed at the deleted `portsc_preserve`, the handles are unforgeable only
outside `mod reg`, and one constant had been doing two jobs.

The old exclusion merge, put back as a mutation, now fails the asserts on
the case the review named, a reset in progress. `make test`,
`test-usb-hub` (19 ok, the same reset lines) and `test-el1-drop` were
green on both commits. On the wire the change is only a RsvdZ bit that
reads 1, now written 0; no capture has shown one, and no board round has
run it yet. Hans merged it as #209. DCBAAP and ERDP still share
`Whole64`, now an item of its own on the roadmap.

## A 1 MiB heap for Proem, and the stall it uncovered (#210, held)

Next was Proem's heap-growth handoff: `HEAP_PAGES` from 64 to 256, so every
program's heap is 1 MiB. Every user of the heap reads its size from
`HEAP_INFO`, so the change itself is one constant, and `/bin/CMEM`, a
picolibc program that mallocs 16 KiB blocks until refused and checks every
byte, showed `heap 1048576 ... 0 bad`, with 64 pages as the control.

Checking a redirect larger than the old 256 KiB capture turned up something
else: `cat` of the 758 KB kernel into a file had `fsd` restarted as wedged
part way through, the file left short. `cp` did the same with the old heap,
so the heap did not cause it, but the old capture limit had kept a redirect
from reaching it. One mistake on the way, recorded because it cost a boot:
I took a silent `wc /tmp.txt` for a hang, and `wc` reads only stdin.

The review of #210 found eight things. The one that mattered most was
already in the code before me: a spawned program gets the slot the last one
gave back, never cleared, so it could read that program's heap and stack. A
mutation without the new zeroing found 568,878 nonzero bytes in the FIRST
`cmem` run. `populate_region` now zeroes the region, `cmem` fails on size or
leftovers, and `make test-heap` runs it twice. Its first finding held the
merge: with a 1 MiB capture, a redirect would now write a short file where
it used to refuse. So the stall came first.

## Why `fsd` was restarted, measured (#211 to #214)

The first guess, written into the roadmap, was a FAT32 write too slow for
the supervisor's 2.5 s wedge limit. Counters in `fsd` said otherwise: each
2 KiB write finished inside two ticks. The supervisor samples task state at
the tick, and the tick reaches the CPU only at EL0, so a tick fired during
a disk read lands as `fsd` returns to EL0, runnable, and 128 of those in a
row look like a wedge. A first fix in the `MSG_RECV` fast path did nothing,
because `cp`'s requests reach a blocked `fsd` by direct delivery; the
signal that works is any call to `MSG_RECV`, since a wedged server never
gets back there. Its review took `MSG_TRY_RECV` out of it: `netd` polls
that from inside its own long loops. Merged as #211.

The per-request cost still grew with the offset, 353 reads for one 2 KiB
write at 160 KB, so #212 added a FAT-sector cache and a free-cluster hint:
32 reads at 640 KB. Its review found a real bug in my hint. The scan was
bounded by the FAT's capacity, not the volume's clusters, and a rounded-up
FAT holds entries past the last cluster that read as free; at cluster 2 the
scan reached them only on a full disk, with the hint ordinary use walked
there. A copy of the image with its recorded size cut by 1,000 sectors, then
filled from the Mac, made it a check that fails: the old bound wrote about
500 KB past the volume, the new one says `disk full`. One thing I could not
show: that dropping the cache at every request mattered, since each
request's directory walk replaced the stale sector first.

That question went to Hans with the review's other point, that the same
partition could be mounted as two trees. He chose to stop double mounts.
I built a refusal, then saw it would shut every later shell out of a
partition for the boot (trees above 0 were never unmounted), and made a
second mount bind the existing tree instead (#213). Its review showed that
with reuse, `/mnt/a` could be tree 0 itself, and an `unmount` followed by a
partition mount could hand slot 0 to another partition; partition mounts
now need `/` and never take slot 0. It also found that `erase`, `partition`
and `format` had refused every time since `/proc` landed, counting it as a
mount.

What `unmount` should clear was Hans's call too, and he chose every disk
tree (#214). Its review caught the next hole in my first version: freeing
the fids on them handed their numbers to the next opener. A fid now stays
allocated and dead until closed. `make test-unmount` holds a file open
across `unmount` and `mount -a` with a new C program, `cfidhold`, and it
caught one more thing on its first run: the kernel refused an `NS_SET` of
length 0, so the shell could never drop its last binding. What is left is
recorded: a binding in another shell can still reach a partition a later
mount puts in the same slot, until a tree carries a generation number.

Between those, two handoffs from Edit, a new editor project, were triaged
and accepted: the console and keyboard a full-screen editor needs, and
`rename` in the C port, which will land beside Proem's `unlink`.

The thread through the day: every review found something real, and three of
the fixes I was sure of were the review's next finding.

## `unlink` and `rename` for the C port (#215)

Two accepted notes landed together: Proem's `unlink` (picolibc's `remove`
calls it, and nothing defined it) and Edit's `rename` (a save through a temp
file). Both are path verbs `fsd` already served, so the library side was
small: `open`'s path resolution factored into a helper all three share,
`errno` set where picolibc has one, and `make test-crename` running both
notes' checks on FAT32 and ext2, the ext2 boot with a partition at `/mnt/f`
for EXDEV.

Its review found ten things, and the worst was not in the new code: no part
of `fsd` refused moving a directory inside itself, which on ext2 unlinks the
subtree into a cycle nothing reaches. The shell's `mv` could already do it;
`rename` would have given it to every C program. `NP_MV` refuses it now. The
others were the library's: an empty path meant the cwd, `..` was not
collapsed before the namespace chose a mount, most statuses became EIO, and
`errno` was switched on by whatever the include path held. Two were my rig's:
it typed `ls /` on the first check line instead of the summary, and it
graded by a substring every passing line contains, so a run cut short would
have passed. One mutation passed when it should not have: dropping the `..`
collapse changed nothing for `/etc/..`, because `fsd` follows `..` entries on
disk itself; only a `..` that climbs out of a mount shows the library's part,
so the check now uses `/mnt/f/../..`. Hans merged it as #215, and both notes
are closed.

## `fstat` for Proem, and the struct it was really writing (#216)

The last small Proem note asked `fstat` to zero what it does not fill, so a
zero `st_dev`/`st_ino` could mean "no identity". The check, a picolibc
program that fills a `struct stat` with 0xA5 and compares it afterwards,
failed on both formats before the zeroing was even in: mode 0, fields not
zero. The port's `file.o` had been compiled with `-Ilibc/include` ahead of
picolibc's headers, so against the hand-rolled two-field `struct stat`,
while its callers use picolibc's. `fstat` wrote the size where picolibc
keeps `st_dev` and `st_ino`. For Proem that made the size the identity, and
two headers of one size the same file: very likely the silent skip its note
described, found by a check written for something smaller.

The review then made the wrong header unspellable rather than out-ordered
(`-iquote` for all three port objects; `crt0.o` and `os.o` had the same
order), turned the uid/gid check into one that can fail (against `ls -l`,
not against itself), and argued me out of reporting mode 0000 on FAT32,
where `fsd` lets everyone through: 0666 and 0777 now. Hans merged it as
#216; the note is closed with a warning to distrust Proem's earlier identity
results on Ouroboros.

## What the day was made of

Eight PRs, #209 to #216, every one reviewed with `/code-review high`, and
every review found something real; for #210, #212 and #215 the worst
finding was a defect older than the PR: a region not zeroed between
programs; spare FAT entries read as free, which only a full disk reached
until #212's hint walked ordinary use there; and a directory moved into
itself, which the shell's `mv` could already do and #215's `rename` would
have given to every C program. The plan the day began with,
Proem's heap, became a chain: the heap exposed the `fsd` stall, the stall's
fix exposed the double mount, the double mount exposed `unmount`, and
`unmount` exposed the namespace and the fid table. Hans made the three
decisions that were his (hold #210 until the stall was fixed, stop double
mounts, `unmount` clears every disk tree). One of them I built in a
different shape than he chose: the refusal of a second mount became a reuse
of the first, because a refusal would have shut later shells out for the
boot, and I said so when it happened.

The pattern to keep: twice a check written for a small thing found a large
one (`test-unmount` the kernel's `NS_SET` refusing length 0, `cfstat` the
wrong `struct stat`), and five times the check itself was blind until a
mutation or a review showed it, with the supervisor's heartbeat a sixth
blind instrument, found by measuring (`blind-instruments-postmortem.md`, the
section of this date). Four handoff notes were closed: Proem's heap,
`unlink` and `fstat`, and Edit's `rename`, one of the two of Edit's that the
morning's triage accepted. What is left in the inbox is Proem's system directories and
Edit's console.
