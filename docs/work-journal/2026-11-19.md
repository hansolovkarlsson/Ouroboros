## The link re-read on the board, twice (#487)

Boot 46 ran #487 as reviewed the evening before. The cable came out, the
next ask said `link down at a wait (no link): sends are refused until it
is up again; the MAC stays on`, a ping during the pull was refused, and
with the cable back the MAC was set again at 1000 Mb/s and the ping had
its reply. It passed, and it did not answer the one question the review
had left for the board. That question was whether a frame in the
transmitter at the drop leaves it busy afterwards. The log showed `first
frame sent` only after the cable went back: nothing had been sent
before the pull, so there was no frame to strand. The run could not
have failed on the thing it was for.

A second review of the branch found seven things. A send's asks did not
count toward the back-off, so a send that read the link up left the
wait at once a minute, and after a drop a stuck MDIO bus was read on
every send. Every ask now tells `linkask` whether it read, and a send
does not ask while the back-off holds, which closes the step 6 item
that nothing remembered a failed read. The restart line claimed a drop
for a speed changed with none read between, and the send's line for a
link that did not read was said once a boot, not once a link. Half
duplex (`CMD_HD_EN`, which Linux sets and U-Boot does not) is recorded
as open. Reading the status register once instead of three times was
declined: the latched read would see every short drop as down.

Boot 47 put a ping before the pull. Two pulls, each the same; the first
frame went before the drop, the transmitter took the next one after

## The counter's frequency (#488)

The other half of step 6's item: `timer::monotonic_us` divided by
`CNTFRQ_EL0` unchecked. The first version read the register at the top
of `kernel_main` and stopped with `panic!` below 1 kHz, and its QEMU
table said 0 and 999 "stopped with the line". The review said
otherwise, and the uefi crate's source agreed: its panic handler prints,
stalls ten seconds on the firmware's timer (the one just refused), then
calls `ResetSystem(SHUTDOWN)`. Re-read whole, the 0 run's log had the
line and then edk2's `ASSERT [MetronomeDxe] ArmArchTimerLib.c(44):
TimerFreq != 0`. I had read the first five lines of each log. On a
release firmware the board would have powered off with the line gone.

Two more findings went deeper. `CNTFRQ_EL0` is a register of each core,
and every call read the core it ran on, so the boot core's check
guarded nothing on a secondary. And 1 kHz was the wrong floor: every
millisecond deadline is `frequency_hz() / 1000 * ms`, truncated first,
so at 1999 Hz a millisecond is about half one. Now `timer::init` reads
and checks once, `FREQUENCY_HZ` is the value every core uses, the floor
is 1 MHz, and the stop parks with the firmware watchdog off. The rule
went into `CLAUDE.md`'s boot list. Boot 48 logged `the generic timer's
counter runs at 54000000 Hz`, the first time the board's frequency is
in any record. My doc comment had claimed QEMU's 62.5 MHz and the Pi's
54 MHz before either was read; neither was in the tree, so the comment
was cut back to "the boot logs it" until the board said.

## The TRB flip, private and then unspellable (#489)

The other half of the same item: `xhci.rs`'s `publish_cycle_word`, the
naked `dmb oshst; str` that hands a TRB batch to the controller, had one
caller by convention. I moved it and `ring_publish` into `mod ring` with
the store private, ran a mutation that showed a second caller did not
compile, and wrote in four places that the hole was closed. The review
pointed out that `ring_publish` still took any `*mut Trb`: a register
address reached the store from anywhere in the file, as before, one
layer up. The fix is a handle, `ring::Ring`, whose pointer and length
are private and which only the module builds, from the ring statics
with each array's own length. Building one from an address, the old
bare call and the store from outside each fail to compile, and the
flip routed around the store fails the image check. The length coming
from the array type closed a second hole nobody had named: a ring
pointer passed with another ring's length.

Boot 49 ran with a USB stick and a keyboard plugged in, at my asking.
The command and EP0 rings enumerated the hub, the stick and the
keyboard, and the keys reached the shell. The bulk rings were not run:
`usb-msd not installed: the SD card is the boot disk`. Hans asked how to
mount the stick, and the answer is that no number does. The kernel
holds one block device, the SD card has it, and `mount N` counts the
card's partitions: his `mount 1 /test` was the root again, made safe by
fsd mounting a partition once and binding the same tree. A second block
device is not on the roadmap.

## One address parser (#490)

The plan's step 8 named three parsers of a dotted address serving
`netd`; there were five, the shell's and `ping`'s besides. The first
version made `netconf::parse_ip` the one, re-exported it through
`clusterkeys`, and added two tests named for `netd`'s wrap
(`18446744073709551617.0.0.1` read as `1.0.0.1`). The review found
both tests could not fail: `netconf`'s parser had always refused a part
of four digits, and the wrap lived in `netd`'s copy and its `parse_dec`,
which nothing tested. It also found the home wrong: the cluster's
identity files, the shell and `ping` now linked `/etc/net`'s crate for a
parser. `netaddr`, with no dependencies, is below all of them, holds
`parse_ip` and `format_ip`, and is named directly by every caller;
`netd`'s `/net/ip` and the shell's mount listing format through it.

A second, medium review found no fault and five cleanups. One was that
the new crate's `parse_dec` copied `accounts::parse_dec` byte for byte,
which `netd` already linked: `netd` calls that one now, and the wrap
test went to `accounts`, which had none. Another made `ping` pass its
argument's bytes without a trip through `&str`, and I committed it
without building: the reply lines still printed the removed variable.
The image build caught it before any rig ran, and `684a6b90` prints the
bytes. Users see one change: `mount -r`, `cpu` and `ping` refuse a part
of more than three digits, as `/etc/net` always did.
