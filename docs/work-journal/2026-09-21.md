# 2026-09-21

## A zero-count read, and reviews that settled the count but not the sentinel

The 09-20 standup left two optional picks. I took the smaller: `NP_PREAD` with
a count of 0 diverged between `fsd` and the host peer. `fsd`'s `want_len`
rejected a zero window with `FS_ERROR`, while `scripts/np9p_server.py` answered
0 for the same frame, and `ninep-abi` says the status is bytes read. No shipped
client sends a zero count (libc's `read()` loop never asks for 0), so it was a
latent disagreement, but a disagreement, and the fix was `fsd`'s: a zero-count
read answers 0, the POSIX shape, still going through `read_at` so the fid gate
and the filesystem's own errors answer as a real read would.

Two reviews then did most of the work. The first (correctly) called the change
over-built: I had wrapped the zero case around `want_len` with an extra branch,
where splitting the helper into `capped` (the shared cap) plus a non-zero floor
let each read verb's choice be one word. It also caught a comment I had written
that was simply false, that a zero-count read touches no disk: the path lookup
still runs, only the data phase copies nothing. The second review found the
same divergence one verb over, `NP_READ_AT`, and I made the deliberate call
*not* to widen the fix: I stated the floor for all three path read verbs in
`ninep-abi` (so the host peer is now the side that diverges from the spec) and
left the lift as a ledger item, because `NP_READ_FILE`'s status is the file
size, not the count, so a zero there is a size query that wants deciding, not
inheriting. The fid gate grew a fifteenth check, shown failing on the old tree;
the host peer's self-test gained a row and a round-trip value check, shown
failing by a mutation. Merged as #148.

## The async remote mount, and an over-reach I had to measure to see

The bigger pick was the standup's headline: session-scoped authentication and
an async `NETOP_RMOUNT`. The fid-verbs plan had said three times that these are
two arcs, not one, so I wrote a plan (`roadmap/roadmap-async-rmount.md`) for the
concurrency half alone and left auth for after. Four decisions: park the call
and reply to a task *identity* (a kernel `MSG_SEND` arm that takes the packed
identity `SENDER_TASK` answers, refused once the slot is recycled, because a
parked reply by slot would complete a stranger's call); one engine, not a
fourth (the `/net/tcp` `DialConn` made generic over its buffer sizes); three
steps, one-shot then session then run; and what stays synchronous on purpose.

Steps 0 and 1 are what landed. The instructive part was a wrong turn I could
only see by booting it. I first parked a path verb arriving at the *re-entrant*
drain too, meaning to close the latent overflow #147 documented. The single-VM
async rig passed, because its mounts are top-level. The two-node rig faulted
netd deep in the `cpu`-run path. Two things were wrong at once. The park still
signs the request, and an Ed25519 frame build is exactly the deep cost that
makes the re-entrant drain unaffordable, so parking there was no cheaper than
the handler it replaced. And the `remotes` table I added lives on `serve`'s
frame, beneath the `handle_run` → `tcp_run` → `build_tcp_generic` chain that
#147's refusal exists for, so it tipped that chain over the guard page. I
reverted the re-entrant park to #147's refusal and grew `STACK_PAGES` 10 → 12
for the table. The premise of the plan, that the signature is the deep cost,
went from an argument to a measurement. The lesson from 09-20 recurred exactly:
making the fault you can reproduce go quiet is not the same as fixing its
cause, and the single-VM pass was the reproducible-but-wrong signal.

Three review rounds followed and each found something real. A parked mount to a
peer that never answers was reaped by `pump_dials` the instant its SYN retries
exhausted, in the same pass that marked it dead, so the caller hung forever;
guarded the reap with `parked.is_none()`. A top-level park starved by a
re-entrant run aged toward its deadline without its SYN ever going out, so a
reachable peer was reported `NO_FS`; the deadline now starts at first SYN send.
And a source-port collision I had *dismissed* in an earlier round the next
reviewer showed was real: the async park breaks the invariant `next_src_port`'s
uniqueness rested on (a full round trip between calls), so two mounts to one
peer could cross replies. That one is worth remembering. I waved it off as
unreachable, and the sharper framing (the design broke the invariant, not the
odds) was what made it worth a fix; each remote slot now takes a disjoint half
of the ephemeral window. Merged as #149.

## The release note that had gone missing

Between #148 and #149 the user chose, from the standup's small pending items,
the release note. Twenty-one PRs had landed since v0.19.0 (2026-09-07) with no
changelog entry at all: the fid-verb-to-export arc and its held client
sessions, the keyboard-ownership chain, the kernel-hardening primitives, and
the async steps. I drafted an `Unreleased` section at the changelog's condensed
one-paragraph-per-arc level, leading (as v0.19.0 did) with the cross-node and
ABI changes a reader must know before upgrading one node: the error floor
moving `MAX-39` to `MAX-43`, `sys.h` naming the task codes, `MSG_SEND` by
identity, an IRQ at EL1 halting with `vector=5`, and the 48 KB stack. The
version tag is deliberately not cut; the note is prepared for whenever it is.
Merged as #150. The syscall-table "13 placeholder cells" the standup also
listed I could not act on: the manual's table stops at syscall 30 and the ABI
has about thirty-eight more, so the reference maps to neither the missing rows
nor the four legitimate no-argument cells, and I left it for the user to
disambiguate rather than guess.

## Ctrl+C, a recommendation that was wrong, and a fix that needed two signals

The last pending item was the keyboard decision filed since the chain arc: a
stray Ctrl+C at a nested shell's own prompt killed the shell, login and cwd and
env gone. I had recommended the roadmap's filed answer, "pass the byte through,
as for task 0." Implementing it, I found the recommendation was wrong: literal
pass-through *traps the keyboard*, because Ctrl+C was the only way back from a
`fg`-handed shell, whose `exit` only logs out. I said so and asked; the user
chose detach. Ctrl+C at a handed-over session now reverts the keyboard to the
parent without killing the session, which `fg` resumes. A foreground command
(the parent is blocked in `WAIT` on it) is still terminated. `fg` is also
refused from a non-owner, so the ownership chain names the caller by
construction. Two new keyboard-chain recipes, each with a measured always-kill
mutation control.

The classification took two tries, and the second was informed by the first
being wrong. I first inferred intent from the parent's live `WAIT` state, which
a review showed has a window: `run_found_command` does `FG` then `WAIT`, and a
Ctrl+C between them misreads a foreground command as a session and detaches it
into an orphan. So I moved to a flag recorded at `FG` time. That, on its own,
broke recipe 4: a bare `fg` back to a task the parent is still waiting on clears
the flag, and the flag-only test detached a command whose parent was stuck in
its `WAIT`. The existing recipe caught it, which is the point. The answer was
both signals OR'd: the flag for the `FG`→`WAIT` window, a live scan for a waiter
for the re-`fg` case. Neither alone is right. A later review round found the
one remaining defect, a documentation one: I had inserted the new helper and
its doc in the *middle* of `interrupt_key_check`'s doc comment, so in Rust the
whole block rebound to the helper and left the function it described
undocumented, compiler-silent. Moved the helper above the block. Merged as #151.

All four arcs merged to `main` and the tree is green. A heavy review day: eleven
review rounds across the four PRs, and the ones that mattered most were the
reviewer being right where I had been too quick, the src-port collision I
dismissed and the Ctrl+C recommendation I gave before reading far enough.
