## Every userland crate linted (#498), and three rounds on one claim

Yesterday's lint (#495) covered the kernel and the four servers; the
roadmap item it left said `make test` linted no other program. The first
commit read the programs under `programs/` from `cargo metadata`, so a
program added later is linted with no edit, and linted them with
`nsresolve` in one clippy run. Its message said that none of them sets a
feature, "so each builds as it ships". That sentence was the whole
reason one run was safe: cargo unifies features across a run, so a crate
that turned on a feature of `ulib` would change `ulib` for every crate
linted beside it, and the lint would be of a build nothing ships.

The first review (high) made the sentence a check. A crate that sets a
dependency's `features` or `default-features = false` is refused by
name, and the list grew from the programs to every workspace member but
the kernel and the pure crates, wherever it sits: 69 crates, `ulib` and
`syscall-abi` among them, with the four servers folded into the same run
and `LINT_SERVERS` gone. The first fix of those six findings put the
list's logic in a new `scripts/lint-crates.py`. Hans refused the edit
and asked for it smaller and inline, so it is one Python line in the
Makefile, `LINT_CRATES_PY`, and the script was deleted before it was
committed.

The second review found the guard narrower than the property. It looked
only at the crates being linted, while the pure crates are in the same
build as their dependencies, and only at a dependency's `features`,
while a `[features]` entry such as `default = ["ulib/ctl"]` turns one on
too. Both are refused now; dev- and build-dependencies are not in this
build and are not. `--keep-going` was added so one run names every crate
with a lint, not only the first. Each refusal and each planted lint was
run as a control, and is listed in the roadmap's item, which is struck
through.

`openprobe`'s one lint went through three names in three commits.
`enum_variant_names` objected to `NoAnswer` in `enum Answer`. The first
fix renamed the variant, the review pointed out that the variant matches
what the program prints, so the enum became `Reply`, and the next review
read `Reply::NoAnswer` as a contradiction beside the reply buffer. It is
`Outcome`. A small thing, but it is three rounds for a name, and each
reviewer was right about the name in front of them.

## `wait_for` marks the end of its match (#499)

The fix promised on 2026-11-15. `drive-qemu.py`'s `Guest.wait_for`
moved its mark to the end of everything that had arrived once a pattern
matched, so of two lines printed together a wait for the first passed
over the second. It moves the mark to the end of the match. Earlier
output is still behind the mark, which is what the mark is for: a
previous prompt must never be matched, or typing starts while the guest
is still printing. `--self-test` holds both halves on a `Guest` with no
QEMU behind it, and it fails with the mark at the end of the buffer, at
the match's start and at 0. `make test` and seven rigs passed.

Asked which review level, I said high, because the diff was small and
the risk was in its callers: 25 rig scripts call `wait_for` by name, and every
rig that drives the shell goes through it by `Guest.run`. The review
found the trade I had not stated. The old rule did two jobs. It lost
the second of two lines, and it also passed over a second copy of a
prompt, which two shells on one console can print within the settle.
The new rule keeps that second prompt for the next wait, so a rig that
does not expect it runs one prompt behind from then on.
`test-keyboard-chain`'s killed middle link and `test-cred-client`'s
`do()` were named as the places it could bite. The review also found
that the self-test could not see the difference: its cases fill a
buffer before each wait, with the settle at 0, so nothing ever arrives
after a match. And it found that a pattern able to match the empty
string returns at once on every wait without moving the mark.

The evidence came from running the rigs, not from reading them. Every
make target whose script waits through `wait_for`, 61 of them, ran one
after another in 91 minutes on the first three commits: 60 passed, both
of the named rigs among them. So the new rule is kept, and rule 2 in the
module docstring says that a rig given two prompts waits for both. The
empty pattern is refused with a `ValueError`, and removing the guard
fails the self-test. The self-test gained a case for a second prompt
after a match and restores `SETTLE` in a `finally`. Four rigs
(`test-kbd-mode`, `test-nav-keys`, `test-cclock`, `test-cfenv`) gave
the old rule as the reason for a workaround; the workarounds still
work, and their comments now say when they were written and why. Two
findings were declined: a greedy pattern cut mid-line, which the old
rule had too, and moving the settle into `run` and `type_line`, a
timing change for every rig that is not this fix.

The one rig that failed was `test-long-set`, in `vroot` and `vlater`.
Both checks are in the setup on the Mac that plants entries in a copy
of the exFAT image, and the rig gives up on them before any boot, so
`wait_for` never ran for either. Run again with main's `drive-qemu.py`
it failed the same two checks with the same output. It is a defect of
its own, on the roadmap: a rig that is red on main and was not run
until something unrelated asked for every rig.

#499 then conflicted with #498, on the one line of
`docs/testing/make-targets.md` that describes `make test`, which both
had changed. Main was merged into the branch with main's line kept and
the `wait_for` clause put back into it, `make test` passed on the merge,
and #499 merged.
