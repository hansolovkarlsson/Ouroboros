## The small ones, and a case that found the kernel making fsd's swap

The day opened on the 21st's closeout (#340) and took the standup's three
small items as one branch, #341. `/bin/ls` built each line in 84 bytes and
dropped whatever did not fit, the newline included, so a long name ran into
the next; both of its line buffers now hold a 255-byte name, and its review
found that a name past `NAME_MAX` should be written on its own rather than
cut. ext2's `bitmap_free` rewrote a whole bitmap block to clear one bit; it
now reads and writes the bit's sector alone, and `test-ext2-blocks` gained
HIGH, an inode whose bit sits in the bitmap's second sector, which fails
with the sector's offset dropped. The third item was a rig for #324's
refusal, an unreadable partition table, in `test-probe-ioerr`.

That third item is where the day turned. The first TABLE case failed sector 0,
and the stick came up at `/`: not fsd making the swap #324 refuses, but the
kernel, a layer below. `init_storage` dropped a virtio disk whose sector 0
would not read, so `install_boot_disk` had nothing held and installed the
stick. TABLE was moved to the GPT header, sector 1, which reaches #324's
refusal, and the kernel's drop went to the roadmap as a question for Hans,
since the rule for an unreadable disk is decision D6's.

## One classifier for a boot the firmware never starts

#342 took the 21st's stall: four NVMe boots and one virtio boot that stopped
in QEMU's firmware and failed every guest check for a kernel that never ran.
`test-usb-hub` already had a classifier for its own stall; it moved to
`drive-qemu.py`, learned the second ending (the `Image type X64` line with
only screen clears after it), and six rigs now call `boot_stalled` and exit
100 when a boot stalled and nothing failed. Every boot goes to
`scratch/firmware-stall-runs.log`, so the stall reads as a rate.

The high review found the trap in the rule. The X64 line is one every boot
prints, so a hang every run meets there, a firmware stopped by the rig's own
failing disk for instance, would be INCONCLUSIVE forever and never a failure.
A boot that stalled on each of its last three runs is now graded. Two
instruments of the controls were wrong before that: the forced-stall wrapper
patched `drive_qemu.firmware_stalled`, but `test-usb-hub` had bound the name
at import and never saw the patch, and `record_run`'s default log path was
bound when the function was defined, so the wrapper's redirect of the log
did nothing. Both are in `blind-instruments-postmortem.md`. Hans merged #341
and #342.

## Sector 0 held, in three reviews

Asked for the open decisions with options, I recommended holding a virtio
disk whose sector 0 will not read as D6 holds one whose table will not, and
closing the exFAT freed-cluster link item as an accepted cost. Hans said to
do what I recommended. The exFAT item closed on his word: a narrower drop
would need a cursor to know every cluster of its chain, and a cursor holds
only its position.

The sector 0 change took three high reviews, and each found a real defect in
my version before it. The first held the disk even when the boot partition
was unknown, where D6 installs it first. The second version fixed that by
writing the rule out in `init_storage` (an unreadable sector 0 answered as
`Unreadable` whenever a boot partition was known), and that copy was wrong
for a GPT disk, whose boot-disk match never reads sector 0, and for an
unknown table. The third version stopped answering in `init_storage` at all:
it reads sector 0 once, for its signature, and asks
`bootdisk::is_boot_disk_retrying`, which holds D6's one retry and already
knows GPT. That review also found sector 0 read four times (the kernel's
retry and then the check's), the GPT0 boot's grade passing on "unknown"
because the install line did not name the boot start, the rig stamping
`esp.img` while booting `espgpt.img`, and a "every byte" check that skipped
sector 0, the sector under test. The test now has seven boots: SECTOR0
(held, the stick refused, the disk the fallback) and GPT0 (a GPT disk with a
dead protective MBR still taken as the boot disk). Three controls each fail
where they should. The disk with no MBR signature, which is still dropped,
stayed a roadmap item of its own on Hans's agreement. #343 is open.

## ValidDataLength, worse than the roadmap said

The roadmap item said fsd read an exFAT file to its DataLength rather than
its ValidDataLength, so a preallocated file read stale bytes. Reading the
write path showed more: `patch_stream_ext` wrote one length into both fields
on every write, so a single append to a preallocated file raised
ValidDataLength over the stale bytes, and from then on every driver read
them as the file's. On `fix/exfat-valid-length` reads return zeros past
ValidDataLength without reading the clusters, `read_file` goes through
`read_entry` so there is one copy of the rule, a write fills its gap from
ValidDataLength, and `patch_stream_ext` takes both lengths. `make
test-valid-length` plants four preallocated files; four controls (the read,
the gap, the two lengths as one, main) each fail it.

Its first run failed a check I had written from my own code comment: that a
write never leaves stale bytes in a sector it writes. It does, when the
sector also holds valid bytes and is patched; the bytes left lie past the
new ValidDataLength, so no reader sees them. The comment and the check were
corrected rather than the code grown to make the claim true. The branch is
three commits, not pushed, awaiting a review.

## Two more reviews, and both merged

The ValidDataLength branch had two high reviews of its own. The first found
an older leak the rewrite had kept: when a damaged file's chain is shorter
than its size, `read_file` replied with the buffer up to the size, the part
the read never reached holding an earlier reply's bytes. The second found
that the fix still missed an entry naming no cluster, which returned before
the zeroing; `read_entry` now zeroes its whole output range first, one rule
for every way a read ends. The first review also raised the 1 MiB gap
bound: measured from ValidDataLength, it refuses every append to a file
preallocated far past its valid bytes. Hans chose to keep the refusal
(option A) and the rig gained BIG, a 2 MiB preallocation whose append must
be refused. Its control, the bound measured from the size as on main,
filled the 2 MiB in one request with no wedge restart, so the one-request
fill (option C) holds at megabytes; the roadmap item says gigabytes are
unmeasured. A control for a new file's ValidDataLength passed at first:
`cp` and `>` create the file empty and write into it, so they never reach
`write_file`, and the check only bit once the rig made a file with
`/bin/write`. Hans merged #343, then #344 after `main` was merged into it to
settle the changelog and roadmap.
