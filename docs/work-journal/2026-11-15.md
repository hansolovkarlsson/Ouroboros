## The first boot: nothing received

`ping 10.0.2.2` said unreachable, and Hans pasted twenty identical
checksums that did not match the local file. The wire was right: the Pi's
ARP request, the Mac's reply within a millisecond, the Mac's SYNs, none
answered. The serial log had one line for it, `a received frame was dropped
(Oversize; 0 taken before it)`, and no frame the Mac sent was over 1403
bytes.

That one line was the whole of the evidence and it was "said once". It
could not tell one bad frame from every frame. I had a hypothesis, that the
driver was reading a descriptor the device had not written, since an
untouched descriptor still holds the set-up's length of 2048 and 2048 reads
as oversize. I could also think of two others the line did not rule out. So
the second boot changed nothing and only read: the ring's indexes, its
pointers, and which of the 256 descriptors no longer held the value the
set-up wrote.

## The diagnostic boot, and the fault

It read: producer index 10 at the set-up, as the firmware left it. After
the first frame, the index 11, the write pointer 3, and exactly one
descriptor written by the device, number 0, holding a whole clean frame of
60 bytes. The driver was looking in descriptor 10.

The crate took the descriptor from the index's low byte, as U-Boot does and
as its comment says U-Boot does. The device fills the ring from where the
write pointer was set, which the set-up makes 0. The two agree only when
the firmware leaves the index on a multiple of 256. Linux keeps a pointer
of its own. The fix is one field, `rx_desc`, counted from 0.

The third boot received. `first frame received: 60 bytes, from buffer 0`,
the ping answered, and the count line said 256 with nothing dropped.

The transmit ring has the same shape and I left it. The diagnostic read
its index as 0 at the set-up on two boots, which is why every send since
step 6 went where the device looked. Counting it from 0 as well is almost
certainly right, and no boot here can show it right or wrong, because the
index is 0. The kernel now prints both indexes at the set-up and warns when
the transmit one is off a multiple of 256. Whether to change it is Hans's.

## Why the host could not find it

The crate has 88 tests, and several of them started the receive index off
zero (at 5, at `0x00f0`, at `0xfffe`) exactly to show the ring index
following the counter. They passed, because the model of the device placed each frame by
the index's low byte. I wrote the model and the driver from the same
reading of U-Boot, so the model had the driver's mistake from the other
side. The tests checked that two things I wrote agreed with each other.

The crate's own doc had said it for days: "the model is ours: only the
board is a foreign observer." It was true and it had not changed what the
tests were taken to show. With the model made to place frames as the board
did, four tests failed against the unfixed driver.

## A check that fooled itself, twice

The twenty identical checksums were of a `404` page. The card's root is
ext2 and spells the file `/bin/cpp`; I had given `/bin/CPP`, the name in
the staging directory, and `curl -s` prints an error page as readily as a
file. Twenty equal hashes looked like a stable wrong answer and were a
stable nothing. The first boot's "checksums differ" had the same cause on
top of the real fault: there the hash was of empty input.

With the name right the file still differed from the local build, by 93
bytes in four pages. Every binary did. `make sdcard` stages the boot
partition alone, so the card's root is whatever was last written to it, an
older build. One man page settled it: the card's `man/tree` is its text
from before an edit on 2026-11-11. So I compared what had not changed, the
246 files under `include` and `man`: 241 equal, 827 KB, and the other five
man pages edited since. Then `/bin/cpp` 1500 times against its own first
hash, all equal, and the count line passed 65536 and 131072 with nothing
dropped.

Both mistakes were in the instrument and both would have been caught by
looking at one response before hashing twenty.

## Step 8: the address from a file

With receive working, the hand-set `10.0.2.2` on the Mac was the next thing
in the way of every board run, so step 8 followed the same day. `netd`
reads `/etc/net`: `address` and `mask` required, `gateway` and `dns`
optional. The rules went into a pure crate, `netconf`, as the project does
for anything that can be tested without a device. A file with a line not
understood is refused whole, with the line named, and the machine comes up
on the defaults: a half-read file would give a machine an address nobody
wrote.

Two decisions I made without asking, both recorded in the PR for Hans to
overturn: the file's name and format, and the configuration held in four
atomics in `netd` and not threaded through the sixty functions between the
start and the places that build a frame.

The adapter run on 2026-11-14 had found `ping` asking the wire for the far
address itself. That was left "for step 8", and step 8 fixed it: `ping`
goes through the next hop as the TCP paths do.

The rig boots three copies of the image, with a good file, a refused one
and none. Each must be reached at the address it should have and must not
be reached at the other, since SLIRP forwards a port to whatever address
it is told and a guest answering at both would pass a check that only
looked for an answer.
