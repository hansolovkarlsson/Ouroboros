The Pi work had stopped on 09-28 waiting for a serial cable, with `make
sdcard` open as #180 and eight commits of bench diagnostics on
`pi400/boot-flags` above it, unreviewed. The only commit since was a roadmap
note on 09-29 pointing the C-portability arc at the workspace's plan for a

A high-effort review of the branch against #180 came back with eight
findings. The `ranges` translation in `0602ca3`, the one real fix on the
branch, came through clean. Two findings were real defects. I checked both
against the code before acting on either. `\FBCON` dropped the serial
console whenever the flag was set, even with no framebuffer to replace it,
which leaves a board with a UART and no GOP with no console at all. And the
console had been added to the front of the extra-device list, making five
entries, while the shared L1 tables that map devices above 512 GB stayed at
four, so the console could take the table the GIC needed. Nothing we own
puts that many devices that high, but the comment that sized the tables
still said four. They now follow `MAX_EXTRA_DEVICES` instead of sitting
beside it.

Two findings were about instruments, and they went into the
[blind-instruments postmortem](../postmortems/blind-instruments-postmortem.md):
the `\FBCON` defect above, which no QEMU run could show because every one had
a `ramfb`, and `scripts/efi-symbol.py`, which did not apply the `SizeOfImage`
check that the 09-28 section of that same postmortem names as the one that
caught the misread photos. The script now takes the relinked `.efi` and
refuses unless the map and the `.efi` share a link timestamp and the range's
length is the image size. A map has no section RVAs, so the size could not
come from the map alone. That is why the `.efi` became a required argument
rather than an optional size.

One finding needed a different fix from the one suggested. The console's own
device mapping gives way when RAM covers its 1 GB block, the Pi 4 case with
"Limit RAM to 3 GB" off. A warning from the table planner would also fire
for the framebuffer, which sits in RAM's span deliberately and is meant to be
cacheable. So the check runs after the switch and asks the hardware walker
(`AT S1E1R`, `PAR_EL1.ATTR`) whether the serial console walks as Device
memory, through a new `mmu::walks_as_device`. It asks the CPU what the
mapping is rather than reading what the planner intended, and it concerns
only the console. The `XHCINOWR` row in `testing-pi4.md` was also corrected:
that flag skips the bring-up after the exit as well as the command-register
write, so a boot that reaches the shell does not single out the write.
`bootflags::present()` opening the volume once per flag was left for later.

All of it went in as `5c30f8d`, and was checked by three QEMU boots that all
reached the shell (no flag; `\FBCON` with `ramfb`, read from a screendump;
`\FBCON` without a framebuffer) and two mutation controls, each run after
committing so that restoring the file could not eat the work. With the old
filter put back, the no-framebuffer boot's serial log ends at
`exiting boot services`. Pointed at RAM (`0x40000000`), the device check
prints its warning. `make test` was green, 175 host tests. #181 was opened
stacked on #180. Then #180 was merged, #181 retargeted to `main` and merged,
both as merge commits like #176 to #179, and both branches kept on origin.
Nothing has run on a board; that waits for the cable.

The `fdt` crate panics on a devicetree with no `/chosen`. Reading the crate
for that call found a second panic beside it, on a zero-length `stdout-path`.
`devicetree.rs` now reads `/chosen/stdout-path` itself (#182). QEMU never runs
this path, since its firmware publishes no devicetree, so the evidence is a
host harness running the old and the new lookup on the pftf Pi 4 and Pi 400
trees and hand-built ones. The harness was itself blind at first: every tree

([blind-instruments](../postmortems/blind-instruments-postmortem.md)). The
review also raised three choices about which UART a board gets (a `:options`
suffix, disabled PL011s, a `stdout-path` naming the mini UART). Each changes
the console a board ends up with, so all three wait for the serial dump.

`bootflags::present()` opening the volume once per flag became one read
(#183). Its review added the one line that matters on the bench: when the
volume cannot be opened, the log now says the flags were not read, so a
`touch NOXHCI` that never took effect cannot pass for an xHCI that was not
the problem. A mutant forcing the open to fail showed the warning and a boot
that went through the xHCI.

## The storage rewind, made observable

`reset_storage_endpoint` rewound the bulk ring to its start after a Stall,
with the cycle bit the controller expects still on the slots ahead. It had
been found by reading and left alone because this is the path confirmed on
Parallels as "Mode A". The way to observe it was QEMU's `usb-storage` itself,
which answers a CBW with a bad signature by stalling Bulk-OUT. With every
seventh CBW corrupted under `test-usb-hub.py --usb-boot`, `main` timed out 12
transfers after its rewinds and failed to run the typed command; dequeuing at
the enqueue position, as EP0 already did, recovered 30 Stalls with none (#184).
The review found that a recovery whose Reset Endpoint took and whose Set TR
Dequeue did not could never be finished, since the next Reset Endpoint is
refused; Set TR Dequeue is now sent after that refusal too. That path is
reasoned, not observed: the corrupted CBW re-stalls on its own and the
ordinary path recovers it either way.

## A Stall test that can fail

The injection proved #184 and was then removed, which left the recovery run
by no committed test. #185 made it permanent: a `\MSDSTALL` flag file, `make
image-stall`, and a third boot in `make test-usb-hub`. The first review found
the new checks could not fail, one matching a line printed before the retry
ran and one bounded by the kernel's sixteen-line log limit in a boot with
thirty Stalls. It also found the fault built into every kernel and switched on
by one empty file; the kernel now arms it only for a stick whose INQUIRY
vendor is `QEMU`. My own first run of the reworked script then failed on a
guard I had just written: it compared the stall image's age with `esp.img`,
which the first boot writes to as its virtio disk, so the stall image always
looked stale. Both images are now compared with the kernel binary, as the
existing guard already did.

Hans asked for a max review of #185. It took about an hour and found what the
two earlier reviews had not: deleting the IN half of the recovery still passed
every check, and moving one Stall from the CBW to the CSW read broke the boot
outright. After a Bulk-IN Stall the device still owes its CSW (BOT 6.7.2,
6.7.3), and the driver answered by sending a fresh CBW, which was stalled in
turn. That is a driver bug from before today, and #185 merged with it on the
roadmap as the next branch.

## Recovering a Stall where the CSW is owed

#186 repairs a Stall in the data stage or on the CSW read in place: clear the
halt, read the CSW, and only then fail the command. `reset_storage_endpoint`
also sends the device CLEAR_FEATURE(ENDPOINT_HALT), only after a Reset Endpoint
that took, since on a healthy endpoint it would reset the device's data toggle
and not the host's. `\MSDSTALL` now also reads some CSWs as 12 bytes, which
QEMU stalls with the CSW owed; 30 are recovered in place, and with the repair
disabled, or the IN reset deleted, nothing mounts.

Two things QEMU would not show. The data phase: a CBW promising more data
than the command returns was the obvious way to make the device stall it, and
QEMU pads instead; the CSW read then gets padding, fails as a mismatch, and
that mismatch is not retried, which went on the roadmap as its own gap. And
the CLEAR_FEATURE: QEMU does not need it and accepts any endpoint address, so
the test passes without it or with a wrong one. A class-type request in its
place does fail the new check, which is the reach QEMU has. The review of #186
found that a data-stage Stall whose CSW says success was retried three times;
it is now `ShortData`, not retried, with partial data for commands that may
legally come back short left to the roadmap. Its other suggestion, recovering
in place after a Babble or a Transaction Error too, was declined: Linux's
usb-storage re-reads the CSW after a Stall only, because after the other
errors the CSW may already be lost and a re-read would time out.

## The Pi 4's serial capture, and the early fault reporter

The Debug Probe was on the bench after all: `screenlog.0`, untracked at the
repo root, was a `screen -L` capture of a Pi 4 boot at 16:34, with no flag
set, which the evening standup had listed as unread. Read this session: the
console line says `0xfe201000 (via devicetree)`, so #181's translation holds
on the board and that item is closed; the boot ran past everything an HDMI
session had ever shown, to `taking the xHCI controller next`; then the
firmware printed `Synchronous Exception at 0x0000000039F2D1A0` twice and
nothing more. The address is above the image, so firmware code, and the fault
came before any of `discover_xhci`'s own lines. The capture was deleted at
Hans's request after its lines were put in `testing-pi4.md` section 6.

The dump the roadmap waited for will not come from the firmware. EDK2's
default handler writes its one line to the serial port directly and the
register dump with `DEBUG()`, which a RELEASE build compiles out; pftf's
workflow builds DEBUG too but packages only RELEASE. So the kernel prints the
dump itself now: `earlyfault.rs` registers a handler for the synchronous
class through the firmware's `EFI_CPU_ARCH_PROTOCOL`, the path the firmware's
own GIC driver uses for IRQs, which leaves VBAR_EL1 and the firmware's timer
alone. The handler gets the firmware's saved context (every x register, SP,
ELR, SPSR, ESR, FAR) and prints it decoded on the serial console with raw
writes, walks the frame-pointer chain, and names the loaded image holding
each address from the firmware's debug image info table: the kernel by
offset, a firmware driver by the name in its PE CodeView entry and the
firmware-file GUID in its device path.

Three things QEMU taught before it worked. The EDK2 context struct keeps
the 32 SIMD registers between SP and ELR, which the first run showed as
`esr=0x3` and an odd `elr`. The kernel had no frame records, so the walk
went straight from the firmware's frames to the firmware's caller of the
kernel and skipped every kernel frame; the kernel is built with
`force-frame-pointers` now. And LLVM puts a frame record 8 past a 16-byte
boundary where GCC keeps it on one, so a 16-alignment check printed no
frames at all. `make test-early-fault` is the check: the `\EARLYFAULT`
flag plants a fault in the DXE core's `CopyMem`, the dump must name
`DxeCore.dll` for the PC and the kernel for a frame, and a boot without the
flag must reach the shell; with the registration deleted, the firmware's
bare line comes back and the test fails. The five merged `pi400/` branches
were deleted, local and origin.
