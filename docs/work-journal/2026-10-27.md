## The rigs' set walker, and a build refused for an edit made during it

The day took the standup's first fix: three exFAT rig helpers walked entry
sets by hand (`test-grow-dir`'s `exfat_dir` and `plant`, `test-stale-cursor`'s
`plant_empty`), and `exfatimg.Volume`'s FAT32 listing and data repeated
`fat32img`'s. They now go through `exfatimg`'s `sets`, `find`, `extent` and
`restream`, and `Volume` reads FAT32 through `fat32img` (#360). Before any rig
ran, the new `Volume` was laid beside the old one, taken from `main` into the
scratchpad: the same listing for all 748 entries of `espexfat.img` and
`esp.img` and the same bytes for 2,141 FAT32 chains, rerun after each review.
A `restream` that did not reseal the checksum made `test-grow-dir` fail on
`fsck_exfat`, so the rig sees the one property the helper exists for.

The first `test-grow-dir` run never booted: `srcid` refused the build because
`exfatimg.py` was edited while the programs were building. The tree was left
alone during every rig run after that. The high review and a medium review
of its fix commit found, between them, `sets` stopping at a File entry with
SecondaryCount 0 instead of stepping over it, a fold that lowered every
letter where fsd folds A to Z alone, NameLength counted in characters where
the spec counts UTF-16 units, a `Volume` that leaked its file on a failed
open, and a FAT32 volume of other than 512-byte sectors read as if it were
one. The second review was of the fix alone: a repair is a change.

## exFAT's read-only volume, refused at the disk

The roadmap item asked for a token that `writable()` returns and the writers
require. Hans asked which way I recommended and why. A token threaded through
the 35 functions that write would still let a new one call
`self.disk.write_sector` directly, so the opt-in shape the unspellable
postmortem warns of survives it. The gate went in at the disk instead (#361):
`Fs` holds its disk only through `gate::Gated`, in a module of its own, whose
`write_sector` refuses until the end of `mount_at` settles the volume
writable, once. With every early `writable()` removed, the read-only boots of
`test-long-set` and `test-volume-bound` still pass.

My first claims for it went past what it did. I had said beforehand that a
`Disk` could be made anywhere in fsd, and then wrote that no writer could
reach the disk around the gate. The high review caught it, and the claims
were cut down to writes through `Fs`'s own disk, with the rest a roadmap
item. The review also moved the allocator onto the gate, and that broke the
control: with the gate's write check removed, BESIDE in `test-volume-bound`
no longer failed, because the allocator now refused first. The control that
fails takes out both checks, 14 checks failing, and the records name both.

## A `Disk` no arm can make, in four reviews

That roadmap item was the next thing done (#362). `disk::Disk` was a unit
struct any code in fsd could name. It now has a private field, and the one way
to make one is `Device::disk`; fsd's `main` claims the one `Device` and lends
from it, and the arms never see it. My first version claimed that closed the
hole, checked by three spellings compiled once by hand.

The high review found the claim wrong one layer down: `syscall4` is visible
to every module, so `BLOCK_WRITE` through it went around the `Disk` entirely.
The fix gave `disk.rs` an `svc` of its own and made `syscall4` refuse the
`BLOCK_*` numbers at run time, and turned the hand-run compile controls into
`scripts/check-disk-handle.py` in `make test`. The medium review of that found
the refusal seen by no check and `MOUNT`, which swaps the device under every
`Disk`, still open. So `syscall4` and `syscall5` take their number as a const
generic, `syscall4::<{ syscall_abi::X }>(..)` at all 19 call sites, and a
`const` assert refuses a device call at compile time. `cargo check` never
evaluates that assert, since it is reached only when the function is
instantiated for a number, so the check builds. The second medium review found
the list of calls kept by hand and `unsafe` open to every module. None of the
seven filesystem modules used any, so each forbids it now, and that closed
the gap I had been documenting as unclosable, an `svc` written out in an arm's
own `asm!`. `#[no_mangle]`, which the check used to keep its callers live, is
itself refused by that forbid, so a `#[used]` static holds them instead. The
review aimed at `main.rs` and the check found its sets still kept by hand
(the modules, `Device`'s field names) and `device_replaced` public; the check
reads them from the source now. Two findings were declined: splitting the
check's builds, ten seconds in all, and the spin after a failed claim, which
no code can reach.

Every round of the check was run against controls that reopen the hole, and
each made exactly its own cases fail. One control was wrong as written:
renaming `Device`'s field with a global replace also renamed a method of the
same name, so fsd did not build and the control said nothing. Renaming the
field alone passed, as it should. After the fourth review Hans asked whether
to run a fifth. I said no: the findings had moved from a hole in fsd to edge
cases in the check, and each fix of those is another change to review.

`test-boot-partition` took three runs on #362's first version. The first had
one firmware stall. The second had four, and its `disk` boot reached
`password:` after fsd had mounted ext2, and login never answered; the same
boot on USB passed in that run. The third was clean, and so was every run
after. The hang is not explained.

The reviews also found one thing older than any of today's changes: the
table-rewritten flag is fsd's memory, so after `erase` or `partition` and a
restart of fsd, it trusts the kernel's boot partition again, read from the
table before the rewrite. The fix is the kernel's, and it is on the roadmap.
