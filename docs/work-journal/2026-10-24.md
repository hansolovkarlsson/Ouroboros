# 2026-10-24

## exFAT's vendor allocations, and seven reviews of the paths that free

The work began on the evening of the 23rd, after that day's closeout
(#347), with the standup's next fix: exFAT's `rm`, `rmdir` and a replacing
`mv` left the clusters a vendor allocation entry (0xE1, as a camera writes)
names set in the bitmap, with no set naming them. The first commit freed
them with the set's Stream and made a rename carry them. It was small, and
it was the smallest the branch would be.

A max review that evening found fifteen things, and they set the shape of
everything after: the free came before the set's delete, so an error between
them left a live set over clusters the allocator could hand out again; only
0xE1 was freed, not every benign secondary with AllocationPossible set; and
nothing bounded a free by the heap or by the volume's own clusters. The fix
made `delete_set` take what becomes of a set's clusters as a required
argument (`SetGoes`), deleted first and freed after, as the spec orders a
removal, and VALLOC was remade so that each of the review's mutants failed
a check. A second max review hit the session limit with its altitude
finder's seven findings, which Hans split: three fixed (a whole-file write
repoints its set before it frees the old chain, the allocator passes over
the volume's own clusters, the bitmap's and up-case table's extents are held
to the volume at mount), three to the roadmap. The resumed review found
fifteen more, of which the weightiest was that a volume with no usable
bitmap still wrote: it is read-only now, every writer asking first.

Then four high reviews in one day, each finding less, and each finding
something next to the previous round's repair. The first found the overlap
test taking a FAT-chained survivor by its first cluster, `ensure_chained`
writing a run's links before the heap's edge refused it, and the scan for
the bitmap bounded only by the heap, which on a large stick allowed a
quarter of a billion reads; finding 8, that a read-only volume answers
read-only to a `touch` of an existing file, was raised and kept, since it
says the true thing about the volume. The second found the new overlap test
walking each chain twice, a replacing `mv` whose source's delete failed
returning before it freed the destination's clusters, and a volume of two
FATs (TexFAT) whose live bitmap fsd cannot tell, now read-only. The third
found a whole-file write freeing an old cluster the set's own vendor run
still names, and a contiguous file over the bitmap's cluster taking a
`writeat` into the bitmap itself. The fourth found the same write still open
to a chained file on the bitmap or a link into it, and a removal that knew
its slots were not a set and deleted them anyway. Two of its findings were
kept on purpose: a whole-file write that fails at the free after the set
names the new data still reports the error, as `rm` and `mv` do, because the
error is true and a retry is harmless; and the read-only answers, already
decided. The chained free a cluster at a time, found by four reviews, stays
on the roadmap where Hans put it on the 23rd.

Three of the day's mistakes were in the instruments, not the code, and each
looked like a pass. A mutant meant to restore the old scan for the bitmap
kept the new found-flags, so the scan stopped before the planted copy and
the rig passed it; restored whole, the old code failed VFIRST as it should.
A mutant meant to make `meets_system` answer false was written `false &&
a || b || c`, which still tested the bitmap's range. And VSYSW, the
contiguous file planted on the bitmap's cluster, could not show that same
check missing even once the mutant was right: the run was one cluster long,
so linking it wrote end of chain over end of chain, and the first-cluster
check added beside it refused the write before any byte landed. VSYSW is two
clusters long now, and a missing check shows as the bitmap's FAT entry
changing. These go into the blind-instruments postmortem.

Two rigs not yet on the stall classifier, `test-write-walk` and
`test-spawn-reads`, each reported a firmware stall as a failure once, and
each passed on a rerun with the documented counts. Moving them onto
`boot_stalled` is the standup's first item.

VCROSS's root ran out of room for the meeting-chains case, so it became a
boot of its own, VMEET, which then took the write cases too. The branch
ended at eleven boots and thirty-nine mutants, `make test` at 239, and #348
merged.
