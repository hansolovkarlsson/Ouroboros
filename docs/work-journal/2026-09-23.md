# 2026-09-23

## The async arc gets its postmortem

The standup carried one decision from two closeouts: whether the async remote
mount gets a postmortem of its own. It does, as the thirtieth,
[`async-rmount-postmortem.md`](../postmortems/async-rmount-postmortem.md). The
case was that the arc is finished (steps 0 to 3, shipped in v0.20.0), that
nearly every arc here has one, and that only two slices of it had reached a
postmortem, both filed under general lessons in `true-when-written` and
`repairing-the-repairs`.

Reading the plan's ledger and the review-fix commits of #149, #152 and #154 side
by side turned up a spine sharper than the outline I had proposed. Eight of the
review findings were jobs the blocking path had been doing for free: a reaper
that could not see parked state because there was none, source-port uniqueness
that rested on calls being a round trip apart, a deadline clock that started at
park because park and send used to be one step, a FIN the deleted synchronous
reap used to send, two runs sharing one buffer that `tcp_run` had serialized.
None was careless code. Each missing guard had never existed, because the
blocking call made it unnecessary. So the spine is that a blocking call is a
lock nobody wrote down, and the practice is to list what a wait serialized
before deleting it.

It ends on the next arc as this one's mirror: session-scoped authentication
replaces stateless per-request signing with a session key and a `seq`, and the
same question applies to what statelessness was providing.

## X25519, and a stack gate that failed where nobody was looking

Step 1 of the session-auth plan: X25519 in `ed25519/`, from RFC 7748's own
pseudocode on the existing field arithmetic. The RFC vectors passed on the first
run, including the million-iteration row in release, as did three exchanges
generated by OpenSSL on random keys; a flipped bit in one vector fails three
tests. On the guest `/bin/edtest` puts one scalar multiplication at 236 µs, under
half a cached sign, and 2,944 bytes of stack.

The gate is what the step was for, and it failed, though not at the new code.
A throwaway probe in `netd` (branch `measure/x25519-stack-gate`), calibrated with
a 4 KB pad that read +4,208, ran a sign and an X25519 at each site a session key
will be computed. Phase two and the export arm had 10.5 KB. `park_session` had
**80 bytes**, for the sign it already does on every fid verb, and a 512-byte pad
there faulted `netd` at its guard page with the same `esr` as step 2's overflow.
X25519 was no deeper than that sign. The problem was already on `main`: every
park is reached from `drain_client_messages`, which the export's connection pump
calls from inside its own loop, ~10 KB below where `service_remotes` runs. The
rigs passed because nothing had yet added those bytes.

So the plan stopped, as its gate says, and the re-plan was the async arc's own
two-phase pattern made the rule: a park never signs. It writes the raw request
where the signed frame will carry it and `service_remotes` signs it in place, in
a function with its own frame. Re-measured after (branch
`measure/x25519-stack-gate-after`): the new signing site has 10,352 bytes of
headroom with X25519, and all three session-key sites pass. The async rig 6/6
and the reentrant rig 3/3 on the rebased tree, `cwrite` and its permission
control, and `cpu` with `/host` reads all pass, with zero faults.

One more thing turned up because I ran a control instead of assuming. `cbig`
failed with a capability error on the first read after a mount, one boot in
three. It did the same on `main`, so it is not this change: it is the
delegation race of 2026-09-03, fixed in `ulib` and never carried over to libc's
NP call. It is on the roadmap with its diagnosis.

The lesson is the postmortem's from this morning, the same day. The margin was
not at the new code; it was at the park, which the async arc had made the
deepest thing standing on step 2's resident tables. Measuring the premise before
building on it found a live hazard that no change had yet tripped.

## The delegation race, closed in libc

The `cbig` capability failure from this morning's control was the last loose
end, and it was small: the 2026-09-03 fix for the delegation race (the shell
spawns, then delegates `TO_NET`, so a fast child is refused in between) went
into `ulib` and into libc's output path, but not into libc's NP call, whose own
comment named the race and then returned the error. The fix is the same bounded
retry, for `netd` only.

The check needed more boots than I first planned. Ten clean boots with the fix
looked conclusive until the control, the same script on the unfixed libc,
failed only once in ten. Across the day that is three failures in sixteen, at
which rate ten clean boots happen by chance about one time in eight. Ten more
made it twenty clean, about one in sixty-four. A control that fails rarely has to
be matched by a pass count sized to that rate, not to a round number.

## HMAC, and an instrument that measured its neighbours

Step 2 of the session-auth plan: HMAC-SHA-512 over the crate's SHA-512. The
vectors came out of the RFC 4231 text by a parser that checks each against
Python's `hmac` before emitting it, which is how I noticed that the RFC's own
test case 3 has no `=` after `Key`. All seven passed first time; the plan's
control (a flipped bit in one vector's key, data and tag, one at a time) failed
all three.

The gate passed plainly: one MAC over a full `NP_NET_MAX` message is 120 to 160
µs against 536 µs for a sign, so four MACs at the largest size are about a fifth
of step 0's 2,926 µs. The arc has its point.

The measurement that needed care was `edtest`'s own. Adding the HMAC as a third
arm of the probe's `work` function put its 2 KB message buffer in the frame the
other two arms share, and the timing's buffer in `_start`, and the probe reads
depth from the top of the stack. Sign+verify read 8,960 bytes, then 6,320 after
the first fix, where it has read 3,584 since 2026-08-31. That is the
sibling-branch rule from this morning's postmortem, turning up in the
instrument rather than the code under test, and it was visible only because
there was a historical figure to compare against. Each operation has its own
frame now, and sign+verify reads 3,584 again.
