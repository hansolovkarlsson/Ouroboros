# 2026-10-30

## Read-only as a property of the mount

The morning merged #372, yesterday's closeout, and took the first item on
the list: fsd had two sources for whether a tree is read-only. D5's
fallback lived in a static, `ROOT_READ_ONLY`, stored by `try_mount` and
cleared by hand in `FSOP_UNMOUNT`, and the verb gate asked it beside the
arm's own `read_only()`. The roadmap offered two shapes, the flag kept with
the mount slot or a `vfs` wrapper carrying the reason, and the wrapper won
because it lets the boot line read the reason the same way the gate does.
`vfs::Mount` holds the filesystem and fsd's reason, only vfs's mount paths
make one, and `Filesystem::read_only` became private to vfs, so `main.rs`
cannot ask the arm alone and miss D5.

The change also moved the fallback's line into the `fsd: mounted read-only:`
form, and that is where the first wrong turn was. I rewrote
`test-boot-partition`'s three expected strings and guessed that disk-badroot
printed the untyped reason ("no partition beside the boot partition
mounted"). disk.img's root is typed 0x83, so it prints the typed one, and
the run said so. The old check had matched only the tail both reasons
shared ("the boot partition is `/`, read-only"), which is why it never had
to know. The mutation control, D5 taken out of the gate, failed four
checks (root's `touch` and the EROFS create on the three fallback boots),
so the rig was seeing the gate and not only the text.

The high review found no correctness bug and six smaller things, and the
two that mattered were mine. The untyped reason was now graded by no boot,
since the shared-tail check had been the only place a third wording would
pass; a new boot, disk-untyped (disk-badroot with its root typed 0x07),
prints it. And the old code had put the fallback's reason before the mount
line on purpose, with a comment saying so, and my change had moved it after
without a check noticing. Both reasons are printed now, D5's before the
mount line and the volume's after it, so a fallback that is also a damaged
exFAT says both, and disk-badroot and disk-untyped check the order. A
control that prints D5's reason after the mount line fails both. The
review also asked for `Mount`'s fields to be private, so no volume can be
put under another's reason, and for `refuses_changes` to be written in
terms of the one `read_only`.

The rerun of `test-boot-partition` after the review fixes failed seven
checks on disk-badroot: fsd printed its lines, in the right order, and the
boot never reached the login prompt. The mutant run that followed in the
same chain reached login on the same boot, and the clean rerun passed every
check. It looks like the 27th's unexplained login hang, and it cannot be
read: the mutant run wrote its transcript over the failing one. The
medium review that followed found five more small things (two records
naming `read_only` where the line asks `reasons`, a 320-byte line buffer
the mount line now reaches 290 of, the line's assembly written twice), all
fixed, and #373 merged. Three firmware stalls came in along the way, on
disk-usb, disk-data-format and virtio-beside, each a run that had to be
repeated.

One more of my own. After the medium review's fixes I posted a PR comment
saying the second `test-boot-partition` run had passed, in the same command
that first printed its result, and the result was exit 100, INCONCLUSIVE.
The comment was corrected within the minute, and a third run passed clean.

## BESIDE on exFAT's own gate

The medium review of #371 had left BESIDE's write graded on fsd's verb gate
alone: `make test-disk-gate` booted test-long-set's read-only volumes on
fsd's `disk-gate-rig` build, but not BESIDE, the one whose bitmap claims
the next partition's first sector, where a write past the gate would land
on another partition. `test-volume-bound.py --disk-gate` now boots it from
a copy of esp.img carrying the rig's fsd, and `make test-disk-gate` runs
both modes. What the two share (the build's line, the staged ESP, the
check of which fsd ran) went into `scripts/diskgate.py`, moved out of
test-long-set rather than copied a second time.

The control taught something about BESIDE itself. With exFAT's gate taken
out (`writable()`, the allocator's check and `Gated::write_sector`'s),
BESIDE in the rig's build fails one check: its write is answered as an I/O
error, not read-only, and the next partition is untouched, because
`bitmap_sector_lba`'s bound stops it. That matches the rig's docstring,
which already named the bound as the last line. The same mutant passes
BESIDE on the shipped fsd, where the verb gate holds alone.

The medium review of #374 found eight things, none in fsd. The one worth
remembering: I had added the which-fsd check to every boot of
test-volume-bound, run BESIDE alone, and written in the CHANGELOG that
BESIDE checks it; thirteen boots carried a check no run had seen. The full
rig ran after the fixes, all fourteen confirming the shipped fsd. The
review also found that `make test-disk-gate`'s "worse exit" took the first
code that was not 0 or 100. The ranking that replaced it was tested over
every pair of codes, after a first table that printed 2 for every pair:
zsh had not split the loop's words, and make exits 2 on any failure
whatever the recipe's code, which only its `Error N` line carries. #374
merged.

## No rig loads another

`test-write-walk` and `test-fat-link` ran `test-spawn-reads.py` through
`importlib` to take four host helpers, the trap #358 closed for the exFAT
rigs. The four moved into `exfatimg.py` unchanged (#375), and the three
rigs passed. Two counts differed from the ones recorded in `CLAUDE.md`: the
exFAT chain read 7 FAT sectors where 6 was written, and fat32-same 775
where 774 was. Rather than argue from the code that a move cannot change a
count, I ran both rigs with `main`'s scripts on the same images, and they
read 7 and 775 too; the images had moved them. `main`'s runs added three
more firmware stalls (two ext2 boots in test-spawn-reads, fat32-same-more
in test-write-walk), which with the three above makes six today, each on a
different boot. The low review found nothing, and #375 merged.
