## Answering while an op waits (#493), and the second review of the echo reply

The first review of #492 had a fourth finding that was not about the
reply at all. Every synchronous op in `netd` (`arp_resolve`, `icmp_echo`,
`resolve_ip`, `tcp_get`'s handshake and data loops) polls `recv` until
its own answer comes, and `recv` dropped every frame that was not that
answer. So for as long as a ping, an ARP resolve, a DNS lookup or a
fetch was in flight, up to a second or so, the node answered neither
ARP nor ping, and the echo reply just built went unheard while the node
did anything of its own. Hans had it done as a branch of its own on top
of #492.

`recv` now takes the MAC and answers an ARP request or an echo request
itself, through `answer_unasked`, which `on_frame` calls too. The MAC is
a required parameter, so no loop can poll without answering. The rig's
new phase logs in and runs `ping 10.0.2.98` (no ARP reply), `ping
10.0.2.2`, `resolve foo.test` and `fetch foo.test`, and into each wait
sends an echo request and an ARP request, after seeing the op begin by
its own frame on the wire and withholding its answer. #492's head
failed the probes in every loop it reached; its handshake gave up
during the failed probe, so its data loop was never reached, which the
record says.

The second review found that `answer_echo` checked the destination MAC
only for a broadcast, so a request under another host's unicast MAC
with our IP was answered; QEMU's virtio-net passes such a frame up. It
compares the MAC exactly now, and the rig has the case. `answer_unasked`
had read the ICMP type at an offset that a header length below 5 would
put inside the IP header; it reads it behind the same `0x45` test
`answer_echo` makes. And `on_frame`'s ICMP arm was dead, since every TCP
path refuses protocol 1. Removing it left a one-arm `match`, which
`cargo clippy -p netd -- -D warnings` refuses, and `make test` exited 0
on that tree. That was the lint gap of the afternoon.

The review's last point was the copy. The reply is its request with the
addresses swapped, the type changed and both checksums made again, the
same length, so Hans had it built over the request on the same branch:
`answer_echo` writes into the caller's buffer, and there is no
1600-byte array on the stack inside every polling loop and no
`ECHO_MAX_FRAME`, the bound no caller could reach.

A wait still drops TCP. A segment for one of the node's own connections
that arrives while an op polls is lost and has to be sent again, which
is why `credit_deaf` stays. Answering it there would need the
connection state reachable from inside the wait without one op
recursing into another. It went on the roadmap with the lint gap as
#494. Hans merged #492 without deleting its branch, #493 was retargeted
to `main` and merged, and the three branches were deleted after.

## The board answers a ping (boot 50)

The card was restaged at `d05972c1` with `KEEP_ETC=1`, so partition 2
kept its `/etc/net` (192.168.77.2/24) and its older `/bin`; the servers
come off the boot partition and were current. Boot 50 came up at
1000 Mb/s with the address from the file and no fault, wedge or restart
line. The Mac pinged it twice, 10 of 10 each time, about 1.2 ms, TTL
64. Before #492 nothing could ping the board at all; this is the first
real-hardware check of the reply, with the Mac's own ICMP stack as the
observer.

That run said nothing about #493. The Pi had pinged twice during it,
but the capture has no timestamps, so there was no telling whether its
two waits overlapped the Mac's pings, and a run with no overlap passes
with the fix taken out: the same fault as boot 46's cable pull with
nothing sent. The run that could fail was a dense one. The Mac pinged
every 0.2 s, a hundred times, while seven `ping 10.0.2.98` on the Pi
each held `netd` in `icmp_echo`'s full wait of about a second. About 35
of the Mac's pings fell in those waits by the arithmetic, every one of
which #492's `netd` would have dropped. All 100 came back, 0.56 to
2.05 ms. Two limits stand in the record: the overlap rests on when the
Pi's pings were typed, and no control was run on the board. The control
that showed the loss is the QEMU rig against #492's head.

## A boot log, because there is one serial port

Asked what came next, step 10 was the obvious answer, and Hans asked
the question that changes its shape: two boards on one switch, and one
serial port to read them by. Every board result so far came from
`screenlog.0`. So the console's output has to be kept on the board and
read off it, which the roadmap has carried for months as "a kernel log
buffer and `dmesg`" and the gap analysis as a missing logging row.

The plan, `docs/roadmap/roadmap-boot-log.md`, is a ring in kernel `.bss`
filled where `console.rs` writes and by the kernel's own logger before
the exit; a `LOG_READ` syscall only `fsd` may make; `/proc/log` at 0400,
reachable by 9P from the Mac or the other board (`np9p_client.py`,
`mount -r`) and deliberately not over HTTP; and `/var/log/boot.<N>` on
the card, so a boot that hangs can be read after a power cycle. A boot
to the login prompt is about 10.5 KB of console. Six decisions are
Hans's, each with a recommendation, and none is answered yet.

## The lint gap (#495)

Hans's scope was the kernel and the four supervised servers. `make test`
had linted the pure crates alone, which is how #484 came to be needed
for the kernel and how #493's one-arm `match` passed. The kernel and
three servers were already clean. `fsd` had fifteen warnings, all
`doc_lazy_continuation`: a doc line starting "- POSIX rename" is a list
item to clippy. They are parentheticals now. A lint planted in each of
the five fails `make test`.

Two clean runs of `make test` took 1,336 s and 1,512 s in the middle of
this, all of it inside the 9P self-test, which takes 53 s alone and
under `make`. The next run was 97 s and it has not come back.
`fileproviderd` was at 140 to 170% CPU and Spotlight's `mds_stores` at
30%, which may be the cause; nothing showed it was.

The review found the branch's own blind spot in its comment. The
Makefile said the servers' rig builds needed no lint because every rig
reads its feature through `cfg!()`, which compiles both branches. True
of all eleven feature reads in the tree, and checked by nothing: the
first `#[cfg(feature = "restart-rig")]` item would never be linted.
`make test` already ran a `cargo check` of each rig build, so those five
are clippy with `-D warnings` now, and the claim is gone. The control
is a one-arm `match` under `#[cfg(feature = "restart-rig")]` in `netd`,
which the default clippy passes and `make test` fails. The review also
caught the comment's pointer to the ROADMAP item by the title this
branch had just renamed, my "about a second" (1.4 s warm, mostly the
kernel rebuilt by its `build.rs`, and 0.4 s for the rig builds), a dev
profile the text called "as built", `nsresolve` missing from the list
left, and a plan to grow `LINT_SERVERS` with 62 programs that are not
servers. What is left is those programs, 61 of them already clean and
`openprobe` with one `enum_variant_names`, and `nsresolve`.
