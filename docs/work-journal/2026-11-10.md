## A `cpu` run's command dies with its connection (#437)

Fix 1 was the orphan the last entry of 2026-11-09 named: a run cut short on
the dispatching machine left its command running on the executing one,
holding a task slot until someone typed `wait N`. The fix is a kill of the
run's child where its connection is freed. Six sites free a `TcpConn`, so
the kill went into its `Drop`, where none of them can leave it out, and it
checks that the slot still holds the identity captured at the spawn, since a
slot is recycled the moment its task is reaped. `make test-run-orphan`
dispatches `cpu recv`, a command that blocks for good, and closes the
connection once by a FIN and once by a RST.

The high review found the rig could not tell its two rounds apart. SLIRP
sits between the host's socket and the guest, and nothing says it relays a
reset as a reset, so the RST round might have been a second FIN round with
every check passing. The rig now reads QEMU's capture of the guest's NIC and
counts the FINs and RSTs that reached the export's port. The review also
named what the kill costs. A connection's close used to lose a run's
output; it now stops the command, so a stale or forged RST or SYN on the
unhardened receive path ends a user's command midway. I recorded that in the
ledger with what is still orphaned (a caller that goes silent without
closing, a restarted `netd`), and Hans accepted the cost.

## The held-key rules onto the host (#438)

Fixes 2 to 4 were three rules of the per-user keys arc with no check that
could fail: a dead login's key signing before the idle pass reaps it, a run
whose key goes between its park and its send, and a credential signed for
whoever sent last. Each turns on a moment inside one pass of `netd`'s event
loop, and no driven boot can put a request there. So the rules moved to
where a test can stand: the table and those decisions became the `heldkeys`
crate, pure, with task liveness passed in as a trait `netd` implements with
the kernel's answer. A parked request's uid and attested flag became one
`Standing`, made at the park, and every way to a seed takes one.

I had written that no seed can be had from a bare uid any more. The medium
review pointed out that a `Standing` can be constructed anywhere, so the
shape discourages the mistake and does not forbid it; the records now say
what the shape is and that review holds the rest. The same review moved the
export's anchor into the `Standing`, so the park and the send cannot
disagree on whether the key was known, and brought two rules that had stayed
in `netd`'s `key_op` into the crate. Twenty-one host tests in `make test`.

## The stack probe: the kernel counts it (#439)

Fix 5 was the probe that broke the rig it was read from. I reproduced it
first: with `8429d38f` applied, `test-async-rmount` fails two checks,
because the probe's log line lands on the shell's prompt and the rig matches
exact lines. The readings it gave on that tree were 11,216, 5,248 and 2,496
bytes.

Three designs were on the table: a feature-gated probe inside `netd`, a
measure branch never merged, or the kernel measuring every task. Hans chose
the kernel. The loader paints each stack before the program's first
instruction and a syscall counts the paint still standing at the low end,
which `fsd` serves as `/proc/<n>/stackfree`. Reading the loader found the
reason the paint cannot be zero: `populate_region` zeroes the whole region
at every load, and a frame's zeroed buffer would be indistinguishable from
stack never reached. The paint is `0xA5`, and `stackprobe` has a mode that
writes zeros to prove the difference. That byte collided with `edtest`,
which paints its own stack with the same value to measure a signing; the
review caught it and `edtest` changed its byte.

One claim of mine was wrong and the transcripts showed it. I wrote that the
async rig read `netd`'s mark after each boot's parked request had met its
deadline. In two of the six boots the read came first, because the shell's
prompt returned before the 5 second deadline fired. The boots now wait for
the deadline's own failure line before reading. The figure did not move:
2,528 of 57,344 bytes never written, in all six.

## Who may read the mark (#440)

The medium review's one security finding was that the mark was open to
every task, and through the export to every peer, and that a fall in
`accountd`'s or `netd`'s mark across a login says a deeper path ran. I left
it on the roadmap as Hans's decision and recommended a root-only file. When
he said to build it I found that recommendation was half a fix: a user's
own program can make the syscall directly, so the file's mode alone closes
nothing for a local user. The gate has two halves, the file `r--------` and
the syscall answering only root and the task itself.

Giving `/proc` modes at all was the larger change. It had none, so `fsd`
skipped every permission check there; a `stat` that returns an owner and
mode switches the ordinary checks on for the whole tree, for local users
and peers alike. The first version of the kernel's rule also named `fsd`'s
slot. Its mutation control changed no check, because `fsd` runs as root and
the root clause already answers it, so the clause came out. A rule with a
clause nothing can observe is a claim waiting to go stale.

The first review of the gate found a leak I had not thought of. A `stat` is
answered to callers who are refused a read, since `ls -l` needs it, and the
size it reported was the line's length: five bytes or six, which is whether
the count is under 10,000. The file's size is now a constant. The review
was also right that my "another task of the same user" check asked about
slot 0 without showing slot 0 was the user's; it now asks about a probe the
user's own shell holds.

The day ended with #439 merged and #440 open after its first review.
