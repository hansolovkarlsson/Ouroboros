# 2026-10-31

## The free, a sector at a time

The morning pushed and merged yesterday's second closeout (#378) and took
the first item on the list, deferred by Hans on the 23rd and found again by
three reviews since: exFAT's chained free read and wrote a bitmap sector and
wrote a FAT sector for every cluster it freed, three USB round trips a
cluster on the Pi's stick, so an `rm` of a large file could outlast the
supervisor's wedge limit and have fsd restarted mid-free. The walk now holds
one FAT sector (the FAT cache itself) and one bitmap sector and writes each
when it leaves it. No program's output can show that, so the rig had to be
QEMU's disk trace: `test-free-chain` boots twice, both making a 1 MiB file
and two files grown a cluster at a time in turn (their chains interleave and
share sectors), one removing three empty files and the other the three real
ones, and the second boot's FAT and bitmap writes past the first's must be
what a model of the walk predicts from the chains read off the disk. 280
clusters took 280 FAT writes and 280 bitmap reads and writes on `main`; on
the branch 10, 3 and 3.

The first version was wrong in a way the counts could not see. It wrote the
FAT sector when the walk left it and the bitmap sector only when the walk
left that, so for most of a long free the zeroed FAT entries reached the
disk ahead of the bits they belonged to. A free cut short there, the very
restart the item was about, leaves clusters with zeroed entries and their
bits still set: a leak until a fsck. The medium review of #379 found it. The
bitmap sector is now written before every FAT sector, which costs 10 bitmap
writes rather than 3, and the rig had to learn order: `disktrace.boot`
records the written sectors in the order QEMU handled them, and the frees'
writes must be the model's sequence exactly, the model itself refusing to
build a sequence that zeroes an entry before its bit is on the disk. A
control that only swapped the end of the free (FAT, then bitmap) passed
every count and failed the order. The same review asked for one writer of
FAT entries, `patch_fat_entry` under both `write_fat_entry` and the free, so
the cursor rule lives once. I declined its finding that the free should zero
an entry before clearing its bit: in exFAT the bitmap alone says what is
free, so a free cluster with a stale link is the safe state, not the leak.

The second medium review put the free's flush rule in one helper
(`flush_free`) and caught the rig comparing every write of the boot against
an empty model if the chains ever came back empty. Of its other findings the
one that mattered later was `ensure_chained`: the first append to a
contiguous file links it a FAT write a cluster, the same cost the free had
just lost. It went onto the allocation item the first review had opened,
and #379 merged.

## The allocation, as a FAT batch

That item was next. Every FAT entry exFAT set was a sector write, and every
cluster allocated a bitmap read and write with the scan starting at byte 0.
For a 2 KiB request that is one cluster at most, but a gap fill (up to
`MAX_GAP_FILL`, 1 MiB) and `ensure_chained` (thousands of clusters on a
camera's file) set hundreds or thousands of entries in one request. I chose a
batch mode rather than a write-back cache for every writer: inside
`in_fat_batch` entries stay in the FAT cache until it moves or the batch
ends, the allocator holds its bitmap sector and writes it before any FAT
sector (`flush_fat`'s one rule), its scan goes on from its last find, and the
set naming the chain is written after the batch, so the disk still gets bits,
then links, then the set. Outside a batch nothing changes.

The rig, `test-alloc-batch`, had to cross a bitmap sector or the scan's
start would not show, and that took two wrong turns. The image's bitmap
covers 6,112 clusters in two sectors, so both boots first fill the first
sector to 128 free clusters with gap fills, and those failed at once because
`writeat` wants an existing file. Then `/CONT`, which was to be a contiguous
2 MiB file, came back FAT-chained: macOS's driver had written it into a
hole, so `ensure_chained` would never have run. It is planted by hand now, a
NoFatChain run at the heap's end. The graded boot's gap fill and append make
14 FAT writes, 5 bitmap writes and 4 bitmap reads in the model's order, where
`main` made 1,025, 257 and 386. Five controls each failed: `main`, the scan
from byte 0, FAT before bits, the set written inside the batch, and nothing
written at the batch's end. One control's run was refused by the image
build's source guard, "the source changed while the programs were being
built", with nothing I know of touching the tree; run alone it failed as it
should.

## Three medium rounds and a high one

The first medium review of #380 found two real things. `write_at` set its
write cursor inside the batch, so a batch whose last flush the disk refused
left a cursor on a cluster its file's link never reached, and a retry walked
on from it; `flush_fat` now drops the cursors with the cache it drops. And
the free's order had come to rest on a comment: `fat_sector` wrote a dirty
sector before reading another, which only a batch should do, and a later
edit to the free reading ahead would have written zeroes before their bits;
outside a batch such a sector is refused. Its finding that `write_chain`'s
give-back could walk stale entries after a refused flush I declined, with
an argument: `extend_chain` sets a new cluster's end of chain before the
link to it, and a link in another sector is set only after the cache has
left the new cluster's, which writes it, so every link on the disk names an
entry already there. I put that rule in `in_fat_batch`'s doc and had the
rig's model assert it.

The second medium round showed the argument was about links and the chain's
head is not one. The head's end of chain waits in the cache like everything
else, so a refused first flush leaves its old entry on the disk, and the
give-back walked from there: a link another driver left in a free cluster's
entry would take it into a live file. A whole-file write is capped at 2 KiB,
one cluster at 4 KiB and so harmless there, but four on a volume of 512-byte
clusters. The model's assertion, which the docstring presented as proof of
the give-back's safety, checked link targets only, so it could not fail for
the one cluster the give-back starts from. The batch now answers
`BatchFailed`, saying whether a refused flush lost entries, and the
give-back leaks the chain when it did. Hans chose to build the rig as well,
since both rounds' worst findings sat on the one path no rig reached:
`test-batch-refused` refuses, through QEMU's blkdebug, the first write of
two FAT sectors of a 512-byte-cluster exFAT, plants a link from the first
free cluster's entry into a live file, and needs a whole-file write over
512 bytes, which no client sent (`write` is bounded by argv), so
`cursorprobe` gained a `whole` mode. Its two cases each fail with their fix
taken out: the give-back ungated frees the live file's first cluster, and
the cursors kept leave a retried append's file one cluster for 515 bytes.
That made the second round's cursor fix graded at last.

The high review found no defect that corrupts data. It found a refusal that
stuck: the dirty sector refused outside a batch stayed in the cache, so every
later FAT read failed until fsd restarted; it is dropped now. And the first
append to a contiguous file walked from the head again after linking the
run, re-reading every FAT sector it had just written, about a thousand round
trips on a 4 GiB camera file, against the PR's own aim; `ensure_chained`
leaves the cursor on the run's last cluster. I told Hans the rig would see
that as fewer FAT writes. It does not: the count is 14 either way, and what
changes is the order (the walk from the head writes the last sector early)
and the reads, which no rig grades. The control fails on the order alone.
The match form the review asked for in `hold_bitmap_sector` does not
compile (a borrow returned from one arm and taken again in the other), so
the unreachable arm stays with a comment saying why. The leaks the batch
still makes, a whole chain when any entry was lost and an append's clusters
past the file's size, went onto the roadmap as one item: give back by the
bits the batch set, with no walk, once there is a way to record them. One
`test-disk-gate` boot stalled in the firmware along the way and passed on
the rerun. #380 merged.

None of it has run on the Pi's stick. The wedge-limit claims are QEMU's, and
a gap fill still writes its 2,048 data sectors one at a time.
