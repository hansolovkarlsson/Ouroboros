## CLAUDE.md from 144 KB to 38 KB

The day opened on a warning that the files Claude Code loads at the start of
a session were over 150 KB. The memory directory was not the cause (its
index is 4 KB); `CLAUDE.md` alone was 144 KB, most of it two things that had
grown in place: the Commands section, a paragraph or more for each of 99 make
targets, and the boot, MMU, exception and timer sections, the debugging
history of phase 0. Both moved out word for word, the targets to
`docs/testing/make-targets.md` and the boot history to
`docs/boot-history.md`, and `CLAUDE.md` keeps a one-line index of the targets
(checked against the old list by diff) and fifteen "rules for boot and
low-level code", each a hazard already hit. Hans asked whether the boot cut
lost anything. The test applied was whether any sentence there was a rule a
session editing that code needs before it starts; those became the fifteen
bullets, and the rest is record. One rule had lived only in the history (the
vector table must be in plain `.text`), so `exceptions.rs` now says it at
the line. #386.

## `partition` refuses a GPT disk

The first item of yesterday's standup. `partition` writes sector 0 alone, so
on a GPT disk not erased first everything that reads the disk went on
reading the old GPT and the new MBR was invisible, with `partition`
answering success. `partition_disk` now asks `partition::is_gpt` first and
answers `FS_ERR_NOT_SUPPORTED`, and the shell names `erase disk`. One trap
caught before the build: an unimported constant in a `match` arm is a
binding that matches everything, so the shell's arm is spelled
`syscall_abi::FS_ERR_NOT_SUPPORTED`. The medium review found the rig's new
check compared sectors 0 and 1 against `espgpt.img` read after the boot, a
file a rebuild could change; it now compares against the copy's own bytes
from before the boot, and with the refusal removed exactly the two new
checks fail. The review also suggested `partition` invalidate the GPT itself
rather than refuse; that is Hans's call and was not taken. Erasing showed a
gap of its own, now on the roadmap: `erase disk` zeros the first 2048
sectors, so the backup GPT at the disk's end survives. #387.

## The allocator's lowering: removed, then kept

The second item asked for a rig that could fail exFAT's allocator lowering
its hint on a refused bitmap write, since deleting the lowering passed every
rig. Reading the code, I concluded no rig could: since #384's medium review
the scan starts at the first byte of the hint's sector, which already reads
the dropped bits again. I offered to remove it or keep it with a corrected
comment, recommended removing it, and Hans said do it. The rigs passed, as
they had to (one first run of `test-stale-cursor` hit the firmware stall and
failed every check, since that rig does not classify a stall as
inconclusive; the rerun passed all 30).

The medium review reversed it. Without the lowering, the only thing keeping
a dropped find's clusters in use was that rounding in `alloc_scan`, another
function, unchecked, which had not existed a day earlier; and `clear_bit`'s
comment, "every byte below the hint stays full", became false. I changed my
recommendation, Hans agreed, and the branch was reset and the lowering kept,
with a doc saying no rig can fail it and why it stays. The second review
found my premise wrong as well: a request that answers `DiskFull` after the
second pass ends holding the sector before the hint's, and there the
lowering does move the hint. Checking the rewrite turned up a third path,
`DiskFull` with no second pass. The doc now lists all three, bounded by the
fact that only `alloc_scan` sets bits in the held sector, and none gives a
cluster out differently. The third review found only records disagreeing
with one another, the wording of the first two rounds, so the argument now
lives once, in `end_alloc_hold`'s doc, and the roadmap and CHANGELOG point
to it. The wrap before `DiskFull`, which had shared the roadmap item, has
an item of its own. The code merged identical to `main`. #388, and a section
in [`true-when-written-postmortem.md`](../postmortems/true-when-written-postmortem.md).
