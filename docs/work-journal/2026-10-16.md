## Five items off the standup, each one reviewed until it held

The day was the standup's list taken in order, one PR each, with a review
after each and a merge on Hans's word: #301 (yesterday's nano-malloc fix)
merged first thing, then #302 to #305 merged, and #306 open at the end of

### picolibc's probes (#302)

Yesterday's finding was that 30 of picolibc's 31 optional-flag probes had
failed since the port began, because the cross file put `--ld-path` on the
compiler line and meson probes with
`-Werror=unused-command-line-argument`. Moving it to `c_link_args` made 27
probe YES. The library then has `-frounding-math`, which mattered in a way
that could be shown: without it clang computed both arms of a choice and
selected one, so `round(1e308)` raised overflow. `/bin/CPICO fenv` and
`make test-cfenv` show it, and fail on the old `libc.a`. The probes also
defined eleven `_HAVE_` macros in `picolibc.h`, which DevTools's `cc` reads
from this working copy, so patch 0002 undefined them to keep the header pin.
The review found the observer's own blind spot: `cpico fenv` cleared the
flags before it had shown it could read one, so a `feclearexcept` that did
nothing would have passed. It now raises and reads back first.

### The spawn buffer (#303), and a hole as old as the latch

The 128 KiB staging buffer became 1 MiB, asserted at build time to cover
the loader's image bound. That was the easy part. Growing the buffer
eightfold made the high review look at what the staging trusted, and the
answer was a high-water mark: `STAGED_IMAGE_END` was the end of the
furthest chunk, so one chunk near the end made every byte below it count
as staged. A new owner could spawn the previous stager's program, one it
had no right to read. The hole dated from the latch itself (2026-10-11).
Chunks are now accepted only in order. The second review found that the
order was checked after the staging was claimed, so a refused chunk still
held it. The third found that a restart left argv, cwd and env latched
from the attempt it replaced. Three rounds on one rule. Each fix was right
for what it addressed, and each left the next step uncovered.

### DevTools's `cc` and `as` (#304) and the macros it cannot take (#305)

`make CCOMP=devtools` builds `/bin/edit` and `/bin/cpp` with DevTools's
compiler and assembler. The review asked how a rig knew which compiler had
made what it tested. The Makefile's word was all it had. Now the rigs
read the objects themselves, since every object clang writes carries its
`clang version` string. The control for that check left stale clang
objects in `build/cpp-cc`, which would have made the next run pass for
the wrong reason. They were deleted, and the comparison was moved to the
assembly. The image's source stamp grew past the eight lines `srcid.py`
scanned for, which broke reading it back. The bound is now 32, with a guard
at write time.

DevTools's probed-macros note then showed that patch 0002 held more than
it needed to: of the eleven macros, four make `cc` refuse a header and
seven cost it nothing. 0002 became three patches, one per condition, each
to be removed on DevTools's notice for it. DevTools was sent a notice before
the header pin moved. I wrote that note with the wrong path for the finding,
and corrected it while the note was unanswered. DevTools had already
committed the note, so the correction sits uncommitted in its tree. Hans
was told.

### The paged directory listing (#306)

`NP_READDIR` skipped a name that did not fit its reply and walked on, so
`ls /include` showed about 60 of its 72 names with gaps anywhere. Now
`a2` is the index of the first entry wanted, a page is whole entries until
the next would not fit, and an empty page is the end. fsd, netd, the host
9P server, `ulib` and the shell all page. `make test-include` requires
every listing whole. Its control, fsd ignoring the start, fails 8 checks,
and a skip-and-walk-on control fails one.

The first review found the paging loop written twice, in `ulib` and the
shell, and the two copies already different. It is now one function in
`ninep-abi`. The review also found a clippy warning on netd's `net_op`
that I had dismissed as old. It was mine: inserting `listing_page` had
put the new function between `net_op` and its doc comment and attribute.
Checking the HTTP index by booting and curling, not by reading the code,
showed a page cut off mid-tag, with `</html>` lost.

The second review found the real design flaw. To tell a server from before
paging, the loop compared a later page with page one. That cannot tell an
old server from a directory that changed between pages. Against an old
server whose directory changes, such as a `/proc`, it never ended. It also
cannot tell an old server with a small directory from a cut-short listing,
so `ls` on an old peer exited 1 on every directory, which made the
CHANGELOG's "a mixed cluster lists as before" false. The fix asks the
question outright. Before a second page, the loop asks for an index past
any directory's end: a paging server answers with an empty page, an old
server with page one. To confirm that the question is what tells the two
apart, I booted against a host peer that ignores the start index, then
re-ran with that listing called incomplete again. Only that peer's
listings then said "cut short". The lesson is not new to this project:
inferring a protocol fact from data guessed where it could have asked.
