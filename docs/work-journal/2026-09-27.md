# 2026-09-27

## The wedge hunt: a busy server, not a lost reply

The standup's first fix was the `netd` wedge that had held user-keys step 4
(#174) as a draft: in `make test-held-keys` the supervisor sometimes declared
`netd` unresponsive and restarted it, dropping every held key. The one wedge
caught the evening before read `netd` blocked in a `MSG_CALL` to `fsd`, and the
entry built on it said two things: that it came at the first `cpu` run after a
boot-shell logout, and that `fsd` was still answering its own pings, so the
reply had been lost or misdelivered.

I ran `login-logout` in batches of up to a hundred, with a small wrapper that
kept every failing transcript, since the rig overwrites its one. While the
first batch ran I read the kernel's message path looking for a way to lose a
reply, and found a real aliasing: direct delivery accepts any message from the
task a caller waits on as its reply, including that task's own new request, so
two servers calling each other at once would turn one request into the other's
reply. It fitted the symptom exactly and was wrong: `fsd` only ever calls
`cond`, so it cannot be the other half. The aliasing is still there, with no
pair of servers to bite today (recorded in `ROADMAP.md`).

The first wedge in the new batch (1 in 15) answered the question the evening
had asked. Its extended report read `task 2 is runnable, 0 queued`: `fsd` was
neither idle with the request unread nor waiting on anyone. I added its PC to
the report, and the next wedge (1 in 20) put it right after the `svc` of
`MSG_RECV` in `fsd`'s main loop, which I read as "woken by direct delivery and
never scheduled since", a scheduler starvation. **That reading was wrong, and
the instrument was mine.** The report read `TASKS[f]`, the context saved the
last time `fsd` was switched out, and when `fsd` is the task running at that
tick the saved context is stale: a task that blocked in `MSG_RECV` and has run
since always shows exactly that PC. The third version read the live frame when
the partner is current and printed the runnable set, and the third batch
settled it, ten wedges in a hundred with the same signature every time: only
the idle task and `fsd` runnable, and `fsd` inside `fat32::Fs::find`, on a
`BLOCK_READ` of a FAT sector.

So `fsd` was working, for `netd`. A `cpu` run makes `netd` read the binary as
98 path-based requests of 512 bytes, each re-walking `/` and `/bin` and then
the file's FAT chain from its first cluster; the images use 512-byte clusters
and `fsd` caches nothing, so a spawn is some 4,800 disk reads, with `fsd`
sharing the CPU half and half with the idle task. A server acks a ping only
from its main loop, which `netd` does not reach until the 98 calls are done,
and the supervisor samples state only at ticks, so it never saw `netd` run
between calls: a ping landing with more than 8 ticks of spawn left timed out.
Both of the evening's claims fell. It was not tied to logout (one of the ten
came at the check right after login), and `fsd` was never idle. None of it was
step 4's code: the spawn, the reads and the ping rule were all on `main`.

## A kernel rule, a review that sank it, and one line in `netd`

My recommendation was a kernel rule: pause a server's ping clock while its call
chain ends in a supervised server that is running, so a server waiting on
another's work is not called wedged. The ping's own history changed its shape
before any code: the control that first proved the ping, recorded in the
changelog in August, was `fsd` calling the idle task, which is always `Runnable` and
never replies, so "the partner is runnable" alone would have hidden exactly the
deadlock the ping was built for. The rule became "a *supervised* partner that
is running", walked hop by hop.

The control came first. `main` unmodified gave 0 wedges in 20 `cpu` runs;
forcing a ping into every spawn with `PING_INTERVAL` at 2 gave only 1 in 10,
which was itself a finding, that most spawns run a little under the timeout and
that is why the natural rate was one in ten. Adding `PING_TIMEOUT` 3 made it
4 in 4, then a `netd` past its restart cap. With the rule, the same mutation
gave 0 in 10; a dropped `fsd` reply was still caught, and so was an `fsd` that
looped forever, by its own heartbeat, with `netd` surviving. On the rig that
found it the rule gave 0 wedges in 100, though the first attempt at that
hundred was invalid: I switched the working tree to the fix branch mid-batch,
the rig script vanished with it, and 99 runs "failed" in no time at all. The
wrapper now stops when its script is missing.

Hans ran a high-effort review, and it changed the fix. Its sharpest finding was
a hole the rule opened: a callee that never replies but blocks briefly now and
then, short calls to `cond` say, resets its own heartbeat each time it blocks
and keeps the caller's pause on, so neither detector ever fires where before
the caller's ping caught it in 8 ticks. My looping-`fsd` control spun without
ever blocking, which is the one shape that could not show it. And the review
pointed at `netd`'s own `heartbeat()`, an unprompted ack added on 2026-09-03 for
the same trap in multi-round-trip remote reads. My case for the kernel had been
the `unspellable` lesson, that an opt-in has to be remembered at every future
loop; it still holds, and this is the second time the trap was hit. But a rule
with a hole in deadlock detection is worse than an opt-in without one, so the
kernel went back to `main` and `cpu_spawn` gained one call per chunk. The same
controls again: 0 in 10 under the forcing mutation, the dropped reply and the
looping `fsd` both caught, and 0 wedges in 100 on the rig (10 in 100 without).
Merged as #175. The kernel rule, with the bound it would need, is an open
question on `ROADMAP.md`, beside two things found on the way: pings can pile
up in a mailbox behind a long loop's acks, and a server past its restart cap
draws one more wedge line.

## Step 4's review, and the stack onto `main`

With the wedge explained, step 4 had its high-effort review: ten findings, six
acted on. One was a real defect in the step: logout dropped its key by handle
after restoring uid 0, root passes the owner check, and a handle is a bare slot
number, so after a `netd` restart a stale handle named whichever login had
taken that slot and logging out wiped that user's key. Logout now drops by task
identity. The others were smaller and real: a seed left in `netd`'s receive
buffer and a plaintext password in `accountd`'s, a first-login upgrade that
stored a clock salt without saying so, a doc comment claiming login never waits
on `netd`. One reviewer claim did not survive checking against the plan: that
step 7 signs by handle. Step 8 finds a key by uid, so handles without a
generation are recorded as a condition on any later step, not a defect now.

Then the stack went onto `main` bottom-up, #170 to #174, without deleting a
branch until the last had merged. Four of the five conflicted, all in the same
place: the site checker's manifest, where each step and #175 had re-stamped a
different page on adjacent lines, plus one pair of `ROADMAP.md` items added at
the top of the same list. Each resolution kept both sides and was checked by
the thing it touched, `make test`'s site check, with a full image build where
source had auto-merged. Step 4 then ran the held-key rig with `main` under it,
5 of 5 and 30 of 30 with no wedge, came out of draft and merged.
