## The one-disk plan, and the experiment already run

`roadmap-one-disk.md` (#284) was written from two read-only sweeps of the
tree. They established what the arc had to change: the boot programs come
off the ESP through the firmware, the block device is the first disk found
(virtio before USB), `fsd` mounts the first partition that validates, and
nothing anywhere knows which disk the system booted from. They also found
that every image's MBR disk signature was zero, so a firmware device path
could not name one disk apart from another. And the second sweep found the
plan's own first experiment already done: in 2026-08 Parallels had booted
from the passed-through stick itself, recorded in the CHANGELOG as the
xHCI contention fix's "Mode B", where storage worked and the keyboard was
not addressed until the boot scan learned to wait. `ROADMAP.md` item 3 still
listed it as open. Step 0 became a re-confirmation on today's tree.

## Steps 1 to 3: the disk the system booted from

Step 1 (#285) reads the `HardDrive` node of the image's own
`LoadedImageDevicePath`. The node was there on every path QEMU offers:
virtio, a USB stick (`PciRoot/Pci/USB/HD`), NVMe, and a vvfat directory,
which the plan had predicted would have none and which carried the only
nonzero signature of the day. The review found a panic waiting for an image
loaded from memory (a null interface that `ScopedProtocol`'s `Deref`
unwraps) and a stall classifier loose enough to call a kernel that never
printed INCONCLUSIVE.

Step 2 (#286) signed every image from a hash of its own bytes. The first
version also checked that the signature equalled the hash of the image's
current bytes, and the review found that every boot breaks it: the boot
counter's file is rewritten on each one, so an image booted once was
refused. The rig had passed only because it read every expectation before
its first boot. The fix was to say what the signature is, a disk's name and
not a checksum, and to check the property step 3 needed instead: nonzero,
and different between disks. The next review then found `mkgpt.py`'s GUIDs
derived from `esp.img`'s bytes, the same mistake in a second place, and an
unsigned USB stick image attached beside the boot disk in three rigs.

Step 3 (#287) installs the disk whose own table holds the boot partition.
Its first rig showed the old behaviour plainly: booted from a stick with an
unrelated disk on virtio, the kernel ran on the virtio disk and login never
came up, since that disk has no `/etc`. Two reviews hardened the matcher (a
GPT header built to overflow had panicked a debug kernel; both CRCs as
`fsd` checks them; the firmware's own table format, not a guess from sector
0), and a fallback boot from NVMe, which the firmware boots and the kernel
cannot drive, reached the branch no boot had. Rewriting that rig also showed
the firmware's boot order following QEMU's argument order: it booted the
stick beside the NVMe disk until `bootindex=0` pinned it.

## Step 4, and three reviews of it

Step 4 (#288) built the disk itself, `build/disk.img`, the ESP first and an
ext2 root beside it (D1, ext2, Hans's choice), with a new system call,
`BLOCK_BOOT_START` (77), telling `fsd` which partition to pass over. It
mounted its root on the first boot. The rig's new check of what `fsd` had
mounted then failed on two boots that had mounted correctly: `fsd` wrote
its line in three pieces and `accountd`'s ready line landed between them.
That was true on `main`; the check was the first observer able to see it.

The three reviews were mostly about `format`. The first found it writing
over partition 1, the ESP, while `/` showed the root. The second found it
writing over a GPT disk from LBA 1, true on `main` as well, and choosing the
root by a rule other than `mount`'s. The third found the repair from the
second reaching the ESP again when the root beside it was damaged, the one
partition there that still probed. Sorted by yesterday's question, which
findings were the branch's and which were `main`'s, the third round was
fixed and the rest became two questions for Hans.

## The DevTools note

A requirement arrived from DevTools mid-afternoon: one condition in the
prebuilt picolibc's `math.h`, so that `cc`, which has the comparison
builtins but not GNU statement expressions, compiles `isgreater` and the
rest. It was kept out of #288 and triaged after it (#289): accepted and
done, as a patch in `libc/picolibc-patches/` that `build-picolibc.sh` now
applies to every regenerated tree, since that script copies picolibc's
headers over the tree wholesale. Clang's preprocessed output was identical
with the old and new header, and the note's own check, run with DevTools's
built `cc` against this tree, printed `ok`; with the old header put back it
failed with the note's error. Nothing was built in DevTools.

## The decisions, and the one I changed

Hans was shown the open choices together and took the recommended answer
to each (#290): D2, a stick staged by writing the image with `/etc`
carried over; D5, a root that does not mount leaves the ESP mounted
read-only; D6, a boot disk's failed read retried once, then taken as not
the boot disk with a line saying the read failed; D3 and D4 deferred until
step 0.

Step 4b (#291) built D5 and D6. D5 held through its reviews: a static for
tree 0, a gate before the root bypass so root is refused too, default-deny
over the verbs, and root's `touch` refused on the rig's damaged-root disk.
D6 did not. The first review argued that a disk whose table could not be
read should be taken as the boot disk rather than for another, and I made
that change, reversing what Hans had decided. The second review found its
cost at once: an unrelated disk with one bad sector winning over the real
boot stick, a dead stick going in over a working disk, and a counted
failure overruling a backup GPT that had said no. D6 went back as Hans had
written it, on a yes/no/unreadable answer in place of a closure counting
failed reads, and the trade went to Hans as a question with three answers
and their costs. He kept D6 as built. The plan now says that choice is not
to be reopened in a review.
