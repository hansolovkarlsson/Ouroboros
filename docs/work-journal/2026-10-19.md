# 2026-10-19

## A case-only `mv` of a directory, reproduced before it was fixed

The day opened on the standup's NEXT item, written the day before from a
reading of the code: on FAT32 and exFAT, `mkdir /Docs; mv /Docs /docs` moved
the directory into itself. `/bin/mv` stats `/docs`, which a case-folding
lookup answers with `/Docs`, so it appends the basename and sends `/Docs` to
`/docs/Docs`; fsd's guard against a move into the mover's own subtree compared
bytes and let it through. Before touching the guard I wrote `make
test-mv-into` and ran it against the byte compare: `mv` exited 0 and both
`/Docs` and `/docs` were gone. The item had been right, and now there was a
check that had failed on it.

The first fix folded ASCII case in the guard on the two FAT formats. Its high
review found the guard was still a byte prefix in every other way: a path with
`//`, `/./` or `/x/..` in it, which `/bin/mv` cannot send but a 9P peer can,
still walked past it into the same loss. The guard moved to
`ninep_abi::is_within`, which resolves the components the way the filesystems
do and compares names by the filesystem's own rule, with host tests in `make
test`. The same review found that "the filesystem's own rule" had been stated
twice, once in the guard and once in thirteen lookups, so each format got one
`names_match` that every lookup and the guard call. Linking that change failed:
slicing a `&str` by a runtime index pulled `core::fmt` into fsd, the PIE trap
the memory notes describe, and the guard went over to bytes. `mv` now names
the refusal (`cannot move /Docs to a subdirectory of itself`) where it said
`invalid name`. A case-only rename of a directory is still refused, not done:
`mv` cannot tell the destination is the source without the server saying so.

## FAT32 past its volume, by a link and then by a first cluster

The next item was FAT32's `next_cluster` following any link below end of
chain. The rig for it needed somewhere for a stray write to land that the host
could see, so `make test-fat-link` builds its own disk: the ESP, then a witness
partition of 0xFF bytes, then the ext2 root. Planted links into the witness,
with the bound removed, showed what the roadmap had predicted from the code:
an append wrote into the next partition, `rm` zeroed a FAT entry inside it in
both copies, and a read returned its bytes as the file's.

My first fix bounded the links a walk follows and not where a walk starts. The
review showed a damaged first cluster in a directory entry still reached the
disk through `rm`, `write_at` and the read, and that my change made one case
certain where it had been likely: `write_at` on such a head now always called
`extend_chain`, which wrote the head's FAT entry past the FAT. The fix that
held is at the three places a cluster number meets the disk, `cluster_to_lba`,
`fat_entry` and `write_fat_entry`, which refuse a cluster outside
`2..cluster_end`; no caller has a check to forget. `free_chain` frees nothing
for a first cluster outside the volume, so such a file can still be removed.
`cluster_end` is computed without overflow and capped below the bad-cluster
mark, but it is still the BPB's word and not the partition's, since fsd's
mount is not told the partition's length; that is on the roadmap. One run of
the rig reported FAT entry 1 corrupted in the second copy. It was not: the rig
read the first copy's entry, which moved the file position, in the same
expression that had just seeked to the second copy's. The reader shared with
`test-write-walk`, `scripts/fat32img.py`, now reads a copy by number.

## The `MOUNT` syscall answered anyone

`MOUNT` with `replace` set swaps the block device for a USB stick, and the
only thing between that and a swap under a mounted filesystem was the shell
asking fsd first. Any task could call it, an ordinary user included, though
fsd's `FSOP_MOUNT` is root-only. The kernel now answers it to the `CAP_BLOCK`
holder alone, as it does the `BLOCK_*` calls, and fsd's `FSOP_MOUNT` makes the
rescan itself, since fsd is the one task that knows whether anything is
mounted. The rig, `make test-mount-gate`, could not tell the boot disk from
the stick by name or by size at first (both 64 MiB, both FAT32, the same
partition table), so it attaches a copy of the stick 1 MiB longer. With the
gate removed an ordinary probe swapped the stick in under the mounted ESP,
`ls /` read the stick, and the rig's own `erase disk` then erased the stick,
not the disk it was meant for.

The review found the swap left fsd's "table rewritten" verdict from the old
disk standing for the new one, and that the rescan fired on any failure to
mount, a transient read error on a good disk included, which would put an
attached stick at `/` and the real disk out of reach. It now resets that state
and skips the rescan when the partition table would not read. A read error
inside a filesystem's probe still reads as "no filesystem"; that is on the
roadmap. The change to `architecture.md` and `manual.md` made `check-site`
flag their two published pages; neither said anything the change made untrue,
so they were re-stamped and not edited, and nothing new went live.

## An exFAT set's checksum, and the shape of a set

exFAT's `patch_stream_ext` checksummed at most 19 entries, the longest set
fsd builds, though the spec allows more (vendor entries after the name, which
cameras write). `make test-long-set` plants a 20-entry set and appends to it;
with the old sum `fsck_exfat` reports an incorrect checksum and offers to
delete the set. The review then found a fault one layer down: `walk_dir`
closed a set that was not contiguous, or that held a primary, so a patch could
write Stream fields into whatever slot followed the File. The walker now takes
a set only in the spec's shape, and a second boot of the rig plants two
misshapen sets and requires their slots unchanged. My first version of the
misshapen PRIM set would have passed under the old walker too, closing before
its name, so the old code would never have found it; I caught that before
running and planted it as the old walker would take it.

## A directory's slots walked once

The roadmap's measure for the free-slot scan was an estimate from the code,
about 15,000 reads for 100 files. Measured with QEMU's own counter it was
19,026 more sector reads for 100 files than for one. Each slot was found by
walking the directory's chain from its first cluster, and the scan read the
slot's sector once per slot. A `SlotCursor` steps forward, the scan holds the
sector it read, and a set is written and deleted once a sector: 4,686 reads,
and the directory's own sectors 4.3 passes a create where they were 19.0.
`make test-dir-scan` grades that. Its review found it graded only half the
change, so it now counts writes too (1.36 a file, from 3.24), and that the
cursor's saving cannot be graded at all: it is FAT lookups, which hit fsd's
one-sector FAT cache and never reach a disk counter. My first write bound, 3,
sat 8% under the old code's 3.24; it is 2.5.

## One lookup for a name, and a claim that was not true

The last item was exFAT's three walks that each matched a name to a set, with
every writer building a set's location from loose fields. `entry_in` is now
the one lookup and a set's place travels as a `SetAt`; the exact-count rigs
read and wrote the same sectors before and after, which is the evidence a
refactor can offer. I wrote, in the code and the CHANGELOG, that a change to
matching such as reading the volume's up-case table now landed in one
function. The review showed it did not: exFAT matched by FAT32's
`names_match`, while its NameHash up-cased by a separate `upcase`. Rather than
reword the claim, exFAT got its own `names_match` on `upcase`, so matching and
NameHash are one rule, and with exFAT's rule reduced to a byte compare
`test-mv-into` fails on exFAT.
