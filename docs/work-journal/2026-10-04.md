and its index row, and the two blind instruments of the evening in their

The capture had one difference from yesterday's: no keyboard behind the

So from here a boot that says `keyboard not available` is the expected
line, and the hub path is exercised only when he plugs one in.

## ERSTSZ and ERSTBA keep their RsvdP bits (#201), and the board says they were 0

The next roadmap item was the one #200's review had set aside: ERSTSZ and
ERSTBA written bare, zeroing RsvdP bits that Linux and U-Boot keep. Built on
`pi4/erst-rsvdp` as a read, a mask and an OR for each, the order from #200
untouched. The first version's commit and roadmap note said the bits "read
0 after HCRST on every controller seen", and the review asked the right
question of that sentence: seen where? Nothing in the tree had ever printed
them before the write; the only reads were in the timeout dump, after it.
So the review's fixes were mostly about evidence: one init line printing
the bits kept, the new values masked to their fields as Linux masks the
address (the first version left that to a comment about `Aligned64`), a
const assert that ERST is 64-byte aligned, mutated to fail before it was
trusted, and ERSTSZ in hex in the timeout dump. CRCR, CONFIG and USBCMD
have the same defect in the same function; they went on the roadmap with a
shared preserve helper, so this round kept one variable.

`test-usb-hub` counted 18 once in five runs, in a run whose output was not
kept; three captured runs gave 19. Noted on the roadmap to watch, not
explained.

Merged as #201 by Hans (the merge needed his hand: the session's permission
check refuses a merge it has only reviewed itself). On the board, staged
stick first and card last this time so the card could be compared byte for
byte with `build/esp`, which it matched: `RsvdP kept: ERSTSZ 0x0, ERSTBA
0x0`. The VL805 holds zeros there after the reset, as QEMU does, so the
change writes what the old code wrote, and now that is a line in a capture
rather than a sentence in a commit. A full session over serial, no fault.

## CRCR, CONFIG and USBCMD onto one helper (#202), and every bit 0 on the board

#201's review had named the rest of the set: CRCR, CONFIG and USBCMD, the
same bare writes in the same function. Built on `pi4/rsvdp-preserve` as one
pair of helpers, `write32_rsvdp`/`write64_rsvdp`, with ERSTSZ and ERSTBA
moved onto them. The masks were checked against Linux's `xhci.h` rather
than memory, which mattered for USBCMD: Linux calls 4:6 and 15:31 reserved
and says nothing of 12 and 13, and the 1.2 spec is recalled as defining
13:16. Only the bits both agree on are kept; 12:16 stay written 0, as
before, so no bit the firmware left set is carried over on a guess.

The first version said itself that no rig could fail on it, since QEMU
reads 0 in every RsvdP field. Its review took that seriously: the merge
became a pure `const fn` under const asserts, and two mutations of it
broke the build. It also moved the log line from after the ERSTBA and Run
writes to before every write (USBCMD's before the reset, all five after
it), since a write that hung the board would otherwise leave nothing.
Halting the controller before HCRST, which the spec asks for and Linux
does, went on the roadmap rather than into this change: it changes what
the controller sees, so it gets a round of its own.

Merged as #202 by Hans. On the board, the card matched `build/esp` byte for
byte, and every value read 0, USBCMD's even before the reset where the
firmware's state is: this change writes what the old code wrote on the
VL805. The boot reached the shell with the stick mounted; the session was
three empty prompts, nothing more.

## Is the controller running when it is reset? (#203) No.

#202's review had found that `init_inner` sets HCRST without halting the
controller first, which xHCI 5.4.1 forbids while HCHalted is 0 and which
Linux never does. Whether that mattered on the Pi depended on a fact
nobody had: what the firmware's hand-over leaves the controller doing. So
the first step was only to read it. Its review sharpened the reading
twice: take it before the CNR wait, so a timeout there could not swallow
it, and read HCH again with nothing between it and the HCRST write,
printing afterwards, since a serial line takes milliseconds and a
controller still halting could finish inside one. The observer was
mutated before it was trusted: with the controller started on QEMU just
before the read, both lines said it was running, and QEMU took the reset
of a running controller without complaint, which is exactly why only the
board could answer.

One `test-usb-hub` run was lost on the way, and not to the kernel: QEMU's
firmware stalled in its own USB boot and never loaded it, and the rig
reported five failures for a kernel that never ran. The roadmap now asks
for that case to be INCONCLUSIVE and counted; the review turned down the
first idea, a retry, since a retry until green hides a change that makes
the stall likelier.

The board's answer, on `7f39b6e`: halted. `R/S false`, `HCH true` as
handed over and at the write. What the firmware leaves are traces, not a
running controller: HSEE set in USBCMD, and EINT and a port change pending
in USBSTS, all cleared by the reset. So the halt step is spec form on this
board and stays on the roadmap as such, for other firmware and for a
re-init path.
