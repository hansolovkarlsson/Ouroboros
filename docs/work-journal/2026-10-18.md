## The cursors given a rig, then a narrower drop

The day began on the roadmap's NEXT item from the 17th: nothing checked that
`write_fat_entry` drops the read and write cursors, and a stale write cursor
writes one file's bytes into another's cluster. `make test-write-walk` and
`make test-spawn-reads` pass with the drop removed, since every read or write
sets its cursor again at its end. #318 added `/bin/CURSORPROBE` and `make
test-stale-cursor`: a file removed, its first cluster given to a new file on
another chain, then the new file read, overwritten or appended to where the
old cursor stood, every byte a pattern of file and offset. With either drop
removed from either filesystem the probe fails where it should. Its review
found the probe could not tell whether a stale case had been built at all: a
FAT32 free path that did not lower its hint made the probe pass every
sequence with nothing tested. So each sequence keeps its files, with
one-cluster witnesses either side of the removed one, and the rig reads their
chains off the disk to confirm the layout, reading through the volumes' holes. The write sequences need clusters of 1 KiB or less, so a
third partition, an exFAT of 512-byte clusters, carries them.

With the rig in, #319 narrowed the drop the roadmap had held back for it: a
FAT write drops the cursors only when the entry it replaces was a link, since
an allocation or a tail extension moves no cluster of any walk. A copy within
the exFAT root went from 867 FAT reads to 323, within the ESP from 5,048 to
3,333, and `test-write-walk` grades both exactly. `write-one` was added as the
sequence that fails a rule deciding on the value written rather than the
entry replaced, the one mistake the other three pass. The max review found
the one way the narrowed rule could keep a stale cursor, exFAT's
`ensure_chained` skipping a size-0 NoFatChain entry that names a cluster, and
found outside the diff that exFAT's `grow_dir` never raised a directory's
DataLength. That went on the roadmap as read in the code, not reproduced, and
became the rest of the day.

## A directory past its first cluster, and what fsd should do with one an older fsd grew

`make test-grow-dir` came first, with `/bin/DIRPROBE` making 100 files in a
directory and finding, listing and touching each. It reproduced the reported
bug, the 43rd file on 4 KiB clusters not found and `fsck_exfat` calling the
chain "too many clusters for its size", and a worse one nobody had reported:
in a directory macOS made, one NoFatChain cluster as it made `/etc` and
`/Users`, the free-slot scan was not bounded by the size either and wrote
entry sets into the clusters after it, `/man`'s directory and the new files'
own data. A probe sees only what fsd answers, so the rig compares every
cluster of the partition before and after the boot. The controls showed what
each part of the fix carries: without the size recorded, the directory grew
at every create until the volume was full and fsd lost its mount.

The first max review found that the fix's promise to bring an older fsd's
hidden entries back into view was the defect. A create's name check ran at
the old size, then growth revealed the hidden sets, and the create wrote a
second set under a name one of them carried. I repaired that by setting the
size to the chain in `dir_at`, before any write read the directory. The
second max review found that repair worse than the bug: only writes went
through `dir_at`, so a read still stopped at the old size, and `echo x >>`
of a hidden file read it as absent and then truncated it. On `main` the same
sequence had written a duplicate and kept the data. This was the "repair is
a change" postmortem lived out in one afternoon.

The redesign put one rule in the walker, `dir_extent`, used by every reader
and writer, built in a git worktree while the review was still reading the
branch. `test-write-walk` caught it twice on cost: a walk of the whole chain
before every read cost a FAT read per 2 KiB request (328 against 19), and
then the root's chain walked on every create cost one more (18 against 19).
Both went, the walk taken a cluster at a time and the root's only at growth.
The rule adopted clusters past the size while the bitmap held them
allocated, and the rig's own planted case found its last hole. A stale link
past OLD's size to a free cluster was cut only by OLD's first write, and
before that write the growth of other directories had already allocated
that cluster, so OLD took a cross-link into another directory. Reads cannot
cut a link. I put the choice to Hans with a recommendation and he took it:
refuse, as Linux does. fsd reads such a directory to its size and will not
create in it until a fsck repairs it, which drops the hidden files. Three
adoption designs had each cost more than they saved.

Five more reviews followed, three high and two medium, and each found less.
The refusal covered harmless writes (a `touch` of an existing file, an
overwrite), so it moved to the create itself. A size-0 entry's named cluster
was refused in three places and trusted in a fourth (an append wrote into
it), so the rule moved to where a set is read. Refused creates leaked what
they had allocated, so `create_entry` takes the decision as a required
parameter. Failures give back what they can safely give back, files are
freed and appended to only inside their size, and a link out of the heap
ends every chain. Several of my own checks could not fail the first time
and were caught by their controls. NAMED's "every cluster allocated" passed
under a cross-link, and the rig gained an ownership check. The `/man` check
passed when the freed cluster was reused in the same boot, so it now
compares bytes. A `free_data` control left the size cap in place. A dry run
imported the main tree's script, not the worktree's. In the final suite
`test-grow-dir` hung once, fsd silent between two allocations, and 30 runs
after it passed on an identical layout. It is on the roadmap as not shown to
be this branch. #320 merged as 6890bcc2 at 09:41 on the 19th, 34 commits,
the rig at 63 checks.
