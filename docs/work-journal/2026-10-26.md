# 2026-10-26

## Three of the standup's fixes, each with its review

The day opened with the closeout of the 25th and its branch merged (#351,
#350), then took the standup's list from the top. The first was exFAT's
cluster check (#352): every read and write of a cluster's sectors now goes
through one `sector_of`, told what the sectors are for, and the mount
records the root's whole chain as runs instead of its first cluster alone.
One step of it was wrong and was undone in the same branch: with
`sector_of` refusing the volume's own clusters, the link checks in
`file_step` and `write_at` looked redundant and were removed, but a walk
can take a link from the bitmap's own FAT entry before any sector is asked
for, and the LX and HX cases of the new VROOT boot showed it. The rig
itself took three tries to build: the image's root had deleted slots a
create reused before the growth the case needed, `rm /RX` freed more, and
the filler that was meant to take them miscounted names of one, two and
five slots. The high review found the table scan recording each extent as
it met it, so an up-case entry claiming the heap, found before the bitmap's
entry in the root's second cluster, made the mount answer an I/O error;
VLATER holds that now.

FAT32's long names (#353) went the way exFAT's had on the 21st: the walk
keeps UTF-16 units and renders them through `utf16.rs`, now shared by both
arms, and `put_lfn_chars` writes units where it wrote a UTF-8 byte to a unit.
The high review found U+FFFF, the unit an LFN entry pads with, accepted in a
name and so ending it early, and a run of LFN entries not started afresh at
an entry flagged the last. The rig needed the ESP's root grown on the host
before the names fit. `BPB_ExtFlags` (#354) followed: a volume with
mirroring off is read and written through its live FAT alone, where fsd
read FAT 0 and wrote every copy. The first rig set the flag on the ESP the
firmware boots, and OVMF then found no boot loader on it; the rig moved to
a disk it builds, booted from NVMe with the flagged volumes on virtio. The
medium review added a volume with mirroring off and FAT 0 live, the one
existing behaviour the fix changes.

Between the merges Hans asked where `gh pr merge` is allowed in the
settings. The rule was already there; what had been refused was one command
that pushed, created and merged a PR together, which the auto-mode
classifier read as a merge without review. Creating and merging are
separate calls since.

## The small ones, and a repair that destroyed what it guarded

The afternoon took the four small items. exFAT now says why it mounted a
volume read-only (#355), a healthy stick whose root grew in more than 64
interleaved steps being the case that mattered; VRUNS plants such a root.
A FAT32 short name holding an OEM code-page byte lists as `?` (#356). The
exFAT rigs' helpers moved into `exfatimg.py` (#358). The size-0 entry's
leaked cluster was left as a question for Hans: freeing it safely means a
walk of every directory on each such `rm`.

The fourth, a failed exFAT `mv` that left two sets over one file (#357),
is the day's lesson. The first version gave the new set back when a delete
failed and kept the replacing `mv`'s order, destination first, which the
review of 2026-10-24 had chosen so that a failure never left two files of
one name. Together they made a failed `mv -f` destroy its destination: the
destination's set deleted and its clusters freed, then the source's delete
failing, then the new set given back, leaving nothing under the name. The
rig checked exactly that outcome ("no U, U's cluster freed") and the
CHANGELOG called it "as before". The high review caught it. Three options
were laid out: source first, accepting two files of one name on a failure;
destination first with the undo only while the destination exists,
accepting the shared clusters back; or a full rollback, which works because
a delete only clears in-use bits and the clusters are freed after both. Hans
chose the rollback. A second review of it found no fault in the paths the
rig drives, and three in the paths where the rollback itself fails: a
destination that could not be put back had its clusters freed under entries
that might still name them, a create whose half-written set was cleared
still reported it written and leaked its clusters, and the rollback was
written twice with two different console lines.

The other reviews each found something too. #355's mount line broke
`test-volume-bound`'s BESIDE boot, which required `mount 2` on a read-only
exFAT to print nothing; the branch had not run that rig. #356's medium
review found control bytes and `/` still copied into a short name, an ESC
reaching the console and a `/` splitting the name as a path. #358's found
`Volume`'s FAT32 entries taken from the live copy while its `fat` offset and
chain rule were still FAT 0's.

## Four merges, one at a time

Hans asked whether all four could be merged together. Each had been tested
against main as it was, not against the others, so they went in one at a
time, main merged into the next branch and its rigs run on the combined
tree before its merge. Only the records conflicted for #355; #357 also met
#355's constant above `ROOT_RUNS` in `exfat.rs`; #358 met #355's VRUNS boot
in `test-long-set.py`, where pyflakes found two calls to the wrappers #358
had removed. Every rig passed on each combined tree. Two firmware stalls
came up in `test-long-set` along the way, VTWOFAT and RENAME, each passing
when run alone; with the two in the morning's `test-dir-scan` and
`test-write-walk` runs, every stall seen is still an exFAT boot.

Two slips of my own, both caught: a PR comment cited a commit range whose
first hash I had not looked up (corrected to the real ones), and an edit to
`CLAUDE.md` while a rig ran tripped the source stamp's guard, which refused
the boot as it should.
