# 2026-10-11

## The owner of the spawn staging

The day opened on the standup's second item, the debt step 4(d) of the
multi-core arc left on 2026-10-10: the kernel's spawn staging belonged to
no task. A spawn is fed in over many syscalls, a 512-byte chunk at a time
with a round trip to `fsd` between them, so a stager is blocked for most of
its spawn, and anything else that spawns meanwhile writes into the same
buffers. The shell and `netd`'s `cpu` are the two stagers today; a child
shell or a program that spawns would be a third. One core was enough for the
interleaving, two made it likelier, and the inventory's remedy, an array
per core, was wrong because a stager moves between cores between chunks.

The plan said "an owner, refused to a second stager until the first spawns
or dies", and that is what went in, with three decisions made reading the
code rather than the plan. First, the owner is a task identity, not a slot:
`live_occupant` already answers "is the task I remembered still there", so
an owner that died by a path that forgot to release is no owner, and the
staging heals at the next claim instead of refusing every spawn for the rest
of the boot. The explicit release in `end_task` is still there, so a dead
stager's environment latch does not wait for the next claim to be cleared.
Second, a stager that cannot finish has to be able to give the staging up,
and the shell does fail after its first chunk in ordinary ways: a file over
the staging bound, a read that fails mid-file, an argv that will not fit.
Without a release the boot shell would hold the staging until its own next
spawn and refuse `netd`'s `cpu` meanwhile. Rather than a new syscall, a
`SPAWN` with a total of 0 is the release: it was already refused as empty,
and `SPAWN` releases on every outcome, so "spawn nothing" means "I am done
with the staging" without a new verb, a new number in `sys.h` or a new
arm. Third, the new code took the error band's floor, as the three codes
before it did, and `FS_ERR_MIN` stepped down to `MAX-45` with its mirror in
`sys.h` and `FS_ERR_CLIENT` below it; the wire check pins the floor, which
is the kind of move it exists for.

The rig took more thought than the kernel. A refusal needs two tasks mid-spawn
at once, and the shell is blocked while a foreground program runs, so the
shell cannot be refused by a program it waits on. `exec` runs a program in
the background and returns the prompt, which is the whole rig: a probe that
claims the staging as a spawner does, one chunk, and then holds it without
spawning. While it holds, the shell's `echo` is refused with the code's
message and prints nothing; a second probe, started earlier and waiting
before it tries, is refused with the code itself and then claims once the
holder exits. A `kill` of a holder releases it, and a holder that abandons
with the `SPAWN` of 0 releases it while it is still alive, which the rig
tells from the order of the lines. The one timing the rig depends on is
that the checker's wait (six seconds) covers the typing of the holder's
command; everything else is ordered by lines the probes print.

## The high review of #268

Hans ran the high review on #268 and it returned seven findings. One was
correctness-grade and mine to be embarrassed by: with the staging owned per
task, `SPAWN`'s argv and cwd lengths were still the caller's word, capped
only to the buffer size, so a new owner that staged one chunk and asked for
a 512-byte argv handed its child the previous stager's argv bytes, and the
`release_staging` comment I had just written asserted the opposite. The
true-when-written trap in the hour it was written. The kernel now records
how much the owner staged (the end of its highest chunk, its argv length,
its cwd length, beside the env latch that already existed) and hands on no
more; a total past the staged end is `SPAWN_ERROR`, which `stageprobe over`
checks. Two findings were messages: `netd` told a remote user refused by a
busy staging "no such /bin program?", and the shell printed "path too long"
for a refused argv or cwd staging (that one older than today, but on a line
I touched). One was the rig's own check that could not fail when the
holder's exiting line was missing. One was an em dash I re-emitted in a
rewritten table row. One was the duplicated owner reading in the two
kernel checks, now one `staging_state`. The seventh asked for a wait on the
staging instead of a refusal, since a long `cpu` spawn refuses every shell
command for seconds. Held to the plan's refusal and recorded in the plan:
a wait inside a staging syscall needs a wake and an interrupt, and the
refusal is honest and visible; the wait is the follow-up if the refusal
shows up in use.

## `/proc/cpus`

Hans asked whether a command shows how many cores are active. None did: the
count was in the boot log and in `coreprobe`'s report, a two-second probe
built for the rig. Two items went on the roadmap (#269), `/proc/cpus` and
`ps` naming the core a running task is on, and the first was built the same
afternoon. `fsd`'s `/proc` had served only slot numbers, so `cpus` is its
first named top-level entry, parsed before the digits and refused as a
directory. The content is one line from `CORE_INFO_UP`, asked on every read
so the file says what the kernel says now, which is the whole point of a
synthetic tree. The rig names its own `-smp` for each of two boots rather
than reading the `SMP` environment, since the check is the pair: 1 on one
core, 4 on four.

## `ps` names the core

The second item from the morning's question, built the same day. The
kernel had the answer all along in the per-core `CURRENT` table, which the
remote kill already read through `running_core`; what was missing was a way
to ask. A fourth `CORE_INFO` operation takes the slot and answers the core
or a "no core" sentinel, and `ps` prints `running on core N` for a runnable
task a core is executing at that instant, keeping `runnable` for one waiting
its turn. The shell itself shows as running on the boot core while it runs
`ps`, which is true and a small check of its own. `/proc/<n>/core` gives the
same answer by file, `none` when no core is, and the idle slot always reads
`none` because every idle core runs it.

The rig went into `test-smp.py` as the plan said, as one more scene after
the foreground hold: `exec /bin/coreprobe hold` in the background, `ps`,
`mount -p /proc` and `cat /proc/<n>/core`, then `kill`. The plan's "done
when" wanted `ps` to name the very core the probe's own line named, and the
rig does not require that, for a reason the file already recorded for the
kill: a program moves between secondaries whenever it blocks, and the
probe's "holding" line is itself a call to the console server. So the rig
requires a secondary on four cores and `runnable` on one, where the shell
running `ps` is the task on the core. Reading the plan against the code
before building, again, and the plan gave way again.

## The high review of #271, twice

The first high review found ten things, the worst a guard: `ps` took any
answer but the "no core" sentinel as a core index, so a kernel without the
new operation would have printed every runnable task as running on core
eighteen quintillion, while `fsd` guarded the same answer properly. Two
readers of one operation with two tests is how they come to disagree; the
test is now one function in the ABI, `core_of`, and both call it. The rest
were a stale sentence I had left standing in the very row I rewrote, and
three weaknesses in the rig: a hardcoded last slot, a silent fallback to a
slot nobody named, and a read of one instant graded as if it were a fact.

The second review, on the fixes, found what I should have found myself: the
keyboard-chain rig grades `ps` with `task 6: runnable` for the very shell
that is running `ps`, and that shell now prints `running on core 0`. Four of
its six recipes were red, and nothing in `make test` says so, because the
QEMU rigs are run by hand when their subsystem changes and I had changed
the output of `ps` without asking which rigs read it. One `grep runnable
scripts/` would have answered. The patterns now read `running on core`, and
the roadmap note I had written an hour earlier, that a `running` state in
`TASK_STATE` was avoided because rigs read `runnable`, had been true of a
change I made anyway by another route. The same review also caught that a
core which halted alone keeps its current-task entry, so a task stranded
on it would have read as running there for the rest of the boot; the new
operation counts only a core that is up, and the kill path's view of the
same entry is the open item it already was.
