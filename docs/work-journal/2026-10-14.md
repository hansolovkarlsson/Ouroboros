## Step 5a: the stick, and a file that stands in for it

The design question that mattered was how to test a tool whose whole job is
to overwrite a physical disk. `hdiutil attach -imagekey
diskimage-class=CRawDiskImage -nomount` gives a raw image file a
`/dev/diskN` the user owns, so `bootstick.py` takes a file and attaches it
itself, and from there the file and a real stick go down the same code: the
guard, the write through the raw node, the read-back. Only `sudo dd`, for a
device the user cannot open, is out of any rig's reach, and the docs say
so. The old root is read with e2fsprogs' `debugfs` in place (`?offset=` on
the image or the device), never mounted: `ls -p` gives mode, owner and
group per line, and each file is fetched with `dump`, because `rdump` tried
to `chown` as the user, failed, and silently stopped partway through
`/Users`.

Two of the first version's rules changed on evidence before the PR. A file
deleted from a home on the stick came back from the image on the next
re-stage, because the overlay let the image's entries stand where the old
disk had none; homes are now replaced whole, which is what `make stick`
does, and `/etc` stays file by file so that a file a newer tree introduces
still arrives. And `CARRY=0` first reset the boot counter along with the
accounts. The counter is the one thing a re-stage must never roll back
(`bootid.rs`: a machine whose variable store does not persist would hand out
a counter twice), so `CARRY=0` now resets `/etc` and `/Users` and nothing
else.

The rig's first mutation pass graded nothing: every boot was refused by the
stale-image guard, because `bootstick.py` is in the tree's source hash and a
mutated writer reads as a stale image. The image those runs boot is built
from the clean tree and contains no line of the writer, so the mutation runs
pass `OUROBOROS_STALE_OK=1`, and the reason is written into the rig's
docstring and the plan. One rig bug of my own: the `CARRY=0` boot waited for
"Login incorrect" and then for a new `login:`, which had arrived in the same
burst and been consumed by the first wait. Four mutations, each failing at
its check, and #293 went up.

The high review found ten things. The one that should not have needed a
reviewer: `homes_from_passwd` read Unix's seven-field passwd, while this
project's is `name:uid:gid:home`, and the self-test passed because I had
written its input in the same wrong format. Every home carried from a `make
stick` stick would have gone to root. The others: the old root's
`/etc/srcid` carried beside a newer build's ESP (two stamps, so the
stale-image guard would refuse the stick); a Linux stick's whole 30 GB root
copied before being refused; a written `esp.img`'s counter not carried; the
tail zeroing stopping short of the last LBA on a disk that is not a whole
number of MiB; the Mac's own disk unrecognised behind an APFS container; the
only copy of the old `/etc` deleted with the temporary directory if the write
failed; a tree that failed to list taken as absent; a `dd` copy of
`disk.img` keeping the signature every such copy shares; and three copies
of the layout. All taken, five new rig checks, each failing with its fix
reverted.

## Step 5b: the Pi's firmware, and what counted as firmware

`PI=1` puts the pinned pftf release at the root of partition 1, inside a
copy of `esp.img` written through `hdiutil` (5 MB of tree and 7 MB of
firmware in 64 MiB). The pin moved to `scripts/pftf.env` so the card and
the stick cannot get different releases. On a re-stage the stick's own
firmware is carried whole, `RPI_EFI.fd` with it, since that file is both
the firmware and the store of its settings and every UEFI variable: this is
`make sdcard`'s "installed once", applied to a disk that is rewritten
whole. `FIRMWARE=1` reinstalls and keeps `config.txt`, where the UART
overlay is set by hand.

I defined "the firmware" as everything at the old ESP's root that
`build/esp` does not own. The high review of #294 found what that included:
`\NOXHCI` and the other boot flags, which are set by hand for one boot to
bisect a hang and would have been carried onto every later kernel. Only the
release's own names (the zip's top level, matched without case) and
`config.txt` are carried now, and anything left behind is named. The same
review found a failed `hdiutil detach` ignored before the copy's bytes were
read, an ESP that would not mount making a stick impossible to re-stage at
all (`PI=0` included, which is exactly the repair), a download failure
reported as "is the ESP full?", `PI=true` accepted as "unset", a check
called "file for file" that compared four of fifteen files, and `PI` and
`FIRMWARE` taken from the shell's environment, where a `FIRMWARE=1` left
over from a `make sdcard` session would reset a Pi stick's settings. The
fetch became one script, `scripts/pftf.sh`, for `sdcard.sh` and
`bootstick.py` alike. One mutation, always refusing an unmountable ESP,
first showed up as a rig crash rather than a failed check: the rig's own
mount of the still-broken ESP raised. The check now grades that case.

## The root by its type

The open question step 4 had left: `fsd` took the first partition beside the
ESP that mounted, so an exFAT data partition before the root became `/`.
`partition::discover` now records whether each entry's type marks a root
(MBR 0x83; on GPT only the Discoverable Partitions AArch64 root GUID, since
the generic Linux GUID marks data partitions too), and a typed root shuts
the untyped partitions out as candidates. A disk with no typed root mounts
as before, which `espexfat.img` needs. One mutation run was refused by the
stale-image guard because I edited `CLAUDE.md`, which is in the source
hash, while its image was being built; the guard was right, and the docs
were committed before the run was repeated.

The high review of #295 found the rule held only while the kernel named the
boot partition. With it unknown (a fallback disk, a stick taken late, or
after `partition` or `erase`), the untyped partitions followed a damaged
typed root as candidates, so the ESP or a data partition came up as a
writable `/` with no line, and `format` would write over the first that
probed. My rig had tested only the case I had pictured, with the boot
partition known. `root_order` now says how many of its entries are the
root's candidates, anything past them is a read-only fallback whether the
boot partition is known or not, and a new boot reaches the unknown case by
booting `esp.img` from NVMe, which the kernel cannot drive, so the damaged
disk goes in as virtio's fallback.

The review's third finding was a design trade, not a defect: 0x83 is the
generic Linux type, so on a disk made elsewhere an ext4 data partition
typed 0x83 that `fsd` cannot read would become the only root candidate.
Yesterday's carried lesson said what to do with that, and it was done: the
trade went to Hans as three answers with their costs, he chose to keep
0x83, and it went into the plan as settled. It took one question.

## One copy of the partition tables

The roadmap's follow-up from #287: the kernel's boot-disk matcher and `fsd`'s
partition reader each parsed MBR and GPT, both CRCs and the backup header,
each with its own CRC-32, and only QEMU boots reached either. `parttable`
is a pure crate taking a read-sector closure, with the MBR entry reader, the
GPT copy validator, the partition list with its root types, and the matcher
answering yes, no or unreadable (D6). `bootdisk.rs` went from 437 lines to
194. Its nineteen host tests, which reach a hybrid MBR, a corrupt primary,
headers built to overflow and a read failing on one copy and not the other,
all passed on the first run, so six mutations went in before anything else,
and each failed them.

The review of #296 found nine things. The behavioural ones: `discover` failed
the whole scan when the kernel did not answer the disk's size, where the old
code lost only the backup header; every failed read came back as an I/O
error, losing "no device"; and `mbr_entry` masked its index, so a partition
number past four read another entry. And one test the review wrote the
mutation for: no test covered a GPT copy unreadable partway through its
array, so `discover` taking such a copy as found would have passed. All
taken; three new tests, 226 host tests in all.
