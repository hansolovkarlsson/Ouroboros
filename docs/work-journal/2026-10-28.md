# 2026-10-28

## The read-only gate on every tree, and what `O_CREAT` changes

The standup's first item was a small one. fsd's read-only verb gate,
`refused_read_only`, refused every change only on tree 0 mounted read-only as
D5's fallback; a volume exFAT mounted read-only was refused inside the arm, at
its disk gate. The gate now asks every tree's `read_only()`, with the arm's
gate kept as the second line (#364). The controls said what that costs: with
exFAT's disk gate and every early `writable()` removed, `test-long-set` and
`test-volume-bound BESIDE` still pass, and with the new arm of the verb gate
removed as well, 11 checks fail. So from today no boot reaches the disk gate,
and a change to it alone is graded by nothing. That went on the roadmap rather
than into a claim.

The high review found the real question. `mutates` counted every `NP_OPEN`
with `OPEN_CREATE` as a change, so `O_RDONLY|O_CREAT` of a file that exists was
refused EROFS. POSIX gives EROFS for `O_CREAT` only "if the file does not
exist", and the bug was older than the PR: it had been true on tree 0's
fallback since the gate was written. `/proc`, a synthetic arm that answered no
`read_only()`, was outside the gate too. Hans split the ten findings: seven
fixed, one to the roadmap, two declined. `/bin/CCREAT` was written to open a
path that way, and two rigs ran it on an existing file and a missing one.

The first medium review found that I had made the rule two rules. The create
was refused by a second check inside `NP_OPEN`, placed after the fid table's
checks, while `check_access`, the fid's write check and the host peer still
took `O_CREAT` as a write. I had named that inconsistency before the review
and recommended fixing it first; the review confirmed it, and the fix became
`ninep_abi::open_changes(flags, exists)`, with `exists` a required parameter
so no caller can decide a create without asking. One consequence was
load-bearing: once `check_access` lets a user open root's file with
`O_RDONLY|O_CREAT`, only the fid's own rule (a write needs `OPEN_WRITE`)
stands between that fd and a write. Control C2, the old fid rule put back,
wrote one byte through it. `test-cerrno`'s `user` boot now checks it.

The second medium review found the existence asked three times, a failed stat
counted as missing in one place and not another, and the gate answering a
missing name before `check_access`, so a user who could not search a
directory could learn which names were in it. One stat an open now, `Found`,
read by `check_access`, the gate and the handler, and the gate moved after
`check_access`, root still refused because the gate has no rule for root. In
the same round I moved the refusal of an open with no access mode into the
handler. The third medium review found that this was the same leak by another
door: `OPEN_CREATE` alone answered FS_ERROR from the handler for an existing
name and FS_ERR_PERM from `check_access` for a missing one. The refusal moved
to the top of `NP_OPEN`, before anything that can tell the two apart. It was
my repair of the second round that the third round repaired, which is the
spine of `repairing-the-repairs-postmortem.md` again.

Three of the round's fixes are reached by no boot: the leak (libc always
sends an access mode, and no read-only tree enforces modes), the single stat
(a cost, not an answer) and the ENOTDIR for a parent that is a file (FAT32's
stat answers the path itself first, so the new branch never runs on the
fallback). The last was found by a control that could not fail, and is
recorded with the day's other blind instruments. I recommended no fourth
medium review; Hans ran a low one, whose first run, with no target, reviewed
the empty working tree and answered "(none)". Run against #364, it found
nothing, and Hans merged.

Two findings were declined with reasons Hans had already settled: a write
through a read-only fid answers FS_ERR_PERM on the wire, which libc renames
EBADF (the #220 design), and `/proc` answering EROFS for a missing entry's
`rm`, which is the gate covering it as the high review asked. Two went to the
roadmap: libc drops `O_EXCL`, so the lockfile idiom opens an existing lock on
every tree, and fsd opens a directory as a fid where the host peer refuses it.

`test-long-set` and `test-boot-partition` stalled in the firmware more often
than usual: one boot in each of six runs, a different boot each time
(vupcase, vlater, vmeet, gpt, disk-format, disk-usb), and no check failed in
any of them.

## `O_CREAT|O_EXCL`, and a skip that outlived its refusal

After the closeout Hans took the next item, the one the morning's #364 had
put on the roadmap: libc dropped `O_EXCL`, and the wire had no flag for it,
so an exclusive create of an existing file opened it and a lockfile's maker
believed it had the lock (#367). The flag is `OPEN_EXCL` (16), in ninep-abi,
`sys.h` and the host server peer; libc sends it beside `O_CREAT` only. The
client peer sends no create and names nothing. The question worth the time
was where fsd answers EEXIST. POSIX and Linux answer it before the file's own
mode, so a user gets EEXIST for `/etc/shadow`, and before EROFS, which is for
a file the open would make. Yesterday's lesson was on hand. Only the
malformed requests answer before it, and none by the name's existence.

My first build split the rule across two places. Inside `check_access`, an
exclusive open of an existing name skipped the file's mode and asked only
the ancestor search. A block after `check_access` then answered EEXIST. The
rigs passed, and three of the four controls failed as they should. The
fourth was the one that mattered. With only the EEXIST block removed,
test-cerrno's `user` opened `/etc/shadow` `O_WRONLY|O_CREAT|O_EXCL` and
wrote a byte to it. The skip had been safe only while the answer two screens
below it stood. The second commit made the decision whole, one function,
`exists_answer`, before an unchanged `check_access`. Removed now, it leaves
EACCES and no write. The control of the moved answer did not run the first
time: the build's source stamp refused, because the tree changed while it
built. Rerun, it failed five checks in test-long-set's read-only boots, each
VG answered EROFS.

The host peer had its own divergence beside the change. It asked for an
access mode only after its read-only refusal, so `OPEN_CREATE` alone of a
missing file answered read-only there and FS_ERROR from fsd. It asks first
now, as fsd does.

Hans ran a high review. Two findings were fixed. Unknown open flags were
ignored, so the next new flag could fail the same silent way: ninep-abi's
`OPEN_FLAGS` now bounds them and fsd and the peer refuse the rest. And
`exists_answer` had copied `check_access`'s preamble and stat rule, where it
can ask `check_access` for `NP_STAT` on the same path. A peer running an
older fsd still ignores `OPEN_EXCL`, and no change here reaches it. Two were
declined: the root statted twice is `check_access`'s own cost, and `..`
answering EACCES is fsd's rule for every verb. Three refusals stay graded by
no boot, the search check and the two flag refusals libc never sends; they
are on the roadmap. Hans merged it once the rigs passed on the final tree.
