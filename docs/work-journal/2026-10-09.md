## The stale reply: what the code actually did

The roadmap described the bug as a late reply landing in the boot shell's
mailbox and being taken by its next call. Reading `tasks.rs` before laying
out the two fixes the roadmap named showed the mechanism was different: no
server holds a send right to slot 0, so a late reply never reached the
mailbox at all. It got in by the reply exemption in `may_send` ("the caller
is blocked calling me"), which a late reply passes whenever the shell has
already moved on to its next call to the same server. That call took the
old answer, and its own answer was then refused. The same reading found a
second consequence nobody had listed: `SAFECOPY` checked the same condition,
so a server still working on the interrupted request could copy into the
buffer the shell had granted for the next one.

## Three designs, four reviews (#244)

The first design was the roadmap's first shape: a call's reply wait ignores
the interrupt, so there is never a late reply. I recommended it as a tenth
the size of the other, and Hans chose it. Its rig needed three tries before
its second control could fail: the read-ahead it was meant to guard survived
being removed when typed on the serial line, because QEMU holds a serial
byte until the guest reads it, and again with six keys on the USB keyboard,
because QEMU queues sixteen events; seventeen keys overflowed it. The first
high review then found what the design cost. A `cpu` whose remote command
never stops printing held the console for good, since netd answers a run
only at its end or after thirty seconds of silence and every line resets
that clock. A Ctrl+C typed while a program loaded, now queued as a byte,
reached the program as a key. The review's own counter-proposal, counting
abandoned calls and dropping the next reply, was wrong for netd, which
answers one caller's requests out of order.

The second design kept every wait interruptible and instead recorded the
abandoned call, made the caller's next call to that server wait for the old
answer before sending, and restarted the call from its `svc` by rewinding
the saved PC. Its rig's first ordering let the "not recorded" control pass,
because the late answer the next call took was identical to its own; the
steps were reordered so the two answers differ. One run hung, and six debug
runs found why: I had run the script directly against an image still holding
the "not dropped" mutant, which `git checkout` had reverted in the source but
nothing had rebuilt. The second review found the drain's cost: after
interrupting a stuck `cpu`, every later call to netd waited behind it,
logout's key drop among them, and a Ctrl+C there left the user's cluster key
held. Its altitude finding said what both reviews had been circling: the
kernel could not tell which call a reply answered.

The third design gave it that. A server reads the request's call handle with
`SENDER_CALL` (74) and answers with `MSG_REPLY` (73), which the kernel
delivers only while the caller is still in that call; `SAFECOPY` takes the
same handle and the reply exemption is gone. The first plan was to fold the
call number into `SENDER_TASK`'s identity, dropped when netd's held-key table
turned out to compare that identity across calls. The rig needed a second
slow peer: with one, the next call queued behind the held one on the peer's
single connection and ran into netd's five-second deadline, a failure of the
setup and not the kernel. The third review found the call number checked only
at `MSG_REPLY`'s gate, while a `MSG_SEND` from the server could still complete
a waiting call; the fix removed the filtered receive outright, so a call's
wait now takes nothing but the reply naming it. It also moved `REPLY_STALE`
into the error band by the band's own rule and had fsd free the fid of an
open nobody heard. The fourth review found the kernel's path correct and left
one netd leak, a `/net/tcp/clone` connection nobody heard of, and stale
comments, the worst of them telling a server to ack the supervisor the way the
kernel now refuses. A low review found nothing, and #244 merged as `00aec31`.
