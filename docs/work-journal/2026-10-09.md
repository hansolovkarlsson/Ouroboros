## The stale reply: what the code actually did

The roadmap described the bug as a late reply landing in the boot shell's
mailbox and being taken by its next call. Reading `tasks.rs` before laying
out the two fixes the roadmap named showed the mechanism was different: no
server holds a send right to slot 0, so a late reply never reached the
mailbox at all. It got in by the reply exemption in `may_send` ("the caller
is blocked calling me"), which a late reply passes whenever the shell has
already moved on to its next call to the same server. That call took the
old answer, and its own answer was then refused. The same reading found a
second consequence nobody had listed: `SAFECOPY` checked the same condition,
so a server still working on the interrupted request could copy into the
buffer the shell had granted for the next one.

## Three designs, four reviews (#244)

The first design was the roadmap's first shape: a call's reply wait ignores
the interrupt, so there is never a late reply. I recommended it as a tenth
the size of the other, and Hans chose it. Its rig needed three tries before
its second control could fail: the read-ahead it was meant to guard survived
being removed when typed on the serial line, because QEMU holds a serial
byte until the guest reads it, and again with six keys on the USB keyboard,
because QEMU queues sixteen events; seventeen keys overflowed it. The first
high review then found what the design cost. A `cpu` whose remote command
never stops printing held the console for good, since netd answers a run
only at its end or after thirty seconds of silence and every line resets
that clock. A Ctrl+C typed while a program loaded, now queued as a byte,
reached the program as a key. The review's own counter-proposal, counting
abandoned calls and dropping the next reply, was wrong for netd, which
answers one caller's requests out of order.

The second design kept every wait interruptible and instead recorded the
abandoned call, made the caller's next call to that server wait for the old
answer before sending, and restarted the call from its `svc` by rewinding
the saved PC. Its rig's first ordering let the "not recorded" control pass,
because the late answer the next call took was identical to its own; the
steps were reordered so the two answers differ. One run hung, and six debug
runs found why: I had run the script directly against an image still holding
the "not dropped" mutant, which `git checkout` had reverted in the source but
nothing had rebuilt. The second review found the drain's cost: after
interrupting a stuck `cpu`, every later call to netd waited behind it,
logout's key drop among them, and a Ctrl+C there left the user's cluster key
held. Its altitude finding said what both reviews had been circling: the
kernel could not tell which call a reply answered.

The third design gave it that. A server reads the request's call handle with
`SENDER_CALL` (74) and answers with `MSG_REPLY` (73), which the kernel
delivers only while the caller is still in that call; `SAFECOPY` takes the
same handle and the reply exemption is gone. The first plan was to fold the
call number into `SENDER_TASK`'s identity, dropped when netd's held-key table
turned out to compare that identity across calls. The rig needed a second
slow peer: with one, the next call queued behind the held one on the peer's
single connection and ran into netd's five-second deadline, a failure of the
setup and not the kernel. The third review found the call number checked only
at `MSG_REPLY`'s gate, while a `MSG_SEND` from the server could still complete
a waiting call; the fix removed the filtered receive outright, so a call's
wait now takes nothing but the reply naming it. It also moved `REPLY_STALE`
into the error band by the band's own rule and had fsd free the fid of an
open nobody heard. The fourth review found the kernel's path correct and left
one netd leak, a `/net/tcp/clone` connection nobody heard of, and stale
comments, the worst of them telling a server to ack the supervisor the way the
kernel now refuses. A low review found nothing, and #244 merged as `00aec31`.

## After the closeout: an empty inbox, and a guard that compares contents (#246, #247)

The closeout above went in as #245. The afternoon began with a handoff triage
that found nothing to triage: the inbox was empty and all five notes
Ouroboros had sent were `done` in DevTools. Its one yield was two stale paths
in this project's own records, which still named the Ctrl-C item 4 note
where it had been before DevTools closed it (#246).

Then the standup's first item, the staleness guard that let the morning's rig
boot the reverted mutant. The rigs compared the image's modification time
with a binary's, and a reverted mutation defeats that by construction: the
mutant's binaries and image are newer than anything compared. The guard that
replaced it (#247, `scripts/srcid.py`) records content instead. `make esp`
stages `\EFI\ORBS\SRCID.TXT`, the git tree id of the working tree, and
`drive-qemu.py`'s `Guest`, which every Python rig and both drivers boot
through, reads it from the image's raw bytes and refuses a mismatch. The
first placement was a stamp file beside the image, given up before it was
built when `make images-2vm` turned out to stage the ESP twice (the first
node's image would have read as older than the stamp); inside the ESP it
travels into every image and every copy a rig makes. The morning's trap was
reproduced before anything else was claimed: a mutation in `timer.rs`, `make
image`, `git checkout`, and the new check refused where the old one passed
(the kernel binary 13:11:33, the image 13:11:50).

Hans ran a high review, and it found nine things, four of them in the new
guard's own reach. It crashed `test-early-fault` and `test-el1-drop` before
QEMU started, because those rigs boot an ESP directory through vvfat and
pass a placeholder path that does not exist; I had confirmed the guard on
`test-heap`, a rig of the shape I had in mind. It hashed the tree only at
the end of the build, so an edit made while the programs compiled would have
been stamped as their source. `run-guest.sh` starts QEMU itself and never
asked, while the docs said every boot did. And the module doc said an image
whose data partition came from an older ESP was refused, when the ext2 and
exFAT payloads did not carry the stamp at all. Two more were of another kind:
it wrote git objects into DevTools's repository, against the rule that a
project changes only its own tree, and it rehashed per boot, so an edit
during a multi-boot rig would have aborted it part way. All were fixed in
the same PR: `stamp_from` for a vvfat rig, a hash before and after the build
with a difference failing it, `run-guest.sh` asking (exit 95), the stamp
copied into both payloads as `/etc/srcid`, DevTools's compiled directories
hashed read only, and one hash per process. Recorded as instruments in
[`blind-instruments-postmortem.md`](../postmortems/blind-instruments-postmortem.md).

## Input dropped without a word (#248, #250)

Hans asked which of the open items were easiest, and then for the first two.
Tab on the USB keyboard was one arm in `keycode_to_ascii` (HID 0x2b to 9), so
filename completion now works from a Parallels or Pi keyboard; Escape stays
unmapped, its decision still open. The shell's sixteen-word cut had been
copied into three places that each built an argv and stopped at `MAX_ARGS`;
they now share `split_argv`, which refuses, and a pipeline is checked before
any stage is spawned. `test-nav-keys` presses Tab through readkey and
completes `/include/el`; `test-cargs` types seventeen words three ways; both
fail with their fix removed. One consequence was named in the PR rather than
left to be found: words are counted after glob expansion, so `echo *` on a
large directory is refused where it used to print fifteen names.

Asked what came next, I said that a glob past the kernel's 512-byte argument
store might be cut silently, and recommended checking it. Reading the code
first corrected me: `stage_argv` did refuse it, but through the same `Err(0)`
as a path that does not resolve, so the shell said "not found" or "path too
long" for a program that existed. Its doc comment called the case
"unreachable with a 128-byte input line", written on 2026-08-22, five days
before globbing made the line up to 1024 bytes
([`true-when-written-postmortem.md`](../postmortems/true-when-written-postmortem.md)).
#250 counts the bytes in `split_argv` from the same definition `stage_argv`
uses, so the two cannot disagree on the limit, and says `arguments too long`.
Its rig makes six files sized so that a glob over them stages exactly 512
bytes (and sums the printed argv to prove it), then one byte more; the
off-by-one control (`>=` for `>`) fails the boundary case.

#249 finished the guard's work: the five rigs' time comparisons are gone, the
three shell rigs asking `srcid.py require` before their boot-retry loops,
which would otherwise have read the refusal as a failed boot and retried it.
It also brought `docs/README.md`'s entry for the blind-instruments postmortem
up from 2026-09-07 to today; a subagent drafted it from the twenty-five later
sections, and its derived total of 119 cases was left out because the
postmortem states none.
