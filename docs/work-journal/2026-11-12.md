## A run ends when its command has (#447)

The plan for the empty message was to mark the run as ending and collect
the command without blocking. Writing it, the message stopped mattering.
What ends a run is that its command has ended, and that is a fact the
kernel holds: the slot is empty, or another task's, or a zombie. So the run
is ended on the state, asked once a pass after the mailbox is drained, and
the message ends nothing. That closed a second defect I had not listed. A
command that never sends the message, killed on the executing machine or
faulted, was never collected, and its caller waited for good on a
connection the idle reap exempted. The rig's new round is that case.

The one care in it is order. A command can exit with output still queued,
so which commands have ended is asked first, the mailbox is drained again,
and only then are they collected. `KILL_ID` does the collecting: it acts on
an identity or not at all, so the two reads before it need not be atomic.
It reaps a zombie with no "killed" line, which I added when I saw that every
ordinary run would otherwise have printed one, and the orphan rig counts
those lines.

## A restarted server's children (#448)

The kernel already kept what was needed. Every task's parent is recorded by
identity, and a slot's generation stands until the slot is filled, so the
server just torn down can still be named after its teardown. The rule went
into `supervisor::restart`, the one function all three teardown paths call.

The case I had to think about was a child that is the task the kernel is
about to return into, which cannot be torn down from under its own `eret`.
It is marked the way another core's kill marks a task, and ended at this
core's next entry. The rig took all three paths between its two runs: ended
at once, marked on one core, ended by its own core on four.

No request makes the shipped `netd` fault or spin, so the rig needed a way
in. I followed `fsd`'s disk-gate build: a cargo feature, built apart, never
staged by `esp`, that faults on a ping of one address and spins on another.

## The keepalive, and what a capture showed (#449)

The first run of the new rig failed in the half I expected to be easy. With
node B alive, node A's command was ended inside forty-five seconds. I took
that for my reap firing on a live caller and went looking for why the dial
side had not answered the probes. It had not answered because nothing in it
answers one, which I fixed, and the rig failed the same way.

The capture said why. Nine copies of the run's request, half a second
apart, and no acknowledgement from the export; then silence from node B.
The export acknowledges a request with the first segment of its reply, and
a run's reply is held until the command ends. Node B's dial side
retransmits eight times and closes. So on `main`, any run from another node
that took longer than about four and a half seconds was told "cpu: remote
run failed" and left its command running. I built `main` and measured it
before writing that down: 5.9 seconds, and `recv` still in node A's `ps`.
No rig had run a slow command between two guests, and the host clients
retransmit for minutes.

That reframed the PR. The ledger's defect, the silent caller, was real, and
behind it sat a wider one that every slow command between two nodes hit.
The fix is one bare ACK.

I also had to give up a check I wanted. A live guest caller cannot be shown
to keep its run for forty-five seconds, because a dispatching `netd` gives
a run up after thirty seconds without output, by a decision already on
record, and a run's output comes only at its end. So the rig reads the
probes and their answers from the capture, and kills node B before its own
deadline.

Hans declined the merge and ran a review, and it found two things that
mattered. One lost ACK brought the whole failure back, since the request's
acknowledgement was sent once; data sent again is acknowledged again now, on
both sides. And my statement that a dispatcher giving a run up "closes with
no FIN and no RST" was `main`'s behaviour, not the branch's: with the
request acknowledged it sends a FIN, which I then measured. The review's
third point was that `netd`'s blocking waits can swallow a probe's answer.
I added a rule for it and a rig round to grade the rule, ran the round's
control, and the round passed with the rule taken out. The round is gone.
The rule stays, on reading alone, and says so wherever it is described.
