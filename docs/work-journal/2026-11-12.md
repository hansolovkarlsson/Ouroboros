## A run ends when its command has (#447)

The plan for the empty message was to mark the run as ending and collect
the command without blocking. Writing it, the message stopped mattering.
What ends a run is that its command has ended, and that is a fact the
kernel holds: the slot is empty, or another task's, or a zombie. So the run
is ended on the state, asked once a pass after the mailbox is drained, and
the message ends nothing. That closed a second defect I had not listed. A
command that never sends the message, killed on the executing machine or
faulted, was never collected, and its caller waited for good on a
connection the idle reap exempted. The rig's new round is that case.

The one care in it is order. A command can exit with output still queued,
so which commands have ended is asked first, the mailbox is drained again,
and only then are they collected. `KILL_ID` does the collecting: it acts on
an identity or not at all, so the two reads before it need not be atomic.
It reaps a zombie with no "killed" line, which I added when I saw that every
ordinary run would otherwise have printed one, and the orphan rig counts
those lines.

## A restarted server's children (#448)

The kernel already kept what was needed. Every task's parent is recorded by
identity, and a slot's generation stands until the slot is filled, so the
server just torn down can still be named after its teardown. The rule went
into `supervisor::restart`, the one function all three teardown paths call.

The case I had to think about was a child that is the task the kernel is
about to return into, which cannot be torn down from under its own `eret`.
It is marked the way another core's kill marks a task, and ended at this
core's next entry. The rig took all three paths between its two runs: ended
at once, marked on one core, ended by its own core on four.

No request makes the shipped `netd` fault or spin, so the rig needed a way
in. I followed `fsd`'s disk-gate build: a cargo feature, built apart, never
staged by `esp`, that faults on a ping of one address and spins on another.

## The keepalive, and what a capture showed (#449)

The first run of the new rig failed in the half I expected to be easy. With
node B alive, node A's command was ended inside forty-five seconds. I took
that for my reap firing on a live caller and went looking for why the dial
side had not answered the probes. It had not answered because nothing in it
answers one, which I fixed, and the rig failed the same way.

The capture said why. Nine copies of the run's request, half a second
apart, and no acknowledgement from the export; then silence from node B.
The export acknowledges a request with the first segment of its reply, and
a run's reply is held until the command ends. Node B's dial side
retransmits eight times and closes. So on `main`, any run from another node
that took longer than about four and a half seconds was told "cpu: remote
run failed" and left its command running. I built `main` and measured it
before writing that down: 5.9 seconds, and `recv` still in node A's `ps`.
No rig had run a slow command between two guests, and the host clients
retransmit for minutes.

That reframed the PR. The ledger's defect, the silent caller, was real, and
behind it sat a wider one that every slow command between two nodes hit.
The fix is one bare ACK.

I also had to give up a check I wanted. A live guest caller cannot be shown
to keep its run for forty-five seconds, because a dispatching `netd` gives
a run up after thirty seconds without output, by a decision already on
record, and a run's output comes only at its end. So the rig reads the
probes and their answers from the capture, and kills node B before its own
deadline.

Hans declined the merge and ran a review, and it found two things that
mattered. One lost ACK brought the whole failure back, since the request's
acknowledgement was sent once; data sent again is acknowledged again now, on
both sides. And my statement that a dispatcher giving a run up "closes with
no FIN and no RST" was `main`'s behaviour, not the branch's: with the
request acknowledged it sends a FIN, which I then measured. The review's
third point was that `netd`'s blocking waits can swallow a probe's answer.
I added a rule for it and a rig round to grade the rule, ran the round's
control, and the round passed with the rule taken out. The round is gone.
The rule stays, on reading alone, and says so wherever it is described.

## After the closeout: the Pi's Ethernet, and a plan (#451)

The day was closed out at #450 and then went on. Hans read the standup and
took the one decision it was waiting for: the Pi's on-board controller
first, a USB Ethernet adapter later and as an item of its own (Pi item 8).
He asked for the plan and for its first step.

The plan is `docs/roadmap/roadmap-pi-net.md`, and the fact that shapes all
of it is that nothing can emulate the device. QEMU 11.1.3's `raspi4b` has
no GENET (the Ethernet range is one of its unimplemented regions) and does
not boot our UEFI path anyway. So the arc is split by what can be checked
where: the controller's logic in a pure crate against a model on the host,
the kernel's half kept thin, and every step that touches the device a card
round trip with one variable. The SD card arc went the same way with QEMU's
`sdhci-pci` standing in; here nothing stands in, and the plan says in its
design that the model is ours and can only catch our arithmetic, never a
wrong reading of the device.

Step 1 was the part the host can do: read the NIC from the board's own
saved DSDT. The Pi declares `ETH0` with a `_CRS` shape `amlscan` did not
read, a method that names its buffer inside itself and returns it, so the
walk gained a third shape and now finds the block at `0xfd580000` and
INTID 189.

Hans ran a review and it found ten points. Two were in the code: the
condition that such a method ends in a `Return` had no test that could fail
for it, because the test written for it broke the name after the opcode as
well and so failed for the other reason. The rest were in the plan, and
they were all the same kind of mistake, a description of code I had not
opened. I had written that an idle `netd` blocks until a frame arrives; it
calls `NET_WAIT` with a timeout of zero and the tick polls every 20 ms. I
had written that the interrupt step would begin enabling the INTID; `main.rs`
enables whatever `net_intid()` returns already, so the GENET arm has to
answer `None` until that step. I had the receive buffers in the xHCI's
uncached pool, which is the only uncached range and is the xHCI's. Each was
found by reading the file the sentence was about.

## A scan nobody can emulate (#452)

Step 2 is the boot that reads the board: under a flag file `\NETDUMP`, the
version, the MAC address the firmware left, the enables, and every PHY that
answers on MDIO. It is the first piece of the `genet` crate, written over a
`Bus` trait so the same code runs against a model and against the board.

The first version worked against the model and would have been a poor
instrument on the Pi. Hans's review of it, before anything was committed,
was about that and not about correctness. All nine registers were logged at
the end, so a read that faulted would have taken the eight before it along,
and each lost reading is another trip with the card. The MDIO scan ran with
the firmware's timer events live, and if the firmware's own driver polls
the PHY from one, a command of its own between ours and our poll is read
back as our answer. A PHY that answered half its identifier was dropped
without a word. A bus held low would have read as thirty-two PHYs with an
identifier of zero. The rework logs each register as it is read, reads only
the version unless it says v5, raises the TPL for the MDIO half, and counts
every address into exactly one of six bins.

I recommended a second review after the rework, on the grounds that the
fixes were unread code, and it was worth it for what it found in the claims
and not the code. No offset or bit was wrong. But I had written that the
scan settles whether the firmware leaves DMA running, and the scan runs
before the exit, where the firmware's driver may still stop the device in
its exit notification. The reading is true and answers a different
question. I had written that the time at raised priority is 20 ms at most;
that is the dead-bus case, and a bus that completes each command slowly is
never cut off, about 2.6 s. And "read-only" rested on what the crate
happened to write, in a crate about to gain reset and DMA writes over the
same trait. The bus the kernel lends the scan now refuses any write but an
MDIO read command, by a function the host tests.

The rig had two of its own. `make test-netdump` was listed as the check to
run when the `genet` crate changes, and on QEMU no GENET is declared, so
none of that crate's code runs there. And its list of lines that must not
appear was kept by hand and already lacked one. It now names the two lines
a machine with no GENET may print and refuses the rest.

One finding was left on purpose, twice: `netscan.rs` is the third copy of
"the one device of this `_HID` declared present". The plan gives the helper
to step 5, where the driver would be the fourth, and records what the
second review added, that the three copies already apply different rules.
