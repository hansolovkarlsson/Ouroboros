# 2026-10-21

## Two decisions taken, and a FAT copy that is written rather than read

The day opened on yesterday's closeout (#332) and two decisions the standup
had left for Hans. The first was a `__has_attribute` guard on picolibc
patches 0002 and 0004, so a compiler that has the attributes would get
the code the patches remove. Tried on a scratch copy of `picolibc.h`, the
guard broke DevTools's `cc`: it answers 1 for `__gnu_inline__` and
`__always_inline__`, the guard then defines 0004's macros for it, and it
refuses `ctype.h`, `fenv.h`, `math.h` and `fastmath.h`, all four of which
it compiles on the committed headers. A guard on the compiler's name,
`__clang__`, would work, and that was declined as well: the headers would
then say different things to clang and `cc`, so a program would not mean
the same under both, and all it would gain is a few inlined functions and
`long double` declarations nothing here uses. Hans chose to leave both
patches as they are for every compiler, and #333 records that in the
roadmap as a decision, so it is not proposed again.

The second was whether FAT32 should copy its first FAT to the others. Until
now `write_fat_entry` read each copy's sector, patched it and wrote it back,
so a 640 KiB `cp` onto the ESP spent 2,559 of its 2,689 FAT reads on the
second copy, which fsd never reads. Linux and FreeBSD mirror instead: they
patch copy 0 and write the same sector to every copy. Hans chose mirroring
and #334 built it. The review found the one case where mirroring is wrong:
`BPB_ExtFlags` can turn mirroring off and make a FAT other than the first
the live one, and on such a volume the mirror would overwrite the live FAT
with a stale copy. Honouring ExtFlags is a larger change, so Hans chose to
refuse such a volume at mount with a line saying why. ExtFlags went to the
roadmap, and `test-volume-bound` plants the case. The mirror check in
`test-write-walk` plants the bad-cluster mark at every free entry of the
second copy, so a sector the copy wrote must come out identical in both
copies and a sector it did not write must still differ. Without the second
half, the check would pass on a run that wrote nothing.

Between the two, the review comments on #331 were looked at and, on Hans's
word, corrected in place on GitHub with `gh api`.

## ext2's metadata, and a stall that is not NVMe's

#335 took the next standup item. Since #331 no ext2 block number could reach
past the volume, but a number inside it naming the volume's own metadata was
used as it stood: a damaged `bg_inode_table` put new inodes over the
superblock, and `rm` of a file whose pointer named an inode-table block
cleared that block's bit for a later allocation to zero. Mount now refuses a
descriptor outside its group, as Linux's `ext2_check_descriptors` does, and
goes past Linux in also refusing one below `meta_end` or overlapping another
group's metadata. The review found that a damaged descriptor must be an I/O
error, not "no ext2": with "no ext2", `format` would take a root that fsck
could repair for an empty partition and write over it. It also found that a
block the allocator passes over must count nothing, and that the reserved
descriptor blocks R and MG lie below `meta_end`, which the rig's model had
to learn too.

Three `test-volume-bound` boots (SHAPES-F, then STALE and SHAPES-B) and one
`test-probe-ioerr` boot (BESIDE) failed every guest check that day, and each
had stopped in QEMU's firmware before the kernel printed a line, the
transcript ending at `Image type X64 can't be loaded on AARCH64 UEFI
system.` Hans asked for STALE and SHAPES-B to be rerun directly, and all 18
checks passed. #336 put the stall on the roadmap as a rig problem: these
rigs grade a firmware stall as failed checks, where `test-usb-hub` already
calls its own stall INCONCLUSIVE. I first called it an NVMe stall, since all
four rigs boot `esp.img` from NVMe. Later in the day `test-long-set`, which
boots from virtio, stalled with the same 11 lines, so the roadmap item now
says it is not NVMe's alone. Its cause is unknown.

## A block taken before the rest are known to be there

#337: `ensure_block` took the data block first and the pointer blocks after
it, so with one block free an append into the indirect range took the last
block, failed on the pointer block, and left the first block set in the
bitmap with nothing naming it. The first fix used `unwrap_or(0)` for the
pointer slots and was replaced by explicit indexing before review. The
review's real find was that the second-level pointer was read again after
the allocation, and on the double-indirect path that read could come back 0
and the write go to block 0. Walking the path once into a `Path` value and
taking every block before linking any closed both. The review also found
`write_at` returning before it wrote the inode, so a write of several blocks
that ran out lost the ones it had filled. Hans chose Linux's answer, a short
write that keeps what it wrote, over unwinding it. A disk error while
linking is still not undone; that is documented rather than fixed, since
undoing it needs the writes it would be undoing to succeed.

## An exFAT rename that kept nothing but the name

#338 was the case-only directory rename's neighbour; the rename itself is a
deliberate hold. An exFAT `mv` built the renamed set afresh, File, Stream
and name, which dropped the File entry's attributes and times, every vendor
extension and vendor allocation entry, and the Stream's ValidDataLength.
`renamed_set` now builds from the old set. The first version moved the
vendor entries but rebuilt the Stream. The review showed that rebuilding the
Stream raised ValidDataLength to DataLength for a preallocated file, so now
the old Stream is kept, with only NameLength and NameHash changed. The
review also found that `walk_dir` takes a name entry anywhere among the
secondaries, so a set whose name entry sat after a vendor entry would have
carried its old name behind the new one. STRAY plants exactly that.
fsck_exfat rejects STRAY's shape before the boot, so the rig allows that one
complaint by name, and requires the volume clean after the rename has put
the set in the spec's shape. The first STRAY control, `|| i > 2 + rest`, did
not model the old code and passed. `|| rest > 0` did model it, and failed
the rig as it should. The roadmap gained two items from the review:
fsd reads an exFAT file to its DataLength rather than its ValidDataLength,
and `rm` leaks a vendor allocation's clusters.

Before #338 could merge, #337's merge conflicted with it in CLAUDE.md, on
two adjacent rig lines that each branch had edited. The branch was rebased
keeping both lines, and `make test` and the exFAT rigs were run again on the
rebased tree before the push.

## Names outside ASCII, and how far a fix should reach

#339 took the next item: exFAT rendered every name to ASCII with `?` for
anything else and looked names up by that rendering, so `café` and `cafè`
were one name and the first set answered for both. Keeping the UTF-16
through the lookup was the fix the roadmap named. What it did not name was
that the listing had to change with it. With the lookup on UTF-16 and the
listing still `?`, a name would be listed under a spelling no lookup
accepts, where before it was at least reachable. So the listing renders
UTF-8, which a lookup takes back unchanged.

While checking the fix I planted a name hashed as fsd hashes it, and
fsck_exfat rejected it as "Invalid file name", whose repair deletes the file.
fsd folds case by ASCII alone, so the NameHash it writes for a name outside
ASCII is not the one the volume's own up-case table gives. Every non-ASCII
name fsd has ever created carries that defect. Fixing it means reading the
up-case table at mount. Hans chose to fix the collision alone and put the
hash on the roadmap.

The review found what the first version had missed in widening the
listing. A name of 255 UTF-16 units can be 765 bytes of UTF-8, more than one
512-byte listing page, and the page that reached it failed. The control
showed how badly: with the root holding such a name, the root's listing
failed, `/bin` with it, and `cat` became an unknown command. The first
version also showed a name with an unpaired surrogate as U+FFFD, which no
lookup matched, and a create of the name as displayed made a second set
that listed the same as the first. Hans chose to fall back to the old
rendering for exactly those names, with a lookup's `?` standing for each unit
the listing could not show. Since `?` is forbidden in an exFAT name, a create
can never spell such a name, so it can never be listed twice. Two such names
that differ only outside ASCII still collide, and the roadmap says so.

Two instruments needed correcting along the way. `exfatimg.py` cut a set's
name at NameLength in Python characters rather than UTF-16 units, so a name
with a surrogate pair came back with a padding NUL, and the rig's own
read-back failed before the boot. And `/bin/ls` builds each line in 84
bytes, so the 100-character fallback name came out cut and run into the
next name. That is an `ls` defect for any long name, ASCII ones on ext2
included, and it went to the roadmap; the rig reads that name through the
shell's glob instead. The first control for the collision, main's own
`exfat.rs`, failed the rig for a different reason: it found no UTF-8 name at
all. It did not show the collision. A second control kept the UTF-8 listing
and folded every unit outside ASCII to one, and it reproduced the collision
exactly: `cat /cafè` printed `café`'s bytes and `echo > /cafë` overwrote
`café`.
