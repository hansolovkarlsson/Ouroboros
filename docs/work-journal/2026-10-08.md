## Raw mode and the way out (#235)

Step 1 was small on paper: a per-task flag, `KBD_MODE` (70), consulted where
the kernel decides what a Ctrl-C means, and Ctrl+\ (0x1c) acting in every
mode. The rig, `test-kbd-mode`, read Ctrl-C as 3 from the serial line and the
USB keyboard and ended programs with Ctrl+\, and four mutations each failed
it. Then came five high reviews, and the pattern of 09-01 played out almost
exactly: the first found the PR's own gaps (an ISO keyboard cannot type
Ctrl+\ at all, a slot-reuse assumption in the rig, a kill line that named the
wrong key), and the next three mostly found the previous round's repairs.

The clearest case is the boot shell's interrupt. Its waits had found a
Ctrl-C by scanning the queue for the byte, which had been safe while only
the boot shell could queue a 0x03. Raw mode made it unsafe: a raw program's
Ctrl-C, left queued when it exited, ended the shell's `WAIT` on that very
program as "interrupted", and the zombie kept its slot. The repair marked each
queued byte read for the boot shell; the next round found the mark lost with
its byte when the queue was full; that repair made the interrupt a return
value of the read itself and never queued it; the next found that flushing
at the prompt lost keys typed just before the Ctrl+C, depending on how fast
the shell read, and `test-kbd-mode`'s `ef` check caught that one before the
review did. The same rounds turned the ISO fix around: mapping both ISO
backslash positions made Ctrl+< an uncatchable kill, so 0x32, the key in the
US backslash position, became the backslash key and 0x64 went back to
nothing. The fifth round's findings were all in the key parser, older than
#235 and the open question of step 3, and were recorded there rather than
fixed. Merged with ten mutation controls.

## `termios` (#236)

Step 2 gave a C program `tcgetattr` and `tcsetattr`, with `ISIG` mapped onto
`KBD_MODE`. The plan said every other flag would be stored and read back. The
first mutation run showed why that could not be checked with Edit's own
recipe: the recipe clears only flags the console already lacks, so a
`tcgetattr` that ignored what was stored read back the same thing, and "not
stored" survived. A check setting flags the console never has fixed the rig.
The high review then questioned the plan itself: POSIX has a program confirm
with `tcgetattr` what took effect, and reading back a stored `ECHO` says echo
is on when it is not. So `tcgetattr` reports the console as it is, a
departure from the plan recorded in it. The same review found the note to
DevTools over-claiming: `plat_raw_on` also calls `sigaction`, and the file
includes `<poll.h>`, neither of which this C library had. That sentence was
the seed of the evening's work.

## The cut keys (#238)

Step 3's second half was a design question before it was code, so it got a
design first: five ways the queue could cut a key, one answer (every byte
through one parser that records where each key starts), and four decisions,
E1 to E4, which Hans settled as recommended. The build's first finding was
about the rig, not the kernel. Reverting E1 alone (the kill's flush follows
`keyseq`) left `test-kbd-cut` green, because at typing pace E2's 40 ms
interval had already reset the parser before the next key. E1 could only be
shown by pushing bytes at chosen ticks, so the queue moved out of the kernel
into the `keyseq` crate as `KeyQueue`, with the time passed in, where `make
test` checks it on the host. That was the day's best decision about an
instrument.

Five high reviews followed, the same shape as #235's. One repair is worth
recording as a wrong turn: to send every byte through the queue, the first
version drained the devices at every read, which handed a Ctrl-C typed after
a command's Enter to the shell as data and on to the command as a byte. The
fix, a read that takes one byte, then could not keep its promise either,
because the tick and the waits read ahead too. The fourth review made it
clear that this is not a bug to chase: a Ctrl-C typed ahead of a program,
before it sets its mode, is judged under whoever owns the keyboard when it is
read, and Unix has the same race. It was documented as such. Merged with the
queue's 23 host tests and the six keyboard rigs passing.

## `poll`, and Edit on the image (#240)

The answer to that notice arrived as a new note later the same afternoon: DevTools
asked for `poll` on fd 0, which Edit uses for its 50 ms escape timeout and
`^Q Q`'s repeat, and for Edit built into the image as cpp is. The first
version was a C-library `poll` over the system calls that already existed,
and `make test-edit` showed Edit running: it opened a file, repeated a delete
with `^Q Q`, took an arrow through the escape timeout and saved, and `cat`
printed `hXi`.

Four high reviews reshaped it three times. The first found the timed wait
spinning a whole core on `YIELD`, which returns at once when nothing else can
run; the repair was a kernel call with a deadline. The second found that
`poll` took the key out of the kernel to answer `POLLIN`, so a program that
polled and exited without reading lost it; the call became `KEY_WAIT_UNTIL`,
which waits for a key and leaves it queued. The third found the remaining
spin, the last stretch before the deadline, still burning the core through
`^Q Q`'s 25 ms polls, and that ticks arrive late enough that the early wake
could miss anyway. That was a trade-off rather than a defect, between the
note's 10 ms and a spinning core, so it went to Hans, who chose tick
precision; the reply to DevTools says so plainly. The fourth added
`SLEEP_UNTIL` so that `poll` with nothing to wait on sleeps blocked too.

One instrument failed silently on the way. The first mutation run for the
third round's fixes used `timeout`, which macOS does not have; every rig
"ran" and printed nothing, which read as three mutations surviving until the
empty output itself looked wrong. The rerun printed each rig's "driven to the
end" line alongside the failures.
