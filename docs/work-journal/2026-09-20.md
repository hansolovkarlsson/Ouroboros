## 2026-09-20: the keyboard chain, and the argument that had an exception

The standup's first pick was the child-shell keyboard bug: a shell spawned
from a shell lost the keyboard the moment its first command exited, because
the revert on an owner's death went to task 0 whatever the chain. It was to be
one rule change and one review. It became four pull requests (#140, #141
reopened as #144, #142, #143), sixteen commits plus four merges, nine
high-effort reviews, and, as yesterday, the real findings were in the rule I
wrote rather than in the code I set out to fix. Everything merged; `main` ends
the day at `897867e` with the suite green, clippy at zero, and a new
four-boot check that fails when the chain is wrong. The reasoning below is
about what three reviews found in one small rule, why a soundness argument I
wrote down turned out to have an exception, and what the instruments did
while all that was going on.

### The revert, and three rounds of my own rule

The fix was witnessed before it was written: `exec /EFI/ORBS/SH.BIN`, `fg 6`,
`cd /EFI`, `echo hi`, `pwd` printed `/`, the boot shell's cwd, and `ps` showed
task 0 runnable and task 6 blocked. `echo` is a `/bin` program, which is also
what the 2026-09-06 ledger entry had got wrong when it said "a builtin, no
child"; its exit is what reverted the keyboard. The rule I chose was the
previous owner rather than the parent: `FG` records who held the keyboard
when it handed it over, as a packed identity, and the owner's death returns
it to that task if it is still that occupant and alive, else to task 0. The
previous owner because every previous owner was a valid `FG` target when
recorded, so the revert can never land on a protected server; a parent can
be netd. After the fix `pwd` printed `/EFI`, task 6 stayed runnable, and
Ctrl+C at a grandchild returned the keyboard to the nested shell and Ctrl+C
at the nested prompt returned it to the boot shell.

The second review found the first hole. A task can die as a link in the chain
without owning the keyboard, a nested shell killed from a shell below it, and
its entry went with it: three deep, `kill 7` from task 8 and Ctrl+C at 8's
prompt sent the keyboard to task 0 past a live shell 6. The splice went in:
every entry naming a dying task is re-pointed at that task's own previous
owner. Witnessed failing first, with the splice removed as the mutation
control, and the honest shape of that failure was not "pwd prints nothing"
as I had first written but "no prompt ever comes back", which is what the
recipe now says.

The third review found what the splice had made spellable. `fg 6` from shell
7, which 6 had handed the keyboard to, overwrote 6's link to task 0 with a
link back to 7; `kill 7` from 6 then spliced 6 onto itself, and Ctrl+C at 6's
prompt handed the keyboard to the dying task and stranded it on an empty slot.
Witnessed: no prompt ever came back. I normalised a self-naming entry to
"none" and wrote in the ledger that with that and the splice "nothing
strands". The review of #142, two pull requests later, found the case that
does: four deep, `fg 7` from 8 loses 7's link to 6, `kill 8` makes 7 name
itself, the normalisation reads that as none, and Ctrl+C at 7 sends the
keyboard to task 0, blocked in `WAIT` on 6, while 6 sits at a live prompt
whose every keystroke that wait discards. Measured on the pre-change kernel:
the prompt printed, `pwd` was never answered. The fix that should have been
the first one went in as #143: `set_input_owner` keeps the table a stack. It
walks down from the holder; if the walk reaches the target, every link
walked is cleared, else the target's entry becomes the holder. No cycle is
spellable, the self-naming special case is gone, and the reader relies on
the shape instead of repairing it.

Three rounds, three repairs to one rule, and each repair was the size of the
finding rather than the size of the defect. The stack semantics were proposed
in the third review of #140 and I filed them as a design change; the next
review made the case that filing was wrong by producing the strand. The lesson
is the one in `repairing-the-repairs`: when a repair adds a special case to
the reader, the writer is what is wrong.

### The cleanup, and the argument with an exception

#141 was the no-behaviour-change PR the #137 ledger had named: one
`switch_to` for the five sites that loaded a frame, set the current task and
activated a view; one `scan_from` behind the two runnable loops; `is_live` and
`task_exists` gone, the identity arms on `live_index`; and `live_occupant(id)`
for the two places that unpacked an identity and asked whether its occupant
was still there. One review round, no code defect.

#142 was the `SyncCell<T>` item: twenty-three hand-rolled `struct
X(UnsafeCell<T>)` plus `unsafe impl Sync` wrappers across five files, each
restating the single-core argument in different words, became one module
that states it once. The bound is `T: Send`, which is what a shared cell of
`T` needs in general, and it refused two cells honestly: `FbCell` holds the
framebuffer's raw pointer and `StoredMapCell` holds the uefi crate's
`MemoryMapOwned`, and both keep their own wrapper and say why. The count went
through three wrong numbers before it was measured once, with an anchored
grep, in the module doc alone; the ledger, the source map and the module had
each given a different figure for one property.

The argument itself said the kernel never runs at EL1 with interrupts
unmasked. The first review of #143 found that `main.rs` unmasked IRQs a few
instructions before `tasks::start`'s `eret`. A tick in that window would have
had the trampoline save an EL1 frame as task 0's context, or, between
`start`'s `msr elr_el1` and its `eret`, sent the `eret` to a kernel address in
EL0 mode. Sub-microsecond, never seen, and the argument every mutable static
now rests on was false for those instructions. Every task's saved SPSR is 0,
so the `eret` into task 0 unmasks for EL0 by itself; the explicit unmask is
gone, IRQs are masked by our own instruction at the exit from boot services
rather than by trusting what EDK2 left, and the second review's point was
taken as well: vector slot 5, IRQ at EL1h, still took the resumable tick path,
so a future EL1 unmask would have corrupted a task context silently. It
diverges now, and reports `EXCEPTION vector=5`. The mutation control was to
unmask inside `start` and spin: the boot halted with exactly that line.

### The instruments

The chain recipes became `make test-keyboard-chain`, four driven boots graded
on the lines their negative controls lacked. Its first run against the
push-only mutant reported all four recipes failing, and two of them should
have passed. The script kept no transcripts; when it did, three of the four
boots had hung in the firmware before its own boot entry, before any kernel
code ran, and only the fourth had run and failed as the mutant should. Measured
directly: one hang in six bare boots, pauses between boots making no
difference, the same image booting on every retry, QEMU 11.1.1 and
edk2-stable202408. Not attributed. The script retries a boot whose transcript
never shows `BdsDxe: starting`, says so, and never retries a boot past that
line, since from there a hang is the kernel's. With that in place the mutant
gave the right answer: the two recipes that need the pop failed, the two that
do not passed. A later review found the target would grade a stale image
without complaint, so it depends on `image` and the script refuses an image
older than the kernel of its profile.

Earlier in the day I had three times taken a boot that hung the same way as
possible evidence about my change, and once stashed and rebuilt to find out.
The guide now carries the measurement so the next session does not spend that
hour.

### Where it ends

Four pull requests merged, `main` at `897867e`, suite green: 137 unit tests,
107 wire constants across four peers, 26 verbs, 17 site pages matching their
source, 65 binaries with no absolute relocation, clippy at zero, and all four
chain recipes passing on the merged tree. What the day settled: the keyboard
returns along a chain that is a stack rooted at task 0, a link that dies out
of turn is spliced out, an IRQ at EL1 is a fault, and every mutable static
rests on one written argument that a vector slot now checks. What it did not
settle is one design question the reviews pressed on every pull request:
whether the kernel should distinguish a foreground command someone is waiting
on from a session handed over with `fg`. Ctrl+C at a nested shell's own prompt
kills the shell and the same gate can drop its type-ahead; `fg` from a task
that does not hold the keyboard is not refused; handing the keyboard to a task
blocked in wait on you leaves nobody reading it. All three are filed, and all
three are the same decision.

## 2026-09-20 (later): three picks from the standup, and a fix scoped to the symptom

The morning had closed out. The afternoon took the top three items off that
standup's list, one at a time, each to a merged pull request with its own
reviews: the C task error codes (#145), the stack-size copies (#146), and the
`tcp_run` re-entrant session nesting that had no rig (#147). The suite ended
green again, `main` at `b9c3919`, with the wire check up from 107 constants to
115. The model changed under me partway through #147, from Fable 5.1 to Opus
4.8, which is why the later commits carry a different co-author line; nothing
about the work changed with it. The reasoning worth keeping is in the third
pick, where I fixed the symptom the ledger named and the real defect was one
level out from it, twice.

### The two that went as planned

The C error codes were the smallest true thing. `libc`'s `sys.h` mirrored no
task code, so a C program printed "failed" for the whole reserved band;
[`#145`](../../libc/include/sys.h) named `TASK_ERR_NO_SUCH_TASK`,
`TASK_ERR_PROTECTED` and `TASK_ERR_SELF`, pinned by the wire check with two
measured negative controls, and folded the two byte-identical `why()` copies
in `cremote` and `cwrite` into one `ouro_fs_strerror` the review asked for.
The second review found a case the first pass had left as "failed" for real: a
downed remote peer answers `NO_FS`, which a C `read()` meets, so that joined
the header and the printer too.

The stack-size work was the copies-drift lesson again. Nine prose copies of
the stack size disagreed with the constant, and the stack top was hand-derived
as `base + size` at seven `Context` literals across three files. The fix put
one `region_end` and a `LoadedProgram::initial_context` where the layout is
owned, and turned the prose into statements of the relationship. The review
found the thing the ledger entry itself had got wrong: my `stack_top`'s doc
claimed to be "the ONE place this is derived" while `tail()` and five boot-log
lines in `main.rs` still spelled the sum, and it found nine *more* stale copies
of the number than the ledger had listed, `SAFECOPY_MAX`'s doc among them still
describing 8KB stacks with no guard page. `tree`'s depth cap, the one place the
32KB was load-bearing, now asks the loader for its stack at start rather than
trusting a comment; a mutation control confirmed a smaller stack shortens the
walk instead of faulting.

### The one that taught something: the fix was one level out from the symptom

The re-entrant nesting was the fid-verbs ledger's one open corner: a remote
mount reaching `netd` while `netd` is inside a `cpu` run, predicted to fault
the guard page, with no rig because nobody had built the concurrency. I built
the rig first. The shell spawns a pipeline's program stages before it runs a
builtin source, so `cpu <A> ping <unreachable> | cbig` puts the client's verbs
at the re-entrant drain while the unreachable ping's ARP wait holds the run
open. It faulted exactly as predicted. It also refuted the ledger's own word:
the entry called the one-shot path "latent", and refusing only the session
path, `cat` faulted the same way one level shallower. The claim was written as
analysis and was wrong about the case it had not run.

Then I fixed the symptom instead of the mechanism, and the review caught it
twice. My first cut refused inside `handle_rmount`; `cat` still faulted,
because Rust reserves a function's whole frame on entry, so a check inside
`handle_client` is too late. I moved it to the re-entrant drain, before
`handle_client` is called, and refused `NETOP_RMOUNT` there. That passed the
`cat` and `cbig` recipes, so I opened the PR believing it done. The first
review's load-bearing finding was that the overflow is the *depth of any
handler* reached from that drain, not the relay specifically: a bystander
`resolve` needs no mount and runs a DNS lookup just as deep. I drove it, and it
faulted. The right refusal is by *sender*, not by op: from the re-entrant drain
service only the supervisor's identity-less health ping and refuse every
identified client, since any of their handlers is too deep. That is the
[`#147`](../../programs/servers/netd/src/main.rs) that merged. The lesson is the
one the review embodied: I had a fault, I made the fault I could reproduce stop,
and I mistook that for making the cause stop. The cause was "a client handler
runs at re-entrant depth", and the op the first fault happened to carry was a
detail of the one I reproduced.

The rig itself needed the blind-instruments discipline. Its first version had a
dead parameter meant to tell "the client succeeded, so the condition was never
created" from "the link flaked", so a run that proved nothing would have been
reported as a hard failure; the third review found it before it lied. And the
session-path witness `cbig` turned out flaky for a reason unrelated to the fix:
a pre-existing race delegates a spawned task's `netd` send right just after
spawn, so its first request is sometimes refused by capability before any
remote request. The rig grades `cat` and `resolve`, which reach `netd`
deterministically, and treats the `cbig` race as an observation, not a failure,
so the check turns red only on a real fault.

### One trap I walked into

Running a mutation control on `sys.h` while my `FS_ERR_BUSY` addition was still
uncommitted, I reverted it with `git checkout` and wiped the addition, the
exact thing the `reference-commit-before-mutating` memory note describes. I
caught it because `file.c` still referenced the define, re-added it, committed
first, then reran the control safely. The note was right; the discipline is to
commit before mutating even when the mutation is only a control you mean to
throw away.
