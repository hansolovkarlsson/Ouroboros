# 2026-10-29

## Three refusals no libc flag reaches, and a probe that read silence as one

The standup's first item was the three `NP_OPEN` refusals #367 left graded by
no boot: `exists_answer`'s stat rule (EEXIST only to a caller who may stat
the name), `OPEN_EXCL` without `OPEN_CREATE`, and a flag outside
`OPEN_FLAGS`. libc never sends the last two, and no rig had a user who may
not search a directory holding the name, so each could be removed and every
check would pass. `/bin/OPENPROBE` sends a raw `NP_OPEN` with the flags it
is given, and `test-cerrno`'s ext2 boot runs it as `user` against a
directory made 0700 for the purpose (#369). Each refusal removed in turn
failed its own checks.

The high review found the probe's own blind spot. It made its call through
ulib's `np_call`, which answers FS_ERROR for a call fsd never answered as
well as for one it refused, and FS_ERROR is exactly what two of the three
checks expect. An fsd that panicked on `OPEN_EXCL` alone, with the
supervisor restarting it, passed them. The probe now sends `MSG_CALL`
itself and prints `no answer` for that case, and the control that makes fsd
panic fails two checks. The medium review after it found smaller things (a
chmod the rig never checked had taken, a relative path the probe passed on)
and #369 merged.

## A directory opens for reading alone

Next, the size-0 exFAT entry's cluster. Freeing it safely needs a walk of
every directory on each such `rm`, to be sure no other set names it, and
Hans chose to keep the leak `fsck_exfat` reports. It is recorded on the
roadmap as a decision.

Then the disagreement the second medium review of #364 found: fsd gave a
fid for any `NP_OPEN` of a directory, and the host peer refused every one.
POSIX settles which side is right. A read open of a directory succeeds; a
write, read-write, truncate or create open is EISDIR at the open. So fsd
keeps its read fid and refuses the rest, and the peer gives a directory a
fid for reading (#370).

The first build put fsd's refusal after `check_access` and the read-only
gate, which is where the code had room for it. The review compared it with
Linux, where `do_open` and `may_open` answer EISDIR before
`inode_permission`, so `user` got EACCES for `/etc` where Linux says EISDIR,
and VRUNS's read-only exFAT said EROFS. The refusal moved beside
`O_EXCL`'s EEXIST in `exists_answer`, with the same stat rule. The second
medium review made the mask one constant, `ninep_abi::OPEN_DIR_REFUSED`,
host-tested to equal `open_changes` of a missing name over every flag
combination, and taught `check-wire-constants.py` to read `A | B` masks on
both sides so the peer's copy is held to it. A first control of that check
reported a "dead entry" instead of a mismatch, because its pattern needed at
least two names; it reads a lone name too now.

The same review suggested replacing the root truncate check with
`O_RDONLY|O_TRUNC`. I declined it, as the first review's version of the
point had been: every truncate open of a directory reaches `write_file`,
which refuses a directory itself, so no root truncate check can tell the new
refusal from the old one. Only `user`'s, through `openprobe`, does. The
CHANGELOG says three of the four root opens grade the refusal, which is the
true count.

## The disk gate, graded through a build of fsd that does not ask the arm

Since #364 fsd's verb gate refuses every change to a read-only tree before
the arm, so no boot reached exFAT's own refusal, the disk gate (`gate::Gated`'s
write check and the allocator's). Two ways past the verb gate were on the
roadmap. A boot flag was the cheaper one and was not taken: a file on the
disk would switch a gate off in the fsd that ships. The other is a build.
fsd's `disk-gate-rig` feature leaves the arm out of `tree_read_only` and
prints a line of its own at startup; `make fsd-disk-gate-bin` builds it in
`target/disk-gate`, so it can never land where the shipped `fsd.bin` is read;
`make test-disk-gate` stages it on a copy of `esp.img` and runs
`test-long-set`'s five read-only boots on it (#371). With every early
`writable()` check removed it passes, so the gate holds alone; with the
gate's two checks removed as well 22 checks fail; with the shipped fsd
staged, every boot's build line fails.

Two medium reviews found the rig's own instruments wanting, which is the
day's postmortem section. The build check sat in six of the fourteen
ordinary boots, though the docstring and the records said every boot; it
now lives in one place, over every transcript `boot()` records. In ordinary
mode it passed whenever the rig's line was missing, so a boot that died
before fsd said anything counted as the shipped build; it now needs fsd's
ready line too. The two modes shared a scratch image and transcripts. A
direct run could stage whatever rig build was left in `target/disk-gate`,
so gate mode runs through `make` alone, which rebuilds it and passes its
path. And `test-volume-bound`'s BESIDE, the case where a write past the gate
would land on another partition, is not booted on the rig's build; that is
a roadmap item rather than a claim.

One review finding rested on a premise that did not hold. It asked for build
coverage of the feature because nothing compiled it. But fsd reads the
feature through `cfg!()`, so the default build compiles both branches. The
`cargo check` with the feature went into `make test` anyway, and the control
I could actually spell was the feature renamed in `Cargo.toml`, which makes
`make test` fail. The comment says that is what it catches.

Three PRs, all merged on Hans's word without deleting their branches. The
closeout moved the three items they struck from the roadmap into
`roadmap-completed.md`.
