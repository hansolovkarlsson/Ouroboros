so `netd` serving 2.56 s of client messages with no frame on the wire

## `NET_RECV`'s length

The standup's next item was older: `NET_RECV` answered a frame's own
length even when the frame was longer than the caller's buffer, and only
`netd`'s clamp kept that from being an index past the buffer. Three
designs were put to Hans: a sentinel for a frame that does not fit,
taken and dropped; the copied length, which hands a cut frame on as
whole; or the frame left on the ring with the length it needs, which
spins a caller that never retries. He chose the sentinel,
`NET_FRAME_CUT` (#482). The bound is in one place, `Nic::poll_frame`, so
it holds for virtio-net and the GENET alike.

The check needed a frame longer than a buffer, and QEMU's user network
never sends one over 1500 bytes. So the rig's `netd` asks with a buffer
shorter than any frame instead: a ping of 192.0.2.249 has it send an ARP
request and read the first frame back into 16 bytes. With
`Nic::poll_frame` answering every frame whole, the probe logged 64, the
frame's own length.

The review found that the check had proved the kernel's half only. The
probe called the syscall itself and judged the answer itself, so `netd`'s
own branch for the sentinel could have read it as nothing and the rig
would still pass; that branch runs only on a frame over 1600 bytes. The
reading moved into one function, `got`, which `recv_one` and the probe
both call, and the rig now requires the probe's line to say how `got`
read the answer. With `got` reading the sentinel as nothing, it failed.
Five more of the review's eight were taken: the probe's line written in
one log call, its wait beating, the three sentinels asserted apart and
above `NET_MAX_FRAME`, and a paragraph of the plan's step 5 that still
said `NET_RECV` answers the frame's length. Two were declined: the bound
in each driver before its copy (two places again), and a loop shared with
`arp_resolve` for a probe only the rig's build has.

One round of the network rigs went red and did not stay red.
`test-server-children`, `test-net-config` and `test-run-callback` failed
once, on a login timeout, a ping off its route and a missed restart
round, while I was editing documents in the same tree. All three passed
on two reruns of the same commits. The cause was not found; it is in the
PR rather than explained away.
