# 2026-11-05

## The Pi at yesterday's build, and a console that lost its column

The standup's first item was Hans's: the Pi 4 at `main`'s build after #408.
He re-staged the card and the stick and booted with `screen -L` on the
serial line, and every expectation the standup had written down was met:
`ACPI declares no virtio-mmio transport` before the exit, `skipping
virtio-blk (no virtio-mmio transport declared present on this platform)`
after it, where every earlier Pi boot had read RAM at QEMU's `0xa000000`,
and then the ext2 root on the stick. `mount -p /proc` and `cat /proc/cpus`
gave 4.

What Hans asked about instead was the serial console itself. The kernel's
lines started at column 0, but `cat /etc/srcid` printed each line where the
last had ended. The log said why: the kernel's UART drivers turned `\n` into
`\r\n`, and nothing did for a program's output, which cond sends through
`CON_WRITE` as bytes. On the framebuffer it had never shown, because cond
and the kernel's FbConsole both return to column 0 on `\n`. Hans asked for a
fix on a branch the same day.

The first version translated in cond, the place the bytes passed through,
and its review found it the wrong layer: a program writing with `PUTC` when
cond is not up went around it, and cond's "the last byte was `\r`" state
could not know about bytes the kernel had written in between. Hans asked
whether a kernel-side translation would touch binary files. It cannot: only
the console's two syscalls reach it, never a file, a pipe or the network.
So the translation moved into the kernel's `console::write_out`, with
`AFTER_CR` carrying the last byte across writers, listed as class E in the
multi-core statics inventory.

The second review found the new probe could not fail on the case it was
written for. `ctermios nl` split `\r` and `\n` across two `write`s to test
the carry, but libc holds fd 1 in a line buffer until `\n`, `fflush`
included, so both bytes always left in one write. The probe now writes every
piece to fd 2, which goes out at once. The same review found the drivers'
own `fmt::Write` impls still translating on their own, which would have
doubled a `\r` the day anything used them; they were deleted. The third
review found the virtio-console path a second copy of the loop that nothing
tested, and it became one loop feeding a per-driver `write_chunk`, with
lines of 256 and 255 bytes so the inserted `\r` lands at the end of the
kernel's 256-byte chunk and just past it. Each new check was shown to fail
under a mutation: translation off, translation in cond instead, libc
reporting no output flags, the carry dropped, the chunk edge. `tcgetattr`
now reports `OPOST | ONLCR` set, which changed a comment in the header
DevTools's `cc` reads, so a notice went to DevTools before `check-picolibc`'s
pin moved. Hans then decided a program should be able to switch the
translation off, and that is on `ROADMAP.md` as a design with three
decisions, not built.

PR #410 was opened, and the Pi was booted from the branch with only the
card re-staged, since the fix is all in the kernel. The first boot had no
stick (Hans had not plugged it in), so there was no root and no `cat`, but
its 3,850 bytes after the exit already had no bare `\n`, against 13 in the
morning's boot. With the stick in, `cat /etc/srcid`, a pipe through `head`
and `/proc/cpus` all came out with every line ending `\r\n`, and no `\r\r`
anywhere.

## One card, no stick: the plan, and a recommendation that was already false

Asked whether both card and stick were needed for that boot, Hans turned
the question into a direction: a Pi should need only its card, so that
several boards need one medium each and the USB port is free for a keyboard
or a mouse. That is Pi item 2 on the roadmap, the SD card as a runtime
disk, which needs a driver for the BCM2711's EMMC2 controller. The rest
exists: the one-disk arc already takes the disk the firmware booted from,
and `make bootstick PI=1` already writes the ESP-and-ext2 layout to a whole
disk.

Before writing a plan I had the firmware's sources read (edk2-platforms'
`Emmc.asl`, `ArasanMmcHostDxe.c`, `ConfigDxe`, and Linux's `sdhci-iproc`).
Three facts set the plan's shape: the Pi's own UEFI driver reads the card
by PIO through EMMC2, so a PIO driver does what the firmware already does;
EMMC2 is declared in ACPI as `BRCME88C` in an SSDT of its own; and the
firmware's variable store is a file on the same card, which the kernel must
never write. QEMU 11.1's `virt` machine takes `sdhci-pci` and `sd-card`, a
standard SDHCI on PCI, so the driver can be written and tested on QEMU and
the Pi left to add discovery, the clock and the takeover. The plan is
`docs/roadmap/roadmap-sd-card.md`, with five decisions, which Hans settled
as recommended.

The first of them was wrong as written. I recommended finding the Pi's
controller through the devicetree "which already finds the Pi's console",
from `dtranges.rs`'s doc and the September records. Starting step 0, I read
that morning's serial log: `devicetree console discovery failed (NoDtb)`,
then `console @ 0xfe201000 (via ACPI SPCR)`. `testing-pi4.md` had already
recorded `NoDtb` on both of the previous day's boots. The Pi as configured
now publishes no devicetree, so the source is ACPI, and the plan says so
with the line that showed it.

## Step 0: the board read, after a diagnostic that ended the boot

Step 0 is `kernel/src/sdscan.rs`: before the exit, touching no controller
register, it logs any devicetree `emmc2` node, every ACPI table holding
`Name (_HID, "BRCME88C")` or `"BCM2847"` (Arasan), and the firmware's
`SdIsArasan` routing variable, found by name so its GUID is read off the
board. With a new boot flag, `\SDDUMP`, it prints those tables in hex, since
the firmware sets EMMC2's base inside a `_CRS` method that `amlscan` does not
read, and I did not want to write a parser for bytes I had not seen. QEMU's
arm `virt` refuses `-acpitable`, so the positive path could not be injected
there; the `_HID` search went into `amlscan` as `hid_string_at`, with host
tests that two mutations fail.

The first Pi boot halted inside it, before the exit. The line naming the
first table stopped after `sd: DSDT `, and the dump's first line panicked:
`Failed to write to stdout: Error`. The Pi's DSDT's OEM table ID holds
bytes the UEFI console refuses; the logger drops that error and
`uefi::println!` panics on it. QEMU's ID has none, so no QEMU boot could
have found it. The fix prints a header name's unprintable bytes as `.` and
writes each dump line without panicking, so a diagnostic cannot end a boot.
Before the board saw it again, QEMU reproduced the Pi's output byte for
byte with a temporary patch (QEMU's own `_HID` searched for, the ID made
`RPI4\0\0\0\0`) on the old code, and the fixed code dumped the whole DSDT,
rebuilt from the hex with its length and checksum whole. The control needed
two tries: the first ran without the flag, because `make esp` re-stages the
ESP and had removed it.

The second boot dumped two tables, both whole: the DSDT, which declares
Arasan, and the 631-byte SSDT `RPI4EMMC`, which declares EMMC2 as
`\_SB.GDV1.SDC3` with `Method (_STA) { Return (0x0F) }` and a `_CRS` method
that stores `0xFE340000` into a named buffer and returns it. `SdIsArasan` is
0, so the card is on EMMC2 with no firmware change. Earlier in the day a
rig run had failed one check, "the staged kernel is this tree's commit",
because I committed while it was building; the rerun on the committed tree
passed, and the check was right to fail.

## Step 0b: two method shapes, and the controller's first reading

`amlscan` now finds a device by any `_HID` (`declared`; `virtio_mmio` is one
caller) and reads two method bodies, each in the one shape the Pi's firmware
writes: a `_STA` that is only `Return (<constant>)`, which nothing can store
to, and a `_CRS` that is only `CreateDWordField (^BUF, n, F); Store
(<constant>, F); Return (^BUF)`. Anything else in either body is still
unknowable. The first version kept the device's named buffers in two slots
and filled them with every `Name` in the device, so `_UID` and `_CCA` took
the slots and `RBUF` was never kept; a debug test showed it. A third pass now
looks only for the one buffer a patching method names, and counts every
definition of it in every table, whatever its kind. On the Pi's own SSDT,
and on it beside the DSDT as the kernel scans them, EMMC2 comes out
`0xFE340000`, 0x100 bytes, INTID 158, and the Pi declares no virtio-mmio.
Seven mutations each fail a test, among them the offset ignored, a second
definition of the buffer ignored and a statement after the `Return`
accepted. One older test changed meaning: its `Method (_STA) { Return
(One) }` is now read, and One is present but not enabled, so absent.

The third Pi boot read six of the controller's registers before the exit,
on the firmware's mapping, none whose read changes anything: SDHCI 3.00,
a 100 MHz base clock, the card inserted, the bus idle at 3.3 V, the SD clock
at 25 MHz on a 1-bit bus as the firmware left it. Unlike Arasan's, EMMC2's
capability registers are real, so the driver can take its base clock from
them. Steps 0 and 0b are done; step 1, the driver on QEMU, is next.

verified on the Pi. `plan/sd-card` holds the plan and steps 0 and 0b, six
commits ahead of `main`, not pushed. The card in the Pi is at `c8bf046a`;
