# 2026-10-07

## The morning: cursor addressing found a kernel bug (#227)

The day began from the 10-06 standup, with Edit's console note accepted and
not started, and Hans chose its first item: `cond`'s cursor addressing. The
parser was small work. Deciding how to check it was not, because on QEMU with
`-device ramfb` the shell's output reaches only the framebuffer, and the
serial line shows the kernel's boot log and nothing after it. So the rig reads
the screen: a QMP `screendump`, cut into 8x8 cells, each cell decoded with
`cond`'s own font table, plain or inverted, and anything that matches no glyph
reads as `?`. It logs in by reading `login:` off the pixels.

Its first full run matched every cell but four: reversed `E`, `V`, `x` and
`z` decoded as `?`, while the reversed `R` before them was right. A pixel
dump showed rows 2 and 3 of each glyph wrong and the rest correctly inverted,
and the disassembly said why. `cond`'s `write_text` loads shift constants into
`q0`-`q3` once at its top and uses them for every glyph, across an `FB_BLIT`
syscall each, and the kernel saved only `x0`-`x30` on the way in; its own
memcpy runs through `q0`. `exceptions.rs` said so in as many words: FP/SIMD
"deliberately not saved", because "nothing running today uses them", and
"this stops being safe the moment real interruptible work with FP/SIMD state
exists". That moment had come the day the first Rust program ran: `shell`
compiles to 1329 vector instructions, `netd` to 1200. Asked, Hans chose to fix
it first, in its own PR, with `cond` stacked on it.

The fix is the obvious one: every resumable path saves `q0`-`q31`, FPCR and
FPSR, the frame grows from 272 to 800 bytes, `Context` grows with it under
compile-time offset asserts, and every task switch carries the state because a
switch is a rewrite of the frame. The probe, `/bin/FPPROBE`, loads all 32
registers inside one `asm!` block and crosses the kernel twice. Its controls
earned their keep: the FPCR control passed with the restore removed, because
the first probe in `fpprobe | fpprobe` wrote its line into the pipe and
blocked, so the two spins never overlapped. The probe now reports once at the
end. The high review then found FPSR saved but never checked, a docstring
claiming that a lone `YIELD` switches tasks (it does not; only the pipeline
tests the switch), and a kernel comment citing a rig that existed only on the
unmerged branch. GitHub refused pushes and API writes with a 500 for about
five minutes in the middle of it, which a retry loop rode out.

## `cond`, the editor's console (#228)

With #227 in, the pixel rig went green. Its controls failed as they should
with `main`'s `cond` and with the old immediate wrap. The deferred wrap was
the one design call: without it, writing the bottom-right cell scrolls the
screen, which a full-screen editor's status line always does. A backspace with
the wrap pending only cancels it, so the shell's `BS ' ' BS` erases the right
glyph; xterm moves back a column instead, and that difference was kept and
stated rather than called xterm's.

The high review found a doc comment promising that every unhandled escape
"never prints" while `ESC ( B` drew a `B` and an OSC drew its title; `CSI 3 J`
wiping the visible screen where xterm clears only scrollback; and the rig's
"no scroll on the bottom row" step unable to fail, since a uniform `#` fill
looks the same scrolled. Every row is its own letter now. Its efficiency point,
erasing a row in one `FB_BLIT`, met a limit the review did not know: the
kernel refuses any buffer over `MAX_USER_LEN`, 512 bytes, 64 glyphs, and the
256-cell attempt erased nothing, silently. The rig caught it at once.

## The navigation keys (#229)

The USB keyboard now sends the VT100 sequences for the eleven keys Edit
named. The shell had to learn to swallow them first: an arrow typed on QEMU's
serial line already put `[A` into the command, and the USB keyboard would have
done the same on Parallels and the Pi. The high review found the worse half:
`passwd` and `useradd` read their passwords through `ulib::read_line`, which
did not filter, while login did, so a password set with an arrow pressed in it
could never be typed at login. The answer was structural: one pure crate,
`keyseq`, that every keyboard reader uses, so two readers cannot disagree about
what was typed. `more` took a sequence as three page-forwards until it read
keys, not bytes.

Two of the review's findings were recorded instead of fixed, because they sit
at the Ctrl-C choke point item 4 had to redesign: a sequence handed out a byte
at a time can be split between two owners, and the tick throws away a byte from
a busy foreground program while it watches for Ctrl-C. Reading the keymap also
showed Tab and Escape sending nothing over USB, so filename completion has
never been reachable from a Parallels or Pi keyboard.

## The screen size (#230)

Edit's Mac version asks the POSIX way, `ioctl(STDOUT_FILENO, TIOCGWINSZ)`, and
falls back to 80 by 24, so that is the interface Ouroboros gave it. A serial
console answers 0 by 0, as Linux does for a terminal whose size was never set.
The kernel half was opening `CON_INFO` to every task: three numbers fixed at
boot. The high review's first finding was mine to own: to let picolibc find the
new header I had put `libc/include` back on picolibc's angle-bracket path with
`-idirafter`, undoing #216's rule that a hand-rolled header can never be
spelled there. The header lives in a picolibc-only directory now. `more`
counted file lines, so a page that fit the screen exactly scrolled its own top
away when a line wrapped; and a kernel refusal had been folded into "size
unknown", so the serial boot could not see the gate close. My own slip: `make
test` went red after the review commit, because my `architecture.md` edit
flagged the published page stale, and a chained command committed anyway.

## The Ctrl-C design (#231)

Item 4 got its design note before any code, as the handoff reply had promised.
Edit enters raw mode with `tcsetattr` and `ISIG` cleared, so `termios` in the C
library with `ISIG` mapped onto a per-task `KBD_MODE` would port it unchanged.
The way out of a runaway raw program is Ctrl+\, in every mode. Hans settled the
four decisions as recommended. DevTools was asked whether Edit binds ^\ before
step 1 is built; the question is still open.

## Keys typed while a program is busy (#232)

Step 0 is a 64-byte kernel queue: the tick reads ahead for a busy foreground
program and keeps what it reads. The flood check, 72 letters then Ctrl+C, kept
failing in ways that turned out to be QEMU, not the queue. The driver keeps one
interrupt buffer, so it takes one report per poll, and a key is two reports;
type faster than that and QEMU's own keyboard queue drops keys, a Ctrl+C among
them. A `poll_key` loop over events was tried and reverted when it changed
nothing. One run hung in its first spin before I bounded the read-ahead loop,
and its transcript was overwritten before I kept it; the cause is unknown, the
bound is in, and every run since has passed.

The high review found the PR's headline untrue. The waits for a child's exit
and for a message also read the keyboard for the owner and threw each byte
away, and an editor redrawing is mostly blocked in exactly that wait, since
every `con_write` is a call to `cond`. The rig could not see it, because
`readkey spin` read everything it was given before it exited: the probe drained
its own input. The review also found that a Ctrl+C left the bytes typed before
it for the next owner, so `rm foo`, Enter, Ctrl+C would have run `rm foo` in
the shell. Ctrl+C flushes the queue now, as Unix does on an interrupt, which
refines Hans's D3 (it said keep type-ahead when a program ends) and is flagged
for him. The first message-wait check wrote to the console during the spin;
its control showed it could not fail, because `cond` answers within the tick,
and it holds the owner in `MSG_RECV` in a pipeline instead.

## Keys arrive whole, half of it (#233, open)

Step 3 shipped first as two mechanisms: a full queue taking a whole key back
out, and a second parse of the bytes handed to readers that dropped a key's
rest when the keyboard changed owner mid-key. The high review found the second
one going stale: a Ctrl+C flush left it mid-key, so the shell would lose the
first letter typed after a kill; a serial terminal's bare Escape left it
waiting for a tail that never came; its drop loop ran unbounded with interrupts
masked. The review named the cause too, a second parser that every path
touching keyboard bytes must keep in step. I took it out rather than patch it,
recorded the review's single-parser design in the plan, and kept the whole-key
half, whose check now uses 63 letters so it reaches the drop branch the 62-letter
version never did.
