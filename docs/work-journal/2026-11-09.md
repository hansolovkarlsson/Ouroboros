## Step 8's medium review: one test of "this user is held"

The medium review of step 8 found ten things, and three of them were one
defect seen from three sides. `netd` had three answers to "is this user
still held": the session lookup asked whether a live login held the key,
`close_unheld` asked whether any key was held at all, and `seed_for`, which
picks the key to sign with, asked nothing about liveness. So in the window
between a login being killed and the idle pass reaping its key, the dead
login's key went on attesting new sessions, and the lookup passed over a
stale attested session and opened a second one beside it. If the user then
logged in again, the old session became usable again, first in slot order,
and the new session's fids were sent down it. The fix was one predicate, a
key counts only while its login lives, asked by every caller; `park_session`
now closes a stale session for the uid it parks instead of passing it over;
and `sign_parked` checks again at the send. A fourth finding I first meant
to leave alone: a verb already on the wire when its session closed was
"left to finish". Reading the export settled it: on a client's FIN the
export drops the connection, reply unsent, so the caller waited out the
deadline. Every parked verb is now refused at the close, which also removed
the high review's special case for an open caught by a logout.

The controls showed two things the rig cannot see. A dead login's key
still signing is not caught, because no request from that user falls
between the kill and the reap; it is recorded as not covered, beside the
uid-at-sign-time mutation from the night before. And the control that
removes `close_unheld` went from caught to not caught on its first check:
`park_session`'s new close sends the logout FIN itself when the `su`'d
request parks, so the check for that FIN passed. The control is still
caught, by the FIN after the kill, which only `close_unheld` sends. Merged
as #429 at 10:24.

## Step 9: the docs, and a plan item no step owned

Step 9 is the arc's docs, rigs and release, and reading Decision 9 to write
the manual found something unbuilt: `useradd` and `passwd` were to print
the `/etc/cluster/users` line for the password they set, and neither did,
and no step had owned it. Without it, only the dev images, whose registry
is staged at build time, could use the arc at all, since a user's public
key comes only from their password. I built it in this step rather than
recording it, because a release whose feature cannot be set up outside the
test images is not a release of that feature. The rest was the docs: the
normative block's scope paragraph, the manual's trust section around root
squash and registered users with its paragraph on strong passwords, a
section in `architecture.md` on `netd` as the key agent, four man pages
(`login`'s still described inline SHA-256 secrets and said there was no
`passwd`), the cluster roadmap's encryption item with the offline-guessing
exposure as a reason its trigger matters more, and the arc moved to
`roadmap-completed.md`.

The high review's largest finding was a design point, and it was right:
with the line printed only when a password is set, registering an existing
user meant resetting their password, root learning it in the process, and
a new realm meant resetting everyone's. The key is a pure function of
name, realm and password, so `clusterkey user <name>` now prints the line
from a password typed twice, on standard output alone, and the user hands
it over. The medium review then caught my fix for that review's copies
finding: I had put the read-and-derive in `ulib`, which put `clusterkeys`
and `ed25519` under every userland program for three tools. It went back
into `clusterkeys`, over a realm file the caller reads with a new generic
`ulib::read_file_status`. That review also read the tree while a mutation
control was applied, and reported the mutant's `&& pwl == usize::MAX` as a
finding. Merged as #430 at 12:09.

## After the closeout: the run ends with its user

Hans answered both questions in the afternoon. A `cpu` run sent with the
user's credential now counts as in flight only while a live login holds
that user's key. That is asked where the run is counted, not after the idle
pass, so Decision 7's `/host` window closes in the same pass as the key. The
caller gets the output so far and a line saying why. The 684-byte limit
stands, because the export refuses any fid path over 96 bytes, so nothing it
refuses would have been served.

The rig took four commits to get right, and the first two were wrong in
the same way. They assumed Ctrl+C would bring root's prompt back: the first
waited for `# ` after it, the second sent a second Ctrl+C to get there. A
Ctrl+C with a nested shell owning the keyboard detaches it, and root's
shell prints nothing new, its prompt having been printed at the `fg`.
Whether the nested shell's `cpu` call is cut as well depends on timing, and
both happened, so the third version's wait on "remote run failed" held
only sometimes. The version that works sends one Ctrl+C, waits two seconds
and types the kill.

The medium review found nine things, and the one that mattered was a run
that escaped the rule: a user who logged out between typing `cpu` and the
run being sent got a run sent without a credential, which the rule then
never ended. A run is now marked from the moment it is queued, and one
whose key went before the send is not sent. The review also found the
manual, the site and a man page saying every run ends at logout, where only
a credentialed one does, and that I had told Hans the command left running
on the far machine was already on the roadmap's item 1 when it was only in
the receive-path ledger, which item 1 now points at. One point was not
taken: a run with no credential keeps its window past a logout. Such a run
either has no realm behind it, where the machine's word serves anyway, or
is root's `su`, and root on the dispatching machine already holds what the
window lends; the plan records the argument, and it is Hans's to overrule.
Merged as #433 at 19:06.
