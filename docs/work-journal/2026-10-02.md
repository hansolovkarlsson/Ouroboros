## The EL1 drop, steps 0 to 2, on QEMU

The plan written last night was built this morning, one step and one commit
at a time on `pi4/el1-drop`. Step 0 was the line the module that owns the
vectors had owed since its first day: `running at EL{n} after the exit`, from
`CurrentEL`. Plain QEMU says EL1; `make run-el2`, the new target with
`-machine virt,virtualization=on`, says EL2, reaches `shell ready` and then
faults at address 0 through the firmware's vectors, which is what the plan
predicted and what the test for step 2 would later have to make go away. A
temporary read on the way, removed before the commit, gave two facts the drop
needed: QEMU's firmware leaves `SCTLR_EL1` at `0x30d0198d` on an EL1 handoff,
and at EL2 it leaves `HCR_EL2` at `0x8000038`, routing interrupts to EL2.

Step 1 split the identity map install into a build half that writes memory
only and a switch half that writes registers, with the build half's result a
value the switch half requires, so the switch cannot be spelled without the
build. The register values moved into one function both switches read. The
module doc asks for its deliberate-fault check whenever the module changes,
so a write to block index 2 after the switch was planted, reported by the
kernel's own handler, and removed; then the plain boot, the early-fault test,
and three spawned programs on the FAT32 image, which is the runtime rebuild
path the split also touched.

Step 2 is `kernel/src/el2.rs`. The decision lives at the switch: at EL2,
`switch_to_identity_map` drops instead of switching, setting EL1's regime to
the built tables, `SCTLR_EL1` whole, the hypervisor controls for a plain EL1
of itself, the firmware's EL2 timer off, and `eret` onto the same stack. One
choice differed from the plan as written: whether the GIC's system registers
exist is read from `ID_AA64PFR0_EL1`, not taken from the MADT, because on a
GICv2 the `ICC_SRE_EL2` write would be an undefined instruction and the ID
register is the hardware's own answer. It worked on the first boot: EL2,
dropped, shell ready, and the fault at address 0 gone. The checks that
followed were the ones that could fail: a twelve-second dwell with `help`
answered and QEMU's own trace showing no abort, the GICv3 shape, the image
with a login and spawns, `shutdown` powering off, and the plain shape
unchanged. The rig is `test-early-fault.py --el2`, whose control now requires
the handoff level, the drop and the answered `help`; with the drop disabled
behind a temporary edit it failed on three checks, the first being the
`EARLY EXCEPTION` of the morning's run. A small line beside it: `power.rs`
logs the PSCI conduit the FADT names, since after the drop an `hvc` from EL1
has nobody to answer it; QEMU names `smc` under `virtualization=on` and `hvc`

## The drop on the board

Hans merged #188, staged a card from `main`, and booted the Pi 4 twice under
`NOXHCI`. The first boot died inside `ExitBootServices`, and the reporter
printed the whole dump this time, rows and all: a firmware write at
`DxeCore + 0xae14` to `0x38670810`, a RAM page the firmware's own tables do
not map, nine frames below the kernel's call into the service. That
instruction, `0x39F36E14`, is where two of yesterday's boots died inside the
xHCI takeover, and today the controller was never touched. So the fault is
not the takeover's doing, as the memory-damage theory had it, but a DxeCore
routine reached from both the PCI protocol and the exit, writing into a
hole in its own tables, on some boots and not others; the pftf build sets no
heap guard, so the hole is not a freed-memory guard. A second dump at the
same address is the next data point.

The second boot was the one the day was for. Checkpoint 5b's three lines
came in order through the kernel's own PL011 driver: `running at EL2 after

## The reporter's rows first, and its walk bounded

While Hans boots the card again for a second dump, the desk took the
reporter's two owed fixes. The register rows now print before anything that
reads firmware memory, since they need only the context the firmware saved,
and yesterday's walk faulted at frame 10 and lost them. The line a fault
inside the report prints carries `far` now, and the address of the image
header or device path that was being read when it happened, kept in a
static set around each such read. And the image walk believes a firmware
pointer only inside the RAM span the memory map reported at arm time, read
in the same pass that finds the stack's end: the table, each entry, each
loaded-image record, the image itself (page-aligned, at most 64 MB) and its
device path. Yesterday's nested fault came from an entry whose image
claimed to hold `0x26e28`; whether that lies outside every RAM descriptor
on the Pi is for the `armed` line to say, which now states the bound (the
kernel's own RAM span there starts at `0x3b0000`, but the reporter admits
more descriptor types, and the tree holds no record of the Pi's map). A
hole inside a descriptor, today's kind of fault, cannot be told from a
range, and the named address is what the dump can offer for it. The rig checks the order, and three mutations in turn showed what each
piece does: with the rows moved back after the walk the order check went
red; with a fault planted inside the walk the rows were on the transcript
and the nested line named the planted address and the image under read;
with every read refused the dump completed, each firmware address marked
as in no loaded image and the kernel's still named by its own range.

A high-effort review found seven, all taken. The bound had been one span
from the lowest to the highest RAM address, which admits a device window
between two RAM ranges, and `in_ram(0, n)` whenever a descriptor starts at

descriptors themselves, through the MMU's own `is_general_ram` rather than

A second review found ten, all taken, two of them real. The bound kept the

a kilobyte copy per range check on the fault path; and three records that

## Four more boots, a third firmware fault, and a cap in the wrong place

Hans booted a card from the merged tree four times under `NOXHCI`. Three
went through the drop to the shell. The fourth died before the exit, while
the firmware was drawing a line of text onto HDMI: a 32-byte copy into the
framebuffer took a level-2 translation fault in the firmware's own tables,
on memory the firmware had been drawing into all boot. The rows printed
first, as #189 meant them to, and the dump also showed #189's defect: the
walk's bound read "3 RAM range(s) ... the map had more", because the cap
of 64 had been applied to raw descriptors before the merge, and the Pi's
map has more than 64, so the top of RAM, where every firmware image lives,
was dropped and the dump named no image. The merge now happens as each
descriptor arrives, so the cap counts ranges; a throwaway host build of the
insert function on six inputs, a QEMU boot with the cap at one, and both
rigs checked it. The bound did give one fact: the Pi's lowest RAM range
starts at `0x3b0000`, so yesterday's entry claiming `0x26e28` is outside
the walk.

Three firmware faults in a day, read together: each a DXE core write to
memory the firmware had mapped and was using, each a translation fault in
its own tables, at three addresses and three kernel steps, on a minority of
boots. That is not a missing mapping; it is a table entry that was valid
and is not, cleared or overwritten. The instrument that tells those apart
is the reporter walking the firmware's live translation tables for the
faulting address at the moment of the fault and printing each level's
entry, which is the next piece of desk work.

## The tables walked at the fault

The instrument is a line in the dump, after the rows and before anything
is placed: the reporter reads `TTBR0` and `TCR` of the level it runs at,
walks the firmware's live stage-1 tables for the faulting address, and
prints each level's entry, its address and its value, down to the leaf or
the first invalid one, with the four entries either side of an invalid one
and a word on whether the level agrees with the ESR's. The planted test
fault moved for it: bit 47 lies above the input range, where the walk had
nothing to read, so both test faults now land on the first byte past RAM,
which on QEMU is `0x60000000`, under a populated L1 with the L2 entry zero
and its lower neighbours valid, the exact shape of the Pi's framebuffer
fault; on a board the address is the lowest page past RAM that no
descriptor of any type covers, chosen from the map at arm time, since
the first byte past RAM may be a reserved carve-out or a device window
the firmware does map (a high review caught the assumption). The rig requires the line and the agreement. On the Pi, the
entry's value is the answer the day's three firmware faults have been
waiting for: zero means cleared, anything else means overwritten.

## The tables read as stack frames

The first boot of a card with the walk faulted at once, in the firmware's
variable store driver, and the line the instrument was built for said
something no one had listed as a suspect. The firmware's root translation
table, at `0x3b3fa000`, holds stack frames: a saved frame pointer into the
same page, a small count, zeros. The Pi firmware's stack is sixteen
kilobytes at the top of RAM, `0x3b3fc000` up, and its page tables sit
directly below; the kernel has run on that stack since its first boot
anywhere, as a debug build with large frames, and on the Pi its deepest
calls, with the firmware's timer interrupt landing on top at a random
moment, push past the stack's bottom and write frames over the tables. The
TLB keeps the firmware running on cached translations until a cold page is
walked, and the walk fails at whichever level's page the overflow reached:
level 3 yesterday and this morning, level 2 this afternoon, level 0 tonight.
Four firmware faults at four addresses in four kernel steps, one cause,
invisible on QEMU because its firmware's stack is 128 kilobytes with the
tables elsewhere. The day's suspect list had the kernel's own writes first,
but as writes outside what it owns; it was the stack, which was never the
kernel's to begin with. The fix is a stack the kernel owns from its first
instruction, and it goes on the roadmap as the next item rather than into
tonight.

## A stack of the kernel's own

The fix went in the same evening after all. The entry's first act is now to
read the firmware's stack pointer, keep it, set SP to the top of a 256 KB
array in the kernel's own image, and call the kernel proper, which never
returns; its frame pointer is left pointing at the entry's frame on the
firmware's stack, so the reporter's walk can cross from the kernel's frames
into the DXE core's and the BDS's that called it, which it does on QEMU
with the firmware's stack at a lower address than the kernel's. The banner
line names the stack it is on, and with the switch skipped by a temporary
edit it names the firmware's instead and the rig's control fails. Both rigs
pass on both shapes, the image logs in and spawns under both, and the
suite is green. What this changes on the Pi is for the board to say: a
`NOXHCI` boot that never faults in firmware code, and, if one does, a
`tables for far:` line with entries in it rather than frames.
