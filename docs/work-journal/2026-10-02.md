## The EL1 drop, steps 0 to 2, on QEMU

The plan written last night was built this morning, one step and one commit
at a time on `pi4/el1-drop`. Step 0 was the line the module that owns the
vectors had owed since its first day: `running at EL{n} after the exit`, from
`CurrentEL`. Plain QEMU says EL1; `make run-el2`, the new target with
`-machine virt,virtualization=on`, says EL2, reaches `shell ready` and then
faults at address 0 through the firmware's vectors, which is what the plan
predicted and what the test for step 2 would later have to make go away. A
temporary read on the way, removed before the commit, gave two facts the drop
needed: QEMU's firmware leaves `SCTLR_EL1` at `0x30d0198d` on an EL1 handoff,
and at EL2 it leaves `HCR_EL2` at `0x8000038`, routing interrupts to EL2.

Step 1 split the identity map install into a build half that writes memory
only and a switch half that writes registers, with the build half's result a
value the switch half requires, so the switch cannot be spelled without the
build. The register values moved into one function both switches read. The
module doc asks for its deliberate-fault check whenever the module changes,
so a write to block index 2 after the switch was planted, reported by the
kernel's own handler, and removed; then the plain boot, the early-fault test,
and three spawned programs on the FAT32 image, which is the runtime rebuild
path the split also touched.

Step 2 is `kernel/src/el2.rs`. The decision lives at the switch: at EL2,
`switch_to_identity_map` drops instead of switching, setting EL1's regime to
the built tables, `SCTLR_EL1` whole, the hypervisor controls for a plain EL1
of itself, the firmware's EL2 timer off, and `eret` onto the same stack. One
choice differed from the plan as written: whether the GIC's system registers
exist is read from `ID_AA64PFR0_EL1`, not taken from the MADT, because on a
GICv2 the `ICC_SRE_EL2` write would be an undefined instruction and the ID
register is the hardware's own answer. It worked on the first boot: EL2,
dropped, shell ready, and the fault at address 0 gone. The checks that
followed were the ones that could fail: a twelve-second dwell with `help`
answered and QEMU's own trace showing no abort, the GICv3 shape, the image
with a login and spawns, `shutdown` powering off, and the plain shape
unchanged. The rig is `test-early-fault.py --el2`, whose control now requires
the handoff level, the drop and the answered `help`; with the drop disabled
behind a temporary edit it failed on three checks, the first being the
`EARLY EXCEPTION` of the morning's run. A small line beside it: `power.rs`
logs the PSCI conduit the FADT names, since after the drop an `hvc` from EL1
has nobody to answer it; QEMU names `smc` under `virtualization=on` and `hvc`
plain, and powers off on both.

Step 3 is the board, and it is Hans's: one Pi 4 boot under `NOXHCI`, the
first whose log past the exit can mean what it says.
