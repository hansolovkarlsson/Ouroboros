# 2026-11-01

## The give-back, by its bits

The morning merged yesterday's closeout (#381) and took the first of the
three items #380's reviews had left. A FAT batch that failed gave its
clusters back by walking the FAT on the disk, or not at all: `write_chain`
skipped the walk whenever a refused flush had lost entries, so its whole
chain leaked, and `write_at` gave back none of the clusters it linked past a
file's size when a data write failed part way, a leak older than the batch.
The bitmap alone says what is free in exFAT, so a batch that knew what it
took could clear those bits and walk nothing. The design question was the
record, since fsd has no heap and the clusters are not always consecutive.
Inside a batch the scan only goes forward, though, so neighbouring finds
extend a run, and 32 runs in about 270 bytes cover every batch a rig makes.
A find past the 32nd leaks, as every failed batch did before.

One FAT entry has to be written before any bit is cleared: the end of chain
of the file's last cluster, which `write_at` linked on from. Without it the
link lies past the file's size, where fsd's walks stop, but fsck_exfat
follows a chain to its end and finds the clusters free. The rig's new GAP
case is what showed that. GAP refuses a gap fill's data write, and from that
day `test-batch-refused` runs fsck_exfat after the boot, which it had not.
Three of the day's rig commits were the rig getting its own evidence right:
HEAD's case read off the fill's own links rather than W's cut entry, and the
cursor control needing both cursor drops removed before it failed, since
either alone covers the other.

The high review of #382 found three more leaks. `write_at`'s set write could
be refused after its batch succeeded, and nothing gave the clusters back;
the record now stays until the next batch starts, so it can. `write_file`'s
replace leaked its new chain the same way, and frees it by a walk now, as
its create does. And the cut cluster was inferred from the record, which a
find past 32 runs is not in, so `write_at_chain` names it. Each run is also
cleared on its own, so a failing bitmap sector loses only its runs. SET and
REPLACE joined the rig, and #382 merged.

## The batch, a type

The second item was the mode flag. A batch was `fat_batch` on `Fs`, changing
what four methods did, and its two rules (nothing frees inside a batch;
nothing leaves a dirty FAT sector outside one) were held by refusals that
answered an I/O error. A later change breaking either would have shown the
user a failing disk. The project's answer to that shape is the unspellable
lesson, and the disk gate already showed the pattern: a type in a module of
its own whose field nothing outside can reach. `batch::FatBatch` holds the
only `&mut Fs` while a batch runs and is made only by `batch::run`;
`write_at`'s walk, outside the module, reads through `&Fs`. A free, a nested
batch and the rest are not refused any more, they do not compile.

The high review of #383 found no bug in what shipped. Its eight findings were
places where the type allowed more than its docs claimed: an entry writer
that took any value, 0 among them, so a free could be spelled as a write;
and a setter for the cut cluster. Both are inside the module now. The review
also asked that the misuses be a check rather than a sentence in the
CHANGELOG. `check-disk-handle.py`, which already built fsd with spellings
that must fail, now builds nine against the batch on every `make test`. With
the field or the entry writer made `pub(super)` it fails on exactly the
spellings that opens. The old refusals stay as tripwires that print a line of
fsd's own. One printed during a control: with `batch::run`'s end flush
removed, `test-alloc-batch`'s fill stopped at its first gap, each `writeat`
printing the line. The client still sees `FS_ERR_IO`, because a wire code for
a path nothing reaches would be a protocol change for nothing. The write
cursor a body leaves is still the body's to get right.

`test-long-set` stalled in the firmware once on the final tree (VRUNS) and
passed when run again. My summary log showed that run as `exit 2`, and only
the rig's own last line said INCONCLUSIVE, which I read before Hans merged
#383.

## The hint

The third item was the allocator's scan. Outside a batch every allocation
started at the bitmap's first byte, a USB round trip for every full bitmap
sector before the first clear bit on a nearly full stick. FAT32 had shown
the fix in October: a hint kept across requests and lowered by every free.
The observation that shaped the change was that while every free lowers the
hint, every byte below it is full, so the first clear bit from the hint is
the one a scan from byte 0 finds. Placement does not move; only the reads do.
That let the change be graded by rigs that already existed rather than a new
one. `test-alloc-batch`'s second request reads 3 bitmap sectors, not 4, and
4 again with the reset put back. `test-stale-cursor` builds its stale cases
by reusing a removed file's cluster, so it fails 4 checks with the lowering
removed. I expected `test-batch-refused` to fail on that mutant too, and it
passed: its given-back clusters sit in the bitmap byte the hint already
points at, and a hint kept a byte at a time cannot tell them from the ones
it would find anyway.

The high review of #384 found a case the old reset had hidden. When the disk
refuses the allocator's bitmap write, the bits it set stay clear on the disk
while the hint has moved past them, so those clusters went unused until a
full scan wrapped; before the hint, the next scan started at byte 0 and
found them. `end_alloc_hold` now lowers the hint to that sector's first
byte. I declined its finding that the wrap costs a request an extra pass on
a full volume, with arithmetic: the hint to the end, then byte 0 to the
hint, one pass in all. The medium review showed the arithmetic was a sector
off. Wrapping from the hint's byte reads the hint's own sector a second
time. The scan now starts at the first byte of the hint's sector, which is
held or read first either way, and the claim is true. That review also
asked for the rig no one has: nothing can fail the lowering on a refused
write, or the wrap, since both need the disk to refuse two writes in one
batch. That went onto the roadmap with the blkdebug case that would build
it, rather than into the PR. `test-alloc-batch`'s model now starts its hint
at the setup's last find, read off the base boot's disk, instead of
assuming it. #384 merged.
