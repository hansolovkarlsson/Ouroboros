# 2026-10-10

## #253 merged, and the `Ozq` check made to fail (#254)

#253 merged in the morning after a low review found nothing. Hans then asked
for the check it had left blind. The question was why `test-kbd-mode`'s Esc
check could not fail even with E1 and E2 both removed, which a reading of the
queue said it should. The transcript of that run answered it: between the
interrupt and `Ozq` the rig typed the shell's next command, `readkey spin 100
keep`, and under the day-old `keyseq` its `r` ends any open Esc. The bytes
the check meant to probe were never the first after the interrupt. On main
the same check had been masked by E2 instead, which closes the Esc 40 ms
after it is read, long before the next key is.

The fix was to make `Ozq` the shell's next line. Run three ways: green on the
tree, red with E1 and E2 removed together (the shell ran `q`), green with E1
alone removed. That last result is not a weakness of the check but a fact
about the system: E1 matters only for a key read within E2's interval of the
Esc, and the shell's wake and its `wait: interrupted` line take longer, so no
rig can see E1 alone. Its host test is the check for it, which
`test-kbd-cut`'s check 3 already said for the kill path.

## The `/net` poll check that cannot be run

Hans asked for the first item of the standup's "unchecked by any rig" list:
`poll` on a `/net` file answering `POLLERR`. Reading `file.c` before writing
the rig answered it. `open` refuses the `/net` binding at `resolve_target`
(ENOSYS, the same refusal the console binding gets), so a C program cannot
hold a `/net` fd, every open fd is fsd's or a remote mount's, and `poll`'s
`POLLERR` branch is unreachable. A check of it cannot fail, and deleting
the branch would change nothing any run could see. The claim that a `/net`
file "is `POLLERR`" stood in `poll.h`, `file.c`, the changelog, the source
map and the gap analysis, a sentence true of no observable run since #240.

What went in instead is the smallest thing that makes the claim checkable:
`cpoll timing` opens `/net/ip` and `/net/tcp/clone` after the rig's
`mount -n /net`, asserted as its own step, and prints each errno, and
`make test-cpoll` requires ENOSYS for both (a high review of #256 added the
connection file, the file a program would poll, since an `open` that
learned only `/net/tcp` would have left the status file refused and the
tripwire green; it also had the verdict quote what the guest printed). The branch stays as the
default an `open` that learns `/net` would fall into, which is safer than
a "ready" whose read blocks; the day that happens, the tripwire fails and
the real check is owed with it. The five records now say that. The lesson
is the standup's own, read the other way round: before writing a check,
ask whether the input it needs can be made at all.

## The ISO key check that no rig can run

The next item from the same list, the ISO keyboard's backslash key at HID
0x32, which `xhci.rs` maps as the US key so Ctrl+\ works from it. The rig's
docstring already said QEMU cannot send it, and before accepting that I
checked it two ways. keycodemapdb, QEMU's keycode table, lists the US key

gives both positions one scancode, so `prlctl` cannot press it either, and
the kernel has no host tests. The check is therefore a by-hand row in the
Parallels matrix, A7, and needs an ISO keyboard; an ANSI one has neither
key. The roadmap says so, and that the mapping rests on the HID usage table
until a hardware session types it. Two items from the list, two checks that
could not be run as asked, each for a different reason: the first because
the input cannot exist on this system, the second because no instrument

## Step 2 of multi-core: the cores started and parked

`kernel/src/smp.rs`, the first code of the arc that runs on a second core.
The boot core fills a parameter block (the EL1 regime it switched to, kept
by `mmu::boot_regime` since the switch; the register values `el2.rs`
writes for a drop, now `pub(crate)`; the vector table's address; the stack
array), cleans it to the point of coherency, and calls PSCI `CPU_ON` for
every core the MADT lists but itself, by affinity. The secondary wakes with
the MMU off in a `global_asm!` stub that touches no stack until the MMU is
on: it loads the block, writes its core index to `TPIDR_EL1`, and either
programs EL2 as the drop does and `eret`s into EL1 with the MMU running, or
at EL1 turns the MMU on in place; then it takes its stack, brings up its
own GIC interface (`gic::init_this_core`, the per-core half split out of
both backends, with GICv3's `SGI_BASE` named as the per-core static it is),
prints `core N up at EL1`, and parks in `wfe`. The console gained a lock
with a bound, so a fault handler on a core that cannot get it still
reports, and every fault line now says which core (`EXCEPTION core=N`),
which made `test-early-fault`'s pattern a thing to update.

`make test-smp` grew to four boots: `-smp 4` on the dev loop and under
`virtualization=on`, `-smp 1`, and `-smp 4` with a `\SMPFAULT` flag that
has core 1 take an undefined instruction after its up line. All the kernel
checks were green on the first run, the EL2 path included; what failed was
the rig expecting a login from a vvfat boot, which has no `/etc`, and then
`echo` from a boot with no `/bin`. The fault boot showed the thing the step
is for: core 1's fault line named core 1, and the boot core's shell went on
answering. The Pi 4 and Parallels boots are owed; on QEMU the caches are
not modelled, so the clean-to-PoC of the parameter block and the stub's
no-stack rule are reasoning, not yet observation.

The high review found nine things, four of them defects a green rig had
not seen. A secondary listed at MADT index 0 (ACPI fixes no order on ARM;
QEMU happens to list the boot core first) would have taken a stack below
the array and the boot core's index; stacks are now indexed by the table's
own index, the boot core takes its own index once the table is read, and
each secondary's stack has a canary the fault line checks. The stub's own
code was not cleaned to the point of coherency, only its parameters; the
firmware's loader cleans to the point of unification, the shared L2 on an
A72, and a fresh core fetches from memory. A secondary's GICv3 init stored
its redistributor frame over the boot core's, which `enable_interrupt` on
the boot core reads; the per-core half now returns the frame and only the
boot core's `init` stores it, and the rig gained a `gic-version=3` boot,
since the owed target, Parallels, is GICv3 and no boot had run that path.
And a core that died holding the console lock left it held, so every later
line on every core would have paid the full bound; the writer now takes the
lock over after the bound. The five others were a `nomem` on the `CPU_ON`
asm that hands memory to another core, three doc comments an inserted item
had stolen, a flag's missing doc line, and the GICv3 rig. The lesson is
the one in the plan's own risks list, now with an instance: QEMU's table
order, QEMU's unmodelled caches and QEMU's default GICv2 each hid one.

Hans asked for a second high review on the repairs, and it found ten
more, four of them real. The `CPU_ON` asm declared the target, entry and
context registers as inputs only, so the compiler could keep `entry` in
`x2` across the call, which SMCCC lets the callee scratch; now they are
outputs too and `x4` to `x17` clobbered, and PSCI's `int32` result is
read as one. `CON_WRITE` wrote `cond`'s batch one `putc` at a time, each
taking the console lock, so a secondary's line could land inside an
escape sequence; the batch takes the lock once. A core marked itself up
before its first console write, so a core dying there counted as up; the
mark follows the line. A panic on a secondary core (GICv3's redistributor
lookup, or the system-register interface refusing) had no path but the
firmware's, which is gone after the exit; the per-core init returns the
reason and the core parks without a GIC interface, saying so. The rest:
the lock's takeover could leave two owners, so it is now owned by core
index and a stale holder's unlock is a no-op; a boot core the MADT does
not list starts nothing rather than sharing index 0; the two single-core
claims (`synccell.rs`'s argument, the rebuild's safety comment) now say
what the parked cores do and do not touch; four prose copies brought to
the code; and the EL2-with-GICv3 boot, the one shape that runs the stub's
EL2 GIC branch, added as the sixth. Two high reviews, nineteen findings,
on a step whose rig was green from the first run: the rig checked what

## Step 3 of multi-core: the three decisions

Three decisions the plan wanted on one core before cores run tasks.

FP/SIMD, eager or lazy: measured. A new program, `syscost`, times 200,000
`GET_TICKS` calls by `MONOTONIC_US`, and `make measure-syscost` runs it
three times and takes the median: 24,934 ns a call on the tree, 25,232 ns
with the save and restore macros emptied. The first thing the number says
is about the instrument: under TCG a syscall's exception round trip costs
about 25 µs, and the 64 vector stores and loads of the save vanish in its
noise. On hardware the round trip is a few hundred nanoseconds and the
save about a hundred cycles, a real fraction but a small absolute cost,
against what a lazy scheme would add per core (a trap handler, an owner
word, the kernel under the task's FPCR until the trap). Eager stays,
recorded in `exceptions.rs` with both figures and the caveat, and the Pi's
figure named as the one that could change it.

The tick's jobs: the boot core's tick keeps all four (counting, the
keyboard read-ahead, the supervisor's checks, timed waits) when every core
has a timer; a secondary's tick switches its own tasks and ends their
waits. Written on `on_tick` and in `supervisor.rs`, where step 4 will
read it.

Task 0's entry: `tasks::start` no longer carries its own `eret`. It lays
a copy of task 0's Context out as a frame on the kernel stack, moves `sp`
to it and branches to `resume_frame`, a new global label at the IRQ
trampoline's restore tail, so task 0 starts with every register its
Context holds, x0 to x30 included, and the kernel has exactly one way
into a task. The measurement's boots were the first to cross it; the
rigs below are its check.

## Step 4(a) of multi-core: the kernel lock

The first PR of step 4. `kernel/src/lock.rs` is one lock around every
resumable entry's Rust half: a syscall, the tick, an EL0 fault, each now a
locked wrapper around its old body, releasing before the trampoline's
`eret`. Owned by core index, never reentrant: a re-entry or a stray
release prints a line and halts that core rather than deadlock in
silence. The plan had named "the scheduler lock and the device locks" for
this PR, and writing it showed why that was one lock too many: while one
core at a time is in the kernel, a device lock guards nothing the kernel
lock does not, so per-device and per-slot locks are the splitting of this
one, each paid for by a measurement once 4(b) gives it a second core to
contend with. The measurement for this PR is `make measure-syscost`:
24,934 ns a syscall before, 27,786 ns after, an uncontended acquire and
release per entry, which under TCG are two atomic read-modify-writes
through its slow path, and on hardware tens of nanoseconds. The 9P verb
cycle from the two-VM rig is the figure for the split, not for this.

## Step 4(b) of multi-core: an idle loop and a tick on every core

The first PR in which a second core runs EL0 code. `tasks::CURRENT`
became one slot per core; a secondary, after its up line, activates the
idle view, allows EL0's `wfe` for itself, enables the timer PPI at its own
GIC interface (a new `gic::enable_ppi_this_core`, since the boot core's
`enable_interrupt` wrote GICv2's banked register for itself and GICv3's
for its own redistributor), arms its timer, and enters the idle loop
through the shared task entry from a fresh idle context, not slot 1's,
which is the boot core's idle (a per-core context array went in first and
out again at the review, having no reader: the frame on the core's own
stack is the state). Its tick, dispatched by core
in the IRQ path, counts and says so once; the boot core's tick keeps every
job, as decided in step 3. A rebuild of the tables now ends with `tlbi
vmalle1is`, since the parked cores walk them.

The first run of six boots found two things the design had not. Every
secondary faulted at EL0 with an undefined instruction at the idle page's
first byte: `smp::start` ran before `tasks::init` had copied the idle loop
into that page, so the cores executed zeros. And the shell never came up,
because the faulting core's EL0 fault handler halted inside an entry,
holding the kernel lock the boot core needed at its next syscall; `halt`
now releases the lock if the halting core holds it. Started after
`tasks::init`, all six boots were green but for the rig's own expectation
that the `\SMPFAULT` victim ticks, which it cannot, having halted before
its idle loop. One thing seen and left: a userland banner written by
`PUTC` one byte a call can have another core's kernel line land between
two of its syscalls (`uroboros user` then `core 1 ticking`), which the
console lock does not cover and should not; it is line-level, not
byte-level.

The high review of 4(b) found nine things, five of them real. Moving
`smp::start` after `tasks::init` had moved it out of the `if` that
guards on a GIC being found and past the console's quiet switch: on a
machine with no interrupt controller every secondary would have panicked
in `gic::info` with no path to say so, and on a framebuffer-only console
every line the start prints would have been dropped; it now runs only
with a GIC, after the idle page is filled and before the quiet switch.
A device interrupt reaching a secondary would have run `on_net_irq` on
it and switched that core into the network server behind the
scheduler's back: GICv2 routed every SPI to CPU 0 by a literal, which is
the boot core only when the firmware started there, so SPIs now go to
the enabling core's own mask (read back from `ITARGETSR0`), and a
secondary's IRQ path takes its timer and drops anything else. The halt
that released the kernel lock let the other cores run over half-written
state; `power::halt` now tells two cases apart, a core holding the lock
or the boot core halts the kernel (`lock::HALTED`, every other core
parking at its next entry), a secondary holding nothing halts alone, and
the two fault handlers that used to end in `main.rs`'s silent `halt`
now end there too, so the rig can see which happened. The rest: the
rebuild's soundness argument restated for cores that now run EL0 code
from the tables it rewrites, with the check that is owed named; a dead
per-core context array removed; the task entry shared by `tasks::start`
and the secondaries as `tasks::enter_frame`; stale "parked" wording; and
one duplicated boot-core test. Rerun: six boots, the suite, four rigs,
all green, and the fault boot now also requires the lone halt line.

The second high review found ten more, one of them a hardware case: a
GICv2 whose first target byte reads as zero would have routed the NIC's
interrupt to no core, so the mask is scanned across the eight banked
registers with a said fallback. The rest were records and shape. On the
confirmation run after those fixes, `test-early-fault`'s control boot
failed once with no transcript kept and passed on the rerun with every
check green; the rig's output in the background run held only the verdict
line, so the cause is unrecorded. A third unexplained one-off for the
standup's watch list, beside `test-kbd-queue`'s and `test-keyboard-chain`'s.

## Step 4(c) of multi-core: the kick

Hans asked for 4(c), the SGI for kills, owner changes and TLB shootdown.
A reading of the plan against the code before any of it was built found
that two of the three uses do not hold. A TLB shootdown needs no SGI on
ARMv8: `tlbi vmalle1is` and `ic ialluis` reach every core in the
inner-shareable domain in hardware, which is why Linux on arm64 sends no
IPI for a flush, and every rewrite of the shared tables already ends with
them. An owner change needs nothing done on the target's core. A kill does,
but no task runs on a secondary until 4(d), so a remote kill built now would
have no check that could fail. The plan's rule for the handler was wrong
too: "an SGI handler takes no lock, its work waits for the next tick"
would make the SGI no faster than the tick. Hans scoped 4(c) to the SGI
itself, with the remote kill moved into 4(d).

What went in: `smp::kick(core, reason)`, called with the kernel lock held,
records the reason and sends SGI 0 without waiting (GICv2's `GICD_SGIR` by
the target's interface mask, which each core records for itself since only
it can read its own; GICv3's `ICC_SGI1R_EL1` by the MADT's affinity). The
kicked core takes it through the IRQ path under the same lock. The GICv2
acknowledge of an SGI carries the sending CPU in bits 12:10 and the end of
interrupt must write them back, so `gic::acknowledge` now returns an
`Acked`, whose whole value only the end of interrupt reads. `smp::start`
pings every core that came up, holding the lock for 50 ms after the send:
the core must not answer under the lock, then must within a second.

The first run was green, 78 checks, and still had a defect in the rig. The
`-smp 1` boot printed `core 0 (the boot core) cannot be sent an SGI`, because
a uniprocessor GICv2 reads `ITARGETSR` as zero, and the rig's failure
pattern did not match the `(the boot core)` wording, so a real failure in
that wording would have passed too. Fixed both: the boot core records its
mask only when there is another core, and the pattern takes the wording.
Controls, each the whole six-boot rig: with the SGI never sent, every core
`did not answer`, red on every multi-core boot; with the kick's work done
before the lock is taken, every core `answered a kick while core 0 held the
kernel lock`, red the same way. The committed tree: 78 checks green, and
`test-fpsimd` and `test-kbd-mode` green, since every interrupt's end goes
through the changed acknowledge.

The high review Hans ran on #265 found nine things. The one that mattered
was the ping's own blindness: its under-the-lock half held the lock for a
fixed 50 ms and trusted the SGI to arrive inside it, so a slow delivery
would have passed a handler that skipped the lock, which is the defect the
check exists to catch. The ping is now decisive by observation. The IRQ
entry acknowledges before it takes the lock, a read of the core's own
interface, and says which interrupt it waits with (`smp::WAITING`). The
ping holds the lock until the kicked core is seen waiting with the kick,
then a millisecond more, and retries an attempt where the core waited
with its tick. The other eight: a comment and a doc left saying what 4(b)
had made untrue, "refuses" where the kick halts, GICv3's range selector
needing the distributor's bit too, two small costs on the IRQ and kick
paths, and the rig assuming the boot core is MADT index 0. Controls, each
the whole rig: no SGI sent, the kick's work done between the acknowledge
and the lock, and done before the acknowledge, each red on every
multi-core boot. The committed tree: one run with two boots INCONCLUSIVE
(the firmware stalled before loading the kernel, both at the same place),
then a full rerun, 78 checks green; `test-fpsimd`, `test-kbd-mode` and
`make test` green.

## Step 4(d) of multi-core: programs on the secondaries

#265 merged on Hans's word, and he asked for 4(d). The design follows the
plan with three departures, each recorded in it. Placement is partitioned,
not round-robin over every core: the boot shell joins the servers on the
boot core, and spawned programs run on the secondaries, so placement is
deterministic and a rig can require it. There is no `Running(core)` state:
the per-core `CURRENT` answers "running elsewhere" through one function. And
an idle core is kicked when work appears, not left for its tick.

One predicate decides every pick, `tasks::may_run_here`. The idle loop is
never saved, since every idle core runs it from its first instruction. A
kill of a task running on another core marks it and kicks that core, which
ends it at its next entry under the lock; a table rebuild halts if it would
change the view of a task some core runs, the check the plan had said was
owed. `CORE_INFO` (75) and `/bin/COREPROBE` show where a program runs, and
`SMP=N` boots any rig on N cores.

It worked on the first boot, a real remote kill included: in a pipeline
whose second stage failed, the shell killed the first, which ran on core 1,
and core 1 ended it. The work was in the checks. Three of the four controls
went red at once: the kill done in place (the rebuild check halted the
kernel), the idle-core kick removed (fsd round trips from a secondary went
from 350-600 us to about 46 ms), and the doom check dropped from the IRQ
entry (a held probe makes no syscalls and never ended). The fourth, the
partition removed, stayed green: with two probes and three secondaries the
kick sends each new program to an idle secondary before the boot core's
round reaches it, so the boot core never takes one. Four probes in one
pipeline on four cores is what separates them: three at once with the
partition, four without. A boot-flag rig also changed under me: a core
that halts alone now marks itself down, so the boot core's ping may find it
down rather than silent, and the kernel says which.

Two process notes. The first batch failed at its first image build because
I edited documents while it ran, and the source stamp refused the image,
which is the guard working; the batch was rerun on a committed tree. And
two of the ten rigs are shell scripts that capture the driver's own notices,
so their logs did not say `-smp 4`; their transcripts did.

Found and not fixed: the spawn staging buffers belong to no task, so two
spawners interleave (possible on one core already). The inventory's remedy,
one per core, does not fix it. Recorded in the plan and the roadmap.

The high review Hans ran on #266 found eight things, seven fixed. A
secondary that halts while running a program now halts the kernel, since
the program's registers are on that core's stack and nothing could end it.
A task another core is about to end counts as kill-pending, so it reads no
keys. KILL's ABI says a kill on another core means "ending". The placement
rule is one predicate for any core, `may_run_on`, which the idle-core kick
had copied. The rig's "shell answered" check matched the echo of the typed
line and now takes the output line. The eighth, the kick's cost, I measured
before deciding: about 8 to 10 us a syscall on four cores in alternating
rounds on the debug kernel the rigs boot, and nothing measurable on a
release kernel (13.2 to 13.8 us with the kick, 13.3 to 18.7 without), so
the cost was unoptimized code. The secondaries up became one word anyway,
and the per-site dirty flag the reviewer suggested was declined: it would
add a rule to every wake site for a cost a real build does not have.

The first verification after the fixes failed once, and the kernel was
right: the held probe started on core 3, blocked in its own "holding"
line's call to the console server, and the kick handed it to core 1 when it
woke. The rig compared the ending core with the starting one; it now
compares it with the core the kill named. Two runs of `make test-smp` at
113 of 113 after, the kill-in-place control red on the changed check, and
seven rigs green on four cores.

Not checked by any rig: the halt of a core running a program (no rig can
raise an SError at EL0), and the doomed task's kill-pending window, which
lasts as long as a kick takes to land.

## What the session was made of

Three PRs across the evening of 10-09 and the morning of 10-10, each merged on
Hans's word. The largest, #253, went through two high reviews and a low one,
and its design changed between them: a cost I had called acceptable looked
different once a reviewer spelled it out as a login that fails. The lesson I
would keep is about controls: a change that widens what the system accepts
silently blinds every check whose control relied on the old refusal, and the
remedy is to choose the input the new rule still treats specially.
