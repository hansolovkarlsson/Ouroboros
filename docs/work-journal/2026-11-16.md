## The transmit ring counted from 0

The standup's first fix item was the transmit ring taking its descriptor
from the consumer index's low byte, which is U-Boot's rule and the one the
board had shown wrong for receive. It worked only because the firmware
left that index at 0. Hans decided to count from 0 and to hold the merge
for a board check (#472).

The check needed an index that was not a multiple of 256, and the firmware
never left one. U-Boot's source says the transmit consumer index cannot be
written, so I expected to have to argue from receive. A temporary
diagnostic wrote 10 to it before the set-up anyway, and it read back
`0xa` and kept that value through the MAC's reset: U-Boot's comment is
wrong for this device. With the index at 10, one send moved the read
pointer by one descriptor's three words while the index read `0xb`, so the
device took descriptor 0, as the new rule says. 1004 frames went round the
ring with no timeout and no drop. The control put the low byte back: the
first frame was not taken in 100 ms, every send after it was refused, and
nothing reached the wire.

That control also falsified a sentence of mine. The kernel had carried a
warning for an index off a multiple of 256, justified by my claim that a
wrong rule would fail silently. It fails with a timeout on the first send.
The warning went with the diagnostic.

Two of the board trips cost time for reasons outside the code. The Mac's
adapter had been put back to DHCP after the previous day, so the board's
address was unreachable until it was set to `192.168.77.1` again, and then
one cable was not seated. Hans found the cable.

## fsd could not be restarted

Reading the board's log for #472, the loader's line `FSD.BIN - image too
large to keep for crash recovery - the server won't be restartable this
boot` was there. It was on every boot of the Pi in `screenlog.0`, 37 of
them, back to at least `7512000f`. `FSD.BIN` had grown to 197 KB and the
supervisor kept each image in a fixed 192 KB slot. It is the second time:
`review-and-split-postmortem.md` records the same warning at 137 KB
against 128 KB on 2026-08-29, and the sentence there that "there is no
test for the recovery path you never exercise" was still true. Hans put it
ahead of everything else: "The reason we want a microkernel and supervisor
etc, is so if a driver fails it can restart."

The fix (#473) is one arena of the same 768 KB in place of four fixed
slots, each image taking its own size, and two checks. A script holds the
built images to the arena at the end of every `make esp`, so no card or
stick can be staged with a server that cannot be restarted. And a QEMU rig
faults and then spins a `restart-rig` build of fsd and watches the kernel
restart it and a fresh fsd serve `ls`. The control put the old 192 KB
limit back: 8 of 13 checks failed, and afterwards the shell could not find
`ls`. A thirteenth check passed in the control too, since an
unregistered server never reaches the line it looked for, and it was
removed. The review found that the script placed images in `loader.rs`'s
order where `main.rs` registers them in another, so it now judges the
worst case of the alignment padding, which holds in any order. Sizing each
kept copy from the image itself, as `LOADER_DATA` pages, went on the
roadmap. The next Pi boot had no such line.

## A restart rig for every supervised server

Hans asked for the same for `cond` and `accountd` (#474). One script now
serves all three, a table entry each, so the copies cannot drift. The
controls refused each server's slot in `register`. accountd failed 7 of 12.
cond failed only 5: its serving check, that an `echo` printed, passed with

alive or not. The rig's cond now answers a word of its own,
`restart-rig-echo`, with a line only it writes, and the control failed 7
of 12.

## Step 9: the receive interrupt

Pi net step 9 replaces the tick's 20 ms poll with the GENET's interrupt,
INTID 189 from the firmware's `_CRS`. The first build cleared receive done
in the ack, as virtio-net's arm does. On the board it worked and took 304
interrupts by 256 frames: more interrupts than frames.

My first theory was a stale re-delivery, the end of interrupt reaching the
GIC before the clear reached the device. A diagnostic boot counted, at
each ack, whether receive done was set on entry, whether a frame was
waiting, and whether the clear had taken. All three said no stale
interrupts. A third boot added what the device itself had taken from its
producer index: 302 interrupts for 257 frames, each with receive done set
on entry and a frame waiting. The clear took effect, and the device set
receive done again for frames already in the ring. Linux's shape is the
answer: its interrupt handler masks receive done as well as clearing it,
and its poller unmasks it only once the ring is drained. With that change
the board took 158 interrupts for 260 frames, and the control without the
unmask took 0. One thing in the control is not explained and is recorded
as such: its 256th frame came after about 270 fetches, where the
interrupt boots got there after about 80.

The step's check had been worded as at least a hundred interrupts after a
hundred pings. That was met, but it is not the property: the count is one
interrupt for a frame or a burst of them. The property is a count that is
not 0 with the unmask and is 0 without it.

## Three reviews, and the comment that had never been true

The first review of #475 found nine things and no fault in what the board
ran. Five were sentences the mask had made false in other files:
`nic.rs`'s contract that the ack clears so the device can raise the next
one, the same in `exceptions.rs`, genetnic's module doc, `start`'s "the
writes are U-Boot's", and a bit "not yet read on the board". The design
finding was better: the masked state lived in a kernel atomic that only a
`&self` forced, so no host test covered how the ack and the rearm
interact. It moved into the crate. Of the controls, removing `start`'s
reset of that flag broke no test at first, and got one.

The second review found that the rearm depended on `netd` draining the
ring to empty. A `netd` restarted between taking its last frame and its
next `NET_RECV` would wait with receive done masked, woken by the tick
alone: the restart case the morning had been about. The rearm moved into
`NET_WAIT`, just before the reader blocks. The same review found the
ack's two writes posted with nothing ordering the GIC's end of interrupt
after them, so the crate now reads the mask back and the kernel has a
`dsb` after the read. A test of the read-back order passed with the read
moved before the writes, because it compared reads and writes apart; it
now records them in order. One finding I declined: the first-interrupt
line printed under the kernel lock in the IRQ path, since every kernel
entry holds that lock and moving the line would gain nothing.

The third review found the one that mattered most. `NET_WAIT`'s comment
said "the poll checks up front, never sleeping through pending input", and
`block_current_and_switch` blocks without looking: only the tick's wake
check asks. With the rearm in `NET_WAIT`, a frame that came in before the
wait would sit masked until the tick. But the comment was older than
anything on the branch. It came in on 2026-08-21 with the TCP
retransmit timeout, and the arm blocked without asking then too. On QEMU,
100 HTTP fetches took 0.25 s with the check in place and 2.78 s with it
taken out: every frame that beat `netd` to the wait had cost a tick, on
virtio-net, for three months. The same review found the GICv2 backend's
reason for leaving the trigger mode at reset, "this project's one SPI
user", false once step 9 made the GENET a second, so the kernel now sets a declared SPI
level-triggered and says what the GIC held. The Pi's firmware leaves it
level.

Each round was followed by a board boot: 155, 133 and 194 interrupts at
256 frames, none dropped, every fetch answered. A low review asked that
`NET_WAIT`'s early return answer what the poll answers rather than its own
`0`, and that went in before the merge.

`main` at `bdae25d3`, the merge of #475, with the card restaged from it.
Step 10, two boards, is next in the plan.

The `NET_WAIT` fix has a consequence I found only in the closeout.
`load_auth`'s retries call `NET_WAIT(40)` as a sleep, and the records said
for weeks that with a frame or message waiting it "returns at once", which
was false: it returned at the next tick, so each retry cost up to 20 ms.
Since #475 it is true, and a disk that mounts late on a busy wire now
spends the retry budget in a moment instead of in about a second.
`roadmap-pi-net.md` and `testing-pi4.md` say so now, and it is the first
item for tomorrow.
