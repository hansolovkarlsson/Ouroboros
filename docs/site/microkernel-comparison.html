Microkernel, protection, fault tolerance: where Ouroboros stands

A self-assessment against the three ideas this project draws on — the microkernel (MINIX), enforced protection, and self-healing (Helix OS) — measured as they actually stand in the code today, not as aspiration.

⚖️ Reads best after the architecture overview, and alongside the two research notes it draws on: how MINIX boots and Helix OS's fault-tolerant design.

The short version: on its one moved service, Ouroboros is now a genuine microkernel — enforced isolation, capability-based bulk IPC, and real crash recovery. The mechanisms are the real thing. What separates it from MINIX and Helix is breadth and generality, not the honesty of the individual pieces.

A note on the sources

This assessment supersedes the "current shape" sections of the two research notes — both were written before this project's isolation work and still say Ouroboros has no fault isolation of any kind. That's no longer true, which is what makes the re-assessment worth writing.

Axis 1 — Microkernel (MINIX)

The defining MINIX move is that the kernel does not contain the services: drivers, the filesystem, and the network stack are separate user-space processes, and the kernel is just mechanism (IPC, scheduling, privilege) underneath them.

Where Ouroboros genuinely qualifies now

The entire FAT32 filesystem lives in userland — fsd runs at EL0 as an ordinary loaded program in task slot 2, and the kernel's own fat32.rs no longer exists. Every ls, cat, cp is an IPC round trip to a separate process. The kernel's remaining storage role is three sector-level block syscalls, accepted only from task 2 — the literal meaning of "supervised." The IPC converged on MINIX's actual primitives: MSG_CALL is sendrec-shaped (a sender-filtered synchronous request/reply), and bulk data crosses the boundary by grant/safecopy — MINIX's sys_safecopy, chosen over a simpler bounds-checked-pointer model precisely to avoid re-introducing trust.

Where it falls short of MINIX

One service, not a driver fleet — the USB/xHCI stack, the block device, the console, the GIC, and the scheduler are all still undifferentiated EL1 kernel code. There is no boot image of many cooperating servers, no capability model for who may call whom (trust is flat within EL0), and no process manager / PID namespace / fork above the spawn + wait/reap primitives that do exist.

Verdict

Structurally a microkernel on the service it actually moved, using the right IPC primitives. Short of MINIX on breadth (one server, not many) and topology (flat trust, no capability graph).

Axis 2 — Protective states / enforced isolation

"Protected" was aspirational here until very recently, so it's worth being precise about the line that got crossed. Before: isolation was a convention — every EL0 region was accessible to every task; nothing stopped one task reaching into another's memory, it was just impolite.

Now — hardware-enforced, and proven by fault injection

Each of the scheduler slots runs under its own translation-table view: identical kernel/device mappings, but EL0 access to that task's own region alone. A context switch swaps TTBR0 and flushes the TLB. This was verified, not assumed — an A/B probe read a byte of the shell's region from a spawned program: it succeeded under the old shared map and faulted under per-task views (faulter killed alone, shell alive). The last soft path closed with it: syscall pointer arguments are now validated against the caller's own region, so the kernel can't be tricked into touching another task's memory either.

Verdict

This is the axis where Ouroboros is strongest relative to both influences. MINIX gets EL0-equivalent isolation from separate address spaces; Helix explicitly does not have hardware-enforced isolation between modules. Ouroboros now has real, MMU-enforced, injection-verified per-task isolation. It lacks only a stack guard page and the reverted per-task-ASID TLB optimization.

Axis 3 — Fault tolerance (Helix OS, and MINIX's RS)

Helix's pitch is self-healing: a module crashes or hangs, the kernel detects it and restarts it without a reboot. MINIX's is the reincarnation server: a crashed process is restarted from a clean slate because it was never in the kernel to begin with. Ouroboros has a real, minimal version of both — and it landed the same day as the isolation work, which is not a coincidence.

What exists

Every EL0 fault is now contained — a faulting task is torn down alone, and the survivors keep running (before the fix, any userland wild pointer halted the whole kernel). The filesystem server is supervised: on a task-2 fault the kernel reloads fsd's image from a static buffer and the fresh server remounts from disk — its state was always disk-derivable, which is what makes this real recovery. A 3-restart-per-boot cap guards crash loops, then it degrades gracefully. Clients blocked mid-call to a dying server are woken with an error rather than hanging.

Where it's short of Helix (and MINIX's RS)

Only fsd is supervised — recovery is special-cased for one task, not a general policy engine. There is no wedged-server detection (a server stuck in an infinite loop, not faulting, is invisible — that needs a watchdog). And restart is not hot-reload: it reloads the same image and re-derives state from disk, closer to MINIX's clean-slate restart than to Helix's live swap. No journaling, either — a crash is survived, data integrity across one is not guaranteed.

Verdict

A genuine, working reincarnation story for one service, with the crucial "state is disk-derivable" property that makes it real recovery. Short of both influences on generality, on the non-crashing failure mode, and on liveness of the swap.

What would close the gap, in order of payoff

Not commitments — the natural next moves toward the fuller ideal, and the shape each would take given what already exists:

  1. Move a second driver out of the kernel. The single highest-value proof: that fsd wasn't a one-off, and that the IPC + grant/safecopy machinery generalizes. A console server or a block server are the obvious candidates.
  2. A general supervision / heartbeat mechanism. Today the restart is bespoke to one task. A uniform "any registered server can be health-checked and restarted" facility would catch the wedged (looping, non-faulting) failure mode that currently has no answer.
  3. A capability model for who-may-call-whom. The flat trust topology is the last big structural gap against MINIX — a per-task table of permitted endpoints would make isolation topological, not just memory-level.
  4. The smaller, already-recorded hardening: a stack guard page (turn silent overflow corruption into a clean fault), and revisiting per-task ASIDs with a proven break-before-make sequence (the reverted optimization).

None of these is a small task, and none is needed to call the current state honest. They're the difference between "the mechanisms are real" (true today) and "the mechanisms are general" (the next era of the project). The full assessment lives in the repository as microkernel-comparison.md.
