# Ouroboros v0.17.0

`mv` and `cp` will overwrite a file now — and will ask you to mean it.

A small-items release rather than an arc: one feature finished, six roadmap gaps
closed, and two of them permission bugs. Everything from
[v0.16.0](v0.16.0.md) still works unchanged — per-machine Ed25519 cluster
keypairs, per-user cluster identity, two-node disk sharing, `/proc`/`/dev/cons`/
`/net` as files, dial-out/dial-in, `cpu` with namespace import. **No wire flag
day this time**: a v0.16.0 node and a v0.17.0 node talk to each other normally.
This is pre-1.0 software: ABI and on-disk/on-wire formats are not yet stable.

## A BEHAVIOUR CHANGE — `mv` and `cp` now refuse an existing destination

Until now `mv a b` failed outright when `b` existed, and `cp a b` overwrote `b`
silently. Both are gone:

```
$ mv /A.TXT /B.TXT
mv: /B.TXT exists (use -f to replace)
$ mv -f /A.TXT /B.TXT
```

`cp` behaves the same way. **This departs from POSIX deliberately**, where both
overwrite without comment — on a system with no undo, no trash and no snapshots,
the overwritten bytes are simply gone. If you have a script that relied on `cp`
clobbering silently, it needs `-f`.

It is a **refusal, not a prompt**, and that is not laziness. Interactivity here
is keyboard *ownership*: a `/bin` program can read keys only while it holds
`INPUT_OWNER` as the foreground task. Neither command has a keyboard as a
pipeline stage, under `cpu` on another machine, or when the request arrives from
a 9P peer — so a prompt would guard the case you are watching and hang or fail
in the three you are not. A refusal behaves identically everywhere.

`--` ends the options, so a file whose name begins with a dash is still
reachable: `mv -- -odd.txt ok.txt`.

The *server* keeps POSIX `rename`. `fsd`'s `NP_MV` replaces without asking,
because a protocol verb has nobody to consult; the caution lives in the commands
a person types. `cpu A mv -f x y` still gets the flag, because that runs
`/bin/mv` on the far side.

## What's new

**`mv` can replace an existing file at all**, on all three filesystems, when
both sides are ordinary files. On **ext2 the replacement is very nearly
atomic**: the whole change is one write of the destination's directory entry,
re-pointed at the source's inode, so the name resolves to the old file or the
new one and never to nothing. FAT32 and exFAT cannot manage it in one write —
their directory entries hold the file's location itself rather than an inode
number — but the new entry is written before the old one is freed, so what those
formats cost is *atomicity*, not the name.

Replacing a directory, or moving a directory onto an existing name, is still
refused. `mv file dir` still moves *into* the directory, as before.

**`grep` understands POSIX character classes**: `[[:alpha:]]`, `[[:digit:]_]`,
`[^[:space:]]` — all twelve names, inside a bracket expression. The definitions
are computed from the standard library's own predicates rather than transcribed
as bit tables, which is why `[:space:]` correctly includes the vertical tab that
most implementations of "whitespace" leave out. An unknown class name is an
error, not a silent fall back to the literal letters.

**A user cannot create an account with an empty password.** `useradd` enforced
nothing where `passwd` refused one, so an account made by pressing Enter twice
was loginable by pressing Enter.

## Fixed

- **The login-time "this filesystem cannot enforce permissions" warning could
  stay silent when it mattered most.** It read *any* error from the filesystem
  server as "permissions are enforced", including the one meaning "not mounted
  yet" — and it ran before anything had waited for the mount. On a slow device
  (USB storage on real hardware) the warning could simply not appear. It now
  asks after the mount has been waited for, and asks the server a direct
  question instead of guessing from the filesystem's name.

- **`ls -l` and `chmod`/`chown` skipped a check every other operation had**, so
  on FAT32 and exFAT they could refuse a path that an ordinary read allowed, and
  every `ls -l` entry paid for work that could not change the answer.

- Two host-side test tools were fixed after it turned out neither could observe
  what it was pointed at. Not user-facing, but they are why the above are
  believed.

## Known

`fsck_msdos` reports a FAT32 `FSInfo` free-cluster-count mismatch after any
write. The count is written when the volume is formatted and never maintained;
it is a hint that every real driver recomputes, and the warning is cosmetic.
Pre-existing, and now recorded in the roadmap with the fix sketched.
