# Ouroboros v0.5.0

The first step toward the cluster. This release lands **Phase 0** of the
distributed-cluster direction ([`docs/roadmap-cluster.md`](../roadmap-cluster.md)):
the servers stop speaking three hand-rolled protocols and instead speak **one
uniform, Plan 9-style file-protocol verb set**, each task composes its own
**namespace**, and — the visible payoff — **two different filesystems can be
mounted at once**. It's the local groundwork the whole "share resources across
machines" vision is built on: *remote is just this same protocol over TCP
instead of local IPC.*

This is pre-1.0 software: the syscall ABI and on-disk formats are not yet
stable. Everything from [v0.4.x](v0.4.1.md) still works — the shell, `/bin`,
FAT32/exFAT/ext2 read-write, the network stack, USB on real Parallels hardware —
this release changes how the pieces *talk to each other* underneath.

## What's new in Phase 0

**One uniform verb set (`ninep-abi`).** A new protocol crate defines a small,
server-agnostic set of file verbs (`readdir`/`read`/`write`/`stat`-ish/
`mkdir`/`mv`/…), each request carrying a **`tree` selector** that picks which
mount. It replaces the three bespoke server protocols:

- `fsd` (filesystem) now serves file operations over the verbs; `FSOP_*` is
  reduced to disk-management control ops (mount/format/…).
- `cond` (console) writes are now a write to the console "file"; its bespoke
  `DSPOP_*` protocol is **gone**.
- `netd`'s file reads (its static-file HTTP server) go over the verbs too.

**Per-task namespaces + `bind`.** The kernel now keeps a per-task namespace — a
table of `bind`ings mapping a path prefix to a mount subtree — modeled on the
existing per-task working-directory store, and a child **inherits its parent's
namespace** automatically. The new shell builtin

```
bind /mnt /EFI      # /mnt now resolves to /EFI, for this shell and its children
```

is Plan 9's `bind` in miniature: **per-task** (no other process's view changes),
and inherited by every command you run.

**Multi-mount — two filesystems at once.** `fsd` grew from one mount to a mount
table, and the shell gained

```
mount 1 /mnt/f      # mount the disk's 2nd partition and see it at /mnt/f
```

so a second filesystem is visible alongside the boot one — `ls /` and `ls /mnt/f`
list two *different* on-disk filesystems in one session. The single-mount model
physically couldn't express this.

## How it was proven

Each step was verified on QEMU and shown **byte-identical** to the prior
behavior for un-bound, single-mount use (an empty namespace is the identity, so
nothing changes until you `bind`/`mount`), with **zero exception-trace aborts**.
The multi-mount payoff was checked against the existing two-partition ext2+FAT32
test disk: `ls /` lists the ext2 root, `mount 1 /mnt/f` then `ls /mnt/f` lists the
FAT32 root — two filesystems, each read over the verb protocol by its tree.

## Scope, honestly

Phase 0 is the **local** foundation. Deliberately deferred:

- **The network half** (Phase 1): carrying the verb protocol over TCP, so a
  machine can *export* a filesystem and another can *remote-mount* it. That's
  where the cluster becomes actually distributed; the uniform protocol + `tree`
  selector + namespace built here are exactly what it rides on.
- **`/net` and `/dev` as files** (Phase 3): `netd`'s client protocol (`ping`/
  `resolve`/`fetch`) and the console's namespace mount stay as they are for now.

## Running it

Identical to previous releases — the disk images boot the same way:

- **QEMU:** unzip `ouroboros-0.5.0-esp.img.zip` and boot `esp.img` (see the
  Makefile's `run-image` target for the exact invocation). Try `bind /mnt /EFI`
  then `ls /mnt`.
- **Parallels (Apple Silicon):** download `ouroboros-0.5.0-esp.dmg`, then wrap
  it into a Parallels-native `.hdd` locally:

  ```sh
  prl_disk_tool create --hdd esp.hdd \
      --dmg "$(pwd)/ouroboros-0.5.0-esp.dmg"
  ```
