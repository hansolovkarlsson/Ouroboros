# Ouroboros v0.16.0

One key per machine. The shared cluster secret is gone.

Since [v0.10.0](v0.10.0.md) the 9P export has been authenticated by a **shared
cluster key**: every machine held the same secret, so any of them could mount or
run on any other. That is sound at two nodes and false at three, because with a
symmetric key **the ability to verify is the ability to forge** — a peer that can
check node A's requests can also make them. And there was no revocation short of
re-keying every member at once.

Each machine now holds its own **Ed25519 keypair** and a list of the peer *public*
keys it accepts (`/etc/cluster/`, the `known_hosts` model). Revoking a member is
deleting a line. Everything from [v0.15.0](v0.15.0.md) still works — per-user
cluster identity, two-node disk sharing, `/proc`/`/dev/cons`/`/net` as files,
dial-out/dial-in, `cpu` with namespace import. This is pre-1.0 software: ABI and
on-disk/on-wire formats are not yet stable.

## A WIRE FLAG DAY — v0.16.0 does not talk to older nodes

The auth magic moved `AUTHNP02` → `AUTHNP03`, and the retired format is **refused
outright** rather than misparsed. A pre-0.16 machine cannot mount from or `cpu`
to a 0.16 machine, in either direction. **Upgrade both ends together.**

The old format survives only as a negative control: `np9p_client.py --legacy-mac`
can still send one, so the refusal is demonstrable rather than assumed.

## What's new

**Every request and every reply is signed**, domain-separated so a signature made
for one direction cannot be presented as the other. The private key never crosses
the wire, and the 152-byte header carries the offered public key the way SSH does
— the exporter decides whether that key is authorized *before* verifying anything,
because "is this key allowed here" and "does this signature check out" are
different questions.

**The two directions look a peer up differently**, which is why an `authorized`
line carries an address as well as a key. An exporter is *offered* a key and need
only decide whether it is allowed. A client is offered nothing and must know in
advance whose signature will do, so it looks up by the address it dialled —
accepting any authorized signature would authenticate "some cluster member" rather
than "the machine I asked".

**`/bin/clusterkey`** manages the identity on the device: show this machine's
public key, `new` to generate one, `peers` to list who is accepted (reporting a
mistyped key by line number, since a peer silently unauthorized in a file that
still looks right is the invisible failure), and `line <name> <ip>` to print what
another machine should hold for this one.

**Generation refuses without real entropy** rather than degrading. A guessable
machine key is worse than none, because it looks like security. On platforms with
no RNG (Parallels, the Pi — neither has virtio-rng) keys are staged at build time
instead.

## Under it

A hand-rolled, host-unit-tested **`ed25519`** crate (SHA-512, field arithmetic mod
2^255-19, extended-coordinate curve points, scalar arithmetic and sign/verify),
built in verifiable steps against RFC 8032's published vectors — reproducing the
*signatures* byte-exactly, which is stronger than "it verifies" and only possible
because Ed25519 is deterministic. That determinism is why it was chosen: hardware
entropy is absent on the target boards, and a repeated ECDSA nonce leaks the key.

Measured on the guest at 3392 bytes of peak stack (10% of netd's 32KB) and
~500µs to sign under QEMU-TCG, which closed the arc's headline risk.

Small-order public keys are rejected by **computing** `[8]A == identity` rather
than matching a table of encodings — an earlier hand-written table had three
wrong entries, accepting three genuinely dangerous keys and refusing one good one.

## Two costs, stated

- A peer list caps a cluster at about a dozen nodes (`AUTHORIZED_MAX`), where one
  shared secret scaled without limit.
- Both ends now need an `/etc/passwd`: a machine that cannot name its own caller
  refuses to send, and one that cannot resolve the name refuses to serve.

## Still open

Keys are per-**machine**, not per-**user**: an authorized machine can still claim
any of its own users' names. That is a *measured* remainder rather than an assumed
one, which was the point of building this tier first — see `roadmap.md` item 1,
which evaluates a Plan 9-style auth server in full and explains why it is not
built yet.

## Verifying a two-node cluster

```sh
make images-2vm-ext2
python3 scripts/drive-2vm.py build/espext2-a.img build/espext2-b.img \
    --a 'login:@@root' 'assword@@root' '# @@uptime' \
    --b 'login:@@root' 'assword@@root' '# @@mount -r 10.0.2.10:564 /mnt/a' \
       '# @@cat /mnt/a/etc/passwd' '# @@cpu 10.0.2.10:564 uptime'
```

Prints both transcripts, both abort counts, and a census of the signed-vs-retired
frames actually on the wire.
