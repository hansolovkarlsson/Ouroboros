# Ouroboros v0.25.0

A cluster user can be vouched for by their own password. Until now the user
a remote request named was asserted by the calling machine and checked by
nothing, so any machine the cluster authorized could act as any user with
an account on the export. Now `login` derives a key from the user's
password and hands it to the network server, which holds it until the user
logs out and signs that user's requests with it. An export that registers
the user serves them only with that signature. A compromised machine can
act as a registered user only while that user is logged in on it.

Fifteen pull requests since [v0.24.0](v0.24.0.md) (#416 to #430), over
three days, 2026-11-07 to 2026-11-09. The arc's first half (root squash,
the key derivation, version-2 shadow lines and the keys held from login to
logout) shipped below the wire in v0.22.0.

**No wire flag day, with one thing to order.** The old request format
(`AUTHNP03`) is still accepted, and nothing changes for a user until an
export lists them in `/etc/cluster/users`. But a v0.24.0 node sends no
credential, so a user registered at a v0.25.0 export is refused there from
a v0.24.0 node. Upgrade every node before registering anyone.

**Four things an installation sees:**

- **On the dev images, `user` is registered**, so a remote request as
  `user` is served only while `user` is logged in on the asking machine.
  Root's `su user` there is refused at the other machine's export, with
  `authentication failed`, and so is a program `user` left running after
  logging out. Root itself is unchanged where the peer is flagged `root`.
- **A password change changes the user's cluster key.** `passwd` prints the
  new `/etc/cluster/users` line, and every export that lists the user
  refuses them until that line is replaced.
- **`useradd` prints the new user's line**, and **`clusterkey user <name>`**
  prints any user's line from their password typed twice, so an existing
  account is registered without resetting its password.
- **A credentialed request costs more at the export**: on QEMU, 0.7 to 3.3
  ms more per one-shot read and 0.7 to 1.9 ms more per session opened.

This is pre-1.0 software. ABI and on-disk/on-wire formats are not stable yet.

## Per-user keys

The per-user keys plan (`docs/roadmap/roadmap-user-keys.md`), steps 5 to 9:

- **The wire.** `AUTHNP05` is the signed request with a typed credential
  block under the machine's signature. Kind 1 is a signature by the user's
  key over the nonce, the name, both machines' keys and a hash of the
  message, so a credential does not verify from another machine, at
  another export or over another request. A future auth server's ticket
  would be kind 2.
- **Both Python peers** speak it, the foreign implementation the wire check
  holds equal, with ten misbehaving credentials for the export to refuse.
- **The export.** One policy decides every claim: root by the `root` flag or
  root's own credential; a `cpu` run's `/host` reads on the run's standing
  until it ends; a registered user only with a credential that verifies;
  an unregistered one on the machine's word. A broken registry line refuses
  its user rather than serving them unchecked.
- **The client.** `netd` signs a credential for every request of a uid it
  holds a live key for, captured when the request was queued. A held
  session opened with one is closed when the user's last key goes, and
  nothing is sent on it after, so a program the user left running is
  refused. The signing's expansion of the key is wiped from the stack.
- **Setting it up.** `clusterkey realm new` on one machine, its
  `/etc/cluster/realm` copied to the others, then each user's line from
  `clusterkey user`, `useradd` or `passwd` into `/etc/cluster/users` on the
  exports that should require it. `manual.md`'s cluster section says how,
  and what the scheme does not close.

**Strong passwords are part of the model now.** A credential is a signature
by a password-derived key, sent in cleartext, so anyone who captures one can
guess at the password offline. The derivation is slow on purpose (about a
second a guess on the QEMU guest), and a realm of the cluster's own stops a
dictionary made for one cluster serving another. Do not use the dev images'
public realm, `ouroboros-dev`, outside them.

## Mounts seen

- **Bare `mount` names every mount** and the path it is bound at, the root's
  partition by its format.
- **A directory lists the mount points below it**, in `ls`, globs,
  completion and `cd`, even where the disk has no such directory.
- **Making something in a directory that holds only mount points** says so
  (`FS_ERR_MOUNTS_ONLY`), not "no such file or directory". The error floor
  moves to `MAX-46`.

## Smaller things

- `make sdcard` keeps the card's boot counter, which on the Pi lives only
  on the card.
- New rigs: `make test-cred-client` (the client's credential across two
  guests, with a capture), `make test-run-callback`, `make
  test-no-identity`, and a sixth `test-held-keys` scenario for the registry
  lines.
- `make test` is at 322 host tests.

## Known on hardware

- **Still not on the Pi or Parallels:** networking, so the cluster and
  everything in this release that crosses it is QEMU-only.

## What is in a release

- `ouroboros-0.25.0-esp.img.zip`: the raw MBR+FAT32 disk image. Boot it under
  QEMU or any UEFI-AArch64 VM.
- `ouroboros-0.25.0-esp.dmg`: self-contained, for Parallels on Apple Silicon.
  Wrap it locally with:

  ```sh
  prl_disk_tool create --hdd esp.hdd --dmg <path>/ouroboros-0.25.0-esp.dmg
  ```

- `SHA256SUMS` for both.

For a Raspberry Pi 4, build from the tag and stage the card with `make
bootstick BOOTSTICK=/dev/diskN PI=1`, as `docs/testing/testing-pi4.md`
section 4 describes ("One disk: the card alone"). The release images are
not a Pi card.
