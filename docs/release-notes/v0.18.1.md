# Ouroboros v0.18.1

Reading a file over a cluster mount used to fail roughly one time in six. It
doesn't now.

A patch release on [v0.18.0](v0.18.0.md): no new capability, five pull requests,
and the substance is one long-standing intermittent finally traced and closed.
Everything from v0.18.0 works unchanged, and there is **no wire flag day** — a
v0.18.0 node and a v0.18.1 node talk to each other normally. This is pre-1.0
software: ABI and on-disk/on-wire formats are not yet stable.

## The headline: remote reads are reliable now

`cat` of a file on a remote mount — and any other command reading one — failed
intermittently, reported only as a bare `cat: failed`. It had been on the
roadmap for weeks as "roughly one remote op in six", with three suspected TCP
causes.

**It was two separate faults, and neither was TCP.** A packet capture settled
that: every TCP connection in a failing run was healthy — SYN, SYN-ACK, request,
reply, FIN — and on the second fault the capture was *empty*, because the
request never left the machine.

**Fault one: the supervisor was restarting the network server mid-read.** A
server that stays runnable for 2.56 s is treated as wedged and restarted. That
threshold was chosen when a request meant a local disk read and a server
returned to blocking in well under a tick. A remote read is a sequence of
network round trips, and `netd` stays runnable for all of them — so a
five-chunk read of a 2 KB file against a slow peer took 3.0 s and was killed
every single time, taking the in-flight command with it.

A supervised server can now report progress *unprompted*, so it is no longer
killed for being busy. A genuinely wedged server never reaches the code that
reports, so the original protection is intact — it simply stops punishing work
that legitimately takes time.

**Fault two: a capability-delegation race.** The shell starts a program and only
then grants it permission to talk to the network server — it cannot grant to a
task that does not exist yet. A program reaching the network inside that window
was refused, and the refusal surfaced as a generic failure rather than as
"try again in a moment". One of the three code paths to the network server
already handled this; the other two did not. All three now share one
implementation, so a fourth cannot get it wrong.

## `ls` reports failures properly

Two fixes to the same command, both about telling you the truth:

- **`ls` used to exit 0 even when it failed.** A missing file, a permission
  denial, an unreachable cluster peer — all reported success to any script
  checking the exit status. It now exits 1 when an operand fails, while still
  listing the operands that worked, as every Unix `ls` does.
- Following v0.18.0's fix to `ls`'s *messages*, this completes the pair: `ls`
  now gets both the message and the status right.

```
$ ls /PRIV ; echo "status=$?"      # a directory you may not read
ls: /PRIV: permission denied
status=1
```

## Under the hood

- **A trace harness**, `scripts/trace-remote-flake.py`, which reproduces a
  remote-filesystem failure with a packet capture attached and checks three
  observers at once — the guest transcript, the peer's request log, and the
  wire. It refuses to report results unless the peer actually received
  something, because a dead test peer produces a beautifully regular failure
  pattern that looks exactly like a bug.
- **A twenty-ninth postmortem**, `docs/true-when-written-postmortem.md`, on the
  defect class three of this release's bugs share: a comment or message that was
  correct on the day it was written and was falsified later by a change in a
  different file — where no compiler, test or code review can see it. The
  supervisor's 2.56 s premise is one of them.

## Getting it

`ouroboros-0.18.1-esp.img.zip` boots under QEMU or any UEFI-AArch64 VM;
`ouroboros-0.18.1-esp.dmg` is for Parallels on Apple Silicon — wrap it locally
with:

```sh
prl_disk_tool create --hdd esp.hdd --dmg <path>/ouroboros-0.18.1-esp.dmg
```

Verify against `SHA256SUMS`. See [`docs/manual.md`](../manual.md) to drive it,
and [`docs/testing-qemu.md`](../testing-qemu.md) for the QEMU and two-node
cluster rigs.
