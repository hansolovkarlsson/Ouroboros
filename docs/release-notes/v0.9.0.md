# Ouroboros v0.9.0

A compute cluster. This release lands **Phase 4** of the distributed-cluster
direction ([`docs/roadmap-cluster.md`](../roadmap-cluster.md)): the Plan 9 `cpu`
model — **run a program on another machine's CPU while it reads your files**.
Where [v0.8.0](v0.8.0.md) made storage, processes, console, and network shareable
*as files*, v0.9.0 makes **computation** shareable: ship the work to another
machine, keep the data yours. Combined with the earlier phases, that is the whole
achievable Plan 9 vision — resource-sharing and explicit remote execution — with
only the shared-memory *mirage* deliberately out of scope.

This is pre-1.0 software: the syscall ABI and on-disk/on-wire formats are not yet
stable. Everything from [v0.8.x](v0.8.0.md) still works — the shell, `/bin`,
FAT32/exFAT/ext2, per-task namespaces, two-node read/write disk sharing, and the
`/proc`/`/dev/cons`/`/net` file servers, all remotely mountable.

## What's new in Phase 4 — `cpu <host:port> <command>`

Run a command on another machine and see its output here:

```
cpu 10.0.2.10:564 ls /            # `ls` runs on machine A; you see A's disk root
cpu 10.0.2.10:564 uptime          # A's uptime
```

And — the point — the remote command reads **your** files, through your namespace
imported at `/host`:

```
write local.txt hi
cpu 10.0.2.10:564 ls /host                # /host is THIS machine (the caller)
cpu 10.0.2.10:564 cat /host/local.txt     # cat runs on A, but reads YOUR local.txt
```

So within one remote command, **`/`** is the machine it runs on and **`/host`** is
the machine you launched from. The computation runs on the remote's CPU; the data
stays on yours; no shared memory is needed. This is distributed processing done the
honest way — *move the work to where the CPU (or the data) is*.

**How it works.** The network server (`netd`) is both a 9P client and an export
gateway. A `cpu` request frames a run over TCP; the remote spawns the `/bin`
program with its stdout piped back (captured non-blocking in netd's event loop) and
binds `/host` to a remote mount back to the caller. The caller's netd stays
responsive throughout — it serves the running command's `/host` reads *while* the
run is in flight — the "a network server must never block" discipline this project
holds to.

Also in this release, under the hood: the **namespace-aware export** — the export
gateway now resolves incoming paths through its own composed namespace with one
shared resolver (used by every client and the gateway), retiring the per-server
routing special-cases the earlier `/proc`/`/dev/cons`/`/net` steps used.

## Scope, honestly

Phase 4 is **trusted-LAN, no authentication** (a remote export serves any peer that
connects — don't expose it to an untrusted network). Deliberately deferred: the
remote command's output is bounded to one message for now (small commands);
authentication over the wire; concurrent multi-writer coherence; and the frontier
**explicit distributed compute** of Phase 5 (partition work, ship it, collect
results).

## Running it

Identical to previous releases for a single machine; the cluster needs two.

- **QEMU (single machine):** unzip `ouroboros-0.9.0-esp.img.zip` and boot
  `esp.img` (see the Makefile's `run-image` target).
- **QEMU (two-node cluster):** `make run-image-2vm-a` in one terminal (machine A,
  IP 10.0.2.10, start it first), `make run-image-2vm-b` in another (machine B),
  then in B: `mount -r 10.0.2.10:564 /mnt/a`, `cpu 10.0.2.10:564 ls /`, and the
  rest. Full walkthrough in [`docs/manual.md`](../manual.md) and
  [`docs/testing-qemu.md`](../testing-qemu.md).
- **Parallels (Apple Silicon):** download `ouroboros-0.9.0-esp.dmg`, then wrap it
  into a Parallels-native `.hdd` locally:

  ```sh
  prl_disk_tool create --hdd esp.hdd \
      --dmg "$(pwd)/ouroboros-0.9.0-esp.dmg"
  ```
