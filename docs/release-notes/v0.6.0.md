# Ouroboros v0.6.0

The cluster becomes real. This release lands **Phase 1** of the
distributed-cluster direction ([`docs/roadmap-cluster.md`](../roadmap-cluster.md)):
the uniform file-protocol verb set from [v0.5.0](v0.5.0.md) now travels **over
TCP**, so one machine can **export** its filesystem and another can
**remote-mount** and read it. The [Phase 0](v0.5.0.md) thesis — *remote is just
this same protocol over TCP instead of local IPC* — is now literally true, and it
ends with **two Ouroboros machines, one reading the other's disk over a protocol
written from scratch.**

This is pre-1.0 software: the syscall ABI and on-disk/on-wire formats are not yet
stable. Everything from [v0.5.x](v0.5.0.md) still works — the shell, `/bin`,
FAT32/exFAT/ext2 read-write, per-task namespaces + `bind` + multi-mount, the
network stack, USB on real Parallels hardware — this release adds a *network*
transport under the same verbs.

## What's new in Phase 1

**A machine exports its filesystem (the 9P gateway).** `netd` gained a second TCP
listener (port 564) alongside its HTTP server: an inbound request is a
length-delimited frame of the same `ninep-abi` verb + params, with bulk data
**inline** on the wire (there is no grant across a network). It decodes the
frame, runs the verb against the local `fsd`, and frames the reply back.

**A machine remote-mounts another (the client).** A new namespace binding names a
*remote* endpoint, and a resolution against it becomes a TCP round trip through
`netd` rather than a local IPC call. The new shell builtin:

```
mount -r 10.0.2.10:564 /mnt/a     # bind a remote machine's export at /mnt/a
ls /mnt/a                          # ...then read it: this lists the REMOTE disk
cat /mnt/a/EFI/ORBS/INIT.CFG
```

The aha: **`ls` and `cat` are unchanged** — the same `/bin` programs over the same
verbs. Only namespace resolution decides local-vs-remote; everything above it is
untouched. The binding is per-task and inherited by spawned commands, like every
other namespace change.

**Two nodes, one disk.** Two Ouroboros VMs on a shared L2 link (no host in the
middle) — machine A exports, machine B `mount -r`s it and reads A's real
filesystem. Each guest derives its IP from its NIC's MAC, so two nodes get
distinct addresses with no new config channel.

**Trust, stated loudly:** the first cut is a **trusted LAN with no
authentication** — an export serves any peer that connects. Who-may-mount-what
(capabilities carried over the wire) is a dedicated later hardening phase, not
faked.

## How it was proven

Verified against a **foreign observer**, the project's standing discipline — a
host-side python 9P peer speaking the wire format (`scripts/np9p_client.py` reads
a guest's export; `scripts/np9p_server.py` is what a guest remote-mounts) — and
then between two real Ouroboros VMs over a QEMU socket link, watched with
`tcpdump`. Readdir, single- and multi-chunk file reads, and nested paths all
verified; local filesystem behavior byte-for-byte unchanged; the export gateway
and HTTP server unregressed; **zero exception-trace aborts** throughout, on both
nodes.

Two bugs the packet trace caught (not the logs) are worth the retrospective: a
client TCP parser that hardwired the peer's port to 80 (dropping the 9P
SYN-ACK), and a fixed ephemeral source port that collided with the peer's
TIME_WAIT on the many back-to-back connections a remote mount makes — fixed with
a per-connection rotating port.

## Scope, honestly

Phase 1 is **read-only** sharing, and a **trusted LAN**. Deliberately deferred:

- **Read + write over the network** (Phase 2): the export is read-only for now;
  two-node read/write with single-writer + clean-disconnect semantics is the next
  milestone.
- **Authentication** (a hardening phase): trusted-LAN first, loudly documented.
- **`/net` and `/dev` as remotely-mountable files** (Phase 3), and **remote
  execution** (Phase 4).

## Running it

Identical to previous releases for a single machine; the cluster needs two.

- **QEMU (single machine):** unzip `ouroboros-0.6.0-esp.img.zip` and boot
  `esp.img` (see the Makefile's `run-image` target).
- **QEMU (two-node cluster):** `make run-image-2vm-a` in one terminal (machine A,
  the exporter — start it first), `make run-image-2vm-b` in another (machine B),
  then in B: `mount -r 10.0.2.10:564 /mnt/a` and `ls /mnt/a`.
- **Parallels (Apple Silicon):** download `ouroboros-0.6.0-esp.dmg`, then wrap it
  into a Parallels-native `.hdd` locally:

  ```sh
  prl_disk_tool create --hdd esp.hdd \
      --dmg "$(pwd)/ouroboros-0.6.0-esp.dmg"
  ```
