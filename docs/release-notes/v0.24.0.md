# Ouroboros v0.24.0

One disk carries the whole system. The kernel names the partition the
firmware booted from, takes that disk as its block device, and the
filesystem server mounts as `/` the root partition beside the ESP. `make
bootstick` writes that layout to a whole stick or card, and a stick written
that way boots the Raspberry Pi 4 and Parallels 27.1.

And the Raspberry Pi 4 now runs from its SD card alone. The kernel drives
the card on the Pi's EMMC2 controller, found in the firmware's ACPI tables.
A card staged by `make bootstick PI=1` boots to a login with no USB stick,
keeps what is written to it across a power cycle, and stays the root with a
stick in a port.

A hundred and thirty-one pull requests since [v0.23.0](v0.23.0.md) (#284 to
#414), over twenty-six days, 2026-10-13 to 2026-11-07.

**No wire flag day.** The cluster's authentication is unchanged, so a
v0.23.0 node and a v0.24.0 node work together. A directory listing now comes
in pages, and a v0.24.0 node reads an older peer's single page as the whole
listing, as before. An exclusive create sent to a v0.23.0 export is not
exclusive there, because that export ignores the new `OPEN_EXCL` bit.
**Four things an installation sees:**

- **The block device is the disk the machine booted from.** The kernel used
  to take the first disk it found, virtio before USB, so a machine booted
  from a stick with a virtio disk attached ran on the virtio disk. Now the
  disk whose partition table matches the firmware's boot partition is
  installed, and any other disk only as the fallback, with a line saying
  so.
- **On a one-disk layout, the root is a partition typed as one** (MBR 0x83
  or GPT's AArch64 root), beside the ESP. If that root does not mount, the
  ESP is mounted as `/` read-only so the system can be looked at, and every
  change is refused until `unmount`.
- **A directory opened to write, truncate or create is EISDIR**, and
  `O_CREAT|O_EXCL` of a name that exists is EEXIST, both at the open. Before,
  the first opened and failed at the first write, and the second opened the
  existing file, so a lockfile believed it had made the lock.
- **`partition` refuses a GPT disk**, with a line saying to run `erase disk`
  first. Before, it wrote an MBR the old GPT went on hiding, and answered
  success.

This is pre-1.0 software. ABI and on-disk/on-wire formats are not stable yet.

## One disk

The one-disk plan (`docs/roadmap/roadmap-one-disk.md`):

- **The boot partition named.** Before the exit the kernel reads the
  `HardDrive` node of its own device path and logs `boot partition: N of
  MBR|GPT at LBA s`. Every image the build makes carries a disk signature
  of its own, so two images are never named alike.
- **`make disk`** builds `build/disk.img`, the FAT32 ESP as partition 1 and
  an ext2 root as partition 2, and `make run-disk` boots it.
- **`make bootstick`** writes that layout to a whole disk, after refusing
  anything that is neither empty nor ours. It carries the old disk's `/etc`
  and `/Users` over, so accounts and home directories survive a re-stage,
  and keeps its signature and boot counter. It reads the whole image back
  before it writes the partition table, since macOS mounts a disk the
  moment it has one. With `PI=1` it puts the Pi 4's UEFI firmware on
  partition 1, carrying a re-staged disk's firmware files and settings
  whole.
- **Booted on hardware:** the Pi 4 from a stick with no card, to a login on
  its ext2 root, and Parallels 27.1 from the same stick through its Boot
  Manager.
- **A blank virtio disk is held**, ranked below any stick, so a disk `erase
  disk` zeroed is still there after a reboot for `partition` to reach.

## The Pi 4 on its SD card

The SD-card plan (`docs/roadmap/roadmap-sd-card.md`):

- **An SDHCI driver**, `sdhci.rs`, a third kind of block device beside
  virtio-blk and USB storage. It brings a card up by the SD specification,
  then reads and writes one sector a command by PIO, 4-bit at 25 MHz. It
  runs on QEMU's `sdhci-pci` and on the Pi 4's EMMC2, which the kernel
  finds by its ACPI declaration (`BRCME88C`).
- **The firmware's partition is never written.** Sector 0 to the end of
  the card's firmware partition, and a GPT's backup copy, are fixed at
  bring-up, and every write into them is refused before the controller is
  touched. The Pi's `RPI_EFI.fd` and its settings live there.
- **Which disk is the root**, when a card and a stick are both in: a card
  that is the boot disk and holds a root with a filesystem goes in ahead of
  the stick. A card `make sdcard` staged, the firmware alone, gives way to
  the stick as before.
- **`make run-sd`** boots QEMU with the root on an SD card, and **`make
  test-sd`** grades nine layouts.
- The Pi's firmware must route the card to EMMC2, not to the Arasan
  controller (`SdIsArasan` 0, `docs/testing/testing-pi4.md` section 5). A
  re-stage carries the card's own firmware settings for that reason.

## The storage server made sound

Three weeks of it, in the filesystem server `fsd` and its three
filesystems:

- **Each filesystem stays inside its volume.** FAT32 refuses a cluster
  number outside the volume, ext2 a block number, and exFAT checks a
  cluster where it becomes a sector. A volume claiming more than its
  partition is not mounted. A damaged entry used to send a write to the
  next partition's sectors.
- **Names outside ASCII are names of their own** on exFAT and FAT32 long
  names. `café` and `cafè` used to be one name, so an `rm` of one removed
  the other. Listings show them in UTF-8.
- **A listing longer than one reply comes back whole.** `NP_READDIR`
  answers in pages, and `ls` and `tree` say when a directory is longer than
  they can hold. `ls /include` used to show about 60 of its 72 names.
- **Read-only is a property of the mount**, and the mount line says why a
  volume is read-only.
- **exFAT:** a directory grows past its first cluster, a failed `mv` is
  rolled back, a file another system wrote keeps its ValidDataLength, a
  vendor allocation is freed with its set, and the allocator writes its
  FAT entries and bitmap a sector at a time.
- **FAT32:** a FAT write reads only the first copy and writes it to every
  copy, and with mirroring off (`BPB_ExtFlags`) only the live copy is read
  and written.
- **ext2:** a listing reads no inodes, a write that cannot finish loses no
  block, and a damaged pointer can no longer free or overwrite the
  volume's own metadata (a group whose tables lie outside it is refused at
  the mount).
- **Fewer disk reads:** a file's cluster chain is walked once, a write
  resumes where the last one ended, and spawning a program resolves its
  path once a read request rather than once every 512 bytes.
- **A read error inside a partition's probe is an I/O error**, not "no
  filesystem".

## Fixed in the kernel

- **Parallels 27.1 no longer faults at boot.** The kernel scanned QEMU's
  virtio-mmio addresses whenever it found a serial console before the exit,
  and Parallels 27.1 gave its VMs one. It now probes only the virtio-mmio
  devices the ACPI tables declare present (the new `amlscan` crate).
- **A program's newline starts a new line on the serial console.** The
  kernel turns a bare `\n` into `\r\n` for every console writer, so `cat`
  on the Pi's serial line no longer prints each line where the last ended.
  Only the console sees it, never a file, a pipe or the network.
- **`MOUNT` answers the filesystem server alone**, and fsd makes the
  rescan.
- **A program file may be 1 MiB**, up from 128 KiB, and the spawn staging
  takes its chunks in order.

## C programs

- **A C program no longer hangs in `realloc`.** picolibc had been built
  without the flags it asks for, so clang deleted a size its malloc relied
  on. It is now built with them.
- Edit's and cpp's own sources can be built by DevTools's `cc`, `as` and
  `ld` (`make CCOMP=devtools CLINK=devtools`). clang stays the default.

## Smaller things

- Every pointer from the code and documents to a document's section is
  checked by `make test` (`check-doc-pointers`).
- The documents and the site drop the em dash.
- Six rigs report a boot QEMU's firmware never starts as INCONCLUSIVE, not
  as a failure.
- `make test` is at 308 host tests.

## Known on hardware

- **Still not on the Pi or Parallels:** networking. The Pi 4's on-board
  Ethernet is not driven, and Parallels' NICs, which it declares as
  virtio-mmio devices, are untried.
- **The SD card** has no DMA and moves one sector a command, and its speed
  is not measured. A write that waits for the card's busy signal, and the
  card's error status on a real failure, have been shown on no card yet: a
  healthy card shows neither.

## What is in a release

- `ouroboros-0.24.0-esp.img.zip`: the raw MBR+FAT32 disk image. Boot it under
  QEMU or any UEFI-AArch64 VM.
- `ouroboros-0.24.0-esp.dmg`: self-contained, for Parallels on Apple Silicon.
  Wrap it locally with:

  ```sh
  prl_disk_tool create --hdd esp.hdd --dmg <path>/ouroboros-0.24.0-esp.dmg
  ```

- `SHA256SUMS` for both.

For a Raspberry Pi 4, build from the tag and stage the card with `make
bootstick BOOTSTICK=/dev/diskN PI=1`, as `docs/testing/testing-pi4.md`
section 4 describes ("One disk: the card alone"). The release images are
not a Pi card.

Networking, and therefore the entire cluster surface, is QEMU-only. Neither
Parallels nor the Raspberry Pi exposes a NIC this kernel can drive yet.
