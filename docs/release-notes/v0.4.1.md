# Ouroboros v0.4.1

A single-fix patch release on top of [v0.4.0](v0.4.0.md): the one frontier
item the v0.4.0 real-hardware pass left open — **`fsd` getting supervisor-
restarted in the middle of a large read** — is fixed. No new capability arc; the
syscall ABI, on-disk formats, and everything else are unchanged from v0.4.0.

## The fix: a sequential-read cursor in FAT32

A large sequential read — a multi-MB `cat`, or `netd` streaming a file over
HTTP — could make the filesystem server drop its mount partway through, because
the server got torn down and restarted mid-transfer.

Root cause: `fat32::read_at` walked the file's cluster chain **from its start on
every call**, and each step reads a FAT sector with no cache. A client reading a
file in 2 KiB chunks therefore re-walked an ever-longer prefix each time —
O(n²) disk reads overall, and a single late-offset request issuing
hundreds-to-thousands of FAT reads in *one uninterrupted request*. On slow real
hardware that lone request runs past the server-supervisor's "runnable-wedge"
watchdog (~2.56 s) and the server is restarted, dropping the mount.

The fix bounds the work per request: `fat32::Fs` now keeps a **read cursor** that
remembers where the last read's chain-walk landed, so a forward/sequential read
*resumes* from there instead of re-walking. Each bulk request becomes
proportional to the chunk, not the offset; the server returns to its idle
receive between chunks (so the watchdog counter resets and the health-ping is
serviced promptly); and the whole read is linear. Only the chain *position* is
cached — never file data, which is still read fresh every call — and the cursor
is dropped the moment anything changes a chain (the single choke point for all
FAT mutation), so a read can never follow a stale chain.

## Evidence

Verified on QEMU with a piped-stdin harness driving the real shell:

- **Correctness.** A 64 KiB file (128 clusters, so the cursor resumes across a
  cluster boundary ~31 times) reads back with all 8192 monotonic per-line
  counters present, strictly increasing, with no gaps, duplicates, or
  reordering. A 1 MiB `cat … | wc` reports the exact `131072 131072 1048576`.
  Zero `-d int` exceptions across the run (only timer IRQs and syscalls).
- **The bug is real and the fix lands.** The same 1 MiB read completes in
  **0.99 s with the cursor** versus **did-not-finish-in-120 s without it** — the
  runaway single-request runtime that trips the watchdog on real hardware, made
  visible even on QEMU's fast virtio-blk.

## Scope

Deliberately narrow, matching a patch release. The cursor helps *sequential
read-only* workloads (`cat`, `netd` file serving — the reported bug). Still
tracked as follow-ups, not in this release: the read-side re-walk inside a large
`cp` (its interleaved destination writes invalidate the cursor), the analogous
walk in `exfat`/`ext2`, and the real-hardware-only Mode A BOT-retry tuning
(left untouched on purpose — it can't be validated on QEMU, and cutting FAT
reads by orders of magnitude already shrinks its exposure).

## Running it

Identical to v0.4.0 — the disk images boot the same way:

- **QEMU:** unzip `ouroboros-0.4.1-esp.img.zip` and boot `esp.img` (see the
  Makefile's `run-image` target for the exact invocation).
- **Parallels (Apple Silicon):** download `ouroboros-0.4.1-esp.dmg`, then wrap
  it into a Parallels-native `.hdd` locally:

  ```sh
  prl_disk_tool create --hdd esp.hdd \
      --dmg "$(pwd)/ouroboros-0.4.1-esp.dmg"
  ```

See [`docs/manual.md`](../manual.md) for the full run/build/shell tour and
[`CHANGELOG.md`](../CHANGELOG.md) for the "Large-read fsd restart fixed" write-up.
