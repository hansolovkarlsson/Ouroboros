# Ouroboros v0.10.0

Locking the cluster door. Phases 1–4 of the distributed-cluster direction all
shipped **trusted-LAN, no authentication**: any host that could reach a machine's
9P export (TCP 564) could read and write its disk (`mount -r`) and run arbitrary
`/bin` programs on it (`cpu`). This release closes that hole — the **export is
now authenticated with a shared cluster secret**, and an unauthenticated peer
gets nothing.

This is pre-1.0 software: the syscall ABI and on-disk/on-wire formats are not yet
stable. Everything from [v0.9.0](v0.9.0.md) still works — the shell, `/bin`,
FAT32/exFAT/ext2, per-task namespaces, two-node read/write disk sharing, the
`/proc`/`/dev/cons`/`/net` file servers, and `cpu` remote execution — now gated
by the cluster key.

## What's new — authenticated export

Every machine in a cluster is configured with the same secret (read from
`\CLUSTER.KEY` on its boot disk). Every export request — a disk op *or* a `cpu`
run — carries an auth header, and the exporter verifies it before serving
anything:

```
framed request:  [len][magic][nonce:16][mac:32][NP message]
mac = HMAC-SHA256(cluster_key, nonce ‖ NP-message)
```

It's a **client-nonce MAC**: the secret never crosses the wire, and it folds into
the existing one-request-per-connection model with **no extra round trip** (chosen
over a server-nonce challenge-response, which would have taxed every `ls`/`cat`
with an added RTT). Because the key is *symmetric*, the bidirectional `cpu` case —
where the remote machine becomes a client of the caller's export to read `/host`
files — authenticates in both directions with no extra machinery.

Two operational knobs: **fail-closed** (no `\CLUSTER.KEY` ⇒ the export refuses
all remote clients, safe for a single-machine run), and a **`\NOEXEC`** flag file
that lets a machine authenticate remote *mounts* while refusing `cpu` remote
execution entirely (remote code execution is a categorically larger blast radius
than disk sharing).

The crypto (SHA-256 + HMAC-SHA256) is hand-rolled, `no_std`, no heap, no crate —
the project's standing discipline — and validated against NIST and RFC 4231
known-answer vectors.

## Scope, honestly

This is **cluster-membership** authentication (one shared secret = who's in the
cluster), not per-peer identity, and it assumes a **trusted LAN** for what remains
deferred: a passive sniffer can replay an *observed* request (it cannot forge a
new one), and the reply direction is not authenticated. Per-peer identity,
mutual/reply-direction auth, and replay protection are each a named next tier —
not faked.

## Running it

- **QEMU (single machine):** unzip `ouroboros-0.10.0-esp.img.zip` and boot
  `esp.img` (the Makefile's `run-image` target). A single machine runs unchanged;
  the export is simply closed to remote peers unless a key is present.
- **QEMU (two-node cluster):** `make run-image-2vm-a` / `-b` (both images carry
  the same dev `\CLUSTER.KEY`, so they authenticate each other); in B:
  `mount -r 10.0.2.10:564 /mnt/a`, `cpu 10.0.2.10:564 ls /`. A machine with a
  mismatched or absent key is refused cleanly.
- **Parallels (Apple Silicon):** download `ouroboros-0.10.0-esp.dmg`, then wrap it
  into a Parallels-native `.hdd` locally:

  ```sh
  prl_disk_tool create --hdd esp.hdd --dmg "$(pwd)/ouroboros-0.10.0-esp.dmg"
  ```
