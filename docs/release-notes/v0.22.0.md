# Ouroboros v0.22.0

Ouroboros runs on a Raspberry Pi 4. The kernel boots from the SD card through
the pftf UEFI firmware, drops from EL2 to EL1, takes over the board's VL805
xHCI controller, and runs a full session: a USB keyboard behind the on-board
hub, a USB stick mounted by `fsd` as the runtime disk, `/bin` run from it,
and a PSCI power-off at the end. The first full session ran on 2026-10-03,
and since 2026-10-04 the Pi is worked over its serial console alone, every
round of register-order work in this release booted on it.

Thirty-nine pull requests since [v0.21.0](v0.21.0.md), one arc: the Raspberry
Pi bring-up (#176 to #207), desk work for the Pi 400 first and then the Pi 4
on the bench. Beside it, steps 0 to 4 of the per-user keys plan
(`docs/roadmap/roadmap-user-keys.md`, #169 to #174), which change nothing on
the wire yet.

**Two things change for an existing installation. Read these first.**

- **Root squash.** An export now refuses a remote claim that resolves to uid 0
  or gid 0 unless its `/etc/cluster/authorized` line for that peer ends with
  the word `root`. A cluster that drove its exports as root from another node
  must add the flag to that peer's line, on each export that should trust it
  with root. Every other account is unaffected. The dev images carry the flag
  for `host`, `node-a` and `node-b`.
- **`/etc/shadow` lines are upgraded at first login, one way.** A version-1
  line becomes version 2 (PBKDF2-HMAC-SHA-512, 210,000 iterations, the same
  width on disk) the first time its user logs in. A v0.21.0 kernel cannot read
  a version-2 line, so a disk logged into under v0.22.0 does not log in under
  v0.21.0. A login now spends about two seconds on key derivation (measured on
  QEMU); that is the point of it.

**No wire flag day.** Nothing in the 9P auth framing changed: a v0.21.0 node
and a v0.22.0 node authenticate each other as before, root squash aside.

This is pre-1.0 software. ABI and on-disk/on-wire formats are not stable yet.

## The Raspberry Pi 4

Each of these was found on the board or on paper against its firmware, and
each fix has a check that can fail on QEMU, except where the note says only
the board can show it.

- **The kernel's own stack, from the first instruction.** The Pi firmware's
  stack is 16 KB with its page tables directly below it, and the kernel
  overflowed it into them; every firmware fault the board showed from
  2026-10-01 was this. `main` now switches to a 256 KB stack in the image's
  `.bss` before any call (#191).
- **The drop from EL2 to EL1.** The Pi's firmware hands off at EL2, where
  every `_EL1` write the kernel made after the exit went to a register the
  running level does not use. `el2.rs` prepares EL1's tables and vectors from
  EL2 and `eret`s into a running MMU (#188). `make run-el2` and
  `make test-el1-drop` reproduce the handoff on QEMU.
- **The early fault reporter.** A fault before the kernel's vectors are
  installed went to a RELEASE firmware that prints one line. `earlyfault.rs`
  registers the kernel's own handler through the firmware's CPU protocol and
  prints ESR, FAR, ELR, a backtrace, the loaded image holding each address and
  the firmware's page tables walked at the fault (#187, #189, #190). It is
  what found the stack. `make test-early-fault`.
- **The console at a bus address.** The devicetree gives the PL011 at its
  VideoCore address (`0x7e201000`); `dtranges.rs` translates every `reg`
  through its ancestors' `ranges` to the CPU's `0xfe201000` (#181), and a
  devicetree with no `/chosen` is handled (#182).
- **The xHCI on the Pi's PCIe.** Found through its own `PciIo` handle at the
  firmware's CPU address (the BAR is a bus address there), taken last before
  `ExitBootServices` (#176); USB 2.0 hubs, since every USB 2 device on the
  board sits behind a VIA hub (#177); EP0 recovery and completions matched to
  their own TRBs (#178); 32 scratchpad pages for the VL805 (#192).
- **Non-coherent DMA.** The BCM2711's PCIe DMA is not cache-coherent. Every
  xHCI ring and buffer lives in one pool mapped Normal Non-cacheable where
  ACPI declares `_CCA 0`, checked at boot through the CPU's own table walker;
  the framebuffer stays cacheable with each write cleaned to memory (#179).
- **Ordering on the bus.** A 64-bit register is two 32-bit stores, low first,
  and the first command timeout dumps the controller (#193); a barrier comes
  before each register that hands the controller a ring (#196); a TD is published whole, its first TRB's cycle bit flipped last
  (#197); every register write has a store barrier inside it (#198), and
  since #207 every xHCI register write goes through a typed handle, so a write
  that skips the barrier or a register's RsvdP bits does not compile.
  `make check-xhci-barriers`, run by `make test`, finds the barriers in the
  built image. ERDP is written before ERSTBA, as edk2 does (#200); the RsvdP
  bits of ERSTSZ, ERSTBA, CRCR, CONFIG and USBCMD are kept (#201, #202); a
  controller found running is halted before HCRST (#203, #205).
- **The SuperSpeed port.** A USB 3 stick on a root port read `speed=0`: the
  port was already up, the reset sent the link back to Polling, and the speed
  was read before it retrained. The driver now logs the port's state and
  waits for it to enable, with a warm reset where the link state calls for
  one (#194).
- **USB storage recovery.** A Bulk-IN Stall where the CSW is owed is
  recovered with CLEAR_FEATURE to the device, and a storage endpoint is
  rewound after an error (#184, #186). `make test-usb-hub` includes a boot
  (`scripts/test-usb-hub.py --stall`, #185) where QEMU's stick stalls on a
  schedule, about thirty times, and each must recover.
- **The card and the stick, each one command.** `make sdcard SDCARD=/Volumes/…`
  stages the boot card: the pinned pftf firmware (v1.53, installed once,
  since its settings live in `RPI_EFI.fd`) and the ESP on top; it never
  formats (#180). `make stick STICK=/Volumes/…` stages the runtime disk, with
  no `EFI` tree and its `/etc` kept (#195). The boot's first line names its
  build: commit, `+dirty`, profile (#199).
- **Boot flag files** at the ESP root switch one boot step off to bisect a
  hang on hardware: `\NOXHCI`, `\XHCINOWR`, `\FBCON` (#181, #183).

**What the board said about the boot identity** (owed since v0.21.0): the Pi
4's firmware offers `EFI_RNG_PROTOCOL` (32 bytes of entropy), and the
counter came from `\EFI\ORBS\BOOTID.TXT` on the card, with the UEFI
variable absent (`boot 1` then `boot 2` across a reboot). So keyed sessions there would have forward secrecy, once the
Pi has a network.

**Still not on the Pi:** networking (no NIC driver, so the whole cluster is
QEMU-only), the SD card as a runtime disk (the kernel has no EMMC2 driver, so
a USB stick is the disk), and multi-core. The Pi 400 has not yet been
re-booted since the stack fix; its faults in 2026-09 were the same stack.
Parallels is parked.

## Per-user keys, steps 0 to 4

The plan closes the gap that any authorized machine could claim any user on
an export, root included. Steps 0 to 4 build everything below the wire:

- **The impersonation gate.** `np9p_client.py impersonate-gate` shows the
  attack served: a dev identity no machine holds read `/etc/shadow` claiming
  root. It is the check the later steps must turn red.
- **Root squash** (above), with a duplicated `authorized` line granting root
  only if every line for the key says so.
- **PBKDF2-HMAC-SHA-512** in `ed25519`, checked against `hashlib`'s vectors,
  210,000 iterations, measured on the guest at 3.9 to 6.2 µs an iteration
  (a TCG band, not a figure).
- **The user key, the realm and version-2 shadow lines**, matched against an
  independent Python derivation for every dev user by `make test`.
- **Keys held by `netd` from login to logout.** `login` derives the user's key
  and hands it to `netd`; the shell drops it at logout and before every
  prompt; `passwd` sends hashes, never passwords; no supervised server ever
  derives. New `netd` operations `NETOP_KEY_HOLD`, `NETOP_KEY_DROP`,
  `NETOP_KEY_DROP_MINE`, `NETOP_KEY_LIST`, and `accountd` operations
  `ACCTOP_SALT` and `ACCTOP_UPGRADE`, in `syscall-abi`. `make test-held-keys`
  drives five boots of it.

Step 5, the per-user credential on the wire, is next. Until it lands a held
key signs nothing.

## Smaller things

- `login` says why it refused: the shadow read's error code, no entry, or an
  entry that does not parse (#206).
- `netd` acks its supervisor between the chunks of a `cpu` spawn, so a long
  spawn is no longer mistaken for a wedge and restarted (#175).
- A keystroke arriving while the kernel waited on an xHCI command was dropped
  and the keyboard never re-armed; fixed (#177).
- `make run-usb-kbd` had found no keyboard for a month: the PCI root bridge
  was opened exclusively and EDK2's network stack refused to stop (#176).
- `scripts/efi-symbol.py` turns a firmware-reported address into a kernel
  function through a relinked map.
- `make test` grew to 175 host tests, `test-usb-hub`'s classifier on fixed
  transcripts, and the xHCI barrier check.

## What is in a release

- `ouroboros-0.22.0-esp.img.zip`: the raw MBR+FAT32 disk image. Boot it under
  QEMU or any UEFI-AArch64 VM.
- `ouroboros-0.22.0-esp.dmg`: self-contained, for Parallels on Apple Silicon.
  Wrap it locally with:

  ```sh
  prl_disk_tool create --hdd esp.hdd --dmg <path>/ouroboros-0.22.0-esp.dmg
  ```

- `SHA256SUMS` for both.

For a Raspberry Pi 4, build from the tag and stage a card and a stick with
`make sdcard` and `make stick`, as `docs/testing/testing-pi4.md` section 4
describes; the release images are not a Pi card.

Networking, and therefore the entire cluster surface, is QEMU-only. Neither
Parallels nor the Raspberry Pi exposes a NIC this kernel can drive yet.
