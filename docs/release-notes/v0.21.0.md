# Ouroboros v0.21.0

A held cluster session is keyed. The first request on a session carries a
fresh X25519 key inside its signature, the far side answers with its own inside
the signed reply, and every later message on that connection carries an HMAC
tag and a strict sequence number instead of a signature. On the two-node rig
the crypto per remote file verb falls from 2,926 µs to 169 µs, the median verb
cycle from 7.50 ms to 4.53 ms, and a captured message on a session can no
longer be replayed.

Eleven pull requests since [v0.20.0](v0.20.0.md), one arc: session-scoped
authentication, planned and measured first (`docs/roadmap/roadmap-session-auth.md`,
eight steps), with the kernel's new boot identity underneath it.

**No wire flag day.** A keyed session is offered, never required. A v0.20.0
export ignores the offer and answers without a key, and a v0.21.0 client then
keeps the session signed exactly as before; a v0.20.0 client never offers, and
a v0.21.0 export serves it signed. Mixed clusters work. One-shot requests (a
shell `cat` over a mount, `cpu`) are signed per request in both versions.

This is pre-1.0 software. ABI and on-disk/on-wire formats are not stable yet.

## Syscall ABI changes, for anyone building against `syscall-abi`

- **`BOOT_ID` (syscall 69), new.** The boot identity the kernel establishes
  before `ExitBootServices`: a per-boot counter (persisted in a UEFI variable
  and in `\EFI\ORBS\BOOTID.TXT`, and trusted only if a store held it from
  before this boot), which stores held it, and the length of the boot entropy
  (`EFI_RNG_PROTOCOL`). The entropy itself (`BOOT_ID_ENTROPY`) is for the
  `CAP_NET` holder alone; every other caller is refused. `/bin/bootid` prints
  all of it and checks that refusal. `BOOT_ID_ENTROPY_MAX` (32) sizes a buffer
  for it.
- **`FS_ERR_AUTH` is named in `libc/include/sys.h`**, and `ouro_fs_strerror`
  says "authentication failed" for it. A C program used to print "failed" for
  a remote refusal, which read like any other error.
- **A C program's first remote operation rides out the delegation window.**
  The shell spawns a program and only then delegates it the right to reach
  `netd`, so a program that reached `netd` in between was refused. `ulib` has
  retried that since v0.18.1; `libc` did not, and the first `cbig` after a
  mount failed about one boot in three. Measured: twenty clean boots with the
  retry, three failures in sixteen without it.

## Keyed sessions

A C program's open file on a remote mount rides one held connection for its
whole life, and on that connection the four Ed25519 operations per verb were
44% of a median verb (step 0 of the plan, measured before any code). The keyed
session replaces them:

- **The handshake rides `NP_SESSION`**, the verb held sessions already open
  with, so there is no new round trip. The client's ephemeral key is its
  payload and the export's is its result, both inside the existing signatures,
  so a man in the middle can neither substitute a key nor strip the offer.
- **Two keys, one per direction**, from `SHA-512` over the shared secret, the
  request nonce and both public keys. The frame is `AUTHNP04`:
  `[len][magic][seq][tag]` ahead of the message, and `[len][tag]` ahead of the
  reply, each tag an `HMAC-SHA-512` truncated to 32 bytes.
- **Any failure closes the connection.** The export answers a bad tag, a wrong
  `seq`, an `AUTHNP03` frame, a second key or a small-order key with an RST and
  no reply (an unauthenticated "auth failed" is what an attacker would forge),
  and names the reason on its own console. The client fails the caller's verb
  with `FS_ERR_AUTH`.
- **Every verb on a keyed session runs as the user who signed its
  `NP_SESSION`.** A keyed frame carries no name, and the client refuses to send
  a verb for a caller whose name has changed since.
- **Where the platform has no entropy,** the ephemerals are hashed from the
  machine key, the boot counter and the clock, so they never repeat but carry
  no forward secrecy. The plan says so rather than claiming it. QEMU's firmware
  offers `EFI_RNG_PROTOCOL`; whether the Pi 4's and Parallels' do is not yet
  measured. A node whose counter cannot be persisted keys nothing.

X25519 and HMAC-SHA-512 are hand-written in `ed25519/`, from their RFCs, and
checked against every RFC 7748 and RFC 4231 vector, three OpenSSL-generated
exchanges, and the two Python host peers, which implement the same key
schedule separately so that one side's mistake cannot pass as agreement.

## A park never signs

Measuring where the handshake's key exchange would run found `netd`'s request
signing already running within **80 bytes of its guard page** on v0.20.0, on
every fid verb, and a 512-byte pad there faulted the server. Every parked
request is now written raw and framed and signed by the service pass at the top
of `netd`'s loop, about 10 KB higher.

## Smaller things

- `np9p_server.py` and `np9p_client.py` speak keyed sessions, and the server
  has `--misbehave` (four kinds of reply a correct client must refuse) and
  `--unkeyed` (plays a v0.20.0 export). `make test` runs a keyed session
  between them, the four refusals, and the unkeyed fallback.
- `np9p_client.py keyed-gate` checks a guest export's keyed sessions in
  thirteen checks, the plan's controls among them.
- `drive-2vm.py` counts `AUTHNP04` frames in each node's capture.
- The wire-constant check reads magics and sums, and pins 137 constants across
  Rust, the C headers and both Python peers.
- The export's keyed dispatch had cost every export verb 1,760 bytes of stack
  in its first build (a `log` call inlined into it, and a second call site that
  un-inlined the verb dispatch); both were found by measuring and fixed before
  release. At the client's deepest point the release costs 336 bytes of
  headroom against v0.20.0, the resident per-session key state.

## What is in a release

- `ouroboros-0.21.0-esp.img.zip`: the raw MBR+FAT32 disk image. Boot it under
  QEMU or any UEFI-AArch64 VM.
- `ouroboros-0.21.0-esp.dmg`: self-contained, for Parallels on Apple Silicon.
  Wrap it locally with:

  ```sh
  prl_disk_tool create --hdd esp.hdd --dmg <path>/ouroboros-0.21.0-esp.dmg
  ```

- `SHA256SUMS` for both.

Networking, and therefore the entire cluster surface, is QEMU-only. Neither
Parallels nor the Raspberry Pi target exposes a NIC this kernel can drive yet.
