# Ouroboros v0.15.0

The cluster stops serving every remote request as root.

Since the export was hardened in [v0.10.0](v0.10.0.md), a shared cluster key has
authenticated the **machine** on the far end of a `mount -r` or a `cpu`. That was
always half the question. `netd` relayed each request to `fsd` under **its own
root identity**, so `fsd`'s root bypass short-circuited before any file mode was
read — an unprivileged user on node B could `mount -r <A> /mnt/a` and read node
A's `/etc/shadow`, or reach A's account server with `cpu A passwd root`.

A request now says **who** is asking, and the far side applies its own
permissions to that answer. Nothing else changes: the wire is compatible with
itself only (see the flag day below), and everything from
[v0.14.0](v0.14.0.md) still works — two-node disk sharing, `/proc`/`/dev/cons`/
`/net` as files, dial-out/dial-in, `cpu` with namespace import. This is pre-1.0
software: ABI and on-disk/on-wire formats are not yet stable.

## What's new — a remote request carries the requesting user

The auth header gained a 32-byte **user name**, and the MAC now covers
`nonce ‖ name ‖ message`, so the claimed user cannot be edited in flight by
anything that does not hold the cluster key. It costs nothing: the MAC was
already there.

A **name**, not a uid. Two machines have independent `/etc/passwd` files, so uid
1000 need not be the same person on both — sending the number is what lets NFS's
`AUTH_SYS` map one user silently onto another. The exporting machine resolves the
name through **its own** `/etc/passwd` and **refuses a name it has never heard
of**, rather than mapping a stranger onto "nobody", which is just a quieter way
of guessing.

In practice, on a two-node cluster where `user` exists on both:

```
$ cat /mnt/a/HELLO.TXT          # 0644 on A — served
hello from an ext2 volume
$ cat /mnt/a/etc/shadow         # 0600 root on A — refused, as it would be locally
cat: permission denied
$ cpu 10.0.2.10:564 id          # the command runs on A, AS you
uid=1000(user) gid=1000(user)
```

`root` on B still reads both, because `root` resolves to `root` — the mechanism
discriminates by account rather than blanket-denying.

**`cpu` is covered by a second mechanism**, because a spawned program is not
`netd`'s request: it makes its own, with its own task identity, and a child
inherits the spawner's. So `netd` assumes the mapped user's identity for the
length of the spawn and the child inherits that. The kernel's saved-uid rule
makes it safe in both directions — `netd` may return to root because root is its
saved id, while the child's saved id is the *user's*, so a remote command can
never restore root.

## What's new — the HTTP server is no longer root either

`netd`'s built-in static-file server (port 80) has no user model, so it read
files with `netd`'s own root credential — meaning an anonymous
`GET /etc/shadow`, with no cluster key and no username, returned the password
hashes. Found by review of the change above, because that change's whole claim is
that a remote request cannot reach `fsd` with root authority.

HTTP is now served as **anonymous** (`nobody`): the `other` permission triad and
nothing more. A file it may not read returns **403 Forbidden** rather than a
misleading 404. World-readable files, directory listings and FAT32/exFAT volumes
(which model no mode at all) are unaffected.

## Compatibility — a deliberate flag day

The auth magic moved from `AUTHNP01` to `AUTHNP02`. **A v0.14.0 or earlier peer
is refused, not misparsed** — the old layout's first 32 message bytes would
otherwise be read as a username. Both nodes of a cluster are built from one tree,
so the cost is nil, and a silently misread identity is not a trade worth making.

Two other consequences worth knowing before upgrading:

- **Both machines now need an `/etc/passwd`.** A machine that cannot name its own
  caller refuses to send; one that cannot resolve the name refuses to serve. The
  same person should have the same *username* on both machines — the uid numbers
  need not match, which is the whole reason the name travels.
- **Supplementary groups do not cross the cluster.** A remote caller is judged on
  its uid and primary group only, so a file reachable *only* through a
  supplementary group is refused remotely and allowed locally. This can only ever
  deny access a local session would grant, never grant one it would deny.

## What this does not do

The cluster key is still **per-machine**, so a peer that holds it can claim any
name. This protects you from the *users* of a machine you trust — the real
exposure, since a machine's own users are not all trusted even when the machine
is — but not from a machine you don't. Per-user **keys** are the next tier, along
with replay protection and transport encryption, all gated behind a "leaving a
trusted network" trigger on the roadmap. Bytes still cross the wire in cleartext.

## Under the hood

The mechanism is the interesting part, and it is the second attempt: the first
was rejected by review with fifteen findings, five of them independent ways a
remote request still reached `fsd` with root authority. Identity is now a
**required parameter** of every `netd` helper that calls `fsd`, carried **in the
request** rather than latched between two messages — so an unproxied export path
does not compile, and nothing can interleave between a request and a field of it.
`fsd` refuses a relayed request that states no identity rather than falling back
to `netd`'s credential, which is root.

See [`unspellable-postmortem.md`](../unspellable-postmortem.md) for the rejected
design and what its review cost to learn, and
[`CHANGELOG.md`](../CHANGELOG.md) for the milestone record.

## Running it

Identical to previous releases.

- **QEMU (single machine):** unzip `ouroboros-0.15.0-esp.img.zip` and boot
  `esp.img`. The HTTP change is visible with `make run-image-server`:
  `curl http://localhost:5555/etc/passwd` succeeds, `.../etc/shadow` is a 403.
- **QEMU (two-node cluster):** use the **ext2** pair — `make
  run-image-2vm-ext2-a` / `-b` — since FAT32 records no mode for `fsd` to
  enforce. In B: `login` as `user`, then `mount -r 10.0.2.10:564 /mnt/a` and try
  the reads above.
- **Parallels (Apple Silicon):** download `ouroboros-0.15.0-esp.dmg`, then wrap it
  into a Parallels-native `.hdd` locally:

  ```sh
  prl_disk_tool create --hdd esp.hdd --dmg "$(pwd)/ouroboros-0.15.0-esp.dmg"
  ```

  Note that the cluster is not reachable on Parallels (no virtio NIC there); the
  two-node behaviour above is validated on QEMU.
