# Ouroboros v0.18.0

Commands stop saying the wrong thing about why they failed — and a `mv` that
quietly put your file somewhere else now refuses.

A correctness release rather than an arc. No new capability: six pull requests,
of which the load-bearing ones fix things the system had been *saying* rather
than things it had been *doing*. Everything from [v0.17.0](v0.17.0.md) still
works unchanged — per-machine Ed25519 cluster keypairs, per-user cluster
identity, two-node disk sharing, `/proc`/`/dev/cons`/`/net` as files,
dial-out/dial-in, `cpu` with namespace import. **No wire flag day**: the auth
frame format is untouched, so a v0.17.0 node and a v0.18.0 node talk to each
other normally. This is pre-1.0 software: ABI and on-disk/on-wire formats are
not yet stable.

## A DATA-INTEGRITY FIX — `mv` onto another mount no longer lies

This is the one to read if you read nothing else.

```
$ mv /F.TXT /mnt/a/NEW.TXT      # v0.17.0
$ ls /
BIN/  EFI/  ETC/  MAN/  NEW.TXT  Users/     <- renamed LOCALLY
$ ls /mnt/a
HELLO.TXT  SUB/                              <- nothing arrived
```

Exit code **0**. The file was not where you asked it to go, the remote mount
never saw the request, and nothing said so.

`ulib::fs_mv` resolved both paths through the namespace and then sent the
request to the **source's** server, handing it the destination's *string*, which
that server read as a path of its own. Any `mv` whose two ends lived on
different mounts — a remote mount, a second local partition, `/proc` — did this.

v0.18.0 refuses:

```
$ mv /F.TXT /mnt/a/NEW.TXT
mv: cannot move across mounts (copy it, then remove the original)
```

`-f` does **not** override it. The guard is below `mv`'s existing
overwrite check, and `-f` was precisely the flag that reached the silent
rename before. A same-mount `mv` is completely unchanged.

Use `cp` across a mount; it has always worked correctly. Doing the
copy-then-delete that Unix `mv` does across filesystems is future work — this
release chooses the honest refusal over a silent wrong answer.

## `ls` tells you what actually went wrong

`ls` printed `no such file or directory` for **every** failure. It was the only
command under `programs/fileutils/` that never used the shared error renderer,
which has distinguished fifteen conditions for weeks.

On any ext2 filesystem — the one that enforces permissions — a file you were not
allowed to read was reported as a file that did not exist:

```
$ ls /PRIV          # v0.17.0, as a non-root user
ls: /PRIV: no such file or directory

$ ls /PRIV          # v0.18.0
ls: /PRIV: permission denied
```

The same string had also covered a cluster peer refusing your signature
(`cluster authentication failed`) and a transient `no filesystem mounted this
boot` while `fsd` restarted. A directory that *is* there and one that *is not*
were indistinguishable, which is misleading in ordinary use and worse in a
security context.

The shell's own copy of that message table — kept separate because the shell has
its own filesystem layer — had drifted too. It was missing two conditions
entirely, and told you an invalid name `must fit this kernel's 8.3 short-name
subset`, a restriction FAT32 long-filename write support removed on 2026-08-27.
Both fixed.

## `ls` works against a host 9P server again

If you use `scripts/np9p_server.py` to serve a host directory to a guest
(`make run-image-9p-client`), `ls /mnt/a` has been failing since 2026-08-27 with
`no such file or directory`, while `cat` of a file under the same mount worked.

The peer implemented no `NP_STAT`, and `ls` began stating a named operand when
it gained `-l` and file operands. The peer now implements it, so the documented
recipe works as written:

```
$ mount -r 10.0.2.2:5641 /mnt/a
$ ls /mnt/a
HELLO.TXT  SUB/
$ ls -l /mnt/a
-rw-r--r--    -    -      1960        -         HELLO.TXT
drwxr-xr-x    -    -         0        -         SUB/
```

It also answers a definitively-absent path with the specific "not found" status
instead of a generic error, which is what `mv` and `cp`'s destructive-overwrite
guard reads to tell *absent* from *could not tell*. Against a v0.17.0 peer those
commands reported `cannot tell whether … exists` for paths the peer knew for
certain were missing.

This affects the host-side test tooling only — nothing in the shipped image
changed, and guest-to-guest mounts were never affected.

## Under the hood

- **The cross-language wire check grew from 12 to 27 constants.**
  `scripts/check-wire-constants.py` compares the Rust ABI crates against both
  Python peers on every `make test`. It now covers `syscall-abi` as well as
  `ninep-abi`, the status codes both peers hand-transcribe as
  `(1 << 64) - 1 - N`, the `StatInfo` record's field offsets, and the directory
  flag bit — which was invisible to the parser on *both* sides, so the bit
  deciding whether a remote entry lists as a directory was pinned by nothing.
- **A new reserved status code**, `FS_ERR_CROSS_DEVICE` (POSIX's `EXDEV`), for
  the `mv` refusal above. It sits inside the existing error band, so the error
  floor `libc/include/sys.h` mirrors is unchanged.
- **`CLAUDE.md` is 75% smaller** (198KB → 50KB), with its two long indexes moved
  to `docs/README.md` (every document, annotated) and `docs/source-map.md`
  (every source file, annotated). Nothing was deleted; both are more likely to
  stay current living beside what they describe.
- **The twenty-ninth postmortem**, `docs/true-when-written-postmortem.md`, on
  the defect class three of the above share: a comment or message that was
  correct on the day it was written and was falsified later by a change in a
  different file, where no compiler, test or code review can see it. One of them
  had a shelf life of four and a half hours.

## Getting it

`ouroboros-0.18.0-esp.img.zip` boots under QEMU or any UEFI-AArch64 VM;
`ouroboros-0.18.0-esp.dmg` is for Parallels on Apple Silicon — wrap it locally
with:

```sh
prl_disk_tool create --hdd esp.hdd --dmg <path>/ouroboros-0.18.0-esp.dmg
```

Verify against `SHA256SUMS`. See [`docs/manual.md`](../manual.md) to drive it,
and [`docs/testing-qemu.md`](../testing-qemu.md) for the QEMU and two-node
cluster rigs.
