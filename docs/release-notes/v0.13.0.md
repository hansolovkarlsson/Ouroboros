# Ouroboros v0.13.0

Mutual authentication on the export. [v0.10.0](v0.10.0.md) authenticated the
export *request* — a client proves it holds the cluster key. This release adds
the other direction: the export now authenticates its *reply* too, so the server
proves *it* holds the key. An active attacker who can inject into the TCP stream
can no longer feed a client forged data (wrong file contents, a fake success);
the client rejects any reply whose MAC doesn't verify. This is the first,
cheapest step of the deferred auth hardening (tier 2).

This is pre-1.0 software: the syscall ABI and on-disk/on-wire formats are not yet
stable. Everything from [v0.12.0](v0.12.0.md) still works — dial-out and dial-in,
the authenticated export, two-node disk sharing, the `/proc`/`/dev/cons`/`/net`
file servers, and `cpu` remote execution.

## What's new — reply authentication

The framed reply gains a 32-byte MAC prepended to its body:

```
reply:  [len][mac:32][status:u64][result]
mac = HMAC-SHA256(cluster_key, request_nonce ‖ [status][result])
```

Binding the reply's MAC to the **request nonce** (rather than a fresh reply
nonce) does double duty for free: both sides already hold that nonce, so there's
no new wire field, and it ties each reply to its specific request — a captured
reply can't be replayed against a different one. It's the same symmetric cluster
key and the same hand-rolled HMAC as the request direction, with no extra round
trip and no server state.

## Scope, honestly

This adds **integrity and authenticity, not confidentiality.** Every byte still
crosses the wire in **cleartext** — a passive sniffer reads your files even with
perfect MACs. Reply-auth is banked as **defense-in-depth under a trusted LAN**,
not because a current deployment needs it, but because the symmetric key made it
nearly free to add.

The rest of the hardening is deliberately **not built** and is recorded on the
roadmap behind an explicit *"leaving a trusted network"* trigger: replay
protection, per-peer identity, transport **encryption**, and reply-auth for the
`cpu`-run output *stream* (which is not a framed reply). Until Ouroboros actually
faces a semi-trusted or hostile network, those stay deferred — building them now
would be a mechanism ahead of its threat model.

## Running it

Identical to previous releases; the reply-auth is transparent (both ends update
together).

- **QEMU (single machine):** unzip `ouroboros-0.13.0-esp.img.zip` and boot
  `esp.img`.
- **QEMU (two-node cluster):** `make run-image-2vm-a` / `-b` (both images share
  the dev cluster key), then in B: `mount -r 10.0.2.10:564 /mnt/a`, `cpu`, `dial`,
  `serve` — every export exchange is now mutually authenticated.
- **Parallels (Apple Silicon):** download `ouroboros-0.13.0-esp.dmg`, then wrap it
  into a Parallels-native `.hdd` locally:

  ```sh
  prl_disk_tool create --hdd esp.hdd --dmg "$(pwd)/ouroboros-0.13.0-esp.dmg"
  ```
