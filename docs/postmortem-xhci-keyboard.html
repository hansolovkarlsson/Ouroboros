🖥️ This is the last of three companion pieces — the boot bring-up postmortem covers the exception vectors, MMU, and console-discovery work everything here sits on top of, and the shell & filesystem postmortem covers the disk-backed userland shell this driver's keystrokes actually reach.

This is a write-up of one day's work getting a real, physical USB keyboard talking to Ouroboros, a from-scratch ARM64 microkernel, running on Parallels Desktop on Apple Silicon. It's kept separate from this project's own historical record because the bugs here aren't really Ouroboros-specific — they're the kind of thing anyone writing a bare-metal USB/xHCI driver and testing it against a real hypervisor is likely to run into, and there wasn't an existing write-up covering them. If you're building your own OS and your keyboard driver "sort of" works — enumerates fine, sends what look like correct commands, but you get garbage or silence back — some of this may save you a day of your own.

Five real, confirmed bugs, each found by direct evidence — register dumps, decoded exception registers, byte-for-byte comparisons — rather than guessing. In order: a PCI Command register bit that looked like a platform quirk until it wasn't; real PCIe firmware panicking on a config-space write a software emulator tolerated silently; a physical PCI address landing outside a simplifying assumption baked into our own page tables; a whole class of USB request silently going nowhere; and a working driver reading the wrong physical device.

Why this was hard to see coming

Ouroboros develops primarily against QEMU, because it's fast to iterate against and fully scriptable. Real hardware testing — in this case, Parallels Desktop running the guest on Apple Silicon — happens periodically, by a human, and each round trip costs real wall-clock time: rebuild, re-image a disk, boot the VM, look at the screen, report back. That asymmetry matters: QEMU is where you can iterate fast and be wrong nine times before breakfast; real hardware is where you find out that some of your "confirmed" fixes were confirmed against the wrong thing.

Every one of the five bugs below is invisible on QEMU. Four of them worked correctly there on the first try — which is exactly the trap: a driver that passes its only automated-feeling test can still be wrong in ways that only real, spec-compliant (or spec-non-compliant) hardware will show you.

Aside — why there's no serial log for any of this

If you're used to dmesg-driving your bring-up, the biggest practical obstacle here isn't any single bug — it's that this guest has no working byte-stream console on Parallels at all. The only console that works post-boot-services is a raw framebuffer text console: write-only, and the only thing there is to look at. Every diagnostic technique below is shaped by that constraint — nothing printed during UEFI boot services is ever visible again once the framebuffer console clears the screen and takes over, so anything you want visible after a crash has to be re-printed through the post-boot console, not just logged once during discovery. More than one debugging round in this project was extended by a day purely because a useful line had already scrolled off-screen by the time a crash happened.

Bug 1 — the Command register bit that wasn't where we thought

Symptom: after discovering the xHCI controller's PCI BAR and writing what we believed was "enable Memory Space + Bus Master" to its PCI Command register, every register read through that BAR came back as 0xffffffff — the standard PCI "nothing responds here" pattern — on both QEMU and real Parallels hardware.

The trap: this presents as a platform problem, not a code problem. On QEMU specifically, the controller's BAR really was completely unassigned by firmware, so we built and shipped a whole BAR-self-assignment routine before ever suspecting the enable bit itself was wrong. Wrong write width, wrong access granularity — both got tested and ruled out first, because they sounded more plausible than "you transcribed a bit position wrong."

How it was found: a diagnostic printing the Command register's value before and after our own write, re-printed through the post-boot console specifically. One real test produced:

xhci diagnosticParallels · real hardware
PCI command register 0x0010 -> 0x0015

0x0010 = bit 4 set (an unrelated bit, firmware's own default). 0x0015 = 0b10101 — bits 0, 2, and 4. Bit 2 is Bus Master Enable, correctly set. But bit 0 is I/O Space Enable — Memory Space Enable is bit 1. The constant in our driver:

pci.rsbefore
// WRONG — this is I/O Space Enable, not Memory Space Enable
const CMD_MEMORY_SPACE: u16 = 1 << 0;
const CMD_BUS_MASTER:   u16 = 1 << 2; // correct

An off-by-one, in the literal sense — bit 0 vs. bit 1 — sitting in a constant that had been reasoned about half a dozen times without anyone re-deriving it from the PCI spec's actual bit table. An xHCI controller has no I/O-space BAR to enable at all, so this bit was, from the device's perspective, meaningless — we were never enabling the one bit that would let a memory-mapped BAR respond to anything.

Lesson

When a register write "succeeds" — no error, readback matches what you wrote — but has no observable effect, re-derive the bit positions you're relying on from the spec table directly, by hand, before looking anywhere else. A successful write of the wrong bit looks, from software, exactly like every other kind of "nothing happened."

Bug 2 — real firmware panics where emulation just shrugs

Symptom: an early version of the driver, on real Parallels hardware, didn't produce a kernel crash or exception report — the whole VM aborted, with a hypervisor-level crash dialog.

The crash report, from Parallels' own hypervisor log:

libMonitorArm.dylibcrash log
mon.abort.message = PANIC@11.28 UEFI-exception-ArmPciCpuIo2Dxe.dll

ArmPciCpuIo2Dxe.dll is the EDK2 firmware driver implementing low-level CPU I/O access for PCI config space itself — underneath the higher-level protocol our own driver calls into. A panic there happens during UEFI boot services, before our kernel's own exception vectors even exist, so there was no way for our code to catch or report it — the VM just stops.

Root cause: a BAR-reassignment probe — the classic "write 0xFFFFFFFF, read back the size mask, write a real address" technique, needed because QEMU's firmware build leaves this controller's BAR completely unassigned. Textbook, and QEMU's own PCI emulation tolerates it without complaint. Real PCIe firmware, apparently, does not — whatever internal state that sequence disturbed on a real, in-use device was enough to make firmware's own PCI layer panic outright.

Fix: stopped touching PCI config space with anything but reads, plus one narrow, conditional Command-register write. If a real BAR comes back genuinely unassigned on real hardware, the honest answer is "this driver can't safely fix that," not "let's try writing to it and see."

A side rabbit hole worth flagging

The self-assignment logic existed at all only to work around QEMU's own firmware leaving an unclaimed device's BAR at 0 — a real, confirmed, build-specific quirk, not representative of production firmware (Parallels' real firmware had already assigned a sane address without any help). If you build a workaround for one dev-loop's laziness, gate it as narrowly as possible — it's exactly what triggered the firmware panic above.

Bug 3 — a real BAR doesn't respect your simplifying assumptions

Symptom: even after the address-space bugs above were sorted, the very first register read through the discovered BAR took a genuine CPU exception.

exceptions.rsdecoded
ESR_EL1 = 0x96000004
  EC   (bits 31:26) = 0x25   Data Abort
  DFSC (bits  5: 0) = 0x04   Translation fault, level 0

Not a permissions problem — a genuine nothing is mapped here fault, at the top-level table walk.

Root cause: our own page tables. This kernel's identity-map setup assumed all RAM and every device region it would ever need lived within the first 512GB of address space — one top-level page-table entry's worth. Reasonable at the time: RAM addresses are always low, and the one device region this project had ever hardcoded was too. A discovered PCI BAR is under no such obligation — this controller's BAR resolved to exactly 512GB on the QEMU dev loop, squarely outside that one entry.

Fix: generalized the identity-map builder to allocate additional top-level table entries on demand, for whichever address range a discovered device actually needs.

Lesson

A value that's "always true" for every address you've picked yourself stops being true the moment you start reading addresses that hardware, or firmware, picked instead.

Bug 4 — an entire request class silently going nowhere

The deepest and most surprising finding of the day.

Symptom: once the controller was enumerating the keyboard correctly, polling it via the standard USB HID mechanism — repeated GET_REPORT requests to the control endpoint — never returned anything resembling keyboard data. It came back, variously, as:

  • This driver's own GET_REPORT Setup packet, echoed straight back — confirmed by decoding the returned bytes against the exact request sent (bmRequestType, bRequest, wValue, wIndex, wLength, all present, in order — including a changed wLength tracking exactly across two separate test builds).
  • In one test, a chunk of what decoded cleanly as a completely different descriptor — real, structured data, just not what was asked for and not a live report either.

Neither of those is "the device sent nothing." Both are "the response buffer contains something structured," which is a much more confusing failure than a clean timeout — it looks like success from a distance.

Ruling out the obvious explanations, each with direct evidence

  • Matching the wrong completion event? Printed every transfer-completion event's own pointer field next to the address of the TRB we expected. They matched, every time. Not this.
  • A buffer-size coincidence? Widened the requested length from 8 bytes to 64 across two separate real-hardware test rounds. The garbage tracked the new length exactly. Not a fixed-size aliasing bug — whatever's happening adapts to what we send, in real time.
  • Is the DMA target even written to? Filled the destination buffer with a distinctive, otherwise-impossible byte pattern (0xEE repeated) immediately before ringing the transfer doorbell. The poison did not survive — the buffer was genuinely overwritten. The transfer mechanism itself was working correctly; the content being delivered simply wasn't real device data.

The test that actually settled it: a completely different, standard request — GET_DESCRIPTOR(Device) — issued right next to a failing GET_REPORT. It came back perfectly:

GET_DESCRIPTOR(Device)real device response
[12, 01, 00, 02, 00, 00, 00, 40, 27, 06, 01, 00, 00, 00, 01, 04, 0b, 01]
 ^^  ^^                          ^^^^^^^^
 bLength=18   bDescriptorType=1  idVendor (a later test: 0x203a — Parallels' own real, registered vendor ID)

Unambiguously live, correct, real device data.

The conclusion: standard USB control requests reach the real device correctly through Parallels' USB passthrough. Class-specific HID requests — the two mechanisms this driver had been built around — do not get forwarded at all. A real gap in the passthrough implementation, not a bug in any driver talking to it — and easy to misdiagnose as "my request encoding must be subtly wrong," because the bytes we were sending were correct the entire time.

The fix: stop polling via GET_REPORT entirely. Use the mechanism every production USB HID driver actually uses at runtime: the device's interrupt IN endpoint. Configured via Configure Endpoint — a standard xHCI command, not a USB class request — the host controller then polls the device on its own schedule and delivers new reports with zero further request/response round trips for software to get wrong.

Lesson

If a request "succeeds" but its content looks wrong in a structured way — not zeroed, not noise, but shaped like something else you recognize — consider whether the platform underneath you might be substituting or misrouting that specific request, before assuming your own encoding is wrong. And when a "simpler" mechanism and a "more standard" one are both available, the passthrough layer beneath you may only have been built and tested against the one real operating systems actually use.

Bug 5 — a perfectly working driver, reading the wrong device

Symptom: once the interrupt endpoint was fully armed, real live data started flowing — continuously, and changing. That was the tell: moving the mouse over the VM's window produced a steady stream of changing report data. It was the mouse, not the keyboard.

A real Parallels VM exposes at least a virtual mouse/tablet on the same xHCI controller as the keyboard, and this driver's port-scan logic — take the first port reporting a connected device — had no way to tell them apart. It grabbed whichever device enumerated on the lower-numbered port.

Fix: walk every connected port, and for each one, fetch its Configuration descriptor and check the HID interface's declared class and protocol — bInterfaceClass = 3 (HID), bInterfaceProtocol = 1 specifically for Boot-Protocol Keyboard (2 is Mouse) — before committing to configuring its interrupt endpoint.

Lesson

In a virtualized, multi-device environment, "the first thing that responds" is never a substitute for checking you've found the specific thing you're looking for — even, especially, once everything else is finally working. This bug only became visible because the rest of the driver was finally right; it had been silently waiting behind the other four the whole time.

Techniques that generalized well

  • Poison your DMA buffers. Fill a transfer's destination with a fixed, distinctive, otherwise-impossible pattern before triggering it. Whether — and how much of — the poison survives tells you directly whether a write happened at all.
  • Widen a request to break a suspicious coincidence. If a buggy result's shape matches some other value in your system, deliberately change that value. If the bug's shape changes with it, you've confirmed a real dependency, not ruled one out.
  • Reach for the most boring request you can, as a control. When one request type misbehaves, test the most basic, universal request in the same family right next to it.
  • Decode raw exception registers by hand, every time. Exception class, fault status, faulting address — the difference between "the VM crashed" and "a Data Abort at exactly this address, for exactly this documented reason."
  • Route diagnostics through whatever survives a crash, not just whatever's convenient to log through at the time.
  • Fix one variable per real-hardware round trip, and predict the outcome before you spend it. Every round trip here targeted one falsifiable hypothesis — which is what made five real bugs findable in a single day.

Where this ended up

A real, physical USB keyboard, on real Parallels-on-Apple-Silicon hardware, typing into a shell running on a from-scratch kernel with no prior USB support at all — full round trip confirmed: individual keystrokes, backspace, Enter submitting a real command line. Getting there took a from-scratch xHCI driver and five real, independently-confirmed hardware bugs, none of which were visible on the software emulator this project otherwise develops against day to day.

If you're doing the equivalent work for your own kernel: budget for the fact that "works on QEMU" and "works on a real hypervisor" are genuinely different claims, that a firmware or passthrough layer's rough edges won't announce themselves as errors, and that the most confusing failures are the ones that come back looking like something, not nothing.
