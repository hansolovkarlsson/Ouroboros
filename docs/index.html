Ouroboros

A microkernel-style operating system for aarch64, written from scratch in Rust, still in its earliest stages. Booted entirely through UEFI — no bootloader stage, no emulator-only shortcuts — developed against QEMU day to day and proven, repeatedly, against real Parallels-on-Apple-Silicon hardware.

What this is

Ouroboros draws its design ideas from Linux, Minix, and Plan 9: a microkernel architecture, POSIX-ish system calls, preemptive multitasking, and a filesystem story that started with "research needed" and has since grown into a real, hand-rolled FAT32 read/write stack. It's built and tested primarily against Parallels Desktop on Apple Silicon rather than an emulator alone — a deliberate choice, since Parallels boots ARM VMs exclusively through UEFI firmware with no direct-kernel-boot shortcut, and real hardware has repeatedly disagreed with what "worked" on the emulator.

Every driver in this kernel — the console, the disk controller, the filesystem, the USB host controller — is hand-rolled directly against the relevant specification, with no external hardware crate. That's not a purity rule; it's mostly a consequence of running with no heap after boot services exit, and it's produced a genuinely large amount of real, documented, hard-hat debugging along the way — see the postmortems below.

Where things stand

The short version: there is a real, disk-loaded userland shell, with a working command surface over a real filesystem, running on real Parallels hardware — with a live display, a real, physical USB keyboard typing into it, and, as of the latest milestone, real preemptive multitasking. Disk commands still don't work on Parallels specifically — no virtio-blk device exists there over any transport this project can drive (see "what's next" below).

  1. Boot & bring-up

    UEFI entry, exception vectors, an MMU running on the kernel's own identity-mapped tables, a GICv2 + generic-timer preemption tick, and a real EL0/syscall boundary — all confirmed working, not just compiling.

  2. Preemptive task switching

    A real (if still coarse — two hardcoded tasks, strict round-robin) scheduler, alternating two EL0 tasks off the timer tick.

  3. An interactive shell

    First UART input, then a disk-loaded, config-selected userland shell — a genuinely separate program, not kernel code, with real tokenized command dispatch.

  4. Runtime storage: virtio-blk + hand-rolled FAT32

    Synchronous polling block I/O and a from-scratch FAT32 reader/writer, growing over several milestones into a full command surface: ls, cat, cd, pwd, mkdir, rmdir, touch, rm, write, cp, mv.

  5. The console-discovery saga

    Devicetree, ACPI/SPCR, and PCI-serial console discovery all confirmed dead ends on real Parallels hardware; a transmit-only virtio-console driver confirmed working on QEMU but confirmed not what Parallels actually exposes; a GOP framebuffer console — five real-hardware round trips, four real bugs — finally reaching a live, rendering shell prompt on real hardware.

  6. USB HID keyboard input

    A from-scratch xHCI driver, seven independently-confirmed real-hardware bugs (five found in the initial push; a sixth — dropped keystrokes under real preemption — and a seventh — an iteration-bounded timeout that should have been time-bounded, found by a user just booting the thing normally — both found and fixed weeks later), ending in a real physical keyboard typing into the shell on real Parallels hardware — full round trip, letters, backspace, Enter.

  7. Real interrupt-controller discovery, and full preemption on Parallels

    Real ACPI MADT parsing replaced the old QEMU-devicetree-derived GIC address; a new GICv3 driver reaches real hardware for the first time. A second real-hardware-only bug (the task switch hanging via wfe, likely trapped by the host hypervisor) was root-caused and fixed the same session. Preemptive, two-task multitasking now works end to end on real Parallels hardware.

  8. What's next

    A relocating loader to remove the current no-core::fmt/no-literal-comparison restriction on userland programs; blocking/waiting primitives; output redirection; virtio-blk/virtio-mmio on Parallels remain unaddressed (no such device present there over any transport this project can drive).

The postmortems

Every real bug found along the way — the ones that mattered, not the routine typos — is written up in detail: symptom, root cause, how it was actually confirmed, and the generalizable lesson. Three pieces, in chronological order, each usable on its own.

Part 1 · Boot bring-up

From "it doesn't boot" to a real console

Exception vectors, the MMU switch, GIC/timer bring-up, the EL0/syscall boundary, and a console-discovery saga that killed three mechanisms and one whole driver before finding the one that worked on real hardware.

 Part 2 · Shell & filesystem

From a bare prompt to a real, disk-backed OS

A relocation bug found twice before its real shape was understood, a hang with zero diagnostic output, a disk that lied about its own filesystem format, and the write-support arc built on top.

 Part 3 · xHCI keyboard

Getting a USB keyboard working on Parallels

Seven real, confirmed hardware bugs bringing keyboard input to the kernel — a PCI Command register bit, a real UEFI firmware panic, a page-table assumption, a silently-dropped USB request class, a driver reading the wrong device, dropped keystrokes under real preemption, and a timeout that was iteration-bounded instead of time-bounded — the last two found weeks later, one of them by a user, not a script.
