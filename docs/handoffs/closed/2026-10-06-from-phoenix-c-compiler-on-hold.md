# The C compiler for Ouroboros will not come from Phoenix

- **From:** Phoenix
- **To:** Ouroboros
- **Date:** 2026-10-06
- **Kind:** notice
- **Status:** done

## What is asked

Nothing is required. This is a change in where two things will come from,
decided by Hans on 2026-10-06.

1. **The C compiler for Ouroboros is DevTools's now.** It will be written
   by hand in C in `~/Projects/DevTools`, beside the editor and the
   preprocessor, and not generated by Phoenix. Phoenix's C compiler,
   `languages/c/` there, is on hold where it stands: it stays in Phoenix's
   tree and tests, but no work goes into it, and its ELF/AAPCS64 target
   (Phoenix ROADMAP 6.11) will not be built.
2. **Phoenix itself is to be ported to Ouroboros, whole, at some point in
   the future.** There is no date and nothing is asked of Ouroboros for it
   now. When it comes, it needs what any C11 program needs there: the C
   compiler from DevTools and the C runtime that
   `docs/roadmap/roadmap-c-hosting.md` is building. Phoenix is C11 with no
   dependencies, and the compilers it writes out are one C file each.

## Why

`docs/ROADMAP.md` here, at lines 2216 to 2221, says the toolchain is
"Proem (the preprocessor), a compiler that Phoenix generates and an
assembler Futamura describes". The middle one no longer holds. A reader
planning the C-hosting arc around Phoenix's output (Apple-style variadic
arguments on the stack, a signed plain `char`, which 6.11 was to fix)
should plan around DevTools's compiler instead.

The decision is recorded in Phoenix's tree: `docs/ROADMAP.md` section 6,
"On hold since 2026-10-06", and `docs/journal.md` under 2026-10-06.
